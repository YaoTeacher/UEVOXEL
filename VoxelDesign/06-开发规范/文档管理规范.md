# 文档管理规范

本文档定义 Voxel 项目中设计文档的管理规范，包括文档命名、分类、维护方式和内容模板。

---

## 文档目录组织

### 目录结构

```
VoxelDesign/
├── 00-设定/                    # 游戏世界观和设定文档
├── 01-需求与问题分析/          # 业务要素、流程、问题分析
├── 02-系统设计/                # 系统边界、核心概念、设计原则
├── 03-架构设计/                # 组件划分、接口定义、生命周期
├── 04-设计计划/                # 阶段划分、任务分解、优先级
├── 05-设计决策记录/            # 关键决策、选项对比、理由说明
├── 06-开发规范/                # 编码规范和文档管理规范
├── 07-测试文档/                # 测试计划和测试报告
├── 08-分析报告/                # 性能分析和问题报告
└── 09-参考资料/                # 外部参考资料和归档文档
```

### 组织原则

- **扁平结构**：所有文档平铺在各级目录下，不创建额外的二级子目录
- **例外**：
  - `09-参考资料/` 目录可以创建子目录（如 `代码设计参考/`、`_archive/`）
  - `09-参考资料/_archive/` 目录可以创建子目录用于归档旧版本的文档
- **示例**：
  ```
  VoxelDesign/03-架构设计/
  ├── 编辑系统-架构设计.md
  ├── 编辑系统-选择系统-架构设计.md
  └── 建筑系统-架构设计.md

  VoxelDesign/09-参考资料/
  ├── _archive/
  │   ├── 编辑系统-v1/
  │   └── 旧文档管理规范-20260112.md
  └── 代码设计参考/
      └── 网站.md
  ```

## 文档分类与职责

| 文档类型 | 做 | 不做 |
|---------|-----|------|
| **需求与问题分析** | 定义"做什么"，记录问题现状 | 不涉及解决方案 |
| **系统设计** | 定义"怎么做"，确定系统边界和概念 | 不涉及具体类和接口 |
| **架构设计** | 定义"代码结构"，确定组件、接口和关系 | 不涉及具体实现代码 |
| **设计计划** | 定义"具体步骤"，确定实施路径 | 不涉及具体技术实现细节 |
| **设计决策记录** | 记录"决策理由"，保存决策历史 | 不重复其他文档内容 |

## 测试文档规范

### 测试文档内容要求

**原则**：测试文档仅记录测试要点，不需要详细的操作步骤和截图。

### 测试文档类型

| 文档类型 | 内容要求 | 命名格式 |
|---------|---------|---------|
| **测试指南** | 测试目标、测试要点、验收标准 | `<系统名>-Phase<数字>-测试指南.md` |
| **测试结果** | 测试结果摘要、发现的问题、统计数据 | `<系统名>-Phase<数字>-测试结果.md` |
| **测试总结** | 测试过程总结、经验教训、改进建议 | `<系统名>-Phase<数字>-测试总结.md` |
| **测试检查清单** | 关键检查项列表 | `<系统名>-测试检查清单.md` |
| **代码审计报告** | 代码质量审计发现的问题 | `<系统名>-Phase<数字>-代码审计报告.md` |

### 测试文档组织

- **扁平结构**：所有测试文档平铺在 `07-测试文档/` 根目录下
- **不创建子目录**：禁止创建 "测试计划/"、"测试结果/" 等子目录
- **不保存截图**：测试截图不需要保存在文档中

### 测试文档命名示例

```
07-测试文档/
├── 编辑系统-Phase1-测试指南.md
├── 编辑系统-Phase1-测试结果.md
├── 编辑系统-Phase1-测试总结.md
├── 编辑系统-测试检查清单.md
└── README.md（可选，测试文档总览）
```

## 文档命名规范

### 命名格式

```
<系统名>-<具体主题>-<文档类型>.md
```

### 示例

- `编辑系统-撤销重做-需求分析.md`
- `编辑系统-工具管理-系统设计.md`
- `编辑系统-选择系统-架构设计.md`
- `编辑系统-实施计划-设计计划.md`
- `编辑系统-设计决策记录.md`

### 注意事项

- 时间信息由文件系统或版本控制系统管理，不加入文件名
- 使用中文描述性文件名，避免英文或缩写
- 文档类型必须对应正确的目录（01-05）

## 文档新增规则

### 以系统为主轴，根据复杂度分层管理

**大系统/核心系统**（文件修改数 ≥5 或 开发时间 ≥3天）
```
编辑系统、建筑系统、AI系统
├── 需求与问题分析 ✓
├── 系统设计 ✓
├── 架构设计 ✓
├── 设计计划 ✓
└── 设计决策记录（多个）✓
```

**中等系统**（文件修改数 2-4 或 开发时间 1-2天）
```
背包系统、时间系统
├── 架构设计 ✓
├── 设计计划 ✓
└── 设计决策记录（可选）✓
```

**小系统/简单功能**（文件修改数 =1 或 开发时间 <1天）
```
UI组件、工具函数
└── 设计决策记录（可选）✓
```

## 文档拆分规则

### 判断标准：子模块是否功能独立

**需要拆分**：
- 子模块有独立的业务边界
- 子模块可以单独被理解和使用
- 子模块有独立的生命周期

**示例**：
```
编辑系统-选择系统-架构设计.md
编辑系统-预览系统-架构设计.md
编辑系统-工具系统-架构设计.md
```

**不需要拆分**：
- 子模块紧密耦合，必须一起理解
- 子模块只是父系统的内部实现细节

## 文档维护方式

### 维护规则

| 文档类型 | 维护方式 | 说明 |
|---------|---------|------|
| **需求与问题分析** | 追加记录 | 每次改动新增一条，标记时间，保留历史 |
| **设计决策记录** | 追加记录 | 每次决策新增一条，标记时间，保留历史 |
| **系统设计** | 覆盖更新 | 在原文上删改，保持唯一正确版本 |
| **架构设计** | 覆盖更新 | 在原文上删改，保持唯一正确版本 |
| **设计计划** | 主体覆盖 | 文档主体保持最新计划，变更历史在设计决策中记录 |

### 设计计划变更处理

```markdown
# 编辑系统-设计计划.md（主体 - 覆盖更新）
## 当前阶段划分
- Phase 1: 核心架构重构
- Phase 2: 工具系统实现
---

# 编辑系统-设计决策记录.md（变更历史 - 追加记录）
## 2025-01-16: 计划调整
**决策**：调整 Phase 1 和 Phase 2 的优先级
**理由**：用户反馈需要先完成预览系统
**变更内容**：将预览系统从 Phase 2 移至 Phase 1
```

## 文档引用规则

### 引用格式

使用绝对路径引用（从 VoxelDesign 根目录）：

```
[显示文本](/VoxelDesign/<目录>/<文件名>.md)
```

### 示例

```markdown
- 一般引用：参见 [编辑系统-系统设计](/VoxelDesign/02-系统设计/编辑系统-系统设计.md)

- 引用子文档：参见 [选择系统架构设计](/VoxelDesign/03-架构设计/编辑系统-选择系统-架构设计.md)
```

## 文档废弃规则

### 混合策略

**1. 临时/实验性文档 → 直接删除**
- 示例：功能探索阶段的草稿文档
- 依赖 Git 历史记录找回

**2. 重要系统文档 → 归档**
- 示例：已完成重构的"编辑系统 v1"文档
- 操作：移动到 `VoxelDesign/09-参考资料/_archive/`
- 保留目录结构：
  ```
  VoxelDesign/09-参考资料/_archive/
  └── 编辑系统-v1/
      ├── 03-架构设计/
      └── 04-设计计划/
  ```

**3. 子文档合并后的冗余文档 → 直接删除**
- 示例：合并后的子系统架构设计文档
- 内容已整合到父文档中

### 废弃判定条件

- ❌ 系统完全从项目中移除
- ❌ 系统重构完成且有新版本文档
- ❌ 文档内容已被其他文档完整替代

## 功能设计流程

### 流程概述

```
问题讨论和分析
    ↓
【01-需求与问题分析】
├── 业务要素提取
├── 业务流程梳理
├── 现有代码问题分析
└── 设计目标与范围
    ↓
【02-系统设计】
├── 系统边界定义
├── 核心概念定义
└── 设计原则
    ↓
【03-架构设计】
├── 组件划分
├── 接口定义
├── 生命周期管理
└── 类关系图
    ↓
【04-设计计划】
├── 阶段划分
├── 任务分解
├── 优先级排序
└── 时间安排
    ↓
【05-设计决策记录】
├── 关键决策记录
├── 选项对比

    ↓

├── 风险识别
├── 问题发现
└── 方案调整
    ↓
实施
```

## 关键原则

### 原则1: 渐进式设计

```
问题 → 需求分析 → 系统设计 → 架构设计 → 实施计划
```

每一阶段都有明确的输入和产出，不能跳跃。

### 原则2: 文档分离

- **需求分析**：不涉及解决方案
- **系统设计**：不涉及具体类
- **架构设计**：不涉及实现代码
- **实施计划**：不涉及技术细节

### 原则3: 决策可追溯

- 所有关键决策必须记录
- 记录选项、理由、权衡
- 便于未来回顾和调整

### 原则4: 设计评审

- 架构设计完成后，进行评审
- 识别风险和问题
- 调整方案后再实施

## 文档内容模板

### 01-需求与问题分析

```markdown
# <系统名>-需求分析

## 1. 问题定义

### 1.1 问题概述
- 用1-2段话描述遇到的问题
- 说明为什么现在需要关注这个问题

### 1.2 问题来源
- 是从哪里发现的问题？（用户反馈/代码审查/性能分析/功能需求等）
- 问题影响范围评估

### 1.3 目标需求
- 当前期望的实现是什么
- 描述理想状态下的行为

## 2. 业务分析

### 2.1 潜在要素
- 列出涉及的业务概念/实体（不要求完整和确定）

### 2.2 要素关系
- 描述要素之间的关系（初步理解）

### 2.3 初步业务流程

**流程描述**：
- 用1-2段话描述整体流程

**步骤表**：
| 步骤 | 操作 | 涉及要素 |
|------|------|---------|

## 3. 目标范围

### 3.1 设计目标
- 列出3-5个主要目标

### 3.2 范围界定
**在范围内**：
- 明确要做的内容列表

**不在范围内**：
- 明确不做的内容列表

### 3.3 约束条件
- 性能/时间/技术/团队等约束
```

### 02-系统设计

```markdown
# <系统名>-系统设计

## 1. 系统上下文

### 1.1 系统边界
- 明确系统负责什么，不负责什么

### 1.2 外部依赖
- 依赖哪些外部系统/子系统

### 1.3 输入输出
- 输入：用户输入、事件
- 输出：系统产生的结果、副作用

## 2. 核心概念

### 2.1 基础概念
- 最底层的基础概念

### 2.2 组合概念
- 由基础概念组合而成

### 2.3 行为概念
- 描述操作和变化的概念

### 2.4 概念关系
- 概念之间的关系

## 3. 设计原则

### 3.1 架构原则
- 组件划分、依赖关系

### 3.2 接口设计原则
- 统一抽象、最小知识

### 3.3 数据管理原则
- 数据所有权、状态管理

### 3.4 性能原则
- 按需计算、缓存策略
```
