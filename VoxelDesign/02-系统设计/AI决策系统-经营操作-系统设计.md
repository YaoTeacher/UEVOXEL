## 1. 系统边界

**负责**：玩家以所有人 / 经营人 / 雇员 / 路人四种身份可执行的经营操作，每项操作的前置条件、写哪份数据、走哪个业务方法。

**不负责**：界面布局与交互形态（UI 卷）、NPC 店主与商圈管理人的后台决策（[店主与商圈管理](/VoxelDesign/02-系统设计/AI决策系统-店主与商圈管理-系统设计.md)）、员工工单的执行细节（[员工与工作执行](/VoxelDesign/02-系统设计/AI决策系统-员工与工作执行-系统设计.md)）、顾客消费流程（[店铺空间与消费流程](/VoxelDesign/02-系统设计/AI决策系统-店铺空间与消费流程-系统设计.md)）。

**与 NPC 的关系**：NPC 店主执行同一批操作，只是没有界面、按经营决策循环后台执行。玩家可执行的每个操作，NPC 都有一条对应的 AI 决策项（对照 §12.4 经营决策项）。不存在只有玩家能做的经营操作。

## 2. 操作主体与权限

经营操作以 `BusinessEntityId` 定位 Global `BusinessEntities` 中的唯一经营实体。商圈、店铺和图外生意共享基础模型并按类型组合模块，经营实体持有资产归属、产权 / 经营关系、`bOpen` / 日程、目录 / 定价 / 订单 / 预留、声誉 / 客流；区域只持空间与空间校验，不保存这些业务镜像。实际空间由实体的区域组件关联 `AreaRef={SceneId,AreaId}`；客房、仓库等子区域只有空间ID并关联已有主体，抽象生意没有实际区域，不创建图外假区域。家具库存、工作点FIFO与门锁仍由对应实例持有，区域看板只为不入档的派生索引。

`BusinessEntityId` 是全局稳定经营 ID（GUID，规则见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)）；不再使用 `ShopId` 别名，也不能用 `Shop->GetAreaId()` 取得经营 ID。Home / Work 仍是空间引用。权属与数据归属详见[区域店铺与商圈管理 §2 / §9](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。

| 身份 | 判定 | 能做什么 |
|---|---|---|
| **所有人 Owner** | 经营实体产权关系；店铺通过经营隶属继承商圈产权人 | 全部操作，含转让所有权、申请改建类许可、产权处置、招商、收购地契 |
| **经营人 Manager** | 经营实体有效经营关系（含承租租户、受雇管理人） | 经营类操作：人员、货、活动、经营类许可、统计；**商圈经营人可修改经营隶属店铺租约**；不碰所有权与改建类许可 |
| **雇员** | 有效合同的 `EmployerBusinessEntityId` 指向该经营实体 | 只读店铺公开信息；自己的班次与工单；不进入任何经营页 |
| **路人** | 以上都不是 | 只读店铺公开信息（营业时间、在售、价格、拥挤度、口碑） |

- 经营权限从经营实体的产权 / 经营关系解析；空间编辑另走 `IsAreaEditable(AreaRef)` 校验，两者不能互相代替。界面只做显隐，业务方法执行同一权限规则；
- **经营管理人只有产权人与经营人两类**；承租经营人与受薪管理人都是经营人，代理人并入经营人，其余都是雇员；空间包含关系不吞并租户资产；
- **商圈经营人**可以修改商圈下各店铺的租约（招商 / 租金 / 退租），但不能改产权、也不能改自己的经营关系；
- **产权转让 / 并购只能由商圈产权人执行**，最小单位是商圈（不能单独购买店铺区域）；自由模式下可与产权人远程协商；
- 承租 / 自营经营人可以在**本人个人钱包 ↔ 本人唯一经营账户**之间双向划转，源账户须足额；薪酬制经营人不能划转产权人的账户，只能发起授权业务支出（§3.7）；
- 员工、承租经营人、自营产权人与薪酬制店主 NPC 都有挂在 Creature 上的劳动安排，按工作区、排班与工作优先级实际干活；定价、进货、招聘、排班、开业等经营决策是抽象业务方法，不占排班或工单，不另设「亲自顶岗」操作。

## 3. 操作清单

每项列出：操作 / 谁能做 / 前置条件 / 后果与数据归属。

**三条交互铁律**（所有经营页面通用，原型已按此实现）：

1. **每个控件都通过业务方法写回状态**：价格、月薪、月租、阈值等数字框与切换类控件都调用对应业务方法，不存在只改样式的假控件；UI 不直写商品目录、营业状态或其他业务数据，非法值拒绝并保留旧值。
2. **每一次花钱都过账本并记流水**：即时采购、许可、活动、募捐、派工都从对应账户扣，流水带时间与事由，个人资产页能看到最近几条。
3. **条件不足就挡住并说明缺口**：关系等级不够、余额不够、源目账户相同、该账户是薪酬制——按钮不可用或点击给具体原因，不静默失败。

**跨页一致性**：任何一页改了钱，锚的资金、检查器的区域卡、统计页的资金段同步刷新；面板不关也能看到数字变化。

### 3.1 人员

| 操作 | 谁能做 | 前置条件 | 后果与数据归属 |
|---|---|---|---|
| 查看名册 | Owner/Manager | — | 只读 `FEmploymentRecord` 与 `FWorkAssignment`。界面分五个**同级**页签：**名册 / 排班 / 工作优先级 / 工单 / 招聘**。名册是左概览右详情——左列每张卡显示在岗状态、忠诚度、每日工时范围、月薪；右侧按四段排列，每项只出现一次：**当前状态**（在岗/休息、此刻在做什么、六条需求、状态 BUFF、今日工时）→ **工作安排**（时段、工种优先级、在手工单，各自带跳转）→ **工作数值**（月薪与调薪、当月折算、忠诚、累计工单、四项属性）→ **个人信息**（身份、种族、职业、基础阵营与来历、HP/AP、性格特质、技能）。V1 不显示与玩家的关系度／认识度。**不显示统计汇总、不显示 NPC 的记忆内容**，也不设"看角色卡"。排班与优先级是**员工和经营人共用的劳动安排矩阵**（劳动者 × 24 小时 / 劳动者 × 工种），不是某个人的子页 |
| 招聘 | Owner/Manager | 有用工需求，候选无有效工资合同（图外合同也有效） | 同时创建该 NPC 的雇佣记录与挂在 Creature 上的劳动安排；雇佣记录写 `MonthlySalary`、`HireTime` 等合同与工资数据，劳动安排写工作区、排班、工作优先级与启用状态。不要求预存首月工资，工资到期直接足额结算并允许经营账户扣负 |
| 招聘 / 任命薪酬制店主（后续版本，V1 不开放 NPC 任命） | 商圈 Owner/Manager | 后续版本有空缺店铺 | 同时创建商圈雇佣记录与劳动安排，再任命为店铺经营人；经营关系只引用 `EmploymentId`。薪酬制店主 NPC 也按劳动安排下场干活，其薪酬只走雇佣记录，经营决策不占排班 |
| 调薪 | Owner/Manager | 员工在册 | 立即修改雇佣记录的 `MonthlySalary`；结算时只读当前值，不在经营关系或劳动安排中复制工资 |
| 解雇 | Owner/Manager | 员工在册 | 按当月在职时长折算并立即结清工资，再终止雇佣与对应劳动安排，员工回失业池；不设辞职梯度、谈判或预告期 |
| 设排班 | Owner/Manager | 员工或经营人有劳动安排；**雇员的排班格必须落在其雇佣记录 `AvailabilityTemplate` 覆盖的小时内** | 修改劳动安排中的 1h 时间块（[员工卷](/VoxelDesign/02-系统设计/AI决策系统-员工与工作执行-系统设计.md) §3）。员工与经营人共用 N × 24 小时格，块类型为任意 / 工作 / 休息 / 睡眠 / 用餐，点一格轮换、按住拖动连刷，支持整行套用全部；V1 不设独立娱乐块。排班是权重式，Anything 时段也可工作但权重较低，Work 权重最高，不作为打烊门禁。可工作时段之外的小时格置灰不可选，业务方法对越界排班直接拒绝 |
| 设工作优先级 | Owner/Manager | 员工或经营人有劳动安排 | 修改劳动安排中的工种优先级。简易模式只勾选工种，启用项按工种固有顺序执行；高级模式手动设 0–4，**4 最高、0 禁止**。两种模式在同一劳动安排矩阵切换 |
| 查看工单 | Owner/Manager | — | 只读**本经营实体**的工单列表；看板由工单索引器维护，玩家不能在看板创建、编辑或指派工单。玩家可自己通过统一劳动业务入口执行动作，或通过经营操作改变世界状态 |
| 设员工休息区（后续版本，V1 不开放） | Owner/Manager | 后续版本店内有一个可标记的员工子功能区 | V1 不显示、不可执行，不创建员工区或改变需求路径；后续才可配置员工设施 |
| 看我的劳动安排 / 我的工单 | 员工或经营人 | 本人的劳动安排 | 只读 |

> V1 不做调岗、独立「亲自顶岗」操作、辞职梯度 / 谈判 / 预告期。经营人下场工作直接使用劳动安排，不产生额外工资；承租经营人拿利润，薪酬制店主按雇佣记录拿月薪。

**人员页面对商圈的差异**：V1 商圈没有公共维护工名册；人员页只显示各店店长（只读 + 邀请/辞退）与商圈管理人。公共维护工、清洁员、治安管理员及其工资/工单留后续版本。

### 3.2 货

商品目录只通过以下五个业务方法修改：**上架 / 下架、逐商品定价、设补货阈值、启用 / 停用、移除商品**。UI 不直写商品目录；任何非法值或非法操作都拒绝并保留旧值。

| 操作 | 谁能做 | 前置条件 | 后果与数据归属 |
|---|---|---|---|
| 上架 / 下架商品 | Owner/Manager | 商品在物品库中存在，且属于当前业态允许经营品类 | 通过业务方法改店铺商品目录；下架只停止新销售，不清空后备储存或货架库存 |
| 逐商品定价 | Owner/Manager | 商品在目录中；新值为有限且 ≥0 的数值 | 通过业务方法改该商品的 `Price`，不设固定上限，0 元合法；负数、NaN、Infinity 或非法输入拒绝并保留旧值；禁止用调价系数（§12.4） |
| 设补货阈值 | Owner/Manager | 商品已在目录中；阈值与补货量为合法值 | 通过业务方法写该**商品目录条目**的补货阈值 × 补货量；判定基数是**全仓库合计**（货架+后备，不分 `bForSale`）。低于阈值且后备有货才产生后备 → 可售货架的 `Restock`；后备为空只提醒库存不足，不包含供应商或自动采购。非法值拒绝并保留旧值 |
| 启用 / 停用商品 | Owner/Manager | 商品在目录中 | 通过业务方法修改目录项启用状态；非法请求拒绝并保留旧状态 |
| 移除商品 | Owner/Manager | 商品在目录中 | 通过业务方法移除目录项；非法请求拒绝并保留旧目录 |
| 即时采购 | Owner/Manager | 商品属于允许经营品类、店铺资金责任人的经营账户余额够、兼容后备储存容量够 | 按基础价原子扣款 + 后备储存入库 + 写店铺采购流水；不生成采购单或在途配送 |
| 丢弃变质库存 | Owner/Manager | 库存存在变质条目 | 扣库存、不产生流水、走损耗分类 |

> V1 真实库存只存于后备储物家具和可售货架；仓库子功能区可选，只组织后备储物家具，不另存店铺总库存。采购先后备储存，余额或容量不足整笔失败；供应商、采购单、在途配送与自动采购均在后续版本接入。

> 旅店房型、房价、退订、预订、入住与退房全部留后续版本，V1 不生成对应商品或操作入口。

库存规则见 [库存与保质期](/VoxelDesign/02-系统设计/AI决策系统-库存与保质期-系统设计.md)。

### 3.3 资产（商圈）

| 操作 | 谁能做 | 前置条件 | 后果与数据归属 |
|---|---|---|---|
| 查看租约列表 | 商圈 Owner/Manager | — | 只读租约（租户、月租、下一收租时点、状态；V1 无押金 / 租期 / 欠租） |
| 签订店铺租约 | 商圈 Owner/Manager；自指合同仅产权人 | 可租经营实体与租用空间、承租身份校验通过 | `SignShopLease` 接收 `LessorBusinessEntityId / TenantBusinessEntityId / LeasedAreaRef / TenantCreatureId / Terms`：校验 → 在Global `LeaseRegistry` 建唯一租约并令实体只引用 `LeaseId` → 建经营关系与实际劳动安排 → 收首期租金 → 原子提交；签约时推算 `NextRentGameTimeSec` |
| 新建店铺区域（建铺） | 商圈 Owner/Manager | 商圈内可用空间；后续收费时产权人经营账户足额 | 同一面板圈地 / 填信息 / 确认，一次创建Shop经营实体 + 实际区域 + 必要关系合同，初始 `bOpen=false`；V1只在预置商圈开局链创建玩家一间标准承租店，不重复建铺；正式Lease先于租户建筑家具写入；子区域只关联已有经营实体，不建第二业务主体 |
| 招商 / 招募（后续版本，V1 不开放 NPC 招商） | 商圈 Owner/Manager | 后续版本有空置铺位或可生成空间 | 后续统一界面才提供承租开店（NPC 自带业态）或应聘经理；V1 只创建玩家标准承租店并招聘普通员工，不生成 NPC 租户、NPC 店长或第二家店 |
| 调月租 | 商圈 Owner/Manager；自指合同仅产权人 | 租约存在 | 调租从下一个收租日起生效，该期按新月租整月收取，不分段、不追溯；V1 无押金 / 租期可调 |
| 退租 / 清退 | 商圈 Owner/Manager（租户也可主动发起） | 租约存在 | 按可配置退租缓冲期提前通知；期满只终止租约与该店相关雇佣，雇员按离职规则结清工资；不拆除、回滚或重新分配资产 |
| 收购地契（后续） | Owner | 钱够 + 市议会关系达标 + 有购置许可 | 写经营实体产权关系，必要实际空间另建并关联；玩家资产查询经营关系与实例归属实时派生，不另建个人资产存档 |
| 并购商圈（后续） | 商圈产权人 | 与目标商圈产权人协商同意 | 变更District产权关系，Shop通过经营隶属继承；仅依赖产权人的后续资金链改用新产权人经营账户，承租营收 / 工资不改、合同雇主实体不换、历史流水不改 |
| 盘下租户资产（后续） | 商圈 Owner / Manager | 产权人经营账户余额够、租户同意 | 从产权人经营账户买下租户自带建筑 / 装修 / 家具，资产归商圈产权方；店铺转带设施空置 |
| 处置遗留资产（后续） | 商圈 Owner / Manager | 店铺空置且存在遗留资产 | 售卖 / 拆解遗留设施与道具；V1 不生成遗留资产或坏账处置链 |

> 商圈收租计划配置 `RentCollectionDayOfMonth`，每月固定收租日 00:00（游戏时间）收租。签约时推算各租约 `NextRentGameTimeSec`，由租约管理器按各自到期时间逐条结算。首期按签约当月剩余日历天数比例折算，并在 `SignShopLease` 提交时立即收取；后续每期在收租日按整月收取。调租从下一收租日起生效，该期按新月租整月收取。标准月租由开局 / 剧情配置提供，默认 0，主线与沙盒均可自定义；非产权人不能配置自己作为乙方的租金。
>
> V1 租金直接足额划转并允许源经营账户为负，不产生欠租、坏账、连续失败、手动补缴或违约收铺，负余额不自动收铺。V1 移除公共设施与公共维护费，设施维护统一为员工维修工单，不在本页产生按日扣费操作。详见 [区域店铺与商圈管理 §6.4/§6.14](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。

### 3.4 活动（完整版本，V1 不实现）

| 操作 | 谁能做 | 前置条件 | 后果与数据归属 |
|---|---|---|---|
| 新建活动（广告投放） | Owner/Manager | 有对应活动许可、资金责任人的经营账户余额 ≥ 预算 | 写活动记录；预算立即冻结，按日扣；效果按渠道分日累计 |
| 中止活动 | Owner/Manager | 活动进行中 | 停止投放；已花不退；记录保留 |
| 集市 / 节庆（商圈，后续版本） | 商圈 Owner/Manager | 有节庆许可、产权人经营账户够 | 占公共区域、生成摊位、收摊位费进产权人经营账户并记商圈业务流水；V1 不实现 |

> **V1 不开放本节的新建 / 中止活动操作**：不生成广告、促销或其他活动实例，不冻结预算、不扣费、不执行效果。`FShopCampaign`、`ActivityTags` 与挂载接口仅为后续扩展保留；活动页只留后续入口，不提供可执行投放。

活动模型属后续版本，V1 不做（见[店铺经营 §5](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）。完整版本的活动可选**目标群体**（种族 / 职业 / 阵营 / 街区），效果直接写入口碑对应群体列（[店铺经营 §1](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）；该写入口径不属于 V1。

### 3.5 许可

> V1 最小版本不实现许可；后续按配置驱动的科技树解锁：每个许可独立配置前置许可 / 节点、势力关系门槛、费用、是否可升级、是否年检、有效期、到期重审、持续义务等（详见[区域店铺与商圈管理 §6.9](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)）。

许可分两类，**校验主体不同**，这是本系统唯一的硬规则：

| 类别 | 覆盖什么 | 用谁的关系校验 |
|---|---|---|
| **改建类** | 扩建、加盖、后巷用地、征地、公共设施建设 | **所有人**的关系 |
| **经营类** | 业态开业、设备使用、活动举办 | **经营人**的关系 |

| 操作 | 谁能做 | 前置条件 | 后果与数据归属 |
|---|---|---|---|
| 申请许可 | 改建类 Owner / 经营类 Manager | 对应势力关系等级 ≥ 门槛、费用够、附加条件满足 | 经营许可写经营实体，改建许可关联实际AreaRef；记录“用谁的关系获得”，V1不启用 |
| 查看许可清单 | Owner/Manager | — | 只读：已获得、可申请、条件不足三类 |

- **经营许可归经营实体，改建许可关联实际空间**，不挂人；同一所有人开三家店，三家分别申请，区域不镜像经营许可；
- **已获得的许可不因关系下降自动吊销**，只在申请与升级时校验；
- 关系值本身挂人，见 §3.8。

势力与许可的对应关系由势力设定决定，见 [势力设定](/VoxelDesign/00-设定/势力设定/总结.md)。

### 3.6 统计

**只读**，不产生任何写操作。五段：业务 / 资金 / 人员 / 口碑 / 营销。

- 指标口径必须与 NPC 店主经营决策的输入同源（§12.3）：客流、销量、库存水位、放弃率、投诉数、平均等待时长；
- 商圈统计的业务段额外包含：**进店客流**（各店汇总）、**路过流量**（进入商圈但未进店）、**转化率**；均按日结聚合、可看时段分布（详见[区域店铺与商圈管理 §6.7](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)）；
- 资金段按流水类别统计（租金 / 维护 / 工资 / 采购 / 建设等）；区域只查询业务账，不保存独立余额，可用经营资金读取资金责任人的唯一经营账户并按当前权限展示；同一人物的全部生意共享该账户，所有人物创建时都有两类账户，不按区域分账户；
- 玩家看到的精度受认知边界约束：本店 / 本商圈精确，竞对商圈只给趋势（§12.5）；
- 行可跳转到对应操作页或对象，但跳转本身不改数据。

口碑段在 V1 按 **5 组统计项**展示：服务（服务速度 / 服务质量 / 商品丰富度 / 价格 / 环境氛围）+ 种族 / 职业 / 阵营 / 街区（客群构成：来访 / 成交 / 客单价 / 满意度）。服务组聚合全部有效体验样本，是 V1 的总体声誉与 `QualityScore` 声誉来源；另外四组只描述客群构成，不与服务维度交叉，也不作为群体声誉输入。`Shop.ExperienceReported` 直接写统计，不创建个人记忆或传播任务。不做 6 维 × 5 群体矩阵与独立「全局」组，完整矩阵后续版本升级（详见[区域店铺与商圈管理 §6.12](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)）。

### 3.7 个人资产、个人钱包、经营账户与区域业务账

V1 每个实际 / 抽象人物创建时都有一个个人钱包与一个唯一经营账户，非经营者也有；该人物所有生意共用经营账户，不按需创建。Shop / 商圈经营实体与子功能区都不保存资金账户或余额，也不按区域拆经营账户。经营页按经营实体业务归属查询唯一流水；资金所有权、可用账户与操作权限由产权人、经营人和具体业务共同决定。

| 操作 | 谁能做 | 前置条件 | 后果与数据归属 |
|---|---|---|---|
| 查看本人账户 | 任何人 | — | 只读本人创建时已建立的个人钱包、唯一经营账户及本人完整流水 |
| 查看经营实体业务账 | 经营实体 Owner / Manager | 有该经营实体业务查看权限 | 只读经营实体收入、支出、净额、唯一流水与资金责任人的经营账户可用资金；区域只提供发生空间过滤，受薪经营人看不到产权人的个人流水 |
| 个人钱包 ↔ 本人经营账户 | 账户所有人 | 两个账户都属于本人、金额大于 0、源账户足额 | 双向注资 / 提取，原子写唯一流水；不能通过互转扣负 |
| 给人划转 | 本人 | 本人个人钱包足额、目标人物有效 | 从本人个人钱包进入目标人物个人钱包，写唯一流水 |
| 执行业务支出 | 有权经营人或系统 | 当前经营关系允许该业务；按业务类型检查余额或扣负白名单 | 从资金责任人的经营账户结算，流水标记经营主体与发生区域 |
| 查看玩家资产 | 任何人 | — | 查询时从各经营实体经营关系 / 产权关系与实例归属实时聚合资产视图；不单独建玩家资产结构，不单独入档 |

**经营资金责任人解析**：

- 产权人自营 / 承租经营的 Shop：经营人就是资金责任人，销售收入、采购、工资和其他店铺支出使用其唯一经营账户；
- 薪酬制经营的 Shop / 商圈：产权人是资金责任人。受薪经营人只能发起授权业务，由业务方法从产权人经营账户结算，不能划转产权人的个人钱包或经营账户，也不能查看其个人流水；
- 租金：承租经营人的经营账户 → 商圈产权人经营账户；工资：雇主经营账户 → 员工个人钱包。设施维护只产生员工维修工单，不产生公共维护资金流。

底层保存个人钱包、经营账户和唯一流水。账户间结算必须原子完成，不得只成功一边；抽象银行与即时采购等系统对手方使用单边入账 / 扣款流水，不伪造区域账户。玩家资产视图不入档，查询时从各经营实体经营关系 / 产权关系与实例归属实时聚合。

**余额规则按业务类型确定**：

- 消费、即时采购、个人之间付款与本人两类资金普通互转必须足额；源账户不足时整笔失败且不扣负。
- V1 只有**经营贷款月供、店铺租金、工资**三项允许源经营账户扣负，到期直接足额结算并执行；不生成贷款逾期、租金欠租 / 坏账或未领薪状态，也不留待下周期重试。普通经营支出、设施维修与公共维护均不进入扣负白名单；V1 无公共维护费。
- 工资总是从雇主经营账户足额进入员工个人钱包，不部分支付，不需要员工之间的工资竞争排序；`MonthlySalary=0` 只跳过流水。负余额本身不触发破产、收资产、收铺或离职；扣负权限只存在于对应业务结算器，不开放给普通划转 UI。
- 不同计划时间严格按时间先后执行；计划时间完全相同时，先执行必须验足额的费用，再执行允许扣负的**贷款月供、租金、工资**。例：经营账户 1000，同时应付采购 800、工资 500，采购先成功，随后工资将余额扣到 -300。

- **承租 / 自营经营人**：经营实体收支使用自己的唯一经营账户；本人可在个人钱包与该经营账户之间双向注资 / 提取，源账户必须足额；
- **薪酬制经营人**：可查看区域业务流水与经营账户可用资金，可发起授权支出，但不能划转产权人的账户；其个人工资从产权人经营账户进入自己的个人钱包；
- 中饱私囊 V1 不做（后续用虚报采购/私拿库存/假账 + 流水审计实现，不改业务权限）；
- NPC与玩家共用账户模型。初始顾客钱包按配置，不在本卷给数值；每个实际 / 抽象人物创建两类账户，非经营者也有。选店 / Browse不读钱包，加入购物篮 / 锁价预留才统一验整单资金与容量，结账再次验余额，不足整笔失败。大多数NPC持图外真实工资合同，工资到个人钱包，图外雇主为抽象账户（`bAbstract=true`，不计余额），支出直接发生、不补资（03A §5.9）；失业且无其他实际收入时真的没钱，不按职业 / 阶层兜底发钱。
- 图外抽象工作不生成Actor / 工单 / 寻路，实际 `WorkAreaRef` 允许不存在；场景未加载不是抽象工作，有实际空间的合同保留原工作引用，不能因未加载造假区域或改雇主。招聘只取无有效合同候选，图外合同也有效，不新增换工 / 吞合同 / 补充NPC政策；候选不足如实显示。

经营实体有业务账，区域没有账户、余额或经营业务副本，只提供按发生空间查询的视图。唯一流水保存双方账户、`SourceBusinessEntityId / TargetBusinessEntityId`（源 / 目标业务归属）与可空 `OccurredAreaRef`；租金一笔交易的两侧分别为Shop / District，不按当前父关系回改历史。同一人物所有生意共用其唯一经营账户，不做区域分账户或钱包内区域分账。

#### 经营贷款（V1）

- V1 由抽象银行向玩家主角提供经营贷款；债务主体是主角但不按店铺或商圈分债，放款进入主角唯一经营账户。贷款只通过 **`TakeLoanOffer / RepayLoan / QueryLoan`** 三个业务方法操作：分别用于接受有效报价、还款与只读查询，UI 不直写报价或借据。每次展示 **5 个全随机报价**，不保底、不提供手动刷新；最多同时持有 5 笔。
- 每个报价的本金、名义年利率、期限独立随机：本金 200,000～8,000,000、按 10,000 取整；年利率 3%～15% 的整数百分点；期限 12～360 的整数月。报价和借据锁定生成时的实际本金、利率、期限与固定月还本金。
- 借走一个报价后该位置空缺，不立即补位；每个游戏月开始时只把空缺补满至 5 个，不替换未借走的报价。重新打开界面或读档不能重摇报价。
- **等额本金**：固定月还本金 `B = RoundHalfUp(P / n)`；常规期偿还 `B`，最后一期偿还全部剩余本金。每期利息 `I = RoundHalfUp(剩余本金 × 年利率 / 100 / 12)`，当期扣款 = 应还本金 + 利息；`RoundHalfUp(x) = floor(x + 0.5)`，结果为整数金。
- 每笔借据从各自放款成功时刻起按月扣费，不统一挂在月界；高倍速跨期按各借据计划时间逐期结算。月供直接从主角唯一经营账户足额扣除，允许扣成负数，不记逾期、不部分扣款、不强制破产或收资产。
- `RepayLoan` 允许**部分或全部提前还款**：还款金额必须大于 0 且不超过 `RemainingPrincipal`，从借款人唯一经营账户扣款并全部冲抵剩余本金；非法金额拒绝并保留旧借据。已还本金不再产生未来利息，剩余本金按原借据规则计息，不设违约金；V1 不记逾期。
- 借据保存放贷方、借款方、实际生效条款、固定月还本金、剩余本金、已结算期数、下一扣费时间与结算状态，避免产品配置变化回写存量借据。
- 报价生成参数只从统一配置读取数量、范围、步长、持债上限、补充周期与权重；信用、收入、经营表现、多放贷方、期限结构、浮动利率、费用与关系修正器均在 V1 跑通后扩展，不改借据快照边界。

### 3.9 区域设置（区域自身字段）

本节保留设置入口与章节锚，但数据分开：覆盖 / 准入与空间校验属区域；店名 / 营业意图 / 日程属经营实体，区域不持业务镜像。**业态在组合创建面板选定，变更走「业态变更申请」流程**，两者都不进普通资料表单。设置入口分别调用对应业务方法。

| 操作 | 谁能做 | 前置条件 | 后果与数据归属 |
|---|---|---|---|
| 编辑业务 | 经营实体Owner / Manager | — | 通过业务方法修改实体**名称与 LOGO**；**业态不在本表单内修改**，走下方独立的「定业态」动作。关联区域类型只用于空间校验、不复制经营数据。Owner / Manager从实体关系只读展示；产权 / 任命 / 出租 / 终止走专门流程，普通保存不写营业状态（[区域业务数据编辑表单](/VoxelDesign/02-系统设计/区域业务数据编辑表单-设计.md)） |
| **业态变更申请** | Owner / Manager 发起；审批按资产权限 | 已创建并已定业态；V1 只开放杂货 | **变更业态的唯一入口**：提交业态变更申请 → 审批 → 生效，不走普通资料表单、不走简单 setter。创建时选定的业态同样只能按此流程变更。未定业态不能开业 |
| 改权限 | Owner/Manager | — | 准入类别白名单、战斗许可、默认访问（区域字段） |
| 改营业时段 | Owner/Manager | — | 调用营业时段编辑业务方法，写Shop经营实体营业时段配置（[营业循环](/VoxelDesign/02-系统设计/AI决策系统-营业循环-系统设计.md) §3）。周期长度 = 时间系统配置的 **N 天**，**N 行 × 24 小时格（1 小时块）**；每天可设多段、支持跨夜（如 20:00–02:00）；至少一天营业，全休息要显式确认；保存后重新派生 `bOperating` |
| 开业 | 店铺经营人 | 无（开业不做设施校验，05 决策29）；不做可用入口校验 | 调用开业业务方法设置 `bOpen=true`，再按当前生效营业时段派生 `bOperating`；不查员工 / 库存 / 设施，缺失项由运行期提醒给出；顾客无法入店时给出去重、带冷却的提示 |
| 停业（营业灯） | 店铺经营人 | — | 调用停业业务方法设置 `bOpen=false`，`bOperating` 随之派生为 false；员工保留、工资照发、租金照收，不手动点开开业就一直停业 |
| 延长营业 | 店铺经营人 | 已开业 | 调用延长营业业务方法调整生效营业时段覆盖，不直接写 `bOperating`，也不能越过 `bOpen=false`；V1 员工仍按原劳动安排离岗，不召回班次外员工，不产生加班工资 |
| 镜头定位 | 任何人 | — | 不改数据 |

### 3.10 开店流程（V1）

1. **同一建造面板圈地 / 填信息 / 确认业务**：V1开局提供预置商圈和抽象产权人的标准承租授权。玩家在连续面板中先选定业态与区域类型、再圈定空间、填店铺信息并确认，一次业务提交创建Shop经营实体、实际区域、经营隶属与必要经营关系 / 租约 / 劳动安排，收首期租金；租约在Global `LeaseRegistry` 唯一登记，实体仅持稳定 `LeaseId`。`LessorBusinessEntityId=District`、`TenantBusinessEntityId=Shop`，`LeasedAreaRef` 是租用空间，`TenantCreatureId` 是玩家，四者不混用。创建默认 `bOpen=false`，不等于开业；玩家不能凭商圈经营人身份批准自己的合同。
2. **建造 / 装修**：正式Lease生效先于租户建筑家具写入，落点同时记录 `LeaseId` 与经营实体资产归属；同一连续面板不要求跳多个模式。V1免费；保存并退出带业态建造时只列缺失设施提醒、不阻断退出；开业同样不做设施校验。子仓库等只创建空间并关联已有Shop，不创建第二经营实体。
3. **定业态 / 备货 / 人员**：V1仅杂货，后备储物设施可组织为仓库子区域；即时采购、上架、定价、招聘与排班走业务方法。招聘只取无有效合同NPC，图外合同也算有效，人数不足如实显示。
4. **开业**：经营人手动点「开业」，只硬校验业态必需设施，通过才置 `bOpen=true`；不查入口、导航、员工或库存。`bOperating` 只由 `bOpen&&当前有效时段` 派生，不入档、不复检；运行期缺设施不系统关店。
5. **停业 / 退租**：停业只置 `bOpen=false`，`bOperating` 随公式派生false，员工 / 工资 / 租金照旧；店内已锁价 / 收银排队 / 结账完成后离店，门外未进店队列清退并一次白跑样本只记服务组。退租按缓冲期终止合同与相关雇佣、结清工资，不拆建筑家具、不回滚装修、不重分资产；新租约使用新 `LeaseId`。

后续NPC接管已有同业态空铺走邀请 / 同意条款 / 签约，不重画区域；模板走NPC业态条款选择 / 预览落位 / 确认，Lease正式生效后才真正写入租户建筑家具。V1不开放这些NPC招商模板、多商圈或住宿。

> 通用「编辑业务」表单只保存名称 / 类型。产权购买 / 出售只走产权流程，经营人任命 / 分配 / 出租 / 终止只走对应经营关系流程；Shop Owner 只读继承商圈产权人，Manager 由有效经营关系解析。任何普通资料保存都不得直写 Owner、Manager、`bOpen` 或 `bOperating`。

> 完整规则及其他开店路径见 [区域店铺与商圈管理 §6.14–§6.16](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。

## 4. 操作与数据归属对照

| 数据 | 归属 | 谁写 |
|---|---|---|
| 营业时段 | Global `BusinessEntities` 中的经营实体 | 营业设置 / 营业循环 |
| 开业 / 停业（`bOpen`） | 经营实体，入档 | 开业 / 停业操作 |
| 运营 / 打烊（`bOperating`） | 经营实体纯派生值，不入档、不复检 | — |
| 产权与经营关系（Mode / LeaseId / EmploymentId） | 经营实体；店铺产权通过经营隶属继承商圈 | 产权 / 签约 / 任命等专门流程 |
| 租约条款与收租时点 | Global `LeaseRegistry` 唯一事实，实体仅引用 `LeaseId` | 签约 / 调租 / 退租 |
| 商品目录、定价、订单、预留 | 店铺经营实体 | 货页 / 消费结算 |
| 补货阈值（含补货量） | 店铺商品目录条目 | 即时采购、Restock |
| 实际库存 | 货架 / 储物家具实例 | 即时采购、Restock、消费 |
| 工作点FIFO队列、门锁状态 | 对应工作点 / 门实例 | 队列与通行业务 |
| 采购单、在途配送（后续版本） | 店铺经营实体 | 供应链系统 |
| 雇佣记录 | Global统一雇佣登记，`EmployerBusinessEntityId`指向经营实体 | 招聘 / 解雇 / 调薪，含图外真实合同 |
| 劳动安排（工作区、排班、工作优先级） | Creature；Home / Work为空间引用 | 人员页、签约、任命 |
| 工单（派生索引） | 经营实体看板，不入档 | 工单索引器唯一写入 |
| 每个人物的个人钱包与唯一经营账户、唯一流水 | `FEconomyRuntimeData`；人物创建两类账户引用，经营实体与区域不设账户 | 消费 / 工资 / 租金 / 采购 / 经营贷款等业务方法 |
| 经营资产视图 | 查询经营实体产权 / 经营关系与实例归属，派生不入档 | 互转、收购、签约与贷款结果查询 |
| 四势力关系值、BUFF | 人 | 事件驱动 |
| 许可（后续） | 经营许可归实体；改建许可关联实际空间 | 许可申请，V1不启用 |
| 口碑、客流（V1五组；后续矩阵） | 经营实体 | 体验、来访、成交直接订阅 |
| 客房、仓库子区域 | 区域只持空间 / 校验，通过关联归已有经营实体 | 子区域创建，不生成经营实体 |

- V1 开店与租约简化：无租期 / 无押金 / 无欠租，保留月租 + 收租计划 + 调租即时改配（下一收租按新价）；退租 / 清退缓冲期可配；员工与薪酬制店主直接清退；租金直接足额划转并允许源账户为负，不生成坏账、连续失败或自动收铺。详见 §3.10 与 [区域店铺与商圈管理 §6.14](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。
