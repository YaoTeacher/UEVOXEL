## 1. 定位与边界

事件系统 = **所有业务事件的统一目录、分发与事务管理层，并承载业务与环境离散状态迁移的触发和结果**。完整版本还在客观事实之上增加 NPC 主观解读、记忆与传播；这些后续层不改变 V1 的事件驱动主链。事件类型、载荷、发布者、发布时机、投递范围和订阅关系必须统一登记，模块不得使用未登记的私有业务事件或绕过目录分发。普通内部函数调用与不构成跨域业务事实的内部通知不属于业务事件。

**划界规则：Tick 管连续过程，事件管业务节点。连续数值过程不逐帧进事件系统，只有到点、到达、碰撞、跨阈、完成等业务节点才发布事件。**

| 层 | 内容 | 归属 |
|----|------|------|
| 连续过程 | 需求衰减、移动、生产进度、战斗过程、物价日常波动 | 各业务系统自跑（tick/状态机），不逐帧发事件 |
| **业务节点** | 交互、交互落定、交易完成、死亡、犯罪、解雇、结婚、饿晕 | **事件系统** |
| 世界状态沿 | 丰收节开始、物价暴涨过线、灾害爆发、季节更替 | 世界系统运行，在有意义的点上发事件进来 |

连续过程与事件系统的接口是状态沿：连续过程在自己系统里跑，跨过有意义的阈值时由**该系统自己**上报一个事件（饥饿每秒掉不是事件，饿晕了是事件；挥剑不是事件，杀死人是事件）。业务与环境离散状态迁移在业务事务内提交，事务可由统一目录事件或外部业务方法启动；提交后按统一目录广播，后续影响由各订阅者事务执行。事件不从属于发布者、载荷实体或某个所属域；发布者只发布，任何订阅者都在自己的事件处理器中开启事务并执行自己的逻辑，事务内部允许普通函数调用。没有特权首处理器或统一业务总控，订阅名单可扩展；需要新的独立业务动作时再发布新事件。UI 只调用 Controller 业务门面方法，由业务方法校验、提交并在成功后广播；校验失败直接返回 UI，不为每次 UI 输入额外增加 Request／Rejected 事件。

**V1 事件系统是会话级（GameInstance）同步分发的通知总线，不是事件溯源日志**：统一目录由薄的 GameInstance 子系统承载，跨场景/跨关卡存活；载荷对订阅者只读，订阅者在分发期间同步响应，World 内订阅者必须在 EndPlay 注销。连续采样不进总线，避免总线成为瓶颈；运行时状态按快照存档，读档不重放事件。完整版本的长期事实库、逐人主观解读与传播簿记仍只属于后续层。

## 2. 类型：只剩内容资产

> 本节的“只剩内容资产”只约束完整版本的**可感知事实文案与主观解读配置**。V1 域事件仍须由架构定义强类型载荷、所属域处理器与提交顺序；不能用文案资产代替业务合同。

事件类型 = GameplayTag，**统一使用域前缀**（`Shop.Purchase` / `Death.Murder` / `Time.DayBoundary` / `AI.Work.Cashier` ……），不再使用早期示例中的 `Event.*` 前缀：域表示"这是哪个业务领域的事实"，不是发布者。类型的职责只有一个：**回答"这种事长什么样"，不回答"这种事会怎样"**。

**类型上唯一的配置是内容资产——文本模板（分档）**：

```
"Death.Murder" 完整档：  "[主动者] 在 [地点] 杀死了 [接收者]"
                       听闻档："听说 [地点] 有人被杀了"
```

- 槽位引用**固定结构的位置**（主动者/接收者/地点/值参数键），全类型通用——实体取名字、数值格式化、枚举查本地化词条；
- 档位由**读取方的记忆条目**决定（来源渠道 + 确信度），听闻时缺细节用缺省措辞；
- 模板是文案资产（字符串表/数据表），按类型 Tag 一行；改文案不动代码。

**机制配置在类型上为零**。逐项归宿：

| 东西 | 归宿 | 性质 |
|------|------|------|
| 事件结构（主动者/接收者/值参数） | 引擎固定结构 + 全局枚举键 | 无配置，结构恒定、天然可校验 |
| 主观效果 | 记忆解读层（按 类型×我与事件的关系×我的状态） | 机制配置，在记忆侧 |
| 合法性/秘密定性 | 规范表（独立资产，按语义判定："未经同意转移他人财物"=盗窃） | 机制配置，不在事件侧 |
| 重要性/传播力/确信度 | 运行时公式（§5） | 无配置，算出来 |
| 文本模板 | **类型上的唯一配置** | 内容资产 |

**新增一种事件的成本** = 业务代码落定处上报 + 配一行文案模板。机制零配置。

（参照：DF 的 45 种历史事件类型在数据侧只有文本模板；RimWorld 的 tale 存的就是 firstPawn/secondPawn——主动者/接收者，没有自由键；Guild 2 的 MemoryEvent 表是元数据，其机制字段在本设计中全部由实例计算替代。）

## 3. 事件实例

### 3.1 全局事实库（客观，全图一份，append-only）

```
事件 {
  ID, 类型Tag, 时间, 地点,
  主动者: [实体], 接收者: [实体],   // 结构恒定，语义由类型承载
                                    //（Murder：主动者杀接收者；Purchase：买家与店主）
                                    // 空数组合法：世界类事件无主动者
  值参数: { 全局枚举键 = 值 },       // 金额/物品/死因……键为全局注册枚举，写错即报
  上游: [事件ID],             // 因果链：这场仇杀的起因是哪次被杀
  结果: [ { 目标, 键, 旧值→新值 } ],   // 见 3.3
}
簿记: { 传播计数 }
```

- **校验**：主动者/接收者是固定字段，永远存在（空数组合法）——结构性错误不可能发生；解读规则和文本模板只引用这两个固定位置与值参数枚举键，全部可在加载期校验；某类型该填的值没填（交易没填金额）→ 解读规则按不命中处理 + 开发期警告日志；
- **传播计数是纯数值，不设翻转阈值**：没有"公开判定"。把柄效力随传播自然稀释（勒索筹码 = 公开后果预估 × (1 − 传播进度)，进度由传播计数读出）；执法介入靠目击/报案/侦探证据（§7），与传播广度无关；名声随每次传播逐人累计（基础层名声字段），不存在"公开瞬间大扣"。

### 3.2 个人记忆条目（主观，每个感知者一份）

```
条目 {
  事件ID, 来源(亲历/目击/听闻),
  确信度, 强度快照, 锚定, 封口
}
```

- **来源**：亲历 = 我在事件的主动者/接收者数组里；目击 = 我在感知清单里但不在两端；听闻 = 传播复制来的。我在哪一端由事件本身可查，条目不重复记；
- **强度快照**：写入时解读的输出定格（原始强度 × 当时人格调制），之后性格漂移不影响旧账；它是唤起的强度载体——没有它，十年后按当前状态重算≈0，锚点记忆名存实亡（DF 的记忆条目同样带 strength 字段）；
- **确信度、封口**：公式与机制归《记忆模型》文档；
- 条目只存引用和视角，事实不复制——传闻改不了事实，只产生各异的私人版本。

### 3.3 结果段（反查日志）

- 感知者解读时把实际造成的效果追加进事件的**结果**段；
- **只读，机制禁读**（AI/解读/传播不许读结果做决策——防止它变成第二个事实源）；只供开发者反查（"当时发生了什么、算出了什么、为什么下一步这样做"）；
- 结果随事件同生同灭，进存档随事件——载入旧档也能反查；
- 埋点位置白捡：统一效应模型的单入口 ApplyMods 带来源事件 ID 即可。

（为什么不能靠"参数+规则重算"代替结果段：重算给的是按今天的规则算的结果，结果段记的是当时实际发生的——规则改过、掷签掷过、当时的状态都只在结果段里。）

## 4. 产生链路

### 4.1 三个上报点（都是现成的收口处）

1. **NPC 行为**：挂在执行器的落定回调上——上报不靠自觉，靠收口；
2. **玩家交互**：挂在业务方法落定处（单向数据流已把玩家交互收敛在业务逻辑层）；
3. **世界系统**：各 World 子系统的生命周期点（死亡结算、灾害爆发、节日开始、物价过线）。

连续过程永不调用。

### 4.2 管线

```
业务落定（钱货两讫是业务系统自己做的）
 → ReportEvent(类型, 主动者, 接收者, 值参数, 地点, 上游)     ← 唯一入口
 → 事件系统：写事实库 + 广播"某类事实发生"
      ├→ 感知服务：在场必知 / 目击按范围品质 / 其余不知
      ├→ 每个感知者的记忆系统：建条目 + 解读
      │    （按类型 × 我与事件的关系 × 我的状态 → 效果，走统一效应管线发放）
      └→ 订阅了该类型的业务系统各自响应（执法订犯罪类、统计订交易类）
```

- backstory 生成（0 岁模拟到当前年龄）跑同一条管线，零特殊通道；
- 订阅广播沿用项目已有的"数据层广播→订阅方刷新"模式。

### 4.3 衍生触发（系统级触发点清单）

衍生事件**不在事件系统内部触发**，各自有主：

- 状态过阈（饿晕、断片）→ 需求系统自己上报；
- 死亡结算（继承、家属处理）→ 生命子系统的业务；
- 犯罪被目击 → 执法系统经订阅启动自己的流程；
- 目标种子 → 记忆解读时性格过滤后种植（目标层已定案）；
- Buff 到期 → Buff 自管。

触发条件全是状态沿（只发一次），链不会无限自旋。

### 4.4 感知服务（在场判定与品质档位）

感知 = 事件 → 记忆的唯一**一手**来源（二手 = 传播，取材/确信度归记忆模型文档）。

**不用引擎 UAIPerception 做主管道**：它是对 Actor 的持续追踪模型（回答"我看没看到这个人"，为敌人侦测设计），回答不了"谁感知到了这个事件实例、感知到什么程度"——事件不是 Actor，刺激到事件实例的映射反正要自己写；且数百监听者挂视觉 sense 持续做 LOS 成本不可接受。UAIPerception 留给战斗模式做敌人追踪。例外：声音类事件可复用 UAISense_Hearing（ReportNoiseEvent 本就是按位置广播的事件模型，与本设计同构）。

**事发时查询**（事件上报那一刻做一次空间查询，筛选链从便宜到贵）：

```
距事发点半径内（空间哈希）
 → 在视野锥内（朝向）
 → 状态过滤（睡眠/醉酒/工单专注等状态层判定 → 降档或剔除）
 → LOS 线迹（只对活到最后的小撮人做）
 → 输出：感知品质档位
```

**品质档位**（决定条目能填哪些字段，也是 §5.3 确信度的感知品质输入）：

| 档位 | 含义 | 条目字段 |
|------|------|---------|
| 目击全程 | 事件起始即在场看完 | 字段全 |
| 看到片段 | 中途到场 / 只看到结果 | 只知结果不知过程（看到尸体没看到凶手 → 接收者有、主动者空） |
| 只听到动静 | 未目视但在听觉范围内 | 只知"某处发生了某类事"（类型+地点，参与者空） |
| 不在场 | —— | 不知道，无条目 |

- 进行中的事件：起始时刻在场才算"全程"，中途路过 = 片段；
- 感知修正来源：七围感知（Perception）、状态层（醉酒/疲惫降档）、专注（工单执行中降档——认真干活的人注意不到旁边的事）；
- 感知是数据层操作，全档位同精度，不进 LOD 分档（LOD 只管演出与执行，见 §18（[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)））；目击判定是事件驱动的稀有操作，无需降频；
- 各档位常数、半径、遮挡系数档位：数值设计环节（§10 #4）。

## 5. 三个运行时公式（结构定案，系数留数值环节）

### 5.1 重要性

```
重要性 = 规模 × 身份系数 × 稀有度系数
```

- **规模**：事件值参数 ÷ 该类型典型值。典型值**免配置**——事实库统计近期同类事件的滚动均值（前期 100 金是大事，后期是小事，库自适应）；
- **身份系数**：主动者/接收者的名声值（基础层字段）换算；玩家或玩家的店/家人涉入时单独加系数（对玩家播报用）；
- **稀有度系数**：该类型近期在事实库中的频率取倒数——谋杀天然稀有所以天然重大，吃饭天然频繁所以天然轻微。免配置。

**消费方**：休眠判定、传播挑选权重、玩家公告、记忆进长期账门槛。一个数，各消费方用自己的阈值分档。

### 5.2 有利不利（对"我"）

不是事件的属性，是"这件事对我"的属性，在我的条目里算：

```
对我 = 已结算损益 + 潜在公开风险

已结算损益   = 条目的强度快照（带符号，解读时已算好）
潜在公开风险 = 规范表判定的惩罚严重度 × 我是主动者 × 传播进度
              （传播进度由传播计数读出：传得越广，越逼近"必然被追究"）
```

最后一项是进度含义：传得越广，被追究就越逼近，掩盖动机越紧迫——掩盖行为的评分随传播进度攀升，不是配出来的。有利由正值表达（救命恩人事件驱使我报恩/结交）。

### 5.3 确信度

```
亲历（我在主动者/接收者数组里）: 100

目击: 100 × 感知品质
      感知品质 = 距离衰减 × 遮挡系数（感知服务档位，§4.4）

听闻: 说者确信度 × 传播折扣 × 信任系数 × 易感修正
      传播折扣 = 每跳常数 <1
      信任系数 = 我对说者的 Friendship 轨换算
      易感修正 = 1 + (1 − 自洽性/50)（传染易感性 ∝(1−SC)，已定案）
      上限 = 说者确信度（听来的不可能比源头更确定）
```

**消费**：写入效果按确信度打折；唤起按**当时**的确信度折算；辟谣/对质/侦探取证可改确信度（已发效果不追溯）——"被骗三年、真相大白"由唤起自然表达。

## 6. 传播的簿记

**分工**：传播是**记忆之间的流动**——取材、条目复制、确信度计算、封口，全部归《AI决策系统-记忆模型-系统设计.md》的解读层（传播 = 闲聊事件的解读规则）。事件系统只管事实侧的簿记。

### 6.1 簿记与传播图

闲聊行为落定即普通事件入库：`{ 主动者:[说者], 接收者:[听者], 值参数:{ 话题 = 被传播的事件ID } }`。

- 听者记忆侧新建条目时，被传播事件的**传播计数 +1**；
- **闲聊事件天然记录了传播图**——谁、何时、把哪件事、告诉了谁；追传播链 = 沿闲聊事件查，不用另建传播日志。

### 6.2 传播计数的用途

见 §3.1——它是纯数值：把柄效力稀释的输入、话题热度参考、统计观察。**没有任何"公开判定"**：秘密不靠阈值失效，靠稀释失效。

（取材权重公式、确信度公式、封口标记——全部归记忆模型文档，此处不重复。）

## 7. 掩盖与发现

**没有掩盖系统。掩盖是普通行为，落定即事件**——藏尸、收买、灭口、撒谎各自产生各自的事件，同样会被目击、被传播、成为新把柄。掩盖者每掩盖一次就给世界多留一条事实，"越描越黑"是必然结果不是编排。

**发现的三条途径**：

1. **物证**：尸体/赃物是实体，存在于某地点；有人经过 + 感知判定 → 产生发现事件 `{ 主动者:[发现者], 值参数:{物}, 地点, 上游=原事件 }`。发现概率由地点人流/隐蔽性决定——藏到地窖是把发现推迟，不是消除；
2. **人证**：询问是提案，走接受度公式（关系/把柄/贿赂/执法权威都是筹码）；对方答应 = 传播发生；
3. **比对**：收集到的条目互相矛盾、或与物证矛盾 → 矛盾本身就是新线索。

**侦探不能读事实库**（那是全知视角，只有系统和开发者能读）——侦探只能从条目和物证逼近真相。侦探服务的本质 = 替你收集别人的记忆条目。

## 8. 消亡与规模控制

- **事实库**：事实**永不从存储中删除**（审查需要）——一个事实在最后一条引用它的条目消亡时**标记为休眠**（退出活跃：不参与话题取材、唤起匹配、传播），但保留在存储里供反查。即"一件事物的死亡 = 最后一个人忘记它"，死亡是标记，不是删除；
- **个人条目**：短期池容量竞争（DF 式：满了挤掉最弱的）→ 撑过期限进长期账；长期账唤起随时间打折；**锚定条目不打折、不挤掉、不回收**；
- **两级痕迹**：弱痕迹（共处/远远看见）只进短期池，不建关系轨（关系系统已定案）；
- **LOD**：图外 NPC 不模拟感知与传播，直接参与的事件仍记账，间接影响按区域状态粗算；
- **零轮询**：一切皆落定触发（已定案）。

## 10. 未决议题

1. **伪事件**（主动撒谎/伪造，Guild 2 式伪证）：标记后做，最小版本不做；
2. **传闻失真**（数值传错/参数缺键）：标记后做，最小版本只做确信度不动内容；
3. **关系破裂自动解除封口**：增强项，待议；
4. 数值细节（传播折扣、感知品质档位、重要性公式系数）：数值设计环节。

**突发状况 → 任务系统口子（已定方向）**：突发状况事件（投诉/打翻汤/插队争执/醉酒闹事…）按"可转任务"结构上报——值参数带 Severity / Deadline / 处置结果（预留）；本版由店铺侧自动处理或自然消散（如投诉不处理 → 差评落地），未来任务系统上线直接消费同一事件结构，AI 侧零改动。

## 11. V1 最小事件目录

V1 只运行**统一事件目录、同步分发与直接订阅**，不启用本文前述全局长期社交事实库、感知、个人记忆、传播与休眠机制。历史由账本、统计和业务存档各自保存。所有跨域业务事件都在同一目录登记，没有模块私有或绕过目录的业务事件；不预设事件总数，也不按“请求／事实”等标签分类。

每个事件只定义自己的发布者、发布时机、业务载荷、投递范围和订阅合同，不携带重要性、确信度、传播计数、记忆效果或“应创建什么目的”的指令。目录由 GameInstance 作用域承载、跨场景存活，事件同步分发，载荷对订阅者只读；World订阅者在EndPlay注销。任何订阅者都不得绕过裁决器直接维护目的。

经营资产与业务唯一归 Global `BusinessEntities` 中的经营实体；商圈 / Shop / 图外生意共享基础模型并按类型组合模块，持产权 / 经营关系、`bOpen` / 日程、目录 / 定价 / 订单 / 预留、声誉 / 客流。区域只空间与校验，不持业务镜像；实体区域组件关联 `AreaRef={SceneId,AreaId}`，子客房 / 仓库非经营实体，抽象生意无实际区域且不造假区域。真实库存、工作点FIFO和门锁归对应实例，区域看板为不入档派生索引。

目录中的店铺 / 雇主业务引用统一为 `BusinessEntityId / EmployerBusinessEntityId`；`BusinessEntityId` 是全局稳定经营 ID（GUID，规则见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)）；不再使用 `ShopId` 别名。空间引用为 `AreaRef`，Home / Work仍空间。交易事实保留 `SourceBusinessEntityId / TargetBusinessEntityId` 和可空 `OccurredAreaRef`；租金一笔交易两侧分别为Shop / District，历史不随当前经营父关系回改，不给区域账户。租约唯一事实在 Global `LeaseRegistry`，实体只引用 `LeaseId`，出租 / 承租业务与租用空间 / 承租人物分别为 `LessorBusinessEntityId / TenantBusinessEntityId / LeasedAreaRef / TenantCreatureId`。详见[区域店铺与商圈管理 §2 / §9](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。

- 高倍速一次推进跨过多个时间边界时，时间子系统按边界在游戏时间上的先后逐个补发 `Time.DayBoundary / MonthBoundary / HourBoundary`。贷款、租约、雇佣等计划时点由经济域统一结算调度器按各自 `Next...Sec` 严格逐条触发并叫醒域管理器，不登记为时间边界事件，也不做月界统一批处理。
- `Flow.NodeSettled` 报告节点实际效果，`Flow.Resulted` 只报告整条 Flow 的结果与原因，不重复携带节点效果；二者都不得直接结束目的。
- `Shop.QueueChanged` 只在工作点自有的 FIFO 逻辑队列实际变更后发布；首位顾客入队产生的状态变化由工单索引器派生对应收银工单，队列清空后由索引器更新看板，事件本身不另写队列。
- **工单索引器叫醒是内部通知，不登记为业务事件**：本店索引出现新工单或更高优先级工单时，索引器直接通知本店在岗且空闲的劳动者立即重新找活并重置冷却；执行中的劳动者不打断，除非更高优先级带按既有覆盖规则生效。无活可干的劳动者可长期睡眠，只在索引变化或冷却到点时醒来。
- `Shop.StateChanged` 在经营实体的 `bOpen` 或纯派生 `bOperating` 实际变化后发布，只报告事实。`bOperating=bOpen&&当前有效营业时段`，不入档、不复检；人工开业保留必需设施校验，运行期缺设施不系统关店。接客状态 `true → false` 时不再进新客，店内已锁价预留、收银排队或结账继续服务到拿货离店，既有消费所需工单仍可派生 / 保留。外部门口未进店队列清退，本次白跑结束只上报一次负满意度服务组声誉样本，不记来访 / 成交客群、不造进店事实。店内无消费的在场者按 `Shop.ExitRequested` 引导离店；清洁 / 补货 / 维修继续，员工自己按劳动安排离岗，不统一强退。
- `Shop.ExitRequested` 只表达店铺要求目标退出的意图，不代表目标已经离店。目标人员自行判断等待／自驱与原子边界，再执行退出；实际跨出区域边界后才发布 `Shop.PresenceChanged(Exited)`，清场、统计、坐位／认领回收均以该实际离店事实为准。
- `Shop.PresenceChanged` 只是中性事件类型，不属于人员或店铺，也没有首域处理器。实际进出店检测链只负责发布；所有订阅者分别启动自己的逻辑：空间订阅者维护实际在场，工作点实例维护自己的FIFO队列，经营实体统计实际顾客客流；坐位模块释放自己坐位 / 工位，经营实体预留逻辑释放Active预留，工单 / 员工处理各自认领，裁决与其他订阅者各自响应，区域不保存经营或队列镜像。发布者不知道订阅者，任何订阅者也不得统一编排其他订阅者。坐位不另发空闲事件。
- `Shop.CheckoutCompleted` 只记实际交付行，月度销量与品质统计不得改用库存、标价或默认品质代替。
- 感知、目击、听闻、传播、关系、犯罪、酒店、供应链、复杂社交和通用突发事件不属于 V1 最小集合。
- `Shop.ExperienceReported` 在V1只由经营实体声誉 / 评价统计直接消费；实际进店与 `Shop.CheckoutCompleted` 分别提供来访和成交数据，店内体验提供服务组与客群满意度。打烊门外未进店白跑只一次负满意度服务组样本，不能写来访 / 成交 / 客群满意度。不得创建个人记忆、感知或传播任务，四类客群不与服务维度交叉成完整矩阵。
