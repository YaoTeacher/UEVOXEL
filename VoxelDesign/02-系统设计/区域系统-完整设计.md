## 0. 一页规则

1. **区域 = 封闭结构内部的空间**，不含包围结构（墙、地板、天花板、屋顶）。
2. **区域覆盖 = 内部格集合**（多盒并集），可以包含区域内部的柱子、隔断等内部结构。
3. **区域内部的一切都可编辑**：体素结构、内部墙/柱、家具、物品。
4. **包围面只能编辑覆盖层和放置物体**：墙纸/贴面、壁挂、顶挂；不能改包围结构的体素。
5. **权限只有一个布尔**：`IsAreaEditable(CharId)`。区域内部编辑和包围面覆盖层/挂件都只看它。
6. **面 key = 实体格 + 朝向区域的方向**；同一堵墙两侧是两个不同的面，各归各的区域。
7. 区域之间**同类独占**：同一区域类型的两个区域不共享格；父层级类型声明为可重叠后，可包住不同类型区域（父子包含）。正体积重叠才算冲突，**贴边/共面合法**。
8. 墙/地板/天花板的结构在区域外，不归区域系统管；区域外结构由建造/建筑系统处理。
9. 不新增结构/面权限层或邻方同意；物品/结构产权与租约日志保留独立来源，编辑布尔不转移资产产权。
10. 房间/NPC占用不是区域数据；住客仅限时房间/设施使用者，不是客房 Manager，区域门按有效授权查询（见 §13）。

## 1. 目标与非目标

### 1.1 目标

- 用一套统一数据表达商圈、店铺、子功能区的空间范围。
- 让区域与体素世界解耦：区域不拥有包围结构，但能编辑内部和包围面饰面。
- 用单布尔权限支撑 Owner/Manager/租户/受薪管理人/关系解锁的全部编辑场景。
- 支持矩形、L 形、多盒并集区域。
- 支撑面级装修（墙纸/贴面/壁挂/顶挂），且不与体素结构归属冲突。
- 可存档、可迁移、可空间查询、可渲染边界。

### 1.2 非目标

- 区域外的建筑壳结构编辑（建造/建筑系统）。
- 多产权共墙的结构改造（未来建筑/产权系统）。
- 房间舒适度、NPC 房间分配（按位置采样/派生，不存区域）。
- 网络复制（当前单人/主机制，后续单独设计）。

## 2. 术语

| 术语 | 定义 |
|---|---|
| 经营实体（BusinessEntity） | 资产和业务数据唯一所有者；商圈、店铺、图外生意共用基础模型，按类型组合模块，存入 `Global.BusinessEntities` |
| 区域（Area） | 一块逻辑空间：内部格集合 + 类型/功能标记 + 空间父子 + 定位/准入约束；不存产权与经营真值 |
| 商圈（District） | 一种业态的经营实体，组织下辖店铺业务；可选空间组件关联真实商圈范围 |
| 店铺（Shop） | 一种业态的经营实体；`ShopId` 是经营 ID 别名，不是区域 ID |
| 子功能区（SubFunction） | 具有 `AreaId` 的空间隔间；不另建经营实体，直接挂所属店铺实体的业务 ID；**用途由创建时选定的区域类型确定** |
| 区域覆盖（Coverage） | 区域内部的格集合，1..N 个轴对齐盒的并集 |
| 包围结构 | 围住区域的墙/地板/天花板/屋顶；结构格在覆盖外 |
| 包围面 | 包围结构朝向区域内部的面 |
| 面 key | `(实体格 Cell, 朝向区域的方向 Face)` |
| 面覆盖层 | 面级饰面数据（墙纸/贴面/材质 id） |
| 挂件 | 壁挂、顶挂等锚定在面上的物体 |
| 经营关系 | 经营实体业务持有的有效经营人、经营方式及租约/任命条款；区域不存副本 |
| 模板 | 只含建造几何、内装布局、功能类型的生成数据，不含权属/租约/占用 |
| 建筑实例 | 结构几何的持有者；区域通过 `BuildingId` 依附，不拥有包围结构 |

## 3. 层级与经营关系（摘要）

### 3.1 经营与空间分别建模

```text
Global.BusinessEntities（共同基础模型，按类型组合模块）
 ├─ 商圈经营实体 ──ParentBusinessEntityId──> 店铺经营实体
 └─ 图外经营实体（可以没有真实空间）
经营实体的可选空间组件 ──AreaRef={SceneId,AreaId}──> 场景区域
场景区域 ──ParentAreaId──> 店铺范围 ──ParentAreaId──> 子功能区
家具/结构资产日志 ──独立产权来源──> 资产归属（不由空间树继承）
```

- 商圈/店铺是**业态**分类，空间树只表达范围包含；楼层/楼栋不新增经营层级。区域侧只有「区域类型」这一个分类维度（按空间作用），业态另属 `Business.Kind.*` 分类；两者互不充当身份，具体 Tag 取值与迁移由配置资产决定。
- `BusinessEntityId` 是全局稳定经营标识（GUID，规则见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)）；不再使用 `ShopId` 别名。`AreaRef={SceneId,AreaId}` 才是空间引用。
- 子区域有 `AreaId`，仅空间与功能标记，关联现有经营主体，不创建经营关系。

### 3.2 产权人、经营人与使用者

- **产权人**：由经营实体产权关系解析；店铺所依附铺位产权按有效商圈产权/授权查询，不在区域复制 Owner。
- **经营人**：由经营实体当前有效的自营、Lease 或任命关系解析，不在区域复制 Manager。
- 雇员只参与劳动安排，不因工作或空间准入取得经营身份。住客只是限时房间/设施使用者，不是客房 Manager。
- 产权人/经营人不能通过普通表单或创建输入框自由填值获得权利；关系解锁的编辑许可按有效授权查询。

### 3.3 实体经营关系

经营关系与相应合同/条款归经营实体的业务模型，按类型组合，不挂区域：

| 数据 | 归属与说明 |
|---|---|
| OperatorCreatureId / Mode | 实体有效经营关系：自营 / 承租 / 薪酬 |
| Lease 与首期 | 承租业务确认授权及条款后生效，先于租户建筑/家具真实写入 |
| 任命 / 薪酬条款 | 专用业务流程维护，不走普通 Setter |
| bOpen / 营业时段 / 目录 / 订单 / 声誉 | 相应实体经营模块；区域不镜像 |
| 两钱包 / 业务账户 | 初始人物持有，经营实体引用业务所需账户，区域不持资金真值 |

经营注册编排与空间注册编排分开；实体保存于 `Global.BusinessEntities`，空间保存于场景。`bOperating=bOpen&&有效时段` 纯派生，只手动写入且存档 bOpen，创建默认 false，无自动资格复检。

## 4. 空间模型

### 4.1 区域是内部空间

- 区域覆盖描述的是**封闭结构内部**的格子；
- 包围结构（墙、地板、天花板、屋顶）的实体格**不在覆盖内**；
- 区域覆盖**允许包含内部实体格**（柱子、隔断、内部楼梯），它们属于区域内部，可编辑；
- 因此"结构在区域内部"和"结构在区域外"有明确区别：
  - 内部实体格 → 属于区域，结构可编辑；
  - 包围结构格 → 区域外，结构不可编辑，只能改朝向区域的面。

### 4.2 覆盖数据结构

```cpp
struct FAreaCoverage
{
    TArray<FIntBox> Boxes;   // 内部格并集，轴对齐盒，闭区间
    FIntBox Bounds;          // 派生包围盒，用于粗筛
};
```

- 存储用"多盒并集"压缩，L 形/凹形用 2..N 个盒表达；支持退化为单盒；
- 权威数据是 `Boxes`；`Bounds` 只是缓存，任何盒变更后重算；
- 格子判定：任一盒包含即为区域内；
- 区域面积/格数：`CellCount()` 为所有盒格数之和（盒之间不重叠）。

### 4.3 边界与重叠

- **同类独占**：同一区域类型的两个区域不能共享同一格。跨类型是否允许重叠由区域类型自身的「可重叠」标记声明（父层级类型标记为可重叠后，才能包住下层的不同类型区域）；父子包含由该标记成立，不由空间包含自动成立。
- **重叠判定**：只有"正体积相交"才算冲突；贴边、共面、共线都合法。
- **父子包含**：子区域的所有格必须落在父区域格集合内。
- **同边**：`A.MaxEdge == B.MinEdge` 合法，体素各归各的，没有共享格。
- 墙在区域外，所以相邻区域通常被墙隔开；没有墙的开放边界允许贴边。

### 4.4 查询

- `GetAreaAtCell(Cell)`：返回包含该格的最小区域（按格数最少优先），用于编辑/物品/AI；
- 包围结构的实体格不属于任何区域，返回 `nullptr`；
- `GetAreaAtWorldPosition(Pos)`：世界坐标转索引后走同一查询；
- 父子层级：`ParentAreaId`，子区域优先于父区域返回。

### 4.5 创建规则

区域编辑工具的提交过程：

1. 玩家拖出一个盒（或涂刷格子）；
2. 查询盒边界上的实体格（紧贴盒边界、且属于包围结构）；
3. 从覆盖中扣除这些边界实体格；
4. 盒内部的实体格保留（柱子、隔断等）；
5. 生成 `Boxes` 并写入区域。

补充规则：

- 空地上先划区（还没有墙）：允许，覆盖保留整个盒；之后在边界上建造的结构按"内部结构"处理（可编辑）。
- 支持涂刷增/删格，用于修整 L 形或补洞。
- 移动/缩放区域时重算覆盖，不是简单平移 AABB。

## 5. 体素与面

### 5.1 结构编辑原则

| 结构位置 | 结构体素 | 面覆盖层 | 挂件 |
|---|---|---|---|
| 区域覆盖内（内部墙/柱/隔断） | **可编辑** | 可编辑 | 可放置 |
| 区域覆盖外（包围墙/地板/天花板） | 不可编辑 | **可编辑**（本区域一侧） | **可放置** |
| 区域外、与区域无关 | 不属于区域系统 | 不属于区域系统 | 不属于区域系统 |

- 区域内部的体素结构编辑（挖/放/拆/换）由区域权限布尔控制；
- 包围结构的体素编辑不属于区域系统，由建造/建筑系统处理；
- 包围面的覆盖层和挂件由区域权限布尔控制，不需要结构 owner 同意。

### 5.2 面 key

```cpp
enum class EVoxelFace : uint8 { PosX, NegX, PosY, NegY, PosZ, NegZ };

struct FVoxelFaceKey
{
    FIntVector Cell;   // 实体结构格
    EVoxelFace Face;   // 朝向区域内部的方向
};
```

- 面属于"相邻内部格所在的区域"：`InteriorCell = Cell + FaceOffset(Face)`，查该格的区域；
- 同一堵墙两侧：同 `Cell`、相反 `Face` → 两个 key，分别属于 A、B 两个区域；
- 区域只存自己这一侧的面数据，互不覆盖。

### 5.3 面覆盖层

```cpp
struct FAreaSurface
{
    FName StickerId;   // 墙纸/贴面/材质 id
};
```

- 渲染时按面覆盖基础纹理：`GetTexture(BlockId, Normal, WorldCell)` 先查覆盖；
- 只有暴露面才渲染，被遮住的面数据保留；
- 数据稀疏，只存非默认面；
- 覆盖层变更只脏相关 chunk，批量重建。

### 5.4 挂件

```cpp
struct FAreaAttachment
{
    FVoxelFaceKey Face;
    FName ItemUri;        // 壁挂/顶挂物品
    FTransform Local;     // 相对面的局部变换
};
```

- 挂件是实体 Actor/物品，锚定在面 key 上；
- 挂在面覆盖层之上，不占体素结构；
- 区域删除、结构失效时返还/掉落。

### 5.5 失效规则

- 实体格被移除或变成空气 → 该格所有面的覆盖层清除，挂件返还；
- 实体格替换为另一种实体 → 面覆盖层保留（建议规则，避免换材质丢装修）；
- 区域删除 → 全部面数据清除，挂件返还；
- 结构失效由体素系统广播，区域系统订阅并清理相邻区域数据。

## 6. 权限

### 6.1 唯一判定

```cpp
bool bCanEditArea = Area->IsAreaEditable(CharId);
```

- 来源：关联经营实体的有效产权/经营关系及授权查询；租户/受薪管理人的许可依有效 Lease/任命，区域不复制 Owner/Manager 或经营条款。
- 关系解锁的布局编辑许可只是查询该布尔为 true 的条件，不新增角色或权限层；区域门同样查询有效准入授权。
- 不新增 CanEditSurface/CanEditStructureAt 或结构/面权限层、邻方同意；结构/物品产权日志仍独立保留，不因该布尔或空间包含转移产权。

### 6.2 覆盖范围

`bCanEditArea == true` 时允许：

- 区域覆盖内的体素结构编辑（挖/放/拆/换）；
- 区域覆盖内的家具、物品编辑；
- 包围面的覆盖层编辑（墙纸/贴面）；
- 包围面的挂件放置/移除（壁挂/顶挂）。

### 6.3 不覆盖

- 区域覆盖外的结构体素（包围墙/地板/天花板/屋顶）→ 建造/建筑系统；
- 其他区域的任何数据；
- 区域权属转让、经营关系变更 → 经营业务规则，不是体素权限（仍由产权人/商圈经营人操作）。

### 6.4 判定流程

```cpp
// 体素编辑
Area = AreaSys->GetAreaAtCell(BlockIndex);
if (!Area) return;                    // 区域外，区域系统不处理
if (!Area->IsAreaEditable(PlayerId)) return;

// 面覆盖/挂件
InteriorCell = FaceKey.Cell + FaceOffset(FaceKey.Face);
Area = AreaSys->GetAreaAtCell(InteriorCell);
if (!Area || !Area->IsAreaEditable(PlayerId)) return;
```

## 7. 创建、编辑、删除

### 7.1 创建

- 通用商圈/店铺同一建造侧栏：拖盒或摆模板预览 → 填名称、类型/业态、经营意图等必要信息 → 单次组合业务确认，不要求先建区域后跳详情补建生意，不要求手动绑定。
- Confirm 概念请求 `CreateBusinessWithArea` 含 OperatorId、BusinessKind、Name、BusinessIntent、ParentBusinessEntityId、空间草稿等，具体 class 待定；产权人/经营人依有效授权与租约/任命确定，不能自由填来取得权利。
- Controller → 业务门面 → 实体/区域存储 → 事件 → UI。同一面板采集事实与范围但分别发给对应业务，经营实体及关系归经营存储，区域 Actor/覆盖/空间索引归空间存储；必要 Lease/首期生效后才允许租户建筑/家具真写入。
- 子区域创建仅空间与关联现有主体；空间覆盖仍按拖盒/扣边界墙格/涂刷规则计算。复用当前范围与模板预览，M13a 纯导航是待迁移代码事实，不是最终创建设计限制。
- V1 只预置商圈玩家标准租杂货店；创建默认 bOpen=false，不等于开业。

### 7.2 编辑

- 普通资料：经营实体名称/LOGO；子区域空间名称与允许切换的功能类型。不编辑产权、经营人、合同或营业状态。
- 覆盖编辑：移动/缩放/涂刷增删格；面数据刷新墙纸/贴面/挂件，沿用现有空间算法。
- 产权交易、Lease、任命与合同变化只走专用业务，权限按实体经营关系及有效授权查询，事件刷新 UI 只读态。
- 开业/停业单独手动写 bOpen 并入档；bOperating=bOpen&&有效时段 纯派生，不设自动资格复检。

### 7.3 删除

- 空间业务处理子区域、面覆盖/挂件、空间索引与 Actor 清理，不凭空间包含转移或吞并资产。
- 区域删除如何解除关联或注销经营实体待定，不自动删除 `Global.BusinessEntities`、经营关系、合同或账本。
- 物品/结构产权及租约来源日志独立保留，返还或资产处置须按有效业务关系处理。

## 8. 生命周期与模板（摘要）

完整生命周期/招商/租约业务见 [AI决策系统-区域店铺与商圈管理-系统设计](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)，这里仅列空间系统交界，不保存经营数据副本。

### 8.1 状态

空间注册/卸载与经营生命周期分开；不以区域 `FAreaFunctionBFragment.Status` 驱动经营目录或营业状态。bOpen 及实体生命周期由经营业务维护，bOperating=bOpen&&有效时段 纯派生；停业不会使有效空间消失，空间卸载不会注销全局经营实体。具体区域删除与实体注销规则待定。

### 8.2 入驻

- 承租：空店或模板先在同一连续面板预览，收集必要信息、候选同意条款及产权授权，建立有效 Lease/首期后才真落位租户建筑/家具；不先生成实物后绑定合同。
- 受薪：有效任命业务设定经营关系，不能通过编辑 Manager 字段取得权利。
- 产权人自营：同样经组合业务入口校验有效授权，确认实体及空间后复用建造执行。
- V1 只预置商圈玩家标准租杂货店，NPC 模板招商和完整客房不加入 V1。

### 8.3 退出

- 履约/主动退出：租户依独立资产来源日志处理自有建筑/家具/装修；不因区域包含或退出自动转移产权。删区域不注销经营实体，只解除空间关联；换租户沿用同一实体（已定）。
- 倒闭/欠租及坏账为完整版本经营业务，不进 V1；处置权只能来自有效合同/业务，不由区域包含直接授予。
- 盘下：经专用资产交易业务处理，不靠空间变更转移资产，资金按人物持有业务账户及有效权限执行。
- 空置/在租布局保护：编辑与拆除均查询有效产权/经营关系及授权；在租需租户同意的业务条件仍由经营业务维护，区域只消费 IsAreaEditable 结果，不存租约。
- 拆除/改造与解约/清退的交界由专用业务处理；本次不自定删除/注销方案。

### 8.4 模板

- 模板内容：建造几何 + 内装布局 + 功能类型 + 装饰；**不含**权属、租约、占用；
- 放置流程：同侧栏选位/模板预览与必要业务信息 → 单次组合确认实体+经营关系+必要有效 Lease/首期+空间注册 → 租户建筑/家具真写入；共边墙融合与模板内部覆盖计算沿用空间方案，不先生成实物后绑定经营关系；
- 模板落位时区域覆盖由"模板内部空间"计算，不含模板外壳；
- 租户自带建筑资产由经营/资产系统记录，区域系统只引用建筑实例。

## 9. 查询与索引

- 空间索引：16×16×16 粗格哈希，按区域 `Bounds` 注册候选；
- 窄相：`Boxes` 逐盒包含判定；
- 最小区域优先：按 `CellCount()` 比较，而非 AABB 体积；
- 墙格不在任何区域：查询返回 `nullptr`，这是正确行为；
- 父子：`ParentAreaId` + `SubAreasIndex`；`GetPlayerTopLevelAreas` / `GetTopLevelAreas` 继续使用 `ParentAreaId == INVALID_AREA_ID`；
- 区域覆盖变更后重注册空间索引。

---

## 10. 渲染与 UI

- 区域边界：多盒线框，选中/只读/父子高亮；
- 面覆盖层：网格生成时按面取纹理，支持墙纸/贴面；
- 挂件：面锚定 Actor，随面/区域失效返还；
- 空间区域树：场景根→商圈范围→店铺范围→子功能区，仅表示空间包含；经营主域按 Global.BusinessEntities与有效关系另列，不镜像。
- 详情面板同屏展示实体业务与空间信息：经营关系读实体，覆盖/面/挂件读空间，不把业务资料存回区域；
- 编辑工具：区域工具（拖盒/涂刷）、面装修工具、挂件放置；
- 只读态：`IsAreaEditable == false` 时禁止所有编辑入口，UI 灰显。

## 13. 与 NPC / 房间系统的交界

- 区域系统不存住客占用或入住合同，住客只是限时房间/设施使用者，不是客房 Manager。
- NPC住处的床位/家具使用关系与空间定位分开；客房限时使用授权由入住业务提供，不转移家具/房间资产产权。
- 区域门查询有效准入/使用授权，不使用客房 Manager钥匙。完整客房流程后续，不加入 V1。
- 房间用途由**创建时明文选择的区域类型**确定，不从内容物推导；区域类型只表达"这块空间是什么用途"，不写入区域权属，也不承担业态。
- 舒适度按 NPC位置采样（空间/光照/室内外/床的舒适分/室友），不存房间舒适度字段。

## 14. 分阶段与验收

### P0：权限与面数据（不改覆盖结构）

- 体素：面覆盖、网格查表、面编辑接口、存档；
- 区域：`SurfaceMap`/`Attachments`、单布尔权限接线、创建时扣边界墙格；
- 修复 §12.3 的 5 个问题；
- 验收：
  1. 相邻 A/B 店铺共用一堵墙，A 能刷 A 侧墙纸、B 能刷 B 侧，互不影响；
  2. 区域内部的柱子/隔断可挖/可拆；
  3. 包围墙体素不可编辑，只能改覆盖层/放挂件；
  4. 墙格查询区域返回空；
  5. 同一区域保存/加载后装修保留。

### P1：多盒覆盖

- `FAreaCoverage` 多盒、冲突/查询/父子/边界显示/区域工具改造；
- 存档迁移；
- 验收：
  1. L 形区域可创建、可查询、可显示边界；
  2. 两个区域贴边不冲突，重叠一格拒绝；
  3. 子区域必须完全在父区域内。

### P2：模板与生命周期接入

- 同侧栏模板预览/业务信息→一次组合创建实体/空间/关系及必要有效 Lease/首期→租户实物写入，经营与空间编排分别接入；
- 共边墙融合规则；
- 区域删除/退租/盘下的资产与面数据清理；
- 多盒导航（NavModifier）方案。

## 15. 边界与待定

1. **区域外结构编辑**：由建造/建筑系统负责；区域系统只保证包围面覆盖层/挂件权限。若后续需要"共墙开洞"，在建筑/产权系统设计，不进入区域权限。
2. **租户自带建筑资产**：结构资产归属由经营/资产系统记录（模板建筑、盘下），区域系统只引用 `BuildingId`，不存资产权属。
3. **多盒导航**：当前 `NavModifierComponent` 是 AABB；L 形区域先按 `Bounds` 近似，P2 再决定多盒导航。
4. **面覆盖材质来源**：使用纹理图集索引还是材质实例，P0 实现时按现有渲染管线定；数据层只存 `StickerId`。
5. **空地上先划区、后建墙**：后建的边界墙按"内部结构"处理（可编辑）；如果业务要求"先划区后建墙要自动变成包围结构"，需要额外的覆盖重算规则，暂不做。

## 16. 目标规则与现有代码差距

### 16.1 业务边界

- **两种层级**：经营实体父级用 ParentBusinessEntityId；场景空间父级用 ParentAreaId，不能由空间包含推出产权或经营归属。
- **管理身份**：产权人/经营人按实体有效关系与授权解析；雇员及限时住客不取得经营身份，区域不存 Owner/Manager 真值。
- **数据归属**：关系、Lease/任命、bOpen、目录、订单、声誉归 Global.BusinessEntities 的组合业务模块；两钱包/业务账户初始人物持有，物品/结构资产日志独立。
- **生命周期**：有效 Lease先于租户真实建造；退租/盘下依资产来源处理，换租户沿用同一经营实体、删区域不注销实体（已定），不自动吞并资产。
- **模板**：产权方/租户模板均不含权属、租约、占用，先预览与业务确认，再真实落位。
- **权限**：前端按有效身份显隐，后端专用业务复核；区域权限布尔消费查询结果，不复制经营关系。经营权限矩阵见相关经营分册。
- **V1**：只预置商圈玩家标准租杂货店，不增加 NPC 模板招商、完整客房、倒闭/欠租/坏账、并购易主或公共设施。
- **多点编辑预检**：提交前整体预检、任一格无权限则整体拒绝并高亮，沿用现有设计。

### 16.2 空间与资产职责表

| 维度 | 当前设计规则 |
|---|---|
| 区域定义 | 封闭结构内部空间，不含包围结构；范围不是产权 |
| 墙 / 表面 | 墙结构在区域外；模板贴边融合单层；区域面覆盖层与壁挂/顶挂保留 |
| 体素定位 | 包围墙格不在覆盖内；内部结构落在区域内仅表示空间位置，不转移产权 |
| 编辑权限 | IsAreaEditable 消费实体有效经营关系/授权的布尔结果 |
| 结构编辑 | 按授权可编辑区域内部；包围结构编辑仍属建造/建筑系统 |
| 在租保护 | 经营业务决定有效授权，不由区域存租约或 Manager |
| 覆盖 / 冲突 | 多盒并集；正体积相交冲突，同边合法，父子包含沿用空间规则 |
| 渲染定位 | 面 key + 面覆盖层，和资产产权记录独立 |
| 产权日志 | 硬装 leaseID 与家具 PlacedByLeaseId 保留独立来源，不因区域包含转移 |

### 16.3 保留但不再作权限依据

- **硬装改动日志 `leaseID`**：保留为资产归属 / 退租结算记录，不再作为体素编辑权限依据。
- **家具 `PlacedByLeaseId`**：保留为租户资产标记（退租/盘下/售卖），不参与编辑权限判定。
- **在租保护 / 店铺控制授权**：保留为业务规则（决定谁拿到 `bCanEditArea`），不是体素归属规则。
- **经营操作权限矩阵**：由经营分册现行规则维护，不由空间系统或普通资料表单替代。

### 16.4 现有代码差距

| 现状 | 新设计目标 |
|---|---|
| `FAreaCoverageFragment` 单 AABB | `FAreaCoverage` 多盒 + Bounds |
| `IsPointInArea` 单盒判定 | 逐盒判定 |
| `GetAreaIndexByPosition` AABB + 体积比较 | 格判定 + 格数比较；墙格返回空 |
| `IsAreaConflicting` 用 `FBox::Intersect` | 正体积相交；同边合法；父包含按格 |
| `GetAreaBounds` 用 `MaxIndex`（少 1） | 统一用 `Bounds`/`Max+1` |
| `IsAreaEditable` 只用于区域编辑/UI | 体素/面编辑唯一闸门 |
| 无面覆盖 / 挂件 | `FVoxelFaceKey` + `SurfaceMap` + `Attachments` |
| 块级 6 纹理，无实例面覆盖 | chunk 生成 context 注入面覆盖 |
| `ModifyVoxelData` 无区域权限 | 前置 `GetAreaAtCell` + `IsAreaEditable` |
| 区域工具只画 AABB | 提交时扣边界实体格 + 支持涂刷 |
| `VoxelSceneSaveGame` 缺 `SaveGame` | 补标记 + 版本迁移 |

### 16.5 权限接线

- 多点编辑预检沿用既有空间规则，消费关联实体的有效编辑授权，不新增权限算法。
- 前端显隐/后端专用业务复核继续适用，不以表单 Owner/Manager字段授予权限。
- 经营操作权限矩阵见经营分册现行规则；区域只提供空间定位与准入校验，不保存经营授权真值。
