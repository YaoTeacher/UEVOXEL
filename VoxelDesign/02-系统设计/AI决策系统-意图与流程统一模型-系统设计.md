# AI决策系统-意图与流程统一模型-系统设计

**版本**: 1.10
**创建日期**: 2026-10-17
**所属**: [AI 决策系统总纲](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)
**本分册职责**: 事件→裁决→目的→派发→流程→结果事件的统一链路与数据结构

> 本文定义统一的意图与流程链路：事件只触发裁决器，裁决器统一维护目的，随后派发 Flow 并消费结果事件。消费与工作不再有两套入口、两套模板或两套执行器。

---

## 1. 统一链路

```
① 事件
   需求跨阈值 / 设施状态跨阈 / 流程节点 / 队列阈值 / 玩家指令 / 突发事件
   每个事件按自己的合同携带业务数据；事件本身不直接修改目的
        ↓（所有订阅者各自启动；裁决器只是其中之一）
② 裁决（目的维护 + 队列整理）
   新增或更新目的 → 判断完成 / 取消 / 失效并删除
   → 建立执行组合并关系 → 按强制规则 / Duty 优先级 / Free Utility 排序
        ↓
③ 派发（主槽 + 次槽）
   主槽空取队首执行组；次槽取相容执行组；此时绑定 TargetRef / PlanRef / FlowStateRef
        ↓
④ 执行（统一 FlowConfig + 流程解释器）
   主行为链与相容次行为链分别推进五原语段、原子步骤、等待和中断
        ↓
⑤ 结算与记录
   节点完成事件启动各订阅者，分别处理需求 / 支付 / 库存 / 设施 / 体验；只上报实际结果，不直接结束目的
        ↓
⑥ 新事件
   Flow 完成 / 失败 / 取消、状态与资源变化再次进入①，由裁决器判断各目的后续状态
```

消费与工作的差异只剩三处：**裁决策略、Flow 内容、工单认领与休眠策略**。主槽与次槽是执行资源，不是另外两套目的队列。

**全局事件化边界**：业务与环境离散状态迁移在业务事务内提交，事务可由统一目录事件或外部业务方法启动；提交后按统一目录广播，后续影响由各订阅者事务执行。Tick 只推进连续量并发布到时、到达、碰撞或跨阈事件。所有跨域业务事件统一登记事件 ID、载荷、发布者、发布时机、投递范围和订阅关系，不允许模块私有业务事件或绕过目录分发，也不按“请求／事实”等标签分类；工单索引器叫醒等普通内部通知不登记为业务事件。事件不从属于发布者或载荷实体，所有订阅者分别在自己的事务中执行逻辑，内部允许普通函数调用；裁决器只是普通订阅者之一，没有首域处理器或统一业务总控。需要新动作时再发布事件。UI 只调用 Controller 业务门面方法，由业务方法校验、提交并在成功后广播；校验失败直接返回 UI，不为每次 UI 输入额外增加 Request／Rejected 事件。裸 Tick、裸 Flow 节点和 UI 不得直接写业务状态。这不是事件溯源，读档不重放事件。

## 2. 数据结构

### 2.1 逻辑枚举

```
UENUM()
enum class ELogicOp : uint8
{
    And,   // 必须满足
    Or,    // 任一满足（组内）
    Not    // 必须不满足（排除）
};
```

UE 没有通用 And/Or/Not 枚举（`EGameplayContainerMatchType` 只有 All/Any，`FGameplayTagQuery` 的表达式枚举是其 DSL 内部类型），因此新增公共 `ELogicOp`，条件判断、筛选、规则配置均可复用。

### 2.2 目标条件

```
FTargetSpec
├─ GoalTag     层级目标 Tag（Eat.Cuisine.Sichuan / Work.Clean.Table / Creature.Skill.Cook）
├─ TargetRef   具体实例引用（可空；实例 ID 不进 Tag）
└─ Op          ELogicOp，默认 And
```

求值：所有 And 满足 ∧ 所有 Not 不满足 ∧（存在 Or 时）至少一个 Or 满足。

不做嵌套逻辑；真需要 `A and (B or C)` 时生成多条意图或后续扩展子条件组。

### 2.3 目的意图

本文是 `FIntent` 在系统设计层的**唯一定义**。其他文档只引用本节，不再复制字段或另立定义。

```
FIntent
├─ IntentId
├─ Source          Self / Work / Command
├─ Targets         TArray<FTargetSpec>（目的与可选目标约束）
├─ CompletionRule  该目的自己的完成条件
├─ Payload         FInstancedStruct（订单品项/货物/污渍簇/同行者…）
├─ PlanRef         派发时绑定的 FlowTypeTag；开放目的生成时可为空
├─ ExecutionId     派发后指向槽位执行项，未派发时为空
├─ BasePriority    基础优先级/分带
├─ Deadline
├─ State           Pending / Bound / Waiting / Executing / Done / Failed / Cancelled
└─ Owner / BoardRef 绑定角色 / 所属**经营实体**看板引用
```

- **一条目的意图从生到死一个对象**；流程进度由执行组件持有的 `FFlowState` 记录，NPC 侧只存执行引用，不在 `FIntent` 或 NPC 个体数据中内嵌、复制流程状态；
- 看板引用只用于定位派生索引，看板不成为 Work 意图的业务事实所有者；工单认领与目的意图分离，不在这里复制认领数据；
- 精度由 Targets 的松紧决定：`Eat` 是开放目标，`Eat + Ref=某店` 是具体目标；
- 具体实例一律用 `TargetRef`，不用 Tag 编码实例 ID；
- `CompletionRule` 按实际状态与效果判断，不能用“某个节点成功”或“主 Flow 完成”替代。购买完成不等于 Hunger 已满足，购买效果却可以独立满足 Shopping。

### 2.4 执行组、槽位与流程

```
FExecutionGroup（裁决产物，尚未执行）
├─ GroupId
├─ PrimaryIntentId
├─ CoveredIntentIds   共用主行为链或可顺带覆盖的目的
├─ CandidatePlanRef   候选行为链，不在此阶段创建运行中 Flow
└─ QueueRank          队列顺序与调试评分快照

FSlotExecution（派发后的槽位执行项）
├─ ExecutionId
├─ PrimaryIntentId / CoveredIntentIds
├─ FlowStateRef      引用执行组件持有的 FFlowState
└─ ResourceUsage     位置 / 座位 / 手部 / 注意力及相容标签

FFlowConfig（按 FlowTypeTag 索引）
├─ FlowTypeTag     Consume.DineIn / Work.Serve / Work.Cashier / Work.Clean …
├─ Nodes: TArray<FPlanStep>    // 节点 = PlanStep，一级结构
└─ DefaultOnFail

FPlanStep（原名 FFlowNode，一级结构）
├─ StepType        Browse / QueueAt / ClaimSeat / Order / Pay / Consume /
│                  UseItem / AcquireResource / Release
│                  （节点类型集见《店铺空间与消费流程》§8.1；Goto/Acquire/Advance/Settle/
│                    Release 是节点内部的五原语段，不是节点；Reserve 是 Acquire 的用途之一）
├─ TargetRef       槽位 / 设施 / 区域
├─ WaitMode        SelfDriven / ServiceDriven
├─ bPausable       可暂停 / 不可暂停
├─ Primitives[]    该步内的五原语段：Goto / Acquire / Advance / Settle / Release（各段可跳过）
├─ Duration / 材料
└─ OnFail          放弃 / 重试 / 跳过
```

- `FFlowState` 由执行组件唯一持有，记录实际行为链、节点与原子步骤进度；槽位执行项和 NPC 侧只保存其引用。主槽持有唯一主交互的 `FSlotExecution`，次槽持有与主行为资源相容的次级执行项，二者均可关联一个或多个目的；
- 主槽空时直接取已排序队首执行组，校验前置条件并绑定 Flow；次槽按相容性取可执行项。**派发不重新裁决**；
- 执行组合并不删除、合并或平均各目的，也不复制多份相同 Flow；
- 单次 Flow 失败不等于所有目的失败。Flow 结果只产生事件；裁决器按各目的完成条件统一判断，未满足的目的由裁决器记录尝试结果、更新状态并保留或重新排入待执行队列，只有目的自身失效或明确耗尽时才删除或进入终态。

## 3. 意图生成

**裁决器统一收口，工厂只辅助构造数据**：

```
业务事件事实
  → 标记相关角色需要裁决，不直接写目的
  → 裁决器读取事实与当前状态，按事件类别选择工厂
       ├─ NeedCrossedFactory      需求跨阈
       ├─ FacilityStateFactory    设施状态跨阈
       ├─ FlowNodeFactory         流程节点与结果
       ├─ CommandFactory          玩家/店主指令
       └─ IncidentFactory         后续版本突发事件，不属于 V1 最小集合
  → 工厂只返回 Targets / Payload / TargetRef 等候选数据，不直接新增或修改目的
  → 裁决器读取目标、完成条件、基础优先级与前置条件模板
  → 由裁决器统一判断新增还是更新同一 FIntent，并维护后续队列
```

- 事件翻译与候选数据构造是代码，目的生命周期只能由裁决器写入；
- 目标模板、完成条件、优先级是配置；开放 Self 目的在生成时不写死 Flow，具体 Work 工单可预先声明允许的工作 Flow；
- 裁决器使用效果声明建立执行组合并关系，派发时才按最新世界状态绑定 `PlanRef / TargetRef / FlowStateRef`；
- V1 统一事件目录中当前登记事件的字段、订阅者见[事件系统](/VoxelDesign/02-系统设计/AI决策系统-事件系统-系统设计.md) §11；不预设事件总数。新增事件类别只增加裁决器使用的构造辅助，不获得独立写目的权限。

不做全配置映射 DSL（V1 过度设计），也不做全代码硬编码（扩展成本高）。

## 4. 裁决、事件边界与派发

**裁决器统一负责目的生命周期与尚未派发队列的全部整理工作**，事件源与执行层都不各自修改目的：

1. 读取事件事实与当前状态，判断应新增目的还是更新同一目的；不同有效目的全部保留，不设固定数量上限；
2. 判断各目的完成、取消、失效或明确耗尽，决定保留、重新排队、进入终态或从队列删除；
3. 根据共享效果、共同路径与资源相容性建立 `FExecutionGroup`，保留全部目的 ID 和各自完成条件；
4. 按当前 RoleContext 对执行组排序：Free 使用 Utility，Duty 使用工作优先级表 × Priority 分带，强制目的按覆盖序列置于相应位置；
5. 普通新目的可在主行为执行时参与待执行队列整理，但不因此打断主槽。当前执行项不放进普通待执行队列重新评分。

| 策略 | 适用 | 规则 |
|------|------|------|
| UtilityScoring | Free 时段自有执行组 | 硬过滤（营业/认知/价格）+ 加法核评分 |
| PriorityTable | Duty 时段工作执行组 | 优先级表 × Priority 分带两层扫描 |
| Forced | 玩家指派 / 安全事件 / 硬生理极限 | 不参与普通竞争，按独立覆盖规则处理 |

统一覆盖顺序沿用现有优先级序列：外部安全 > 硬生理极限 > 玩家指派 > 可压制 Critical > 当前 Job > Urgent > 新需求/常规工单。强制事件先按原子边界中断并结算当前执行，再从有序队列派发。

**事件事务边界**：状态修改、业务结算和级联事件处理期间，事件只携带事实并标记相关角色需要裁决；最外层事件结束后统一运行一次裁决器，由其集中维护目的与队列。去重的是裁决通知，不是目的意图，也不是独立事件事务；不设置“每 NPC 每 Tick 只能裁决一次”的玩法限制，不在原子结算中途递归维护目的或启动行为。

**派发条件**：队列已经有序时，主槽空直接取队首；次槽空取与当前主、次行为资源相容的可执行组。只有队列被相关事件标脏或队首前置条件失效时才重新裁决，槽位为空本身不触发重新排序。

## 5. 生命周期与工单认领

```
Self：Pending（角色待执行队列）→ Bound / Executing（派发到主槽或次槽）→ Done / Failed / Cancelled
Work：候选（由工单索引器派生并映入所属经营实体看板）→ 认领 Bound → Executing → Done / Failed / Cancelled
      认领释放或工单失效 → 触发裁决，按当前业务事实回 Pending 或进入终态
Command：强制 Bound → 按覆盖规则派发 Executing
```

执行组件持有的 `FlowState`：

```
Running → Waiting（服务驱等待，保留资源占用）
        → Paused（工作：可暂停工单进度留存）
        → Sleeping（消费：流程断点持久化，事件唤醒）
        → Completed / Failed / Interrupted
```

- 工单认领 `{WorkOrderId, CreatureID, StartGameSec}` 只用于去重与防抢单，不涉及钱、不是合同，也不入档；执行结束、中断、目标失效或认领人消失时释放，看板与认领在读档后由业务状态重建；
- 玩家手动接管与 NPC 自主执行共用劳动动作业务入口。目标存在对应工单时才建立或接管认领，且只在原子边界让出；目标没有工单时直接执行合法的状态修改，不为了手动动作创建工单；
- 资源预约在 Acquire 步骤写入，步骤结束/失败时释放；工单认领与资源预约分开；
- Flow Completed 只表示本次行为链走完，并向裁决器上报结果事件。裁决器按所有关联目的各自的 `CompletionRule` 判断完成、保留、更新或重新排队；未满足的目的可重新选择路径或进入兜底，执行层不直接结束目的；
- Flow Failed / Interrupted 先完成实际进度结算和资源释放，再把结果交给裁决器分别处理目的与工单，不自动把所有 `CoveredIntentIds` 标成 Failed 或 Done。

## 6. 结算与记录

统一出口：Flow 的 Settle 步应用该节点声明的全部效果，随后统一上报：

- 需求回填 / 支付 / 小费；
- 设施三槽 / 库存变化 / 设施状态；
- 体验上报 → 店铺声誉与评价统计；个体记忆仅完整后续版本，不进入 V1；
- 事件记录 / 账本流水 / 日志。

节点效果不由主目的限制，也不只回填一个 `SatisfiedDemandTag`。购买、使用道具、休息、聊天等各节点分别产生自己的效果；结算只应用实际效果并上报事实，随后触发裁决器统一回查所有关联及待执行目的的完成条件，决定完成、更新、保留或删除。部分结算只按实际进度应用已完成部分的效果，不直接给目的盖章。

## 8. V1 范围

**做**：ELogicOp + Targets 数组；目的意图队列与执行组；执行组件持有 FlowState、槽位执行项与 NPC 侧只存引用；主 / 次槽资源相容派发；统一 FlowConfig 表；事件系统 §11 的统一目录与当前登记事件（不预设总数）；三种裁决策略；生命周期与工单认领；按节点全部效果统一结算。事件工厂只辅助裁决器构造候选数据，不独立写目的。

**不做**：嵌套逻辑条件、全配置映射 DSL、意图的脚本化扩展。
