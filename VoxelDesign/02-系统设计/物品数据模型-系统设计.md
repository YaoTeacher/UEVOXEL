## 1. 系统上下文

### 1.1 系统边界

**物品数据模型负责**：
- 物品行的静态配置结构（身份、通用语义、功能片段、属性表）
- 物品实例的运行时数据结构（核心字段 + 功能模块）
- 物品身份体系（ItemTag / FullId / HandleId）与查找链路
- 类型级运行时缓存（Profile）与加载期形状校验
- 行子类的准入规范

**不负责**：
- 各功能的具体业务行为（家具使用见家具系统；消费/装备结算见对应业务系统）
- 区域权属与权限（见区域系统文档）
- 存档文件格式（由存储系统负责，本文只定义需持久化的字段）
- 配置表的编辑界面（由 UI 系统负责）

### 1.2 依赖与被依赖

- **被依赖**：ConfigDataSubsystem（加载与缓存）、编辑系统（放置）、AI 决策系统（设施/消费决策）、UI（物品库/详情）
- **依赖**：无（纯数据结构层）

## 2. 身份体系

每个物品行有三层身份，职责不重叠：

| 身份 | 形态 | 唯一性 | 用途 |
|------|------|--------|------|
| **ItemTag** | `FGameplayTag`（`Item.Type.BuildItem.Chair`） | 可被多行共享 | 品类身份：层级匹配查子类、交易分类、ALLOW 名单匹配、配方过滤 |
| **FullId** | `Source:IdentityName`（`core:item.chair.wooden`） | 行级唯一 | 持久化身份：模板/存档只写此字段 |
| **HandleId** | `int32 = GetTypeHash(FullId)` | 行级唯一 | 运行时句柄：实例只存 int32，查表/比较快 |

规则：
- **一行 = 一个 FullId**；同一个 ItemTag 下可以有多行（木椅/石椅/布椅都是 `Item.Type.BuildItem.Chair`）。
- HandleId 加载时由 ConfigDataSubsystem 计算填充，配置表不手填；哈希碰撞直接 Fatal（改 IdentityName 规避）。
- **ItemTag 不承担能力判定**：它只回答"这是哪一类"，回答不了"它能坐+能储+能售"的组合。能力判定一律查功能片段（见 §4）。现有 8 个 `Item.Type.BuildItem.*` 子 Tag 目前没有任何功能消费方，这正说明 Tag 不是能力的载体。
- **ParentHandleId 字段废弃**：原意是"Sub 变种指向主道具"做配置继承，实际全工程零消费。变体概念保留（材质/样式差异是真实需求），机制改为"独立行 + 共享 ItemTag"，不用 Sub 字段。

## 3. 行结构（静态配置）

### 3.1 继承链

```
FVoxelItemCoreBase                    身份与外观（所有行共有）
├─ Source / IdentityName → FullId → HandleId
├─ ItemTag / ItemName / ItemDescription
├─ StyleTags（风格标签，装修风格分布用）
└─ AssetFragment（图标/颜色/网格/贴图集）

FVoxelItemBase : FVoxelItemCoreBase    物品通用语义
├─ MaxHitPoints: float                所有 ITEM 的物理耐久上限（> 0）
├─ CirculateDataFragment（可流通/可销毁/堆叠/重量/价值）
├─ FPerishableFragment（保质配置；V1 只预留，不运行腐败推进）
├─ IsPlaceable / LimitPlace
├─ Stats: TMap<FGameplayTag,float>     跨系统属性表（美观/舒适系数…；不含品质）
└─ FunctionSet: TArray<TInstancedStruct<FVoxelFuncFragmentBase>>

FVoxelNormalItemBase : FVoxelItemBase  可放置实体物
└─ FPlacementFragment { Volume, OccupiedBlocks }

FVoxelBlockItemBase : FVoxelItemBase   方块（体素地形）
├─ FVoxelBlockItemFragment（实体/透明/邻接渲染/六面贴图配置）
└─ FVoxelPhysicFragment

FVoxelTemplate : FVoxelItemBase        运行时模板（组合体，独立表 RuntimeTemplates）
└─ Guid / Version / Size / Anchor / Entries / 作者与时间
```

三层基类的语义差别：

| 层 | 回答的问题 | 不含 |
|----|-----------|------|
| CoreBase | "这一行是谁、长什么样" | 任何玩法语义 |
| ItemBase | "它作为物品怎么参与世界"（流通/放置/使用/属性/能力） | 物理尺寸细节 |
| NormalItemBase | "这个可放置实体占多大空间" | 方块/模板的独立存储形态 |

### 3.2 三类行的区别

| 行类型 | 存在形式 | 独立存储 | 例子 |
|--------|----------|----------|------|
| NormalItemBase | 场景中的家具/道具 Actor | 无（ItemMap） | 椅子、货架、干粮 |
| BlockItemBase | 体素数据（区块数组） | 区块数据 | 石头、空气、水 |
| Template | 组合体模板 | `RuntimeTemplates` 独立表 | 玩家保存的建筑模板 |

### 3.3 放置数据（FPlacementFragment）

```
FPlacementFragment
├─ Volume: FVector            物理包围盒（厘米）→ 预览框 + 默认矩形占位
└─ OccupiedBlocks: TArray<FIntVector>
      可选·异形占位 override（L 形吧台等）
      不配 = 按 Volume / BlockLength 向上取整生成矩形占位
```

世界占用计算（`VoxelItemWorldSubsystem::CalculateOccupiedCells`）优先用 OccupiedBlocks，为空时回退 Volume 推导——这是现有实现，保持不变。

## 4. 功能片段（FunctionFragment）

### 4.1 形态与命名

- 命名统一 `F*FuncFragment`；配置为 `TInstancedStruct` 数组，空 = 无此能力。
- **结构参数 + 使用效果一体**：效果项内嵌在片段里，不允许再挂第二张"动作→效果"表（否则两处配置必然不同步）。
- 效果项结构沿用现有 `FVoxelItemBasicFunctionFragment`：

```
Effect
├─ LinkedDemand: FGameplayTag      目标需求 / 状态 Tag（需求为 Creature.Demand.*）
├─ EffectValue: float            基础增量
├─ DurationSec: float            生效时长
└─ SustainSec: float             持续段
```

`LinkedDemand` 指向六条 `Creature.Demand.*` 时，`EffectValue` 为带符号增量，正值回填、负值消耗，统一调用需求规则的 `ApplyDemandDelta` 并参与跨阈检测；不再经过 `EDemandEnum`。

### 4.2 数值归属规则

| 数值性质 | 归属 | 例子 |
|----------|------|------|
| 只有该功能自己用 | 片段字段 | FStorageFuncFragment.MaxCell、FPassageFuncFragment.bDefaultLocked |
| 多系统读、可被外部修改 | Stats 扁平表 | 品质、美观、舒适系数（设施加成、三状态槽修正作用于它） |
| 全物品共享的调参 | 全局配置 | 清洁堵塞阈值、劣化速率、槽位间距常量 |

### 4.3 片段全集

**家具类**（详细字段与业务见 [家具系统-系统设计](/VoxelDesign/02-系统设计/家具系统-系统设计.md)）：

`FSeatFuncFragment`、`FDineFuncFragment`、`FSleepFuncFragment`、`FToiletFuncFragment`、`FStorageFuncFragment`、`FProduceFuncFragment`、`FJoyFuncFragment`、`FLightFuncFragment`、`FPassageFuncFragment`、`FSightFuncFragment`、`FMaintainCleanFuncFragment`、`FMaintainRepairFuncFragment`

**物品通用**：

- `MaxHitPoints: float` 直接归 `FVoxelItemBase`，所有 ITEM 都有物理耐久上限；不再以可选 `FDamageableFuncFragment` 决定是否创建 HP；
- `FPerishableFragment` 包含 `ShelfLifeSec`（0 = 不腐坏）与预留的 `Disguise`。V1 保留配置但不推进腐败、不扣新鲜度，后续计算规则另定。

`HitPoints` 只表示物理损坏／磨损，不表示腐败、清洁或品质。所有 ITEM 初始化时都具有 `HitPoints = MaxHitPoints`；是否存在实际损耗来源由对应玩法决定，不能因为没有工具耐久链就删除 HP 状态。

**消费品**：

```
FConsumeFuncFragment
├─ UseAction（Eat / Drink / Medicine / …）
├─ bDestroyAfterUse        使用后销毁
├─ bSustainable            可持续使用
├─ bNeedTable              需要餐桌（大餐）vs 站着对付（干粮）
└─ Effect                  饱腹/口渴等基础增量
```

`bNeedTable` 让"大餐 vs 对付一顿"成为**数据差异**而不是 NPC 逻辑里的硬编码分支：NPC 按设施可用性与需求压力自然分流，找不到餐桌时降级站立进食、体验降档。

**装备**：

```
FEquipFuncFragment
└─ EquipSlot（手持 / 上身 / …）
   // 攻防数值走 Stats，不在此加字段
```

### 4.4 Stats 扁平表

- 键为 `Stat.*` 命名空间下的 GameplayTag（`Stat.Quality` / `Stat.Beauty` / `Stat.ComfortFactor`…），合法标签在加载期校验。
- 读取统一带默认值：缺失 = 中性值（0 或 1，按语义定），业务不判空。
- 设施的加成、三状态槽的修正都通过统一效应模型作用在 Stats 上，不写回配置。

## 5. 实例模型（运行时）

### 5.1 结构

```
FVoxelItemInstanceBase
├─ HandleId / ItemTag / Quantity        配置身份、品类与堆叠数量
├─ HitPoints: float                     所有 ITEM 共有的当前物理耐久
├─ Direction                            放置形态朝向
├─ ParentArea                           放置形态所属区域（区域反查唯一来源）
└─ FunctionModules: TMap<UScriptStruct*, FInstancedStruct>
      按 FunctionSet 逐条实例化的功能模块，模块内装该功能的状态
```

容器槽位通过 `ItemInstanceRef` 引用整个 ITEM 实例，以此表达实例所在位置；`Quantity` 和下列状态都只由 ITEM 实例持有，槽位不另存副本。`ItemId / HandleId` 回答“这是哪一种配置”，`ItemInstanceRef` 回答“这是具体哪一摞实例”：两堆罐子可以具有相同 `ItemId / HandleId`，却是不同实例引用。

`ItemInstanceRef` 的运行结构只保存稳定 `FGuid ItemInstanceId`，无效 GUID 表示空引用。`UVoxelItemWorldSubsystem.ItemInstances` 是世界、容器与背包内全部 ITEM 的唯一实例登记表，运行时通过该 GUID 解析实例，不持久化进程指针；槽位不复制另一份 `ItemId + Quantity` 或状态。整堆转移属于纯移动，保留原 GUID；只有部分拆分创建的新堆才分配新 GUID，原堆保留原 GUID。合堆保留目标堆 GUID，来源堆数量耗尽后删除来源 GUID；HP、清洁度等数值仍按本文既有实际移动数量加权规则处理。读档先恢复实例记录并重建索引，再恢复槽位引用；字段与完整顺序见[物品子系统架构 §9](/VoxelDesign/03-架构设计/VoxelItemWorldSubsystem-架构设计.md)及 [AI 决策系统架构 §7 存档](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md)。

`FVoxelInstanceEntry`（模板/存档条目）只存核心字段 + FunctionModules，不含类型级缓存；模板文件本身不存运行时状态（模板是静态设计图，放置时重新初始化）。

### 5.2 功能模块

| 配置片段／来源 | 运行状态归属 | 状态字段与边界 |
|----------|----------|----------|
| 任何带槽位的片段（坐/睡/吃/排队…） | `FSlotModule`（共享一份） | `TMap<int32, FVoxelSlotUse{CreatureId, bReserved}>` |
| `FVoxelItemBase.MaxHitPoints` | ITEM 实例核心 | `float HitPoints`；上限读取静态配置，不用可选片段决定有无 HP |
| FStorageFuncFragment | `FStorageModule` | `TArray<FVoxelInstanceContainerFragment>`；内部槽位引用 ITEM 实例 |
| FMaintainCleanFuncFragment | `FMaintainCleanModule` | `float Cleanliness = 1`；只在放置 OBJECT 中推进，ITEM 形态保存值 |
| FMaintainRepairFuncFragment | 无独立耐久状态 | 磨损／维修读写实例核心 `HitPoints`，不另存 `Integrity` |
| FPerishableFragment | `FPerishableModule` | V1 可保留初始状态但不推进、不扣值；最终字段与后续公式由易腐专项确定 |
| FPassageFuncFragment | `FPassageModule` | `bool bLocked` |
| FConsume/FEquip/FSight/… | 各自独立状态 | 片段本身无持续状态时不创建模块；核心 HP 始终存在 |

槽位模块按**运行期关注点**共享，不与片段一一对应——坐/睡/吃/排队占用的是同一个物理事实，拆开反而要同步。物理耐久同样只有一份：维修能力不再拥有另一份 `Integrity`。

**状态分离与生命周期**：

- 所有 ITEM 都有 `HitPoints`；`Integrity = HitPoints / MaxHitPoints` 为派生比例，不单独存储；
- 普通 ITEM 的 HP 归零时保留实例，但不可使用、可以维修；消耗品通过使用被消耗／销毁，堆叠 `Quantity = 0` 时销毁该堆实例并清空容器引用；
- `Cleanliness` 只表示脏污，清洁工单不修改 HP；只有放置 OBJECT 推进清洁度，ITEM 只保存收起时的值；
- V1 不运行腐败推进：不随时间扣新鲜度、不推进腐败进度、不过期，也不自然进入 `Spoiled`。后续腐败字段和计算规则另定；
- 品质不并入 HP。启用实例品质时使用独立实例状态，不同品质不能共槽、共堆；本次不给所有物品新增品质模块；
- `Quantity` 只表示数量。堆叠 HP 是这一堆的共享状态，不是 `单件 HP × Quantity`；不同 HP 按 §5.4 的实际移动数量加权合并，HP 为 float、不取整，HP0 合并不另设例外。

### 5.3 状态读取与初始化

"没有该可选状态"与"状态处于默认值"由语义化 getter 区分或兜底，业务代码不散落判空：

```cpp
GetCleanliness(Inst) // 无清洁模块 → 1.0
GetIntegrity(Inst)   // 所有 ITEM：HitPoints / MaxHitPoints
IsLocked(Inst)       // 无门模块   → false
GetStat(Inst, Tag)   // 无该属性   → 0
```

`Integrity` 不作为实例字段持久化；存档保存实例核心 `HitPoints` 与实际存在的功能模块状态。

放置／生成实例时读取 Profile：所有 ITEM 的核心 `HitPoints = MaxHitPoints`；声明了附加状态的片段再实例化对应模块（清洁度初始 1、锁取 `bDefaultLocked`），无状态片段不产生模块。V1 易腐配置不产生时间推进。

### 5.4 容器引用与堆叠操作

- 槽位为空或保存一个 `ItemInstanceRef`，不得另存 `ItemId + Quantity` 作为第二份权威；读取数量、HP、清洁度和品质都访问被引用实例；
- 纯移动只改变实例所在槽位，不改变实例及其状态；数量耗尽时销毁堆实例并清空引用；
- `CanStackWith` 先检查物品身份与显式状态门槛，不同品质直接拒绝；**是否可放置不是共堆门槛**；
- 通过 `CanStackWith` 的不同 HP、不同清洁度都允许合并。目标堆接收 `MovedQuantity` 后：

  `NewHitPoints = (TargetHitPoints × TargetQuantity + SourceHitPoints × MovedQuantity) / (TargetQuantity + MovedQuantity)`

  `NewCleanliness = (TargetCleanliness × TargetQuantity + SourceCleanliness × MovedQuantity) / (TargetQuantity + MovedQuantity)`

  没有清洁模块的 ITEM 只计算 HP。部分合并时，源堆未移动数量保留原 HP 与原清洁度；拆分时新堆与原堆都复制拆分前的各状态；纯移动不变；
- 合并后只保留整堆共享 HP 与清洁度，不保留逐件历史。HP 为 float、不取整，`Integrity` 从合并后的 HP 派生；HP0 合并不另设例外。该加权只是合并时的一次换算，不是 ITEM 形态下的持续清洁度计算。

### 5.5 ITEM／OBJECT 放置生命周期

```text
可放置 ITEM 堆
  → 需要放置一件时 SplitOff(1)，交接当前实例状态
  → OBJECT 恢复所保存的状态，并启用放置态逻辑
  → 使用、环境、清洁等只修改 OBJECT 的 Cleanliness
  → 收起时把当前 Cleanliness 等状态交回单件 ITEM
  → 背包／货架内不推进清洁度；入包时按兼容规则合并或独立占槽
  → 再次放置时恢复保存值并继续 OBJECT 计算
```

任一时刻只有当前形态持有权威状态，ITEM 与 OBJECT 不能各自保存一份同时变化。花朵、罐子等可以同时拥有放置能力与 `MaxStackCount > 1`；需要保留复杂内部状态的对象可配置为单件，但不能对全部可放置物一刀切。

## 6. 类型级缓存（Profile）

加载期每个 HandleId 构建一次，同型实例共享：

```
FVoxelItemRuntimeProfile
├─ FunctionMask: uint64            能力位掩码，HasFunc<T>() O(1)
├─ Fragments: TMap<UScriptStruct*, const FVoxelFuncFragmentBase*>
├─ Stats: 只读副本
└─ SlotTable: FVoxelSlotTable      仅可放置物；socket 解析或规则推导结果
```

加载期校验（报告到配置表，运行期零校验）：
- 片段声明的状态类型未注册 → Error
- 有状态模块定义但无片段引用（孤儿） → Warning
- Stats tag / Effect 目标不合法 → Error
- 行结构与 ItemTag 不匹配（`Item.Type.Block.*` 必须是 BlockItemBase 行等） → Error
- 槽位命名不合规 / socket 缺失 → Warning + 回退规则推导

## 7. 衍生规范

**总规则：能力差异走功能片段，结构差异才走行子类。**

允许新增行子类只有三种情况：
1. **独立数据块且全类型共有**：该型有一整套自己的数据、业务读取路径完全不同（方块=体素渲染/贴图数组）；
2. **独立存储或索引表**：实例不在 ItemMap/Actor 链上（Template 的 RuntimeTemplates、Block 的区块数组）；
3. **持久化形式不同**：存档里存法都不一样（Block 存体素 ID，Normal 存 InstanceEntry）。

禁止加子类的情况（一律加片段）：
- 只是多几个字段且仅部分物品有；
- 只是"这一类能做某事"（→ FunctionFragment）；
- 加完子类后业务出现 `if (ItemTag.MatchesTag(A)) static_cast<A*>` 分支——这个差异不该用子类表达。

配套纪律：
1. 子类只装数据、不带行为；**构造函数不准写隐形默认值**（`FVoxelBlockItemBase` 构造函数里设 ItemTag 的写法移除，由配置或加载器显式赋值）；
2. 业务禁止裸 `static_cast` 取子类，统一用 `ConfigDataSubsystem::GetItemAs<T>(Handle)`（带真实结构校验与日志）；
3. 新增能力优先新增片段 + 可选模块，配置主结构和实例主结构零改动；
4. 新增 Stats 键必须先在 `Stat.*` 标签表注册。
