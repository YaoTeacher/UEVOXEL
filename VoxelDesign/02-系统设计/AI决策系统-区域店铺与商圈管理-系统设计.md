## 1. 系统上下文

### 1.1 系统边界

**负责**：

- 经营实体的经营层级，以及区域 / 子功能区的空间关系;
- 产权人 / 经营人 / 雇员三类角色，以及经营实体关系（自营 / 承租 / 薪酬制）；
- 店铺与商圈的生命周期：营业、空窗、倒闭、空置、招商、签约、退出、易主；
- 招商、租约、盘下与退出规则；坏账、违约收铺和遗留资产处置仅保留后续版本边界；
- 区域权限与体素编辑权限的交界规则。

**不负责**：

- 体素建造工具、几何编辑与历史记录（建造域）；
- 顾客消费流程与员工工单执行（空间卷 / 员工卷）；
- NPC 店主的经营决策循环（见[店主与商圈管理](/VoxelDesign/02-系统设计/AI决策系统-店主与商圈管理-系统设计.md)）；
- 区域物理渲染、导航与空间索引（区域子系统）；
- UI 布局与分区（屏幕分区卷）。

### 1.2 外部依赖

| 依赖 | 用途 |
|---|---|
| 区域子系统（VoxelAreaWorldSubsystem） | 区域实例、覆盖范围、层级、空间查询 |
| ConfigDataSubsystem | 区域类型 / 业态配置 |
| 物品 / 家具系统 | 设施与道具的归属、库存 |
| 店铺装修卷 | 硬装改动日志、软装 `PlacedByLeaseId` |
| 店铺经营卷 | 区域账本、口碑、雇佣记录 |
| 时间系统 | 租期、营业时段、游商年度回归 |
| AI 关系系统 | 关系解锁的编辑许可、并购协商 |
| 建造域 | 模板建筑生成、区域增删、体素改动落地 |

### 1.3 输入输出

**输入**：玩家经营操作、NPC 经营决策、租赁/招商事件、时间节点（到期/日结/年度回归）、关系事件、建造域产物（模板建筑/区域）。

**输出**：经营实体关系、租约状态、人物钱包流水与经营业务账、空置/营业状态、产权变更结果、体素编辑许可判定；坏账与遗留资产不属于 V1 输出。

## 2. 核心概念

| 概念 | 定义 |
|---|---|
| **经营实体 BusinessEntity** | 经营资产及业务主体；有全局稳定 `BusinessEntityId`，独立于区域和场景 Actor 的生命周期。商圈、店铺、图外生意共用基础模型，按类型组合业务模块 |
| **区域 Area** | 一块逻辑空间（覆盖范围 + 用途 + 空间层级 + 相应校验）；以 `AreaRef{SceneId, AreaId}` 定位，可以包含墙体体素；区域本身不是资产，不持有经营业务真值 |
| **区域组件** | 经营实体与实际经营场所的关联；区域数据仍由空间系统登记，不复制经营状态。抽象经营实体没有实际区域组件 / 区域引用，不伪造图外区域 |
| **店铺 Shop** | 店铺类型的经营实体，持有经营关系、营业、商品目录、订单、声誉与统计等业务，实体店关联店铺主区域 |
| **商圈 District** | 商圈类型的经营实体，管理下属店铺、权属、租务和商圈业务，实际商圈关联商圈主区域 |
| **城市区划 Zone** | 城市地理分区（设定层），不是经营实体，不进入经营层级 |
| **子功能区 SubFunction** | 店铺内部的功能隔间（厨房 / 客房 / 员工区 / 仓库），只有物理功能 |
| **产权人** | 商圈产权的持有人；店铺产权人继承所属商圈的产权人 |
| **经营人** | 实际经营该经营实体的人：产权人自营、承租租户或薪酬制管理人；不是区域自身的身份字段 |
| **雇员** | 与经营实体存在雇佣关系的人；`EmployerBusinessEntityId` 指向店铺 / 商圈 / 图外经营实体，不直接指向人物，合同付款时实时解析资金责任人 |
| **经营关系** | 每个经营实体一份：经营人 + 经营方式 + 对应合同引用；区域查询这份关系，不另存副本 |
| **经营方式** | 产权人自营 / 承租（定期交租、剩余索取者）/ 薪酬制（工资 + 授权业务支出） |
| **租约** | 承租方式下的条款集合；完整版本含租金、押金、起止、续租优先权与状态；V1 只保留月租、生效时间、收租计划与状态，无押金 / 固定租期 / 续租 / 欠账状态 |
| **坏账** | 后续版本的违约处置概念；V1 租金直接划转并允许源经营账户为负，不生成坏账 |
| **遗留资产** | 后续版本中租户留在店铺内的设施 / 道具 / 自建部分，归商圈产权方处置；V1 不实现该处置链 |
| **盘下** | 后续版本由商圈产权人使用自己的经营账户买下租户自带的建筑 / 装修 / 家具，资产转为产权方所有 |
| **模板落位** | 承租户自带装修模板，在商圈内生成独立建筑与区域实例，玩家只决定摆放位置 |

## 3. 层级与空间

### 3.1 经营层级

**V1 特例**：只实际加载玩家商圈及其 Shop / 子功能区，商圈外为平地；不生成 NPC 竞争商圈，不运行并购、多商圈或其他街区。以下层级是完整版本结构，V1 复用同一父子关系但只实例化其中一条商圈链。

```text
经营关系树                         实际空间树（由区域组件关联）
商圈经营实体                       场景
 └─ 店铺经营实体                    └─ 商圈主区域
                                    └─ 店铺主区域
                                         └─ 客房 / 仓库子区域（非经营实体）
图外抽象经营实体                    不生成对应空间区域
```

经营层级和空间层级是两种关系，不互相充当身份或资产所有权来源。`BusinessEntityId` 表示生意；`AreaRef` 表示地点；NPC 的 `KnownShopIds` 保存店铺经营实体 ID，住所和工作位置使用空间引用。实际库存、门锁和 FIFO 队列仍归家具 / 工作点实例，不放入区域几何模型。经营 ID 的具体引擎表示由架构实施前确认，不在本分册选定 GUID 或整数。

- 主地图 = 城市里的一个核心商业街区，内含多个互相竞争的商圈；城市其他区域在探索模式（商圈生态卷 §17.1）。
- **商圈不嵌套**；店铺必须直属某个商圈；子功能区只能直属店铺。这三条是**区域类型的父级规则**，由区域类型配置声明（必需/允许的父类型），不写死在代码里。同类型区域不重叠；父层级类型声明为可重叠后，跨类型的空间包含才成立。
- 商圈之间是并列关系；玩家可通过并购持有多个商圈，但每个商圈仍是独立管理单元。
- 楼栋、楼层、多栋独立建筑只是体素几何：**不构成区域层级，不设切层/楼层管理**；查看用相机高度、渲染切片、剖切框。
- 城市区划（Zone）只用于设定与客流群体口径，不属于经营层级。

### 3.2 店铺区域的两类来源

| 类型 | 来源 | 生命周期 |
|---|---|---|
| **产权方铺位** | 产权人通过建造域建造的店铺区域 | 持久存在，租户更换不影响区域 |
| **租户自建铺位** | 承租户模板落位生成「独立建筑 + 区域实例」 | 建筑、装修与家具归租户；退租不自动拆除建筑、删除区域或重分配资产，被盘下后转为产权方铺位 |

### 3.3 区域覆盖与体素归属

- **区域覆盖可以含墙**：玩家划区域时无法强制排除墙体，接受这一点。
- **同边允许**：两个相邻区域的边界可以共面（如 A 的左边 = B 的右边），只要没有正体积重叠就不算冲突；同级区域禁止体积重叠，父子区域仍允许包含。
- **体素归属 / 渲染按体素中心点判定**：区域边界使用体素边坐标（连续整数平面），体素属于哪个区域由中心点落在哪个区域决定，避免同边时出现"一个体素属于两家"。
- **双层墙**：两个盒体店铺贴边放置时，各自生成自己的墙体，中间是两层结构，方块 ID 各是各的；每层归各自建筑的所有者（租户自建归租户，产权方建造归产权方）。不做单层共墙、共墙归属特例、墙纸 / 表面层。

## 4. 权属与经营关系

### 4.1 角色

- 经营资产具有**产权人**与**经营人**两类管理关系；雇员通过有效雇佣合同取得工作身份，顾客通过服务记录取得使用授权，均不因此成为经营人。
- 「代理人」不单独建模：代理人就是经营人。
- 区域与子功能区不单设产权人 / 经营人；空间准入与编辑请求查询关联经营实体的权属、合同及有效授权。
- 产权只到**商圈经营资产**一级：店铺的产权人在**创建与易主时写入实体自身的产权人字段**（取值即所属商圈产权人），运行时只读该字段，不沿父实体上溯；店铺不可单独买卖。空间包含关系不改变租户建筑、装修、家具的独立权属。

### 4.2 经营实体的经营关系

每个经营实体各有一份经营关系；商圈、店铺和图外生意共用基础关系模型，按适用业务关联租约或雇佣条款。区域只提供空间关联：

| 内容 | 说明 |
|---|---|
| 经营人 | 该区域的经营人；产权人自营时 = 产权人 |
| 经营方式 | 产权人自营 / 承租 / 薪酬制 |
| 承租条款 | 完整版本：租金、押金、起止、续租优先权、租约状态（仅承租）；V1：月租、生效时间、收租计划与状态，无押金 / 固定租期 / 续租 / 欠账状态 |
| 薪酬条款 | `EmploymentId` 引用（仅薪酬制）；工资只读对应雇佣记录，不在经营关系中复制 `WageConfig`。V1 使用产权人唯一经营账户，不设区域独立预算余额 |
| 劳动安排 | 所有实际劳动者都有挂在 Creature 上的劳动安排；承租经营人、自营产权人与薪酬制店主 NPC 均包含在内。经营决策是不占排班的抽象业务方法 |
| 资金与业务权限 | 承租 / 自营 = 使用经营人自己的唯一经营账户；薪酬 = 只能发起授权业务，从产权人经营账户结算，不能划转其个人钱包或经营账户；区域流水对所有有效 Owner / Manager 开放 |

- **商圈与店铺都可以是承租或薪酬制**；受薪经营人只管理已有店铺，不生成新建筑。
- **商圈经营人**可以改商圈下其他店铺的租约（招商 / 租金 / 押金 / 租期 / 续租 / 退租），但不能改产权，也不能改自己作为乙方的合同；这类自指合同只能由产权人办理。角色同时具有产权人身份时，才可按产权人权限处理。V1 只有月租与退租，押金 / 租期 / 续租仍属后续版本。
- **店铺经营人**不能改自己经营关系里的租约条款，只负责店铺日常经营。
- **合同唯一登记**：租约在 Global `LeaseRegistry` 中保存唯一事实，不建独立契约 Actor / UObject，经营实体只持 `LeaseId` 引用；每次生效的承租关系有稳定、可持久化的 `LeaseId`，用于资产归属、租金结算和存读档。退租后重签生成新租约 ID，不复用旧 ID；这不自动决定经营实体是否重建。需要留痕的只有账本流水（操作者 + 事由）与可选租约变更记录。
- V1 沙盒玩家是商圈受薪经营人，同时是自己店铺的承租经营人；初始标准租约的产生顺序见 §6.14。

### 4.3 开局关系与并购（完整版本，非 V1 沙盒）

- 商圈产权人 = 游商（常年不在，一年回来一次）；玩家 = 商圈经营人；酒店 = 玩家在商圈下经营的店铺。
- 主线剧情不依赖并购；自由模式下玩家可整体并购商圈：远程告知游商、与产权人协商价格与意愿，成交后产权过户。
- 并购最小单位 = 商圈；不能单独购买店铺区域（避免 NPC 建造的店铺出现玩家无权修改的碎片产权）。
- 产权转让遵守**买卖不破租赁**：经营实体 ID、既有租约与雇佣关系保持稳定；收租方及自营 / 薪酬制等依赖产权人的后续结算改为新产权人的唯一经营账户。承租店收入、采购与员工工资仍使用承租经营人的账户。付款时按当前经营关系解析，不批量改雇佣人，不改写历史流水。
- 商圈经营人变更、商圈经营关系调整、产权转让等产权级动作只能由产权人决定；产权人不在场时通过远程协商办理。
- 交易门槛以经济为主：钱、卖方意愿、程序性费用（税费 / 许可 / 关系）影响价格与流程，不做硬性身份锁。

## 5. 生命周期

### 5.1 状态机

```
营业 → 空窗（店主死亡/离开，经营决策挂起）
     → 停业（bOpen=false，员工/工资/租金照旧）
     → 主动退租 / 产权人按缓冲期收回
     → 空置 → 招商 → 签约 → 营业

营业 → 履约退出 → 空置（缓冲期结束）
```

- **没有「清算」阶段**：V1 不因资金耗尽、经营账户为负或租金结算自动倒闭；退出只走主动退租或产权人按既有缓冲期收回。
- 店铺区域本身不因租户退出而自动消失；租户自建铺位的建筑与区域也不因退租自动删除，资产处置只按权属与另行协商的盘下条款进行。

### 5.2 负债与倒闭边界（V1）

- 租金到期从承租经营人的经营账户足额划到商圈产权人的经营账户，源经营账户允许为负；不生成欠租、坏账或连续失败次数。
- 经营贷款月供、工资和租金造成的负经营余额只表示经营者的整体净负债，不触发自动倒闭、收铺、收资产或员工清退。
- V1 不设置 `bNoCollection`、`ArrearsEvictionPeriods`、欠租补缴或催收状态；后续若恢复违约收铺与坏账玩法，必须另行业务决策，不能从负余额隐式推导。
- V1 退出不产生坏账；遗留资产售卖、债务清算与催收玩法均不实现。

### 5.3 履约退出

- 租户 / 产权人按**可配置的退租缓冲期**提前通知，期满终止租约；
- 退租同时终止该店相关雇佣关系，雇员按离职规则结清当月工资；
- 退租只处理租约与雇佣，**不重新分配资产**：不自动拆除租户自建建筑，不自动收起家具或道具，不回滚装修，也不将任何资产转归产权方；
- 产权人 / 父级管理人需要取得租户自带建筑、装修或家具时，按 §5.4 的「盘下」条款另行协商收购（后续版本）；
- V1 无押金、无坏账，也不生成欠租、装修欠费或没收处置。

### 5.4 盘下

- 商圈产权人 / 经营人可以与租户协商，经授权从**商圈产权人经营账户**出钱盘下租户的店铺资产。
- 成交后建筑、装修、家具归商圈产权方，作为店铺「原有设施」；
- 店铺转为「带设施的空置店铺」，可再次出租；
- 商圈经营人只负责谈判、执行与记账，个人不拥有商圈内建筑资产。

### 5.5 空置与在租

| 状态 | 规则 |
|---|---|
| **空置铺位** | 商圈经营人可随时编辑 / 删除；出租形态二选一：带设施出租，或清空只留区域；也可直接删除区域 |
| **在租铺位** | 默认不能编辑 / 删除（建筑与装修是租户资产）；关系足够好且租户允许时，可编辑布局 / 装修，但不改变所有权，也不能借许可删铺 |
| **产权方铺位** | 租户走了区域仍存在，永远是产权方铺位 |
| **租户自建铺位** | 自建建筑、装修与家具归租户；退租本身不删除建筑或区域、不改变资产归属；盘下后转为产权方铺位 |

### 5.6 停业与租金负债（V1）

- **停业** = 经营人通过业务方法将 `bOpen=false`；`bOperating` 随即按 `bOpen && 当前在营业时段内` 派生为 false，不单独手动改写。员工保留、工资照发、租金照收，亏损由经营人承担，经营人可自行解雇员工或与产权人谈减租。
- **租金直接结算**：到期从承租经营人的经营账户足额划到商圈产权人的经营账户，允许源经营账户为负；不形成欠租、坏账、连续失败或自动收铺条件。
- **无欠租补缴**：V1 没有旧欠租可补缴，也没有手动补缴入口；负经营账户通过后续经营收入自然回升，不被解释为某笔租约或某个区域的欠款。
- **主动离开 / 被清退**：提前一个可配置的退租缓冲期通知，期间继续营业 / 交租，到期只终止租约与相关雇佣；该店雇员按离职规则结清工资，资产不重新分配，店铺进入空置。
- **雇员离职结算**：普通员工与薪酬制店主均按当月在职时长结清工资后终止雇佣，不设辞职梯度、谈判或预告期。

## 6. 招商与出租

### 6.1 承租与受薪的落位差异

| 经营方式 | 现有空置店铺 | 自带模板生成建筑 + 区域 |
|---|---|---|
| **承租** | ✅ 可使用同业态空置店铺 | ✅ 两类皆可 |
| **受薪** | ✅ 只管理已有店铺 | ❌ 不生成建筑 |
| **产权人自营** | 通过建造域自行建设 | — |

### 6.2 承租户的两种落位

1. **使用现有空置店铺**：玩家指定一个同业态空置店铺，带设施或清空后直接使用；
2. **模板生成**：使用承租户自带的装修 / 布局模板，在商圈内**完全独立生成实体建筑与区域实例**；建筑、装修、家具归承租户，V1 建造 / 装修免费，玩家只决定摆放位置与租约条款。模板是租户 / 店铺初始布局数据，不从业态配置取默认装修模板。

- 模板生成需要商圈内有可用空间，并做落位合法性校验（不与既有结构冲突、不阻塞公共通道）；
- 生成的建筑与区域实例绑定该承租户；退租不自动拆除建筑、删除区域或改变资产归属；被盘下后资产转产权方，铺位转为产权方铺位；
- 装修 / 布局模板随承租户或店铺初始布局数据提供；业态配置只负责类型、设施要求与允许经营品类，不提供装修兜底模板；

### 6.3 招商来源

沿用[员工与工作执行](/VoxelDesign/02-系统设计/AI决策系统-员工与工作执行-系统设计.md)的三条来源：人力市场（主路径）、店主引入（自带模板，玩家布置落位）、熟人邀请。来源可不同，但邀请、查看 NPC 意愿与业态、确认获准条款、选择空铺或摆放模板可在当前建造面板内连续完成，不强迫玩家跨模式创建实体或手动绑定区域。

- **租现有空铺**：选空铺 → 选同业态且同意开店的 NPC → 确认有权批准的租务条款 → 签约、首期与劳动安排生效 → NPC 接管经营；复用已有区域和合法设施，不重画范围、不把产权方原有设施转给租户。
- **模板开店**：选 NPC / 自带业态与模板 → 填获准租务条款 → 在商圈内摆放预览并通过空间校验 → 确认；后台先使租约与 `LeaseId` 生效，再按该租约写入租户建筑、装修、家具及区域关联。预览不是已落地建筑，不收预览租金。业务完成后仍选中新店，继续在原建造面板操作。
- **签约后的经营**：承租 NPC 是经营人，不自动成为有薪员工；收入和经营支出由其经营账户承担，按营业、采购、招聘与劳动安排等既有业务推进。签约不绕过设施要求或强制开业，玩家仍按商圈租务权限管理合同。
- 以上 NPC 招商、模板生成属后续版本；V1 不开放该入口，也不创建 NPC 承租店。

### 6.4 租金收取与负债边界

- **商圈收租计划**：每个商圈配置 `RentCollectionDayOfMonth`，在每月固定收租日的 **00:00（游戏时间）** 收租。签约时按所属商圈计划推算该租约的 `NextRentGameTimeSec`；结算调度器到点叫醒租约管理器，由租约管理器严格按各租约自己的到期时间逐条结算并推进下一时点，不做全局月界统一批处理。高倍速跨期时按时间顺序逐期执行。
- **首期签约即收**：签约当月按剩余日历天数比例计租，并在签约业务提交时立即收取。剩余日历天数按首个收租日期与签约日期的日历日期差计算，忽略时分；首期租金 = `Ceil(月租 × 签约当月剩余日历天数 ÷ 签约当月日历总天数)`。首期属组合创建六件之一，与经营实体、区域、经营关系、租赁、劳动安排同生共死，任一失败整体不成立。
- **后续整月收取**：首个及后续收租日均按当时生效的月租收取完整一期，不按日拆分；零月租不产生流水，但仍推进 `NextRentGameTimeSec`。
- **调租从下一收租日起生效**：产权人调租后，下一收租日该期直接按新月租整月收取，不按变更日分段，不追溯已结算租金。同一期内多次调租由下一次收租读取最后配置。
- **资金与流水**：租金从承租经营人的经营账户划到商圈产权人的经营账户，流水记录 `LeaseId`、系统操作者、店铺事由与双方账户。允许源经营账户扣负，到期总是足额划转，不因余额不足失败、不部分扣款；V1 不生成欠租、商圈坏账或连续失败次数，也不因此自动收铺。
- **租约字段**：租约是 Global 事实，存 `LeaseRegistry`（不随场景卸载），经营实体只持 `LeaseId` 引用。字段为 `LeaseId / LessorBusinessEntityId / TenantBusinessEntityId / LeasedAreaRef{SceneId, AreaId} / TenantCreatureId / MonthlyRent / StartGameTimeSec / NextRentGameTimeSec / RentCollectionDayOfMonth / SettledRentPeriodCount / Status / ExitGameTimeSec`。出租经营主体、承租经营主体、签约人物和租用空间分别表达，不以空间 ID 代替合同主体。`Status` 只有 `Active / PendingExit`，退出完成后移除当前租约，历史流水仍保留 `LeaseId`；不保存欠租、坏账、催收字段。
- **无补缴链**：自动收租只处理当期，不存在历史欠租或手动补缴；负经营账户是经营者所有生意共享的整体资金状态，不反向拆成某期租约或某个区域的债务。
- **押金与催收（后续版本）**：押金、违约收铺、坏账、催收与资产清算均不属于 V1；若后续启用需另行定义，不从当前负余额隐式生成。

### 6.5 设施维护

- **V1 不做公共设施专属系统**：不生成专属长椅、不做公共设施清单与按日维护费；但商圈区域内放置的普通家具仍注册到商圈设施索引，并产生保洁/维修工单。
- **设施维护统一为员工维修工单**：设施状态变化由工单索引器转换为所属用工区域的维修候选，员工按自己的劳动安排认领并执行；不存在按设施数量或游戏日扣费的维护链。
- **V1 无公共维护费**：不产生公共维护流水，不设置公共维护结算任务，公共维护也不属于经营账户扣负白名单。贷款月供、租金、工资以外的普通经营支出仍须足额。
- V1 不设公共维护工、清洁员、治安管理员等专属岗位；商圈区域工单由普通员工按劳动安排认领，不另设公共员工编制。

### 6.6 活动（V1 不实现，接口预留）

- **V1 不做广告投放、促销或其他活动**：不生成 `FShopCampaign` 实例，不冻结预算、不扣费，也不执行触达、引流、声誉或体验效果。
- 店铺活动页只保留后续入口，不提供可执行投放；`ActivityTags`、活动配置与挂载接口保留。
- **完整版本归属与出资**：商圈广告挂商圈、店铺广告挂店铺，分别按业务归属从资金责任人的经营账户扣款。
- **完整版本付款规则**：每次活动执行前足额扣除 `CostPerExecution`，成功才产生当次效果；余额不足则当次不执行、不记欠款、不自动中止，下个执行周期重新尝试。有限周期活动到期自然结束。
- **完整版本发起权**：由该商圈的经营人发起——玩家商圈玩家手动发起；NPC 商圈由 NPC 经营人按经营决策循环发起。
- 广告、促销、集市 / 节庆 / 摊位、节日与特定事件活动均后续实现；V1 店铺认知不新增任何活动写入来源。

### 6.7 客流统计

- **V1 同时统计进店客流与路过流量**，均按日结汇总、保留时段分布：
  1. **进店客流**：进入店铺区域的 NPC 人次（按店铺分别统计），以及进店后的成交 / 放弃 / 客单价（来自消费链路）；
  2. **路过流量**：进入商圈覆盖区域、但未进入任何店铺的 NPC 人次；V1 用于观察自然路过与进店转化，完整版本可进一步判断广告 / 引流效果与商圈整体热度。
- **转化率** = 进店客流 / 路过流量（按日 / 时段）。
- **数据来源**：`Shop.PresenceChanged(Entered / Exited)` 是中性事件，所有订阅者各自启动逻辑；统计订阅者只对 `Role=Customer && Entered` 按绝对游戏小时累计一次进店人次，区域、坐位、库存、工单、员工工作与裁决等订阅者分别处理自己的状态。商圈覆盖区域进入 / 离开接口提供路过流量，消费流程结果提供成交 / 放弃 / 客单价。日结聚合，支持按日 / 周查看；统计只由一个统计订阅者写入，其他订阅者不得重复计数。
- **信息边界**：本商圈精确；竞对商圈仅趋势级。

### 6.8 商圈业务账与资金权限

- **商圈没有独立资金余额**：区域经营页只显示按商圈业务归属过滤的收入、支出、净额和逐笔流水；实际经营资金在商圈产权人的唯一经营账户中。
- **流水必须分类并保存区域归属**，供统计与用户查看；V1 分类覆盖租金、工资、即时采购、经营贷款及其他实际启用业务，广告 / 活动、建设 / 盘下等后续分类随对应业务接入。
- **支出权按经营关系区分**：
  - 承租 / 自营经营人：经营收支使用自己的唯一经营账户，本人可与自己的个人钱包双向注资 / 提取，普通转出须源账户足额；
  - 受薪经营人：可查看商圈业务流水与经营账户可用资金，只能发起授权业务，由系统从产权人经营账户扣款；不能划转产权人的个人钱包或经营账户，也不能查看其个人流水；
  - 产权人自营：使用自己的唯一经营账户。
- V1 同一产权人的所有区域共享其唯一经营账户，不设分类预算、区域独立现金池或钱包内区域分账；区域流水只用于业务统计与权限查询。
- 分类统计与唯一流水同源，展示在商圈资产 / 统计页资金段；本商圈精确、竞对只给趋势。

### 6.9 许可（V1 最小版本不实现，配置预留）

- 许可**逐个配置**，不做统一枚举：每个许可独立配置区域类型 / 业态范围、前置许可 / 科技树节点、势力关系门槛、费用、是否可升级、是否年检、有效期、到期是否重新审核、持续义务（如维护责任）等。
- 解锁关系类似科技树：许可之间有前置 / 依赖节点，按配置逐级解锁。
- 现有两类校验主体保留：改建类用所有人关系、经营类用经营人关系（店主卷 §4.4）。
- **V1 最小版本不实现许可**：许可不阻塞开店 / 营业；只预留配置结构与接口，避免后续改存档 / 架构。

### 6.10 营业状态与营业时段

- **周期长度由时间系统配置为 N 天**（不假设地球的 7 天）；营业时段模板 = N 天 × 24 小时格，**1 小时块**。每天允许多个营业段，支持跨夜（20:00–02:00）。营业时段归属 Shop 配置并入档，与员工排班复用小时格结构但语义独立。
- **状态两字段**：`bOpen` 是经营人的开业 / 停业意图，只通过开业、停业业务方法手动设置并入档；`bOperating = bOpen && 当前在生效营业时段内`，是派生状态，不提供单独手动改写入口、不单独入档。实际接客直接读取该派生结果，消费链路不使用 `EAreaStatus`。
- **统一业务入口**：开业、停业、延长营业和营业时段编辑均调用业务方法。每次 `bOpen` 或生效营业时段变化后重新派生 `bOperating`，在同次业务变更完成后广播 `Shop.StateChanged{旧/新 bOpen、bOperating、原因}`；普通区域资料表单不得直写这两个字段。
- **打烊区分两类队列**：实际接客条件 `true → false` 时，停止新入店与新接客来源。店内已锁价预留、收银台排队或正在结账者继续完成结账、拿货与离店，既有服务所需收银工单继续，不作硬清场。尚未进店的店外门口队列清退并释放门口队列位，按 `Shop.ExitRequested` 引导离开；其离开不伪造店内 `Presence.Exited`。
- **店外白跑体验**：被打烊清退的门口等待者一次性上报 `Shop.ExperienceReported{BusinessEntityId, CreatureID, 原因=打烊门外清退, bEntered=false, bPurchased=false}`，只作为服务组负满意度样本进入总体声誉，不计来访、不计成交、不更新种族 / 职业 / 阵营 / 街区客群构成。店内服务正常完成不因“打烊”这一事实额外产生差评，具体服务体验仍按正常规则评价。
- **内部工作继续**：清洁、补货、维修等内部工单不因打烊关闭，员工按自己的劳动安排决定到岗与离开；经营决策仍是抽象业务方法，不进入排班。
- **手动停业黏滞**：`bOpen=false` 时 `bOperating` 必为 false，营业时段变化不会重新开业；再次开业只改 `bOpen`，随后按当前生效营业时段派生实际接客状态。
- **延长营业走业务方法**：延长或取消延长只调整生效营业时段的覆盖，不直接写 `bOperating`，也不能越过 `bOpen=false`。V1 不做班次外召回、加班合同或加班费，员工仍按原劳动安排离岗；特殊日期 / 季节营业与完整加班规则留后续版本。
- **无入口硬校验**：开业不做 `HasUsableEntrance` 式可用入口条件。NPC 找不到路就不来消费，只向玩家提示「有顾客想到你的店但进不去」，提示需去重并带冷却。
- 营业时段 UI 为 N × 24 的排班式网格（1 小时块），支持预设、整行套用、复制到全部；`bOpen` 与营业时段入档，读档后由二者重建 `bOperating`。

### 6.11 店铺控制授权（基础设计，V1 不实现）

- 只有二元状态：店主**允许**或**不允许**某个角色参与店铺管理；公开信息（营业时间、在售、价格、拥挤度、口碑）无需授权即可查看。
- 不设「只读经营数据」独立档位：允许参与管理即进入经营页；不允许就只能看公开信息。
- 授权由店主对当前角色的**信任度 + 角色个性**综合决定，不是硬阈值：
  - 店主可以主动提出让角色 / 玩家参与管理；
  - 角色 / 玩家也可以主动与店主谈是否参与；
  - 信任度下降时，店主会主动撤销。
- 授权不改变产权、经营关系、租约；不能转授；随时可撤销。
- **V1 不实现**，只有基础设计；V1 的产权人 / 商圈经营人默认只能看公开信息。

### 6.12 店铺统计口径（V1）

- **V1 不做 6 维 × 5 群体矩阵，也不另设「全局」统计组**。
- 统计项分 5 组：
  1. **服务**：服务速度、服务质量、商品丰富度、价格、环境氛围（上菜速度并入服务速度 / 服务质量）；
  2. **种族**；
  3. **职业**；
  4. **阵营**；
  5. **街区**。
- 服务组聚合全部有效体验样本，就是 V1 的总体店铺声誉；五个服务维度分别保存滚动聚合与有效样本数并做贝叶斯收缩，综合有效声誉供 `QualityScore` 读取。
- 种族 / 职业 / 阵营 / 街区四组统计的是**客群构成**（来访人数、成交笔数、成交金额、客单价、满意度等），不是把服务指标按群体再交叉一遍，也不作为群体声誉输入。
- `Shop.ExperienceReported` 直接写入服务统计；实际进店、成交与体验结果更新四类客群构成。V1 不创建个人记忆，不接完整感知系统或口碑传播；普通路过发现只走 NPC 卷 §5.2 的简化认知规则。
- 完整「维度 × 群体」口碑矩阵、独立全局组、个体记忆、完整感知与传播留后续版本升级。
- V1 存档只保留五组统计聚合、当日集中评价保护所需的最小状态和在途未上报体验报告；已完成上报的逐条体验样本不永久保存。服务组逐维保存 RollingScore / SampleCount 与保护日／负面样本数，四类客群保存来访／成交／金额／满意度聚合；星级、综合声誉、客单价和平均满意度只派生。字段及读档顺序见 [AI 决策系统架构 §7 存档](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md)。

### 6.14 通用开店流程（从创建到开业）

**一个建造面板，一次创建意图**：玩家选择商圈 / 店铺 → 拉区域或摆放模板预览 → 在当前侧栏填写名称、类型 / 业态和必要经营意图 → 确认。组合业务入口校验空间及有效授权，后台分别建立经营实体、区域、经营隶属与本次所需合同；成功后仍选中新对象并留在建造模式继续装修，不要求分别创建、手动绑定或跳详情页补建经营实体。产权人、经营人和合同条款由有效授权及签约 / 任命业务决定，不可通过普通资料字段取得产权。

- 商圈创建建立商圈经营实体和主区域；V1 商圈由开局装配，通用手动创建属于完整版本路径。
- 店铺创建建立店铺经营实体和主区域，并关联所属商圈；玩家自营、承租或留作出租的关系按有效授权处理。V1 标准承租由产权人预先授权，玩家不自行批准自己的合同。
- 子区域创建只建立空间区域并关联所属经营主体，不生成第二个经营实体或钱包。
- 名称 / LOGO 等后续资料编辑不等于签约或任命，营业开关也必须走专门业务入口。创建后默认 `bOpen=false`，不把“创建完成”当成“已经营业”。

**归属前置原则**：真实建造、装修落点前必须能确定资产归属；以租户身份建造前已有生效租约和 `LeaseId`。范围 / 模板预览不代表真实写入，可先预览位置再最终确认；不允许真实落地后补签并追溯改写产权。

| 开店路径 | 区域、合同与建造顺序 | 资产与资金口径 |
|---|---|---|
| 产权方建空铺 | 产权人 / 商圈经营人创建 Shop 区域与外壳，之后再招商或任命经营人 | 已有外壳归产权方；V1 建造 / 装修免费，后续收费时由产权人经营账户承担；签约不会把已有产权方资产自动转给租户 |
| **V1 沙盒玩家承租** | 同一建造面板圈范围、填信息、确认 → 系统按产权人授权完成店铺经营实体、区域关联、经营关系、租约、承租人劳动安排与首期原子提交 → 继续建房 / 装修 | 空间在商圈内，经营资产关系与空间关系分开；签约后新建与改造部分归玩家租户；V1 建造 / 装修免费；经营贷款进入玩家唯一经营账户，店铺经营直接使用该账户 |
| 承租 NPC | 确定业态与承租关系后生成本次 `LeaseId`，再落位租户模板 | 建筑 / 装修归对应租户；V1 建造 / 装修免费，资产不因退租自动重新分配 |
| 薪酬制经营人 / 产权人自营 | 先确定经营关系与劳动安排，再由产权方建设或装修 | 资产与利润归产权方；V1 建造 / 装修免费，后续经营费用由产权人经营账户承担；薪酬制经营人工资按雇佣记录从产权人经营账户进入其个人钱包 |

**组合创建是一个不可分割的业务动作**：经营实体、区域、经营关系、租约、劳动安排、首期六件事同生共死；任一步失败，世界状态回到确认之前，不允许出现「有租约无实体」「有实体无区域」「有劳动安排无雇约」这类半份结果。**租现有空铺**路径不新建区域（区域已存在，只做冲突复核），其余成员相同：空铺尚无经营实体时新建，已有实体则复用并只改经营关系。提交顺序、失败点与回滚语义见 `03A §3.9`——失败点全部在校验阶段，故不需要补偿层。

V1 玩家承租合同的规则：

- 开局由抽象产权人提供标准承租授权与条款；玩家在建造面板**圈定店铺空间**并创建区域，但圈地不等于有权批准自己的合同——合同仍由产权人作为出租方办理。开局装配同时创建商圈抽象产权人（游商）的唯一经营账户，作为租金收款方。店铺区域不预置，圈定的范围内签约前已存在的结构（商圈既有墙/地/公共设施）仍归产权方。
- **标准月租由开局 / 剧情配置提供**，主线与沙盒自定义剧情可设置不同值，默认 `MonthlyRent=0`。默认零租金不是缺陷，也不产生租金流水；需要非零租金的场景通过该配置构造，而不是改变默认规则。
- 合同出租方为商圈产权人，承租方与店铺经营人均为玩家，`Mode=承租`，初始 `bOpen=false`；`bOperating` 按营业状态规则派生为 false，不单独入档。
- 玩家同时是商圈薪酬制经营人，统一雇佣登记中另有一条 `EmployerBusinessEntityId=商圈经营实体` 的有效记录；经营关系只保存对应 `EmploymentId`，薪酬从该雇佣记录读取。V1 标准初始 `MonthlySalary=0`，零工资只跳过月末转账，普通员工工资不受影响。
- 签约同时为玩家创建挂在 Creature 上的承租人劳动安排；经营决策不占用其中的排班或工单。租约使用 §6.4 的字段，签约时推算 `NextRentGameTimeSec`，之后由租约管理器按各租约到期时间逐条结算。
- 首期租金按签约当月剩余日历天数比例折算，在签约时立即收取；后续每个收租日 00:00 按整月收取。首期是组合创建六件之一，与其余五件同生共死，任一失败整体不成立、不留半份世界。零租金首期只跳过转账，不影响签约和收租计划。
- 调租从下一个收租日起生效，该期按新月租整月收取，不按调租日分段，也不追溯已结算租金。
- 玩家不能修改自己作为乙方的合同，只有产权人能修改；每次新承租关系生成新 `LeaseId`，退租重签不复用旧 ID。

后续共同流程：

1. **业态（创建时选定）**
   - 组合创建面板中**先选业态与区域类型，再框选区域**；业态属于创建必填，未定业态不能开业；
   - 创建后变更业态须走**独立的业态变更申请流程**（申请 → 审批 → 生效），不得用普通资料表单、「编辑业务」或简单 setter 直接改；
   - V1 只做杂货店；业态走 `Business.Kind.*` 分类（具体取值由业态配置资产定义），区域类型只表达店铺空间，见 [业态模板](/VoxelDesign/02-系统设计/AI决策系统-业态模板-系统设计.md)；
   - 后续版本的承租 NPC 自带业态，招商 / 邀请时可见；签约后玩家不能手动改，只能走变更申请或退租；V1 不生成承租 NPC；
   - 「通用店铺」也是独立业态，不是无业态。
2. **装修 / 设施**
   - V1 建造 / 装修免费，不产生装修欠费、没收或材料返还；后续收费时按业务归属从资金责任人的经营账户支出；
   - 不能编辑权限外区域 / 场景；退租不改变装修与设施归属，产权人 / 父级管理人需要取得租户资产时按盘下规则协商；
   - 带业态的店铺在保存并退出建造模式时做**非阻断提醒**：列出缺失的必需设施清单，但不阻止退出、不把玩家锁在建造模式；**人工开业同样不做设施校验**，缺失项由运行期提醒给出（05 决策29）。
3. **开业**
   - 签约后默认**停业**（`bOpen=false`）；没有「未开业」状态；
   - 经营人通过开业业务方法将 `bOpen=true`，只硬校验业态必需设施，不查员工 / 库存，也不做可用入口校验；商品目录无品类 / 品类无库存给提醒，顾客无法寻路入店时按 §6.10 给出去重提示。
4. **营业**
   - `bOpen` 是手动入档的经营意图，`bOperating` 由 `bOpen` 与当前生效营业时段派生，不单独手动写入或入档；实际接客读取 `bOperating`；
   - 开业、停业、延长营业与营业时段编辑均走业务方法；停业期间员工保留、工资照发、租金照收，亏损由经营人承担；打烊后的接客与内部工单按 §6.10 处理。
5. **退出**
   - V1 租金直接足额划转并允许源经营账户为负，不产生欠租、坏账或自动收铺；退出只走主动退租或产权人按缓冲期收回；
   - 缓冲期内继续营业 / 交租，到期只终止租约与该店相关雇佣，雇员按离职规则结清工资；
   - 退租不拆除建筑、不收回家具、不回滚装修，也不重新分配资产；租户资产的协商收购按盘下条款处理。

### 6.15 资金与经营业务账

- **个人钱包与唯一经营账户**：每个实际 / 抽象人物在建立身份时即有一个个人钱包和一个跨生意唯一经营账户，没有经营资产的人也有经营账户。经营实体的现金、债务按资金责任人归集到该人物唯一经营账户，经营实体 / 区域 / 子功能区均不另建钱包或保存余额。玩家资产视图从经营资产的权属 / 经营关系查询，不在账户上重复保存资产清单。
- **初始资金与图外工作**：顾客初始个人钱包按生成配置赋值，多数 NPC 的工资收入来自图外经营实体的真实雇佣合同；工资从雇主资金责任人经营账户进入员工个人钱包，图外工作不生成实际区域、Actor、工单或寻路。V1 图外雇主为抽象账户（`bAbstract=true`，不计余额），支出直接发生、不补资（03A §5.9），不因余额触发破产；不用职业定期发钱或系统虚假工资替代合同。失业且无其他收入者真实收入为零，资金耗尽就买不起。
- **建铺与启动资金**：产权方建设由产权人经营账户承担；V1 玩家承租店建造 / 装修免费，经营贷款进入玩家唯一经营账户，经营支出直接使用该账户。本人可在个人钱包与经营账户之间双向注资 / 提取，普通转出须源账户足额；承租 NPC 自带（抽象）与薪酬 / 自营 NPC 店铺均为后续规则，V1 不生成这些店铺。
- **资金责任人**：自营 / 承租 Shop 使用经营人的经营账户；薪酬制 Shop / 商圈使用产权人的经营账户。受薪经营人只能发起授权业务，由业务方法扣产权人经营账户，不能划转产权人的个人钱包或经营账户，也不能查看其个人流水。
- **唯一流水**：消费从消费者个人钱包进入店铺经营账户，工资从雇主经营账户进入员工个人钱包，租金在双方经营账户之间划转；贷款与即时采购等抽象对手方使用系统单边入账 / 扣款。设施维护走员工维修工单，不产生公共维护流水。一笔结算只存一条流水。详细规则见 [经营操作 §3.7](/VoxelDesign/02-系统设计/AI决策系统-经营操作-系统设计.md)。
- **独立业务账**：V1 商圈、店铺分别按经营实体查询唯一流水；子功能区不另建账套。交易一次记录 `SourceBusinessEntityId / TargetBusinessEntityId / OccurredAreaRef`，业务对手不是经营实体时对应业务归属可空。租金源业务归承租店，目标业务归商圈，双方查询同一交易，不能为两侧统计复制流水，也不能仅按人物账户推断店铺归属。
- **发生区域与业务归属分离**：发生位置记录为带场景的空间引用，图外业务可空；付款位置和客房服务位置分别表达。历史流水保留当时两侧业务归属与账户，新流水按当前有效关系写入，区域改挂 / 商圈易主不追改历史。同一人物账户服务多个生意不代表业务统计合并。
- 商圈收租计划配置 `RentCollectionDayOfMonth`，每月固定收租日 00:00 触发；首期在签约时按当月剩余日历天数比例立即收取，后续各租约按自己的 `NextRentGameTimeSec` 逐条整月结算。源经营账户允许为负，不产生欠租或商圈坏账。

### 6.16 经营关系与任免（V1）

- 经营实体关系包含 `Mode`（产权人自营 / 承租 / 薪酬制）；店铺产权人在创建/易主时写入实体，承租不变更该产权。**产权人与经营人只存在经营实体上**，区域不存一份 Owner / Manager 真值；区域只保留准入规则。经营权限不因空间层级自动授予，不在区域迁移时回填产权字段。
- 承租：租户是经营人；产权人可提前收回（提前一个缓冲期通知，下一期结束走）；租金直接足额划转并允许源经营账户为负，不因欠租、负余额或资金耗尽自动收铺。
- 薪酬制：完整版本先按商圈员工招聘（统一雇佣记录的 `EmployerBusinessEntityId` 指向商圈），同时创建雇佣记录与劳动安排，再任命为店铺经营人；经营关系只引用 `EmploymentId`。薪酬制店主 NPC 与其他实际劳动者一样有工作区、排班和工作优先级并下场执行工作，工资只按雇佣记录从产权人经营账户出，利润归产权方；定价、进货、招聘、排班、开业等经营决策是不占排班的抽象业务方法。解雇 / 离任按离职规则结清工资，店铺停业等新经营人或改变经营方式。V1 只保留玩家作为商圈受薪经营人的标准记录，不任命 NPC 店铺经营人。
- V1 员工与薪酬制店主离职均按当月在职时长结清工资后终止雇佣，不做辞职梯度 / 谈判 / 预告期。
- **招商 / 招募界面（后续版本）**：完整版本候选卡标注意图（承租开店 / 应聘经理）；承租走租约，经理走商圈员工招聘 + 任命。V1 不开放该招商入口，只创建玩家标准承租店并招聘普通员工。
- 后续版本的产权人 / 商圈经营人不能手动改承租 NPC 的业态；承租 NPC 签约后不能改，只能退租；V1 无承租 NPC。

## 7. 权限

### 7.1 权限矩阵

| 操作 | 商圈产权人 | 商圈经营人 | 店铺经营人 | 雇员 |
|---|---|---|---|---|
| 转让商圈产权 | ✅ 仅此一人 | ❌ | ❌ | ❌ |
| 任免商圈经营人 / 改商圈经营关系 | ✅ | ❌（自己的合同不能自己改） | ❌ | ❌ |
| 商圈租务 / 招商 / 活动 / 业务支出权限 | ✅ | ✅ | ❌ | ❌ |
| 店铺租约（签约 / 租金 / 押金 / 租期 / 续租 / 退租 / 盘下） | ✅ | ✅（自己作为乙方的合同除外） | ❌ | ❌ |
| 店铺经营（人员 / 货 / 活动 / 统计） | ❌（仅公开信息；受权后可参与，见 §6.11） | ❌（仅公开信息；受权后可参与） | ✅ | ❌ |
| 产权方结构 / 店铺布局 | ✅（空置；在租需租户同意） | ✅（空置；在租需租户同意） | ❌ | ❌ |
| 租户自建资产 / 软装 | ❌（需租户同意） | ❌（需租户同意） | ✅ | ❌ |
| 空置铺位编辑 / 删除 | ✅ | ✅ | ❌ | ❌ |
| 自己的劳动安排 / 工单 | ✅（实际劳动时） | ✅ | ✅ | ✅ |

- 商圈经营人处理下属合同前，后端必须检查合同乙方是否就是自己；若是，只能转由产权人办理。兼具产权人身份时按产权人权限执行，不能仅靠 UI 隐藏绕过。

### 7.2 在租保护与关系解锁

- 在租店铺默认不能编辑 / 删除；
- 与租户关系足够好、租户允许时，商圈经营人 / 产权人可按**店铺控制授权**（§6.11）获得参与店铺管理的许可；授权不改变所有权，不能借此删除铺位；
- 该机制 V1 不实现，只在基础设计中保留；对应玩法设定的「帮朋友规划店铺」与布局修改权限跟关系度挂钩。

### 7.3 权限判定原则

- 前端只做显隐，后端业务方法必须再判一次；
- 权限判定统一入口：产权人 / 经营人 / 雇佣关系 / 关系许可；
- 产权人转让、商圈经营关系变更等产权级动作只能产权人执行。

## 8. 体素编辑权限

### 8.1 体素归属来源

| 体素类型 | 归属 | 判定来源 |
|---|---|---|
| 世界生成 / 产权方建造的结构 | 关联经营资产的产权人（空间定位 → 经营资产关系 → 公共兜底） | 经营资产权属关系 + 无租约标记 |
| 租户自建 / 改造的结构 | 租户 | 硬装改动日志 `{格坐标, 原方块, 新方块, 租约ID}`（装修卷 §4.2） |
| 产权方提供的家具 / 门窗 | 产权方 | 实例无 `PlacedByLeaseId` |
| 租户放置的家具 / 门窗 | 租户 | 实例上的 `PlacedByLeaseId` |
| 不在任何区域内的公共体素 | 场景 / 公共产权 | 无包含区域 |

- 租户建造、改造或放置家具时，生效租约必须已经存在；编辑落点与归属日志 / `PlacedByLeaseId` 写入是同一业务提交，不能先落点再补租约引用。
- 签约前已有结构维持原归属；历史日志始终引用当时的 `LeaseId`，新租约不接管旧租约资产。

### 8.2 编辑判定流程

1. **定位**：体素中心点 → 最近包含区域（子区域优先）；边界 / 无区域时向上归父级商圈或公共域；
2. **判归属**：查硬装改动日志（租约 ID）→ 租户；否则产权方；再否则公共；
3. **判权限**：产权方结构 = 产权人 / 授权经营人；租户结构 = 租户本人或租户授权的编辑者；公共 = 场景 / 城市权限；
4. **在租保护**：体素位于在租店铺范围内且改动影响围护 / 入口时，即使操作者是产权方，也需要租户同意（关系 / 协商）；
5. **多点操作**：提交前对整个体素集合预检，任一区块无权限则整体拒绝并高亮无权限方块，不做静默的部分执行。

### 8.3 与其他系统的交界

- 体素编辑工具、模板生成、区域创建 / 删除归建造域；本文只定义**谁有权编辑哪些体素**，不定义建造工具实现；
- 现状：体素编辑链路当前没有区域 / 归属权限校验，`IsAreaEditable` 只用于区域编辑与 UI；实现时需在编辑确认路径接入统一预检；
- 硬装改动日志是体素归属的基础数据，需在编辑落点时同时写入。

## 9. 数据归属（概念级）

**经营实体拥有经营业务，区域只拥有空间数据**。Global `BusinessEntities` 注册经营实体及其唯一业务模型，按类型组合营业、销售、声誉客流、商圈租务、后续住宿等模块。区域组件只关联空间登记中的实际范围；区域系统负责几何、层级、定位与空间校验，不保存经营关系或营业 / 销售 / 统计镜像。家具的真实库存、设施状态、工作点队列仍由物品 / 现场实例管理。

**实例存续与空间加载分离**。抽象经营实体本来没有区域；实体店暂未加载仍有区域关联，二者不是同一种生意。场景卸载不销毁经营实体或终止合同，图外只运行已约定的工资等结算，不启用图外生活、消费、设施模拟。

| 数据 | 唯一归属 | 存取与引用 |
|---|---|---|
| 经营身份、经营隶属、产权 / 经营关系 | Global 经营实体模型 | 保存 `BusinessEntityId`、类型与关系；Shop 的产权由明确经营资产关系解析 |
| 商圈收租配置、营业意图 / 日程、商品目录、销售预留 / 订单、声誉 / 客流 | Global 对应经营实体的业务模块 | 保存业务事实，订单引用现场设施但不在 Scene 再存副本 |
| `bOperating` | 营业模块派生值 | 由 `bOpen && 生效时段` 重建，不入档 |
| 真实区域范围、空间父子关系、用途 | Scene 区域登记 | 以 `AreaRef{SceneId, AreaId}` 定位，不含资产身份或经营状态 |
| 租约与收租到期计划 | Global `LeaseRegistry` | 两侧经营实体、签约人物与租用空间分开记录，经营实体只存合同引用 |
| 雇佣与工资到期计划 | Global 统一雇佣登记 | `EmployerBusinessEntityId`；按当前经营关系解析付款账户 |
| 劳动安排 | Creature | 工作位置与排班 / 优先级；图外工作无实际区域仍有合同 |
| 实际物品库存、设施状态、工作点 FIFO | 物品 / 工作点唯一实例 | Scene 保存实际对象与其引用，不在经营实体或区域复制库存 / 队列 |
| 在途体验、预留与收银业务事实 | 经营实体 / 执行流程各自唯一模型 | 保留稳定交叉引用，业务原子段内部无存档点 |
| 看板、认领、可达性与索引 | 派生运行时 | 不入档，先恢复引用再重建 |
| 每人个人钱包与唯一经营账户、唯一流水 | Global 经济模型 | 两账户引用在人物；流水含两侧业务归属及可空发生区域 |
| 体素归属日志与家具租约标记 | 建造 / 物品模型 | 保存实际产权依据，不由空间包含改变产权 |
| NPC 店铺认知、住所和工作位置 | NPC / Creature | 认知指经营实体，住所 / 工作指空间；不复制经营模块 |
| 玩家资产视图 | 查询结果 | 从经营资产权属与经营关系聚合，不另建持久名单 |

**后续住宿边界**：旅店住宿模块用入住记录关联经营实体、客房 `RoomAreaRef`、住客、有效时段、费用和使用授权；房间预订 / 占用归业务记录，房间范围归子区域。住客不是客房产权人或经营人。收费从顾客个人钱包到旅店资金责任人经营账户；入住授权控制指定空间与设施使用，清洁工通过工作授权进入，具体隐私策略另定。`HomeAreaRef` 指房间空间，退房结束授权、更新住所、释放占用并派生清洁需求。V1 不创建这些业务。

**入档原则**：时间、经济、经营实体、雇佣、租约仅入 Global，不在场景存档双写；空间、实际设施和现场状态入 Scene。读档先恢复事实和稳定引用，再重建 `bOperating` / 工单索引等派生，最后启用时间与 AI，不重放成交、发薪或体验事件。

**不建**：区域独立账户、区域经营镜像、合同 Actor、独立房间经营资产、玩家资产镜像名单、自动修档 / 重试 / 补偿层。

## 10. 待定问题

- **租务后续扩展**：V1 已确定固定收租日、签约即收首期、逐租约结算与调租下期生效；后续版本的租期、续租、提前退租赔付、押金、违约收铺、坏账与催收需另行决策。
- **商圈管理后续内容**：公共设施及其维护责任、公共员工编制、广告 / 促销与活动投放、集市 / 节庆 / 摊位等均留后续版本；V1 不做公共设施或公共维护费，设施维护只走员工维修工单。
- **统计与许可细节**：客流统计的时段粒度与去重口径、流水分类口径、许可配置表结构（科技树前置 / 关系门槛 / 费用 / 年检 / 有效期 / 到期重审 / 持续义务）与后续接入仍待细化；V1 最小版本不实现许可。
- **营业状态与时段**：固定逻辑 tick、倍速、暂停和时间边界事件的基础规则已确定，见 [时间系统-系统设计](/VoxelDesign/02-系统设计/时间系统-系统设计.md)；V1 不做加班，延长营业不改变员工原排班。特殊日期 / 季节营业及后续员工加班规则另定。
- **店铺控制授权**：信任度 + 角色个性的判定细节、NPC 主动提出 / 角色主动申请的双向流程（V1 不实现，基础设计见 §6.11）。
- **店铺统计**：5 组统计项的字段与口径细化（服务 5 项 / 种族·职业·阵营·街区客群构成）；后续升级 6×5 矩阵。
- **游商年度回归**：回归时的产权动作流程、远程协商的消息/关系门槛、主线与自由模式的差异。
- **商圈易主承接**：仅依赖产权人的后续收租 / 自营 / 薪酬结算切换资金责任人，承租店收支仍归承租经营人；完整产权交易和活动合同承接细节后续确定，V1 不做并购。
- **NPC 商圈经营人的决策循环**：与[店主与商圈管理](/VoxelDesign/02-系统设计/AI决策系统-店主与商圈管理-系统设计.md)的店主决策的差异与复用。
- **模板生成与建造域接口**：模板资产格式、落位校验、体素归属写入、区域实例创建/删除的调用链。
- **区域同边/中心点判定的实现**：重叠检测的容差与半开区间规则、渲染按面归属的退化方案。
- **玩家酒店 / 沙盒标准合同**：主线玩家受薪、经营工资初始为 0；标准月租由开局 / 剧情配置提供，主线与沙盒可自定义，默认均为 0。零金额不产生租金或工资流水，也不要求为验收改成非零。玩家不能修改自己作为乙方的条款；后续非零薪酬由雇主决定，非零租金场景通过开局 / 剧情配置构造。
- **身份与迁移实施边界**：经营实体 ID 的具体引擎类型、旧存档迁移、换租户是否续用经营实体 / 口碑、删除空置空间后经营实体的注销方式尚未确认。正文只确定两种身份分离及唯一事实归属，不将区域删除等同生意删除、不自行重置声誉或批量换雇佣人。
- **招聘与初始配置**：图外工作合同计入有效雇佣；招聘仍从无有效合同的名册候选选取，不足如实显示。具体初始就业 / 钱包分布以及后续换工政策需配置或另行确认，不吞掉图外合同、不补造人口。
- **存档与迁移**：经营实体、租约、人物双账户、唯一流水与场景空间的持久化结构见03；时间、经济、雇佣不放Scene，V1无坏账字段。
- **与消费 / 雇佣链路的接口**：区域营业状态、租约、资金责任人的经营账户、模板铺位如何被消费 / 雇佣系统读取。
