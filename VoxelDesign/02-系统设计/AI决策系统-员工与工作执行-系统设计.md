## 2. 员工全周期

```
失业池（V1 = 固定名册中当前无雇佣记录的 NPC）
  → 招聘板定期刷新 / 玩家免费手动刷新，最多展示 5 名候选，不足按实际人数
  → 谈薪即签（玩家在招聘板操作；NPC 店主委托招聘）
  → 入职：统一登记新建唯一有效雇佣记录，同时在 Creature 上建立劳动安排
  → 在岗（劳动安排 / 工单 / 状态 / 交接）
  → 离岗：解雇即走；辞职梯度留后续版本
  → 旧雇佣记录移出有效登记并停用对应劳动安排，NPC 回失业池
```

**统一登记与唯一关系**：V1 全部有效雇佣记录（含图外合同）由 Global 统一雇佣登记管理，同一 `CreatureID` 同一时间最多一条有效工资合同记录；经营实体与 NPC 只引用记录，不保存合同副本。`EmployerBusinessEntityId` 指向 Shop、District 或图外雇主经营实体，不能用区域引用或个人代替，不直接人员雇佣人员。招聘板仅查询无有效合同的名册NPC；图外合同也有效，不开放在职挖角、自动换工或吞并旧合同。候选不足如实显示，不因此补充人口。

**雇佣记录与劳动安排分离**：`FEmploymentRecord` 只保存合同与工资关系；`FWorkAssignment` 挂在 Creature 上，唯一保存 `WorkAreaRef / ShiftTemplate / WorkPriorities / bEnabled` 等实际劳动数据。员工、承租经营人（玩家）、自营产权人与薪酬制店主 NPC 都有劳动安排；经营关系的薪酬条款只引用 `EmploymentId`，不复制 `WageConfig`。工资只走雇佣记录，经营人下场劳动不另产工资：承租经营人取得利润，薪酬制店主按雇员月薪结算。字段见本文 §2。

`AvailabilityTemplate` 只约束 `RoleTag=Staff` 雇员合同中的可工作时段；经营人（Shopkeeper / 自营产权人）不受该雇员合同字段约束。NPC 个人日程的工作部分引用自己的劳动安排，生活日程仍归 NPC，不复制班次或工作优先级。

**当前记录与履历扩展口**：V1 只保存有效雇佣，离职即移出有效登记，不保留历史列表；历史工资仍查唯一流水。后续履历系统可接收被终止记录及离职时间、原因，不改变当前招聘与在职查询。

V1 失业只表示名册 NPC 当前没有雇佣记录，不是另一类人。招聘板候选最多 5 人，不足时显示实际人数；定期与手动刷新都只重选展示候选，手动刷新免费，不生成、删除或迁移人口。后续手动刷新可收费，定期刷新保留为免费等待路径；具体定期周期间隔另行配置。

**主地图 / 图外抽象工作口径**：工资由真实雇佣合同与薪酬条款决定，不要求对应图内劳动演出。大多数NPC有图外真实工资合同，抽象工作保留NPC、`EmployerBusinessEntityId`、薪酬与结算结果，实际 `WorkAreaRef` 允许不存在；不生成Actor、工单、寻路或设施操作。场景未加载与抽象工作不同：实际工作即便场景未加载，也保留原 `WorkAreaRef={SceneId,AreaId}` 和合同，不改成抽象工作、不造假区域；V1 不新增未加载场景的劳动执行方案。

每个实际 / 抽象人物创建时都有个人钱包与唯一经营账户，非经营者也有；初始顾客钱包用配置不给数值。工资从雇主经营账户进入个人钱包，图外雇主为抽象账户（`bAbstract=true`，不计余额），支出直接发生、不补资（03A §5.9）。失业且无其他实际收入时没钱，不兜底补钱，也不开启图外生活模拟。

商圈 / 店铺 / 图外雇主共享经营实体基础模型，唯一注册 Global `BusinessEntities`，持经营资产及产权 / 经营关系、`bOpen` / 日程、目录 / 定价 / 订单 / 预留和声誉 / 客流。区域只空间与校验，不持业务镜像；实体区域组件可关联 `AreaRef={SceneId,AreaId}`，子客房 / 仓库非经营实体。身份类型与分工见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)与[区域店铺与商圈管理 §2 / §9](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。Home / Work 仍空间，真实库存、工作点 FIFO 和门锁归对应实例。

明确不做：试用期、入职培训、升职体系、离职通知期、工伤/请假系统、班次外召回与加班结算。

- **缺勤**由 NPC 自身状态自然涌现（Critical 需求/事务冲突导致无法到岗），不建考勤系统；固定月薪不按缺勤班次或工时扣减，损失的是实际工作产出；
- **解雇**：即走，无遣散费；当月工资按实际在职时长折算，从雇主经营账户足额转入员工个人钱包并允许源账户扣负，结清后再移出有效登记；剩余员工按性格小幅情绪/忠诚下降；
- **工资结算**：固定月薪按统一月末规则足额支付，允许雇主经营账户为负；不设置 `bWageUnpaid`、欠薪金额或补发状态，不因工资不足持续降低 Loyalty 或自动解除雇佣，也不需要决定员工之间的抢薪顺序；
- **结束经营 / 退租清退到期**：仅终止该店相关雇佣，工资按当月实际在职时长立即足额结清并允许雇主经营账户扣负，再移出有效登记、停用对应劳动安排；普通打烊或手动停业不解雇、不强退员工；
- **店长**：经营实体有效经营关系中的Manager，不是空间权属字段；薪酬制任命另引用有效 `EmploymentId`，V1不开放NPC店长；
- **候选合同约束**：招聘与店主邀请只取无有效合同者，图外合同也有效；不在本版擅加在职挖角、换工或旧合同吞并。

## 3. 排班（RimWorld 式权重时间块）

### 3.1 结构

- 粒度：**1 小时 1 格**，存于劳动者本人的 `FWorkAssignment.ShiftTemplate`；
- 排班是行为权重，不是工作门禁：任何时段都不凭时间块禁止工作，员工合同的 `AvailabilityTemplate` 只约束 Staff 的排班配置；
- 块类型：

| 块 | 行为权重 |
|----|----------|
| Work | 工作子树权重最高 |
| Rest | 提高离店休息 / 回抽象住所的权重，V1 不使用员工休息区或店内客座 |
| Sleep | 提高回抽象住所睡眠的权重，V1 不使用员工区床铺 |
| Dine | 只提高吃饭 / 使用行为的权重，不是唯一允许吃饭的时段 |
| Anything | 工作子树权重较低，但仍允许工作；其他行为按需求与决策正常竞争 |

- 吃饭与使用由需求驱动的 `UseItem` Flow 执行，优先级高于工作；Dine 只调权重，吃饭不占独立排班类型。硬生理极限仍强制中断，不可压制；
- **V1 工作区需求规则**：实际劳动者位于其劳动安排对应的 Shop 区域内时，六条需求不因自然时间或工作动作下降；离开该工作区域恢复。已有需求值与 Critical 状态不清空，正向回填仍按统一入口执行，不新增冻结状态或存档字段；
- 可压制 Critical 需求优先于工作，通常先完成当前原子段再处理；Urgent 不频繁打断工作。

工作优先级与排班时间块正交，均只存于劳动安排。简易模式只勾选工种，启用项视为同优先级并按工种表的 `naturalPriority` 固有顺序执行；高级模式逐工种设置 0–4，**4 最高、0 禁止**。详见[店铺经营](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md) §11.3。

**可工作时间是排班的上界**：雇员的 `AvailabilityTemplate`（`FWeeklyHourMask`，仅 `RoleTag=Staff`）存在雇佣记录里，是合同约定的可上班时段；实际排班只能落在它覆盖的小时格内——合同写 8–10 点，就只能排 8–10 点。排班 UI 必须把可工作时段之外的小时格置为不可选，业务方法对越界排班直接拒绝。改可工作时间属于变更合同条款，不是改排班。经营人（Shopkeeper / 自营产权人）不受该字段约束。

### 3.2 覆盖规则

店主按“营业时段 × 关键工作类型 × 劳动者技能”调整劳动安排；只在覆盖缺口、人员变动或营业时段变更时调整，不每次重排。经营决策只是修改劳动安排的抽象业务方法，不在店主的个人排班中占时间块，也不生成经营决策工单。

### 3.3 V1 休息、用餐与睡眠

```
Rest → 离店休息 / 回抽象住所
Dine → 提高吃饭 / UseItem 权重；实际时机由需求决定
Sleep → 回抽象住所
```

- V1 不创建员工休息区、员工餐台、员工床铺或员工实体居住区，不按成本价消耗店内员工餐，也不占用店内客座。
- 吃饭 / 使用统一走需求驱动的 `UseItem`：选物品（背包优先）→ 就位 → 等待使用时长 → 应用物品配置声明的需求回填、状态效果与消耗。V1 员工不使用员工餐台、不占店内客座；离开店铺后的需求解决沿用普通 NPC 的回家／离场规则，不生成跨店排队、付款、座位或销售流水。后续多店版本再评估跨店消费。
- 后续版本再接员工专用设施、店内休息座与员工餐成本价流程，不在 V1 生成这些区域、家具能力或账目。

### 3.4 到岗

不做打卡：劳动者按自己的劳动安排形成到岗与工作倾向，从所在地通勤，到店后按当前权重参与决策；迟到由通勤距离与性格自然决定。固定月薪不按迟到时长扣减，损失的是实际工作产出。

## 4. 工单：状态派生 → 认领 → 执行 → 更新

### 4.1 看板与产生

看板是给 AI 的需求发现机制，即**经营实体的物化视图（派生索引）**，不是业务事实。**每个经营实体一块看板**（Shop 一块、商圈 District 一块），**挂在经营实体上，不挂在区域上**。区域只通过自身的 `EntityId` 指向所属实体——子功能区挂店铺实体、商圈范围挂商圈实体——所以仓库、子区域里的设施读 `Area.EntityId` 就直接落到本店看板，**不需要祖先区域解析**。V1 不做公共设施专属系统与公共维护费，但商圈内放置的家具仍正常注册并产生工单。劳动者只读自己所属经营实体的看板，V1 不做跨店支援。

**唯一写入口是工单索引器**。索引器订阅设施、库存、队列、建造以及经营操作造成的业务状态变更，按设施的 `Area.EntityId` 增量维护对应**经营实体**的看板；各业务域不直写看板。看板主要回答“本店哪里有什么需求需要处理”，玩家只能查看需求列表，不能在看板上创建、编辑或指派工单。

| 业务事实来源 | 状态变化 | 派生工单 |
|------|------|------|
| 设施状态跨阈值 | 清洁度低 / 完善度低 / 库存低 | Clean / Repair / Restock |
| 顾客流程节点 | 点餐 / 定制 / 退房 / 现货拿空 | Serve / Craft / Clean / Restock |
| 收银队列 | 首位顾客进入收银队列 | Cashier |
| 队列状态 | 队长超引导阈值 | Guide |
| 事件结果 | 打翻 / 故障 / 打斗损坏 | 对应处置 |
| 玩家经营操作 | 改变世界状态或形成业务目标 | 由新状态派生对应工单 |

不做主动环境巡检：劳动者只查所属经营实体的看板。无活时进入待机，不由 NPC 定时扫描环境；看板出现新工单或更高优先级工单时，索引器直接叫醒本实体“在岗且空闲”的劳动者并重置找活冷却，执行中的劳动者不因普通索引变化打断。该叫醒是索引器到决策组件的内部调用，不进入业务事件目录。找活冷却、退避、分帧预算与前 K 个候选的可达性检查属于执行调参，不改变看板的数据归属。

工单字段：`WorkOrderId`、`TaskTypeTag`、来源对象、目标设施/区域、基础 Priority（程度分带）、预估工期与所需材料。索引器按“来源对象 + 类型”去重，只留最高优先级条目；Cashier 的来源对象固定为收银台实例，因此同一收银台同时只保留一张收银工单。

### 4.2 执行

```
劳动安排 bEnabled → 当前时间块调整工作子树权重（Work 最高；Anything 较低但可工作）
→ 只读本人 WorkAreaRef 对应看板
→ 过滤：工作优先级为 0 的工种、技能/权限不满足
→ 排序：简易模式按启用工种的 naturalPriority；高级模式按 4→1，再按工单 Priority 分带
→ 认领：写 FWorkClaim{WorkOrderId, CreatureID, StartGameSec}，标记 Claimed
→ 按工单类型的 Work Flow 执行（FlowType = Work.Serve / Work.Cashier / Work.Clean / Work.Restock…）：
     Goto(设施槽位) → Acquire(取货/占位) → Advance(动作进度) → Settle(产出/结算) → Release
→ 原子段不可打断；节点边界按需求、下班、玩家指令与安全事件规则处理让出
```

**携带**：上限 = 个体数值（力量等）+ 搬运工具加成（托盘/推车/背包）；超出分多趟；V1 只做搬运工具，清洁/烹饪工具抽象不建模。

**工具**：装备类物品，提供携带上限加成，不做耐久/品质链。

### 4.3 更新与认领释放

```
Pending（候选）→ Claimed（已认领）→ InProgress（执行）→ Completed / Failed / Cancelled（完成 / 失败 / 失效）
```

- 完成、失败或失效时先更新对应业务状态，再由索引器根据新状态移除或变更看板条目，并释放认领；
- 执行者在节点边界下班、被允许的中断打断、死亡或消失时释放认领，未完成工单回到候选；原子段内不换人；
- 玩家接管已有工单时，在当前原子段完成或工作位释放后建立 / 接管认领，防止 NPC 重复执行；
- 工单认领只用于去重与防抢单，不涉及钱、不是合同，不自动续约，也不入档；认领人消失必须显式释放，不能靠租约过期回收。

### 4.4 V1 收银工单与单职责待机

- 首位顾客完成选品并进入收银队列时，队列状态变化由工单索引器派生 `AI.Work.Cashier`，来源对象取收银台实例；同一收银台按“来源对象 + 类型”去重，队列未空时不按后续顾客重复生成。
- 劳动者认领 `Work.Cashier`，占用该收银台的 `slot_staff_cashier`，到岗后按 FIFO 连续服务。队列清空才完成工单并释放认领；没有顾客时不存在常驻 Cashier 工单。
- 劳动者中断时按原子段规则处理当前服务，释放认领并将未完工单回池；顾客仍留在队列等待或按忍耐规则离开，不把工单绑定给单个顾客。
- **单职责岗位待机**：只有劳动者除 Cashier 外其他工种均停用时，队列清空后才留在原收银工位待机；待机不是常驻工单，不保持 InProgress，也不产生额外薪资。只要启用了其他工种，完工后就释放工位并重新找活，即使当前没有其他工单也不绑定收银台。
- 新队列到来时由索引器派生 Cashier 工单并叫醒本区域空闲劳动者；单职责劳动者因已在工位可直接认领执行。需求、下班、玩家指令和安全事件仍按统一规则处理待机。

---

## 5. 管理动作与玩家劳动

- **NPC 店主 / 商圈管理人**：定价、进货、招聘、排班、开业等经营决策全部通过抽象业务方法后台执行，不建模物理动作，不占个人排班，也不生成或认领经营决策工单；
- **玩家经营操作**：在招聘板与经营操作页调用同一批业务方法改变世界状态（操作清单见[经营操作](/VoxelDesign/02-系统设计/AI决策系统-经营操作-系统设计.md)），由状态变化派生工单；看板只提供需求列表，不是操作前提；
- **玩家自主劳动**：自主开启且未被直接操控时，与所有实际劳动者一样读取自己的劳动安排，只扫描本人 `WorkAreaRef` 看板并按工作优先级认领、执行。非受薪自主劳动不另领工资；玩家作为商圈受薪经营人时按统一雇佣记录领薪，与工单完成和自主开关无关；
- **玩家手动劳动**：直接对目标发起与 NPC 自主劳动共用的业务动作，先校验目标状态与工作位占用。目标有对应工单则建立 / 接管认领；没有工单时不创建工单，直接执行合法的状态修改。动作结束或中断后更新业务事实，由索引器刷新看板并释放认领；
- **打断与反馈**：原子段不可打断，玩家自己的原子段也一样。新指令需等待当前原子段完成或目标工作位释放，并明确反馈“等待当前操作完成”或“工作位被占用”；节点边界可让出与随时可停由动作自身声明。直接操控结束后，自主劳动者从当前位置重新找活，不强制续占旧工单；
- **不做**：面试、巡店、巡检的物理执行；后续看性能再考虑物理化。

店主在店内的实体价值来自自己的劳动安排与在场监督光环；薪酬制店主 NPC 同样具有劳动安排，其 Work 块与光环条件读取 `FWorkAssignment`，不读雇佣记录中的排班。

## 6. V1 范围

**存读档**：保存 `Employment.ActiveRecords` 的有效雇佣记录、Creature 上的劳动安排及不可重建的业务事实；排班与工作优先级只在劳动安排保存一份。看板、工单认领、索引器内部状态与派生索引不入档，读档后由业务状态重建看板，劳动者重新找活；`ActiveByCreatureId`、WorkingNPCs 和执行对象引用由稳定 CreatureID / ExecutionId 重建。完整顺序见 [AI 决策系统架构 §7 存档](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md)。

**做**：只无有效合同的招聘池（图外合同也有效）、谈薪即签并建立雇佣记录与实际劳动安排、图外真实工资合同抽象结算、1h权重排班块、简易 / 高级工作优先级、需求驱动UseItem、区域派生工单索引与叫醒、步骤模板执行、携带上限与搬运工具、工单认领、解雇及结束经营 / 退租到期解雇、工资足额结算并允许经营账户扣负、玩家自主与手动劳动统一入口。普通停业 / 打烊不解雇、不强退员工。

**不做**：培训/试用/升职、考勤与迟到惩罚、主动环境巡检、跨店支援、玩家直写看板、清洁/烹饪工具、物理化巡店/面试。
