**日期**: 2026-01-26

## 1. 系统上下文

### 1.1 系统边界

**负责内容**：
- 工具详情页的模块化展示和管理
- 根据当前工具类型动态显示对应的参数控制模块
- 草稿预览流：UI → Controller 草稿业务 → StateComponent → 广播 → VisualComponent/PreviewActor；正式确认流：Controller → 业务门面 → 实体/区域存储 → 事件 → UI
- 模块的可复用性和组合性

**不负责内容**：
- 工具切换逻辑（由 `Tool.Tag` 系统管理）
- 工具栏按钮显示（由 `BuildPanelWidget` 的主/子工具列管理）
- 预览逻辑（由 `VisualComponent` 管理）
- 数据持久化（由各子系统管理）

### 1.2 外部依赖

**依赖系统**：
- `VoxelControllerStateComponent`：单一状态源，存储当前工具参数
- `VoxelControllerVisualComponent`：接收状态广播，更新预览
- `ConfigDataSubsystem`：提供素材库、模板库、区域类型等数据
- `VoxelAreaWorldSubsystem`：区域创建和修改
- `GameplayTagsManager`：工具标签管理

### 1.3 输入输出

**输入**：
- 用户操作：点击、拖动滑块、输入文本等
- StateComponent 广播：`OnAreaFieldChanged`、`OnAreaModificationChanged`、`OnTmpEditRequestChanged` 等
- 当前工具标签 (`CurrentToolTag`)

**输出**：
- 修改 StateComponent 的参数
- 触发 VisualComponent 更新预览
- 显示状态信息、错误提示等

## 2. 核心概念

### 2.1 基础概念

**工具标签 (Tool.Tag)**
- 使用 GameplayTag 表示工具类型和层级
- 层级结构：`Tool.Selection.Brush`、`Tool.Edit.Template` 等
- 三维架构：工具标签 + EVoxelPlacementMode + ESelectionOpMode

**模块 (Module)**
- 可复用的 UI 组件，负责特定功能的数据展示和编辑
- 每个模块继承自 `UToolDetailModuleBase`
- 实现 `ShouldShowForTool(FGameplayTag ToolTag)` 控制显示逻辑

**状态组件 (StateComponent)**
- 单一状态源，存储所有编辑参数
- 广播状态变化事件
- UI只采集意图，经 Controller草稿业务更新 StateComponent，预览订阅广播；正式确认交业务门面

### 2.2 组合概念

**工具详情页 (Tool Detail Panel)**
- 由多个模块组合而成的容器
- 根据当前工具类型动态显示/隐藏模块
- 不为每个工具创建独立的详情页类

**模块库 (Module Library)**
- 建造库模块：素材选择和手持物品管理
- 模板库模块：模板选择和素材需求显示
- 区域类型库模块：区域类型选择和分类

**编辑参数组**
- 选区参数：几何形状、包围盒、笔刷、魔棒
- 编辑参数：放置规则、选区运算、几何参数
- 区域参数：基础信息、类型、边界、权限
- 模板参数：位置、旋转

### 2.3 行为概念

**显示/隐藏行为**
- 模块根据当前工具标签决定是否显示
- 支持精确匹配和标签匹配
- 动态响应工具切换

**数据读取行为**
- 模块初始化时从 StateComponent 读取数据
- 监听 StateComponent 广播事件
- 实时更新 UI 显示

**数据写入行为**
- 用户操作经 Controller 草稿业务修改 StateComponent 参数
- StateComponent 广播草稿变化，VisualComponent 响应更新预览
- 正式确认交业务门面，不以草稿 Setter 修改经营/合同真值

### 2.4 概念关系

```
工具标签 (Tool.Tag)
    ├── 决定详情页显示哪些模块
    ├── 通过 StateComponent 传递
    └── 模块实现 ShouldShowForTool() 判断

模块 (Module)
    ├── 继承 UToolDetailModuleBase
    ├── 实现显示逻辑和数据读写
    └── 可复用于多个工具

状态组件 (StateComponent)
    ├── 单一状态源
    ├── 广播变化事件
    └── UI → Controller草稿业务 → StateComponent → 广播 → VisualComponent/UI
```

## 3. 设计原则

### 3.1 架构原则

**模块化优先**
- 使用可复用的模块组合，而非为每个工具创建独立类
- 模块职责单一，高内聚低耦合
- 支持模块的动态加载和卸载

**单一数据流**
- UI 经 Controller 更新临时草稿，不直接修改状态存储或预览
- StateComponent 是编辑草稿唯一来源，不是经营真值存储
- VisualComponent 与 UI 订阅草稿广播；正式业务确认经门面写实体/区域存储

**数据驱动**
- 使用 GameplayTag 实现工具系统的数据驱动
- 模块显示逻辑基于标签匹配
- 避免硬编码工具类型判断

### 3.2 接口设计原则

**统一抽象**
- 所有模块继承 `UToolDetailModuleBase`
- 统一的 `UpdateFromToolState()` 接口
- 统一的 `ShouldShowForTool()` 接口

**最小知识**
- 模块通过注入的 Controller/ViewModel读草稿与提交意图，不直接操作实体/区域存储
- 模块之间不直接通信，不依赖具体工具类
- 草稿在 StateComponent，正式确认统一交业务门面，不把模块扩成经营所有者

### 3.3 数据管理原则

**状态所有权**
- StateComponent 拥有所有编辑状态
- 模块不缓存状态，每次从 StateComponent 读取
- 状态变化通过广播通知

**单向数据流**
- 用户操作 → 模块 → Controller草稿业务 → StateComponent → 广播 → VisualComponent/UI；正式确认交业务门面
- 不允许反向数据流
- 避免循环依赖

### 3.4 性能原则

**按需显示**
- 只显示当前工具需要的模块
- 不使用的模块不创建或隐藏
- 避免不必要的 UI 更新

**延迟加载**
- 模块按需创建和销毁
- 大数据列表使用分页
- 图标和预览按需加载

## 4. 模块分类

### 4.1 基础模块（所有工具通用）

**M1: 建造库模块**
- 手持物品显示
- 素材库列表（体素方块、家具）
- 搜索、TAG 筛选、分页
- 素材按钮（缩略图、数量、单价）

**M1b: 模板库模块**
- 模板列表和搜索
- 素材需求显示（是否缺素材）
- 模板选择和高亮

**M2b-1: EVoxelPlacementMode 模块**
- 覆盖/填充/替换/指定替换
- 单选按钮组

**M2b-2: ESelectionOpMode 模块**
- 新选/加选/减选/交选
- 单选按钮组

### 4.2 选区工具模块

**M3: 几何形状选择模块**
- 立方体/球体/圆柱/金字塔
- 单选按钮组

**M4a: 包围盒定义模块**
- 两角点定义盒体
- 最小/最大坐标输入

**M4b: 几何参数控制模块**
- 旋转滑块（Pitch/Yaw/Roll）
- 厚度输入
- 正方体模式 CheckBox

**M5+M6: 选区信息与操作模块**
- 选区统计（体素数、尺寸、中心）
- 清空选区按钮
- 保存为模板按钮（弹出对话框）

**M7: 笔刷参数控制模块**
- 笔刷形状（圆形/方形）
- 笔刷大小滑块
- 笔刷模式（绘制/点击）

**M11: 魔棒参数控制模块**
- 选择模式（连通区域/全局相似）
- 最大体素数限制
- 最大深度限制

**M10: 采样参数控制模块**
- 采样模式（单体素/区域采样）
- 采样预览

### 4.3 区域工具模块

**M8: 区域信息显示模块**
- 区域基本信息显示
- 子区域列表

**M9: 墙壁方向编辑模块**
- 6 个方向 CheckBox（上下左右前后）
- 厚度控制
- 建造按钮

**M12a: 组合创建信息采集模块**
- 同一建造侧栏接续拉范围/摆模板预览，采集名称、经营意图及必要条款；与 M12b、M4a/M14 共同构成一次组合创建。
- 产权人/经营人只读展示业务解析结果；不能自由填人名/ID取得权利。角色候选只能用于专用租约/任命流程，须满足有效授权及条款。
- Confirm 提交概念请求 `CreateBusinessWithArea`：OperatorId、BusinessKind、Name、BusinessIntent、ParentBusinessEntityId、空间草稿等，不硬定 class；业务门面创建实体+空间+经营关系+必要 Lease/首期，有效 Lease 先于租户建筑/家具真写入。
- 子区域分支只创建空间并关联现有经营主体，不另建经营实体。

**M12b: 类型/业态库模块**
- TAB 分类（常用/全部/商业区/店铺/附属），搜索和 TAG 筛选；库内同时收录**区域类型**（按空间作用分类）与**业态**（按经营业务分类）两个独立分类维度的 Tag，具体取值由配置资产决定，不因命名含 Area 变成空间身份。
- 普通资料编辑不改变主经营类型；子功能区只选区域类型，不受业态约束。

**M13a: 区域导航模块**
- 已有范围及父子导航/只读信息，不提供 Owner/Manager/状态 Setter。
- 纯导航若作为当前代码事实保留，应标明待迁移；不是最终创建信息采集的限制。既有名称/LOGO 走普通资料业务，合同变化走专用业务。
- 不要求先创建区域再跳详情补建生意，不要求玩家手动绑定。

**M13b: 权限控制编辑模块**
- 是否公开、是否允许战斗
- 阶级/职业/种族限制编辑
- （暂缓，权限系统未定）

### 4.4 模板工具模块

**M14: 模板参数控制模块**
- 位置坐标输入（X/Y/Z）
- 旋转方向选择（东南西北上下）
- 单选按钮组

### 5.14 M12a: 组合创建信息采集模块

**布局**：与范围/模板预览同一侧栏，连续采集，不新增跳转。
```text
组合创建
 ├─ 名称输入（必填）
 ├─ 类型/业态（M12b） + 经营意图
 ├─ 当前范围（M4a）或模板预览（M1b/M14）
 ├─ 父经营实体 / 场景父空间（各自业务校验）
 ├─ 有效授权与必要 Lease/任命条款确认
 ├─ 产权人/经营人解析结果（只读，不自由输入）
 └─ 确认：CreateBusinessWithArea → 实体+空间+关系+必要 Lease/首期
```

经营实体存 `Global.BusinessEntities`，是资产/业务唯一所有者；商圈/店铺/图外生意共同基础模型按类型组合模块。`BusinessEntityId` 全局稳定（GUID，规则见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)），不使用 `ShopId` 别名，可选空间引用 `AreaRef={SceneId,AreaId}`。经营与空间注册分开，不在区域镜像权属、租约、营业/目录/订单/声誉；家具/结构产权日志独立，空间包含不转移租户资产。

## 7. 数据流设计

### 7.1 模块初始化流程

```
用户切换工具 → StateComponent.CurrentToolTag 变化
    ↓
StateComponent 广播 OnCurrentToolTagChanged
    ↓
BuildPanelWidget.HandleToolTagChanged()
    ↓
遍历所有已注册模块
    ↓
调用 Module->ShouldShowForTool(NewToolTag)
    ↓
返回 true → 显示模块并调用 UpdateFromToolState()
返回 false → 隐藏模块
```

### 7.2 模块数据读取流程

```
模块显示 → 调用 UpdateFromToolState()
    ↓
从 StateComponent 读取相关参数
    ↓
更新 UI 控件显示
    ↓
完成
```

### 7.3 草稿与正式数据写入流程

```text
用户输入 → 模块采集 → Controller草稿业务 → StateComponent
 → 草稿广播 → VisualComponent/PreviewActor 与 UI订阅

用户确认新商圈/店铺 → Controller → 业务门面 CreateBusinessWithArea
 → 实体+经营关系+必要 Lease/首期 / 空间注册（分别归属对应业务）
 → 有效 Lease 后租户建筑/家具真写入 → 数据事件 → UI

用户确认子区域 → 空间业务创建空间、关联现有主体 → 事件 → UI
```

StateComponent Setter 仅为草稿内部接口，正式经营/合同/资料写入不能沿草稿预览流绕过业务门面。

## 8. 关键技术决策

### 8.1 为什么使用模块化而非继承？

**原因**：
- 避免类爆炸：17 个模块 vs 为每个工具创建独立类
- 提高复用性：模块可组合使用
- 便于维护：修改模块影响所有使用它的工具

**权衡**：
- 需要设计良好的模块接口
- 需要管理模块的显示/隐藏逻辑

### 8.2 为什么 UI 不直接修改预览？

**原因**：
- 单一数据源：StateComponent 是唯一状态源
- 解耦：UI 和 VisualComponent 独立
- 可扩展性：未来可以有多个组件监听状态变化

**权衡**：
- 增加了一层间接性
- 需要定义明确的广播事件

### 8.3 为什么使用 GameplayTag 而非枚举？

**原因**：
- 数据驱动：可通过配置文件扩展
- 层级结构：支持父子标签关系
- 灵活匹配：支持 `MatchesTag()` 语义

**权衡**：
- 性能略低于枚举
- 需要管理标签定义
