## 2. 核心概念

### 2.1 基础概念（四层分离）

系统严格分离四个不同层次的概念，每个层次有明确的数据归属：

经营资产与业务唯一归 Global `BusinessEntities` 中的经营实体。商圈 / 店铺 / 图外生意共享基础模型、按类型组合模块，持产权 / 经营关系、`bOpen` / 日程、目录 / 定价 / 订单 / 预留与声誉 / 客流；区域只空间与校验，不存业务镜像。实体区域组件关联 `AreaRef={SceneId,AreaId}`，客房 / 仓库等子区域仅有空间 ID 并关联已有实体，抽象生意无实际区域且不造假区域。身份类型与分工见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)。Home / Work 仍空间。真实库存、工作点 FIFO 与门锁仍在对应实例，区域看板只为不入档派生索引。

**功能（Function）—— 家具/区域的静态能力配置**
- 定义：可交互对象固有的"它能做什么"
- 数据：家具行上的功能片段 `FunctionFragment`（FSeatFuncFragment 等，见[家具系统-系统设计](/VoxelDesign/02-系统设计/家具系统-系统设计.md)）
- 归属：写在物品配置行里，运行时不变
- 示例："这张床有 FSleepFuncFragment，睡眠回填精力"

**状态（State）—— 家具实例的运行时数据**
- 定义：当前这个具体实例的运行情况
- 数据：实例核心 `float HitPoints` 与功能模块 `FunctionModule`（FSlotModule / FStorageModule / FMaintainCleanModule / FPassageModule…）；静态上限为 `MaxHitPoints`，`Integrity` 只派生
- 归属：跟着实例走，与功能片段按类型配对；清洁度只在放置 OBJECT 中推进，收起为 ITEM 后保存但不持续计算
- 示例："这个座位槽被 1 人占用，清洁度 0.7"

**任务（Task）—— 区域级的工作分配**
- 定义：道具/子区域/消费流程产生的"需要在岗 NPC 来做的事"
- 数据：`FIntent`，由工单索引器归集到用工区域的派生索引
- 归属：每个用工区域一份索引，唯一写入口是工单索引器；劳动者通过工单认领（Claim）防止重复执行
- 示例："3 号桌客人点了餐，需要服务员上菜，优先级偏高"

**动机（Motivation）—— NPC 内部的决策结果**
- 定义：NPC 决策后产生的"我要做什么"
- 数据：`FIntent`
- 归属：属于 NPC 自己
- 示例："去 5 号餐厅吧台吃饭"

### 2.4 组合概念

**双源候选模型（按 RoleContext 分流）**
```
劳动候选（员工与经营人）:
  候选 = 劳动安排所指向用工区域的 FIntent（工单）
  决策 = 工作优先级 × Priority 分带两层扫描，不走评分公式
  排班只调整工作子树权重：Anything 时段也允许工作，Work 时段权重最高

消费候选（顾客）:
  候选 = 店铺/道具的 FunctionModule + 店铺商品目录
  先过硬过滤漏斗（营业状态 → 认知 → 价格期望）
  决策 = Utility 加法核评分

两源不混合评分；Critical 个人需求在任意 RoleContext 下都优先
```

**任务上报与认领机制**
```
家具实例/子区域/消费流程节点状态变化（事件驱动）
  ↓
更新自身功能模块（占用 / 维护槽 / 库存，可用性由此派生）
  ↓
工单索引器订阅状态变化，增量维护所属用工区域的工单索引（唯一写入口）
  ↓
索引去重（同 SourceObject + 同 TaskType 只保留最高优先级）
  ↓
劳动者按劳动安排与优先级扫描所属经营实体的看板
  ↓
建立工单认领（Claim），防止其他劳动者重复执行
  ↓
完成后更新业务状态 → 索引器移除或变更工单 → 释放认领

执行结束、中断或劳动者回收时释放认领；未失效的工单恢复待认领。
发起方取消（顾客离开 / 需求消失）后，对应业务状态变化由索引器移除工单。
```

**FFlowState 流程实例**
```
消费/工作流程不再写死固定阶段:
  FFlowState 按 FIntent.PlanRef（FlowTypeTag）加载 FFlowConfig
  逐节点（FPlanStep）执行: Browse / QueueAt / ClaimSeat / Order / Pay / Consume / ...
  每个节点内部 = 五原语段骨架（Goto/Acquire/Advance/Settle/Release，见 8.2）
流程实例可休眠持久化:
  中断于（节点 i, 原语段 j, 子进度 k）→ 持久化断点 → 事件唤醒后从断点恢复
  （典型：定制订单下定金后休眠，订单完成事件唤醒验货付尾款——一条代办日程）
```

**记忆与事件（完整后续版本；V1只直接上报业务事实和统计，不建个人记忆）**
```
结算时（消费流程结束（离店）/工作完成/异常）
  ↓
ReportEvent 上报事件（类型Tag + 主动者/接收者 + 值参数 + 地点）→ 写入全局事实库
  ↓
在场者建个人记忆条目 → 解读管线发放效果并快照（记忆模型 §4）
  ↓
店铺侧：消费体验在离店时一次性归因写入 FShopReputation（[店铺经营 §1.7](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）；个体侧：记忆快照供评分修饰与唤起
```
事件实例结构、感知与传播见《AI决策系统-事件系统-系统设计.md》；条目与解读见《AI决策系统-记忆模型-系统设计.md》。

## 8. 消费流程：业务模板配置化

### 8.1 流程模板

`FFlowConfig`（**按 FlowTypeTag 索引**，DataAsset；消费行为 `Consume.*` 与工作类型 `Work.*` 同表，见[意图与流程统一模型](/VoxelDesign/02-系统设计/AI决策系统-意图与流程统一模型-系统设计.md)）：`FlowNodes` 有序节点列表（节点 = 一级 PlanStep）。

`FPlanStep{StepType, TargetRef, WaitMode, bPausable, Primitives, OnFail}`：
- OnFail 策略：放弃 / 重试 / 跳节点
- 等待段参数（配在节点上，仅服务驱 Advance 生效）：衰减率 / 减缓来源（AspectTag 或设施）/ 预警边距；放弃分支由流程上下文自动推导（当前节点在 Pay 之前还是之后、PayTiming），零手配

**节点类型集**（代码各实现一次，编排靠配置）：

| 节点 | 职责 |
|------|------|
| Browse | 进店浏览商品目录 |
| QueueAt(PointTag) | 到指定工作点排队；站位方式由工作点的 `QueueMode` 决定 |
| ClaimSeat | 找座位 |
| Order | 下单（抛对应工单） |
| Pay(时机) | 支付；时机：预付 / 定金 / 尾款 / 日结 / 月结 / 离店结；杂货现货在收银台执行唯一 `CheckoutSale` 原子事务，详见 §8.6 |
| Consume | 消费回填需求（支持子进度序列：多品项逐道"等待→食用"） |
| UseItem | 需求驱动的通用物品使用：选物品 → 就位 → 等待使用时长 → 触发物品配置效果 → 扣减数量/生成剩余物，详见 §8.9 |
| AcquireResource | 拿货/取资源 |
| Release | 释放占用（座位/房间等） |

### 8.2 FFlowState = 流程实例与节点骨架

- 按当前 `FIntent.PlanRef`（FlowTypeTag）加载 `FlowConfig`，逐节点执行
- **每个节点内部是同一条五原语段流水线**：① Goto（移动到 LocationHint）→ ② Acquire（占用资源：锁座位/占队列位/预留商品）→ ③ Advance（推进节点进度，核心段）→ ④ Settle（计价/回填需求/记录体验/更新业务状态）→ ⑤ Release（释放占用）；各段可跳过，节点类型 = 骨架的不同填充组合。商品预留只锁可售数量，真实扣货、入包与所有权转移只能由对应业务事务完成；
- **Advance 只有两种驱动方式**：自驱（NPC 自己做事，进度随时间推进，速率受属性修正）/ 服务驱（等外部交付推进：服务点空位、工单履约、叫号）；**等待段只挂在服务驱期间**（§2.5，[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)）——排队与等上菜是同一个逻辑
- **多品项由 Advance 子进度序列承载**（非新节点类型）：如 Consume 的品项清单按"等菜 i（服务驱）→ 吃菜 i（自驱）"交替推进，节点完成 = 子进度全部完成
- 流程实例可休眠持久化：断点 = (节点 i, 原语段 j, 子进度 k)，事件唤醒后从断点恢复

### 8.3 典型编排

| 服务行为（典型业态） | FlowNodes 编排 |
|---------|---------------|
| 餐厅 | 门口等位 → 找桌位 → 点餐(抛 Serve 工单，N 品项一单) → 逐道等菜/吃(Consume 子进度) → 等买单 → 离店结账 |
| 杂货现货 | 进店 → Browse 浏览并形成购物篮，加入购物篮/锁价预留时通过 `CanReserveBasket`（必要时缩篮子）→ 收银台排队 → 到收银台开始服务时创建 Pending 订单，Pay 执行原子 `CheckoutSale` → 商品已入背包 → 按需 UseItem / 离店 |
| 装备现货 | (满员时门口排队) → 选品 → (橱窗并发受限才排队) → 收银台排队 → 付全款 → 拿货 |
| 装备定制 | 下定金+交材料 → 流程休眠+代办日程入 Agenda → 订单完成事件唤醒 → 验货付尾款 |
| 旅店（后续版本，V1 不开放） | 前台排队 → 按既有预订规则付尾款（walk-in结算方式待定）→ 旅店住宿模块创建StayRecord与入住占用 / 费用授权，Home空间更新为RoomAreaRef → 居住 → 退房结束授权、释放占用、更新Home空间并触发有工作授权的清洁需求；客人不是客房Manager |

注：需要排队的店门同样持有容量为 8 的工作点队列；店内满员时新顾客在门口工作点排队，队列满则先转其他可用门，无可用则离店。开业不设置"必须有可用入口"或 `HasUsableEntrance` 式硬校验，门或未封死开口均可作为通行形态。NPC 找不到路就不来消费，只向玩家提醒"有顾客想到你的店但进不去"，提醒按店铺去重并带冷却。

### 8.4 异步双机制

**店铺侧订单队列 Bill Queue（RimWorld 式）**：
`FBillOrder{商品, 材料需求, 工期, 客户ID, 已付定金, 交付期限, 优先级}` 挂店铺生产队列；店主可排序插单；员工认领生产；完成 → 可交付 → 通知客户事件。

**NPC 侧代办日程 Appointment**：
FAppointment 语义是代办日程（义务/待办，非社交约会）。到点/事件触发 → 注入候选池参与评分（非强制，可逾期未办），并携带**临期权重斜坡**——越临近截止评分加成越高，宽限期过半后足以压过普通需求（"最后一刻赶去取货"自然涌现）；超宽限期 → 违约结算：定金没收 + 差评 + 订单取消。

**玩家委托 = FAppointment 的一种来源**：玩家对 NPC 的指派/委托统一走代办日程通道——劳动者的店内工作指派走强制意图并在扫描时置顶（雇主指令强制力最高，见[员工与工作执行](/VoxelDesign/02-系统设计/AI决策系统-员工与工作执行-系统设计.md)），不写看板、不创建工单；NPC 的个人委托（办事、外派探索采集经 SpawnArea 出城，见[商圈生态](/VoxelDesign/02-系统设计/AI决策系统-商圈生态-系统设计.md)）= 注入 Appointment 按关系度评估接受。看板对玩家只读，玩家不能在看板创建或指派工单。

### 8.5 流程节点产生工单需求（与员工解耦的关键）

| 触发 | 派生工单 |
|------|---------|
| Order(点餐) | AI.Work.Serve |
| Order(定制) | AI.Work.Craft |
| 退房 | AI.Work.Clean |
| 可售货架经付款履约真实扣货后低于阈值 | AI.Work.Restock |
| 首位顾客完成选品并进入收银队列 | AI.Work.Cashier |

顾客流程不直接调用员工，也不直写看板；流程节点只更新消费状态，由工单索引器据此维护所属经营实体的派生看板。劳动者按劳动安排与工作优先级认领，两侧解耦。`Restock` 的来源是后备储物家具，目标是触发阈值的可售货架；后备储物家具可集中在仓库子功能区，也可位于营业空间，区域本身不保存库存。

`Cashier` 以收银台实例为来源对象去重，不按单个顾客生成。员工占用 `slot_staff_cashier` 后按 FIFO 连续服务，队列清空才完成；无顾客时不生成常驻工单。只有其他工种优先级全部为 0 的单职责收银员，完工后才留在原收银工位待机，其他员工照常重新扫描看板。

### 8.6 店内选品、库存预留与原子销售

**Browse 与购物篮**：

进店 Browse 读取商品目录，揭示真实价格与区域可售聚合现货（认知边界见 §5.1，[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)），再根据执行组覆盖的目的、背包已有物品、物品使用基础作用、个体购买行为预期与品类意愿形成 1～3 件待购商品。进入 Browse 不调用预留守卫，不读钱包，也不因现货或背包容量拒绝浏览；没钱同样可以逛。

**唯一预留守卫**：

加入购物篮与锁价预留统一调用 `CanReserveBasket(BusinessEntityId, CreatureID, Basket)`，不在其他节点各写一半校验。守卫仅包含以下四项：

1. 店铺营业中且货页商品可售；
2. 区域聚合现货 `ΣOnHand − ActiveReserved` 足够整单预留；
3. 买家钱包不少于整单锁价金额；
4. 固定 16 槽背包的整单可放置模拟通过。

```
Browse 形成购物篮
  → 加入购物篮 / 锁价预留时调用 CanReserveBasket
  → 任一项不通过：减少数量或放弃部分商品，按调整后的整单重新校验
  → 持续缩篮子直到整单通过；一件都买不起或放不下则放弃购物并离店
  → 通过后记录各商品当前单价为 LockedUnitPrice，整单原子预留
```

**预留与锁价语义**：

- 预留归经营实体，记录 `{ReservationId, BuyerId, BusinessEntityId, Lines[{ProductTag, Quantity, LockedUnitPrice}]}`；不同目的选中同一 `ProductTag` 时先合并为一行再计算整单 1～3 件；顾客不选择具体货架或堆叠，预留不保存 `ContainerId / StackId`；
- 区域可售量是全部可售货架真实库存的实时聚合减去本店有效预留，不包含后备储存，也不另存区域库存副本；真实库存与容量仍归家具实例；
- 预留只减少其他顾客可购买的数量，货架 `OnHand` 不变，商品仍属店铺且不进入顾客背包；建立与释放预留都不产生销售、购买效果或 Restock 真实扣货事件；
- `LockedUnitPrice` 在选品预留时取自商品目录。之后玩家调价只影响新选品，不影响已预留订单；收银总价为各行 `LockedUnitPrice × Quantity` 之和，流水保存实际成交明细；
- 排队期间保留预留与锁价。主动放弃、未付款流程中断 / 取消 / 失败、付款失败或离店时释放整单预留；之后仍需购买则按当时聚合现货和价格重新选品、重新锁价，不沿用旧价格；
- V1 不做顾客按货架 / 堆叠选货，因此不存在顾客预留的堆叠引用迁移。库存内部的实例状态与容量堆叠按库存分册运行，V1 不推进腐败。

**收银订单与原子事务**：

- 顾客到收银台开始服务时，由收银业务入口在经营实体创建 `Pending` 订单，随后转 `Completed / Failed / Cancelled`；订单持 `BusinessEntityId + ReservationId + BuyerId + 锁价明细 + AmountDue + 状态`。收银台实例只保留当前订单引用，不持订单副本；同一台仍只有一个活动订单，Cashier工单生命周期不变；
- `CheckoutSale` 是同一收银台活动订单的唯一结算入口，顾客 Pay 与员工 Cashier 不分别执行销售扣款；结账保持整单原子，全成或全败；
- 一次原子校验预留仍有效、锁价总额一致、买家钱包足额，并按当前实际可售 ITEM 堆生成 FIFO 扣货／交付计划及固定槽位背包放置计划，确认整单可放置后同时完成：按锁价全额转账 → 核销预留 → 依计划从区域实际可售货架扣货 → 保持源堆拆分／合并后的实例状态进入买家背包并转移所有权 → 写含锁定成交单价的统一账户流水；源堆计划不回写商品预留，背包规则见[库存与保质期 §2.2](/VoxelDesign/02-系统设计/AI决策系统-库存与保质期-系统设计.md)。成功后订单转为 `Completed`；
- 成交结果发布后，由买家 Flow 的购买行为方法根据其当前需求、性格、特性与本次购买上下文结算 Shopping、Mood 等购买体验；该体验不属于原子销售或商品固定配置。实际扣货输出仅供本次入包与对应货架 Restock 检查使用，不回写为顾客预留的货架 / 堆叠绑定；
- 任一校验失败则上述销售事项全部不发生，订单转为 `Failed` 并释放整单预留；主动取消则转为 `Cancelled` 并释放整单预留。不做部分付款、部分交付、赊账或自动替换商品；
- 未付款流程实际离店或退租经营终止时，残余 `Pending` 转为 `Cancelled` 并释放预留；打烊先服务完店内既有锁价 / 收银排队 / 结账再清理残余，不因bOperating变false提前取消订单。成功后不存在已付款未交货状态，后续普通离店 / 中断不自动退款；真实扣货后才检查 Restock 阈值，食物 / 饮料之后由 UseItem 实际使用才产生配置效果。

### 8.7 组团消费

几个 NPC 结伴消费（与代办日程是不同概念：代办日程是义务/待办，组团是社交结伴）。**团体是行为概念**，不是新的实体或流程类型：

```
成团（仅两个来源，不存在远程邀请——被邀者不在图则无响应通道）:
  ① 结伴出场: 同住所 + 高亲密 + 时段重叠的 NPC 概率性一起刷出，刷出即成团（§2.3，[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)）
  ② 场内面对面邀请: 某 NPC 产生消费需求 + 有社交意愿
      → 要求物理共现，从在场关系 entry 里挑关系程度高的同伴当面发起
响应: 邀请 = 一次即时数据请求，被邀者当帧评估接受/不接受（当前需求 + 时段是否
      Free + 对发起者亲密度），无等待超时概念（团可大可小，1 人也成立 = 单独消费）
选店: 发起者跑一遍正常评分选候选
      → 同伴对候选有否决权（该店对自己评分过低 → 退出团）
      → 剩下的成员同行
执行: 同店同流程；排队与占座按人头计（每个成员各占一个队列位/座位资源）
      → 消费中触发社交互动（聊天），回填 Social/Leisure 需求
共进退（按 §11.9（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）优先级序列分层）:
      成员 Urgent 及以下需求波动 → 不单独判定，等待忍耐与需求压制统一由发起人容忍度控制
      成员可压制 Critical → 不直接离队，发催促外化（"我快饿死了"），
        作为发起人容忍度判定的输入修正，仍由发起人判定
      成员硬生理极限 / 安全事件 → 无条件个体优先脱离，团体规模 -1 继续
      发起人离场（被攻击/昏厥/自己退出）→ 团解散，成员各自重新决策
分开: 退出者按自己当前状态独立重新决策

占座: 团体需要整团同桌，按人头匹配桌位容量:
      有空桌容量 ≥ 团人数 → 整团入座
      暂无合适桌（如 6 人团只有 4 人桌）→ 整团按人头进等位队列，等匹配桌位
      释放；不为团体拼桌、不拆团分散就座
```

收益：涌现"朋友聚餐"场面；社交需求有了合法满足途径；团内成员互相影响对店的记忆（口碑载体）。

### 8.8 等待社交

服务驱等待段期间，NPC 可与邻近 NPC 概率触发互动配置池（Social 需求的合法满足途径之一；等待场景天然是观察热点，外化素材密度与玩家注意力对齐）：

| 互动 | 条件 | 效果 |
|------|------|------|
| 闲聊 | 任意两 NPC 邻近 | 双方 Social 回填 + 等待体验衰减减缓（聊天让等待不那么难熬）+ 外化 |
| 熟人打招呼 | 双方有关系 entry（面熟以上，《关系系统》§2 阶段） | Friendship 轨+，影响组团邀请成功率（8.7 闭环） |
| 拼桌 | 餐厅满座且双方都等位（仅限散客之间；团体整团占座不参与拼桌，见 8.7） | 合并座位 + 社交回填 + 关系变化 |
| 抱怨队伍 | 等待体验值已较低 | 双方 Mood 微升（宣泄），但对店记忆微降——负面情绪会传染，排队怨气是真实经营风险 |

### 8.9 需求驱动的 UseItem

使用 / 吃喝由个人需求触发 `UseItem` Flow，其优先级高于工作；吃饭不占排班类型，`Dine` 时段只调整权重，不是唯一允许吃饭的时间。通用流程如下：

```
需求触发 UseItem
  → 选物品：背包已有物品优先
  → 就位：有限搜索半径内优先选择店内餐桌 / 座位
       有可用位：预约、寻路并就位
       无可用位：原地使用，并记一次"无餐桌"负面体验
  → 等待物品配置的使用时长
  → 触发物品使用效果
  → 扣减数量；有剩余物配置时生成剩余物
  → 释放本次占用的座位等资源
```

需求回填、状态效果、消耗数量与剩余物均由物品配置定义，Flow 只执行通用流程，不为具体食物另写效果。餐桌与座位只提供就位条件和相应的体验修正，不取代物品自身效果。

## 9. 工作点队列系统

### 9.1 逻辑队列与站位分离

- 需要排队的工作点（收银台、门、取餐口、前台等）持有自己的 `FWorkPointQueue.Entries`：每项保存 `ExecutionId / CustomerId / EnqueueGameSec / QueueNumber / CalledGameSec`；数组顺序就是 FIFO，队首为 `Entries[0]`，离队只移除该项并保持其余相对顺序。队列状态归工作点，不需要独立的"排队区"资产。
- 逻辑队列容量统一为 8，与可用站位数量无关。只有队首可进入服务；站位格子、队列线形状或等待区位置都不参与 FIFO 排序，站位与队列顺序完全解耦。
- 站位由工作点的 `QueueMode` 决定：`Line` 使用队列线，`WaitingArea` 使用关联等待区。队列线站位变化走导航不瞬移；等待区顾客轮到自己时再走到工作点。
- 普通等待不设置统一 `QueueTimeoutSec`：等待时长 = 当前游戏时间 − `EnqueueGameSec`，服务期望跌破个人 Min 才离队；等待区叫号后的过号判定读取 `CalledGameSec`。
- 需要跟踪在场的订阅者可自存 `PresentPersons[(PersonId, Role)] = {ExecutionId, EnterGameTimeSec, bPendingClearance}`，只有顾客角色计进店客流，队列不是在场清单。`ExitRequested` 只表示离店意图；`Presence.Exited` 表示实际跨出区域边界的事实，清场、统计与回收以 `Presence.Exited` 为准。区域、坐位、库存、工单、员工工作、裁决与统计等订阅者分别处理自己的状态，没有首处理器或统一清理总控。

### 9.2 队列绑定工作点，不绑定店铺

需要排队的工作点声明 `PointTag` 与队列配置：`QueueMode{Line, WaitingArea} / QueueLine / WaitingAreaRef / Comfort`；家具侧的配置声明见[家具系统 §3.3](/VoxelDesign/02-系统设计/家具系统-系统设计.md)。

一个店铺可有多个工作点、多个独立 FIFO 队列；`QueueAt` 节点参数为目标工作点的 `PointTag`。`QueueAt` 不是特殊节点，是"Advance 服务驱 + 等待段"在排队场景的标准实例（见 §8.2）。

### 9.3 两种站位方式

1. **队列线（QueueLine）**：一串可编辑的排队点，只决定站位，不决定 FIFO 顺序。玩家未配置时，工作点按自身朝向与周围可站立、可达格子自动生成默认队列线，不要求玩家手动摆放任何排队资产；自动生成失败（如贴墙或无可站位）时，该工作点禁用并向玩家告警。
2. **等待区（WaitingAreaRef）**：关联一个已有区域 / 子区域，顾客在等待区内等待，轮到自己时走到工作点。等待区只提供站位与等待设施，不另存一份顾客顺序。

两种方式都只服务站位选择；工作点的 `Entries` 始终是唯一队列顺序来源。

### 9.4 动线影响

队列线的实际站位格对其他 NPC 的导航标记为动态高成本区——队伍挡路会迫使绕行。可编辑队列线与关联等待区的选择是玩家的动线设计环节。

### 9.5 等待区等待与叫号

`QueueMode=WaitingArea` 时，顾客入队后不站队列线，而在关联等待区内等待；轮到队首时通过叫号通知顾客走到工作点：

```
入队（FIFO 顺序写入 Entries）
  → 在等待区坐着 / 进行轻量等待活动
  → 轮到自己 → 叫号 → 终止等待活动 → 走到工作点接受服务
  → 过号超时 → 跳过重排，并记录一次轻微负面体验
```

等待区模式下顾客**主槽始终是 QueueAt**（等待段挂着，计时照走），只允许并发槽 / 子动作层的轻量行为——坐等待区座椅、闲聊、看表演；**不允许在等待期间发起新的主槽流程**（不能再点一杯）。叫号后主槽推进，并发行为自然终止；过号产生的负面体验仍在离店时随本次消费体验一次性上报。

### 9.6 等待区设施

有座 / 遮阳 / 娱乐 → Service 维度等待体验扣分减缓。**装修等待区 = 购买顾客忍耐度**（工作点队列配置的 `Comfort` 汇总设施加成）。

### 9.7 队列引导

队长超引导阈值 → 工单索引器根据队列状态生成或更新 AI.Work.Guide 工单 → 引导员到岗后：
1. 队中顾客等待不满累积减速
2. 沿队列预登记（提前完成 Order 节点）→ 服务点吞吐提升

### 9.8 容量、打烊与退出

- 逻辑队列容量固定为 8，与站位数量无关；队列满时，新顾客先转其他可用的同类工作点，无可用工作点则离店。
- 引导阈值（队长超过则由索引器生成 Guide 工单）。
- 工作点并发数（店门容量即门口工作点并发数）。
- 个体忍耐（服务等待段模型，见 §2.5/§6.7，[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)）。

**打烊停止新接客、区分店内与门外**：店内已锁价预留、收银排队或正在结账继续履约到拿货离店，既有消费需要的Cashier / Serve工单继续保留或派生，不因打烊中断原子收银。外部门口尚未进店队列清退，白跑结束一次上报负满意度体验样本，只写服务组声誉，不记来访 / 成交客群、不伪造进店事实。店内无消费行为者按退出意图引导离店。工作点FIFO与门锁状态仍归对应实例，清洁 / 补货 / 维修继续；员工按自己的劳动安排决定离岗，打烊不统一强退。

**排队中自身需求跨阈值的去留判定**：排队顾客自己的需求（如饥饿）跨 Critical 时，比较「预计剩余等待时长」与「该需求的容忍窗口」——预计等得到就继续排（需求在容忍窗内可压制），预计等不到就弃队走紧急决策。判定用同一把尺：预计剩余等待走估算等待统一入口（§2.5，[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)），容忍窗口 = 该需求 Critical 阈值规则配置的可压制时长。

**离店意图、事实与清理**：主动放弃等离店决策只发布 `ExitRequested`，不把它当作已经离店；实际跨出区域边界后发布 `Presence.Exited`，各订阅者再分别移除自己的队列项与在场记录、释放坐位等槽位、取消关联发起方工单。库存订阅者按 Flow 的 `StockReservationId` 释放整单 Active 预留，未完成的 `Pending` 收银订单强制转为 `Cancelled` 并释放预留；预留释放只恢复可售聚合数量，不扣货架真实库存、不入包、不支付，已完成的原子销售不自动退款。事件发布者不编排这些订阅者逻辑。

**体验上报**：等待、购买、无餐桌等在本次流程累计，消费结束且实际离店时一次上报到Shop经营实体，不逐节点重复写统计。门外未进店队列清退在白跑结束时上报一次负满意度样本，仅写服务组声誉，不计四类来访 / 成交客群。服务组单日集中差评保护按现行统计规则执行，不增加个人记忆或首客保护。

**存读档**：工作点实例保存Entries实际顺序与NextQueueNumber；需要持久化的空间在场PresentPersons归对应订阅者；TrafficStats、Active预留和Pending订单归经营实体；Flow保存ExecutionId / StockReservationId / ActiveCheckoutOrderId。区域不复制客流、预留、订单或FIFO队列。只恢复Active预留与Pending当前订单；原子收银等结果已被 Flow 消费并离开节点后才允许快照。消费者的持续活动由 Flow 节点／进度／Stage 恢复；员工侧由业务状态重建工单索引后重新找活，看板与工单认领不入档。Processing 只是 `CheckoutSale` 原子调用内部状态，不是跨 Tick 收银进度；一次性扣货／入包计划提交后的结果已经写入 ITEM、背包、钱包与唯一流水。读档分别恢复Global经营实体与合同、ITEM / 容器 / 实际空间，再恢复各自所有的在途记录与Flow，按BusinessEntityId、AreaRef及实例稳定ID分别连接；抽象生意不依赖区域恢复。不重放进店／离店／成交事件、不重排 FIFO、不重复计客流。完整字段表和失败边界见 [AI 决策系统架构 §7 存档](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md)。

### 9.9 不做

插队、黄牛、付费优先队列（队列配置保留扩展位）。

## 24. 关键场景走查

### 24.4 排队太长离队换店

```
餐厅 A 门口 QueueAt 节点:
  排队 4 人, 估算等待 8 分钟
  等待体验值随等待时长下降（无等待区设施, 无减缓）
  → 跌破 Expectations[Service].Min（该 NPC 挑剔, 底线高）
  → 离队，记录本次排队负面体验 + 写当日候选冷却（排队主动放弃防徘徊，§2.5（[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)）；餐厅 A 当日冷却期内评分大幅下调）
  → 发布 ExitRequested；实际跨出边界后发布 Presence.Exited，消费体验一次性上报；指店外化由外化层订阅演出（§16.2，[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)）
  → 触发重决策
  → 餐厅 B（队列 0 人, QueueFactor 高）评分更高 → 选餐厅 B

同场景换随和顾客（Service 底线低, 带宽）:
  → 体验值仍在带内 → 继续排队
```

### 24.6 装备定制全流程（异步双机制）

  → 店铺 BillQueue 新增 FBillOrder(客户ID, 已付定金, 交付期限)
  → 顾客流程休眠持久化, FAppointment 代办日程(事件Tag=订单完成, GracePeriod) 入 Agenda
  → 顾客离开, 正常过日子

店铺: 工匠按劳动安排与工作优先级扫描 → 认领 BillOrder 对应 Craft 工单 → 生产
  → 完成 → 可交付 → 发射"订单完成"事件

顾客: 代办日程事件触发 → 唤醒流程, 从断点恢复 → 到店验货 → Pay(尾款) → 拿货

逾期未办分支: 超 GracePeriod 未到店 → 违约结算: 定金没收 + 差评 + 订单取消
