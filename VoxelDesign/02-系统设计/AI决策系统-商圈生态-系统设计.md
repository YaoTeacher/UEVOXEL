### 12.7 商圈生态演化回路

商圈形态不是静态的：消费者层"用脚投票"（声誉 → 客流 → 营收）已经接通，资本层响应由本回路补上，构成 开业 → 经营 → 扩张或亏损 → 退出 → 招商 → 新业态进入 的完整循环。

**退出（NPC 店主）**：
- 持续亏损 → 关店/搬走决策；坚持多久由性格决定（头铁型多扛几个月，精明型及时止损）
- 决定退出后走 §12.6（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）既定流程：缓冲期届满终止租约与相关雇佣、结清工资；不拆建筑、不清空模板家具、不回滚装修、不改资产归属。该生态循环为后续版本，V1 不运行NPC招商或退出调度。

**进入（商业街管理 NPC + 候选店主）**：
- 后续商业街管理NPC对空置店铺经营实体发起招商；同业态空铺邀请 / 同意条款 / 签约接管不重画区域，模板路径在同一连续面板选NPC业态条款 / 预览落位 / 确认，正式Lease先于真正租户建筑家具写入；V1不开放
- 候选 NPC 店主读商圈信号（品类分布、饱和度、客流）决定是否入驻、开什么品类——同类过饱和则入驻意愿低，互补品类意愿高（"这条街餐馆太多，开杂货铺机会更大"的涌现来源）
- 候选来源含取得开店意愿的 NPC（职业流动见 §10.1（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)））；储蓄只影响经营底气，不是硬门槛

**暂不做**：在营店铺转行（餐馆改杂货）——复杂度高，留接口，先跑通进出循环。

**频率**：低频结算（周/月级），挂在既有结算体系上。

**玩家店铺**：不参与生态调度（玩家始终直接经营，V1为标准承租，不等同产权自营，见§12.1（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)））；V1负余额不自动破产或收铺，其他失败条件后续另议。

**商圈内部业务**：商圈 / 店铺 / 图外生意是 Global `BusinessEntities` 中共享基础模型、按类型组合模块的经营实体，持经营资产、产权 / 经营关系、营业意图 / 日程、目录 / 定价 / 订单 / 预留与声誉 / 客流。区域只空间与校验，不存业务镜像，实体区域组件关联 `AreaRef={SceneId,AreaId}`；客房 / 仓库仅空间，抽象生意无实际区域、不造假区域。身份类型与分工见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)。

V1 只保留月租与收租计划，租约唯一事实在 Global `LeaseRegistry`，经营实体仅持 `LeaseId` 引用。租金唯一交易保存源 Shop 的 `SourceBusinessEntityId` 与目标 District 的 `TargetBusinessEntityId`，实际地点 `OccurredAreaRef` 可空，历史不随父关系回改。每个实际 / 抽象人物创建时都有个人钱包和唯一经营账户，非经营者也有，不设区域账户。普通家具仍注册空间设施索引、正常产生保洁 / 维修工单；真实库存、工作点FIFO和门锁在对应实例，区域看板只为不入档派生索引。押金 / 租期、公共维护工、专属公共设施、集市 / 节庆均留后续版本，见[店主与商圈管理-系统设计](/VoxelDesign/02-系统设计/AI决策系统-店主与商圈管理-系统设计.md) §4及[区域店铺与商圈管理 §2 / §9](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。

### 16.6 闲聊与叙事传播

闲聊（待机、等待社交、排队与就餐中的交谈）不只是 Social 回填，也是信息与叙事传播的载体——传播沿真实社交接触发生，不做全广播模拟。

**闲聊 = 传播的同步通道**（传播管线归《AI决策系统-事件系统-系统设计.md》§6，本节只定选材方向）：

- 话题 = 被传播事件的 ID 引用，不是事件内容副本；内容文本由事件类型的文本模板 + 实例参数现场组装
- 选材：闲聊时双方从**自己的记忆条目**里挑近期、高重要性、对方可能感兴趣的条目作为话题——说者是亲历/目击/听闻，听者对说者的信任度影响接收确信度
- 接收：听者建一条来源=听闻的记忆条目，走统一解读管线（情感极性、效果都是听者侧解读出来的，话题本身不带）
- 闲聊行为本身也是一条普通社交事件（双方各建条目照常解读）——"我们聊过天"和"我从他那听说了 X"是两笔账
- 群体列事件（种族拒客等，见[店铺经营 §1](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）优先沿同群体接触传播——口碑传播的个体级通道接在这里（§7.9（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）预留通道由此启用）

**关系事件**（把关系织成叙事）：

- 低频周期检查：共现统计 × 关系阶段 × 性格相性 → 概率产出关系事件（同事交好/交恶、常客结缘等），经 ReportEvent 上报，与一切事件同管线
- 关系事件反哺行为：交好 → 组团消费概率提升（§8.7，[空间卷](/VoxelDesign/02-系统设计/AI决策系统-店铺空间与消费流程-系统设计.md)）、互相替班、正面话题互传；交恶 → 回避、对抗、对方负面信息放大传播
- 涌现示例：交好的员工结成小团体下班结伴吃饭（与组团消费天然对接）；不满员工的去意沿交好同事传播（§11.5（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）辞职梯度的共振通道）；攒钱开店的员工成为全街话题（§10.1（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）的叙事素材在此落地）

**不做**：故事导演层（事件预算、强度曲线、节奏调控）——本版不实现，先跑通"事件 → 传播 → 关系 → 行为"的自然回路，导演层留作后续方向。

## 17. SpawnArea 与流量分布

### 17.1 设定基调

**V1 世界特例**：只实际加载玩家自己的一个商圈，初始只有道路与空地，商圈外为平地；不运行多商圈竞争、其他街区、探索切换或图外流量结算。以下核心商业街区设定是完整版本方向，不是 V1 当前世界结构。

**主地图 = 城市里的一个核心商业街区**：主地图承载的是这个核心商业街区（内含多个互相竞争的商圈）的人流，不是整座城市。城市的其他区域（其他街区/城外）不在主地图，是探索模式下经 SpawnArea 可达的其他地图。玩家在主地图经营与竞争。

**探索与经营的时间轴分离**：探索模式与主地图不共用同一条经营时间——玩家外出探索期间主地图经营暂停；探索结束返回时结算本次外出耗时，外出队伍在到时间后才回到主地图。

主地图本身客流量不小，问题只是玩家商业街位置偏。因此**人口总量静态**（大城市背景，指本商业街区的人口盘子），不做移民/流失模拟；要模拟的是**"流量分布"**——与第 14 章（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）活动系统咬合：广告的本质就是把主街流量引进深巷。

### 17.2 SpawnArea = 地图切换点

```
FSpawnArea{
  AreaID,
  Location,              // 图内入口位置（城门/地铁口/街口）
  LinkedAreas: TArray<FAreaLink>,   // 对接的其他区域（类似 MMO 地图切换点）
  TrafficWeight,         // 流量权重（单位时间通过人数）
  TimeCurve              // 时段曲线（早晚高峰/饭点加成）
}
```

**V1 使用边界**：SpawnArea 只作为固定名册 NPC 从地图边缘 / 抽象住所进出图的点名与位置引用，不承担玩家地图切换。`TrafficWeight`、`TimeCurve` 和图外触达在 V1 不参与刷人、人口补充或消费决策；字段所在完整结构保留供后续版本使用。

一套切换点数据，NPC 寻路、玩家探索、流量分布全复用：
- **NPC 用途**：V1普通居民的 `HomeAreaRef={SceneId,AreaId}` 直接定位抽象住所对应的实际SpawnArea进出点（不是图外雇主假区域），进场从该点刷出、退场回该点消失，不经过住所配置表二次解析；完整版本的实体居住区与 SpawnArea 绑定仍属后续扩展，不在 V1 新建住所实体。
- **玩家用途**：探索模式下通过 SpawnArea 切换到目标区域（城外探索/素材采集的出口，接 §15.2（[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）探索通道）

### 17.3 进场与退场

```
进场: 日程段需要进图 → 从对应 SpawnArea 刷出 → 寻路到目的地
退场: 日程结束离图 → 寻路回对应 SpawnArea → 消失
```

NPC 来去方向符合直觉（住城东的人从东门进），组团消费有自然的汇合点。

### 17.4 图内人口

**V1 人口 = 一套有限的固定名册**：开局生成后，顾客与员工都来自同一名册并使用稳定 `CreatureID`；离场只回收实体并保留名册业务数据。V1 不生成季节性 / 一次性游客、行商或背景人，不按流量临时刷顾客，也不做移民、流失或人口补充模拟。下面的“固定住户 + 游客 / 行商”是完整版本人口构成，V1 只保留其中的固定名册原则。

**人口 = 固定名册**：开局按街道生成固定住户，另有季节性/临时的游客与行商（外来 NPC，见 §2.2（[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)））；名册上每个人都是完整个体（画像/需求/记忆/关系全量数据）。在场人数由"日程出场判据"（§2.3，[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)）自然决定——到生物钟活跃时间或需求触发即经绑定 SpawnArea 刷出——不需要额外人口系统。玩家不开店也不影响人口——影响的是**流量去向**，不是流量总量。人口规模取向：在性能允许范围内图内人越多越好（个体化呈现），街道热闹程度由名册密度决定。**不设"背景人"装饰层**——图内不出现无个体的幻影人流；若未来性能需要纯视觉人群，那是永不交互的装饰层，届时单独立项。

**决策只由事件触发**：每个决策都发生在"有需求/有任务"的事件时刻（§2.5，[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)），不存在周期决策，也不存在对人群做统计采样决策——不在事件时刻的个体不做任何决策运算。

**TrafficWeight/TimeCurve 的作用域**：只服务图外抽象结算——指路牌的图外触达量（§14.3，[经营卷](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）、传单在人流入口的触达量；**不控制图内刷出**。主街流量天然存在（名册中通勤/消费路径经过主街）；深巷没流量 = 没有路径经过 → 指路牌（FootTraffic）把部分流量引入深巷路径；传单投放点 = 直接选 SpawnArea（在人流入口发）。

### 17.5 天气接口（预留）

评分公式在 TimeMod 同模式上加天气修正窗（见 §5.3（[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)）公式的 WeatherMod 槽位）：

```
WeatherMod 由全局天气状态驱动（雨天: 室外队列忍耐加速衰减 / 客流系数下降）
```

本版只定义接口（WeatherMod 槽位 + 天气状态查询函数），数值与天气系统本体等环境系统实现时再填。
