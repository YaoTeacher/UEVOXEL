## 1. 系统边界

**负责**：
- 容器槽位对 ITEM 实例的引用、堆叠拆分／合并与数量扣减；
- 储物家具与可售货架的容量硬上限，以及仓库子功能区内的库存聚合；
- 库存内 FIFO 扣货顺序与原子履约所需的实际源堆计划；
- 保质配置的预留，以及后续腐败推进、变质处理的专项边界。

**不负责**：
- 采购单与配送（后续版本，V1 不做；V1 即时采购见经营操作 §3.2）；
- 补货工单（家具系统 / 员工与工作执行）；
- 账本记账（[店铺经营 §2](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）；
- 偷窃/打斗/灾害等事件性损耗（后续由事件系统写库存）；
- V1 不运行随时间腐败、到期或自然变质处理。

## 2. V1 库存归属与仓库

V1 采用“**仓库子功能区 + 储物家具**”模型，不做 RimWorld 式地面堆放区：

```text
Shop
├─ 营业空间
│   └─ 可售货架（FStorageFuncFragment.bForSale=true）
└─ 仓库子功能区（可选）
    └─ 后备储物家具（FStorageFuncFragment.bForSale=false）
```

- 真实库存只存在家具 / 物品实例容器中。店铺库存按经营实体关联的实际空间与合法所属设施聚合；仓库子功能区只作空间分组，不凭空间包含转移租户资产，不另存区域或经营实体总库存；
- 经营资产与业务唯一归 Global `BusinessEntities` 中的经营实体，商圈 / Shop / 图外生意共享基础模型并按类型组合模块，持产权 / 经营关系、`bOpen` / 日程、目录 / 定价 / 订单 / 预留、声誉 / 客流。区域只空间与校验，不存这些镜像；实体区域组件关联 `AreaRef={SceneId,AreaId}`，子仓库 / 客房只有空间ID，抽象生意无实际区域且不造假区域。FIFO队列 / 门锁仍归对应实例，区域看板是不入档派生索引；
- `BusinessEntityId` 为全局稳定经营 ID（GUID，规则见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)）；不再使用 `ShopId` 别名。Home / Work 仍空间。详见[区域店铺与商圈管理 §2 / §9](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)；
- 独立仓库是推荐的空间组织方式，不强制单独建房；后备储物家具也可直接放在营业空间。仓库子功能区不提供额外容量，不独立核算；
- V1 即时采购只进入符合物品过滤条件且有剩余容量的后备储物家具。没有后备储存容量时不能采购，但不增加开业设施硬校验；
- **补货按全仓库判定**：判定基数是该商品在**店铺范围内全部储物设施**（可售货架 `bForSale=true` + 后备储物 `bForSale=false`）的 OnHand 合计，不是只看货架。合计低于补货阈值 → 库存不足，分两种处理：
  - 后备有货 → 产生 `AI.Work.Restock`，理货员从后备搬到可售货架；
  - 后备为空（货全在货架上）→ 补货搬无可搬，不生成工单，只给「库存不足、需要进货」提醒（V1 即时采购由玩家触发，不自动采购）。
- 后备储存不等于可售现货：可售量仍只算 `bForSale=true` 的货架；
- 采购货款从店铺资金责任人的唯一经营账户支付：自营 / 承租为经营人，薪酬制为产权人；扣款、入库与唯一流水原子完成，余额或容量不足整笔失败，不生成采购在途单或应付账款。每个实际 / 抽象人物创建时均有个人钱包和唯一经营账户，非经营者也有；经营实体和区域不设账户。流水按 `SourceBusinessEntityId / TargetBusinessEntityId` 区分源 / 目标业务归属，`OccurredAreaRef` 可空；租金两侧分别Shop / District，同一交易只记一次，历史不随空间父关系回改。

### 2.1 顾客选品预留与销售扣减

- **聚合范围统一为「店铺范围」= 经营实体主区域（`AreaRef`）及其 `ParentAreaId` 链下的全部子区域**。设施按「最小包含区域」注册（家具系统 §3.2），所以仓库等子功能区里的货架也属于本店，不能只查单一 AreaId。
- 顾客可售数量按 `Available(Product) = Σ OnHand(店铺范围内可售货架, Product) - ActiveReserved(Shop, Product)` 计算；不包含 `bForSale=false` 的后备储物家具。聚合是实时查询，不另存区域库存副本；
- 经营实体持有预留，只记录 `BusinessEntityId + ProductTag + Quantity + LockedUnitPrice` 等销售信息，不引用具体 `ContainerId / StackId / ItemInstanceRef`。同一店铺多个货架的现货共同满足一张待购清单，整单预留失败不保留部分行；
- 预留不扣任何货架 `OnHand`、不改变容量占用、不转移所有权，也不进入 NPC 背包；未付款流程放弃／中断／取消／失败或付款失败时释放整单预留，只恢复聚合可售数量，不向货架伪增真实库存；
- 收银时才根据当前货架实际 ITEM 堆生成一次性扣货／交付计划，再据此模拟背包放置。该计划引用实际源实例并读取其状态，但只在本次原子履约内使用，不回写商品预留，也不提前把预留绑定到货架或堆；
- `CheckoutSale` 在同一原子履约中核销预留、按锁价付款、依计划扣减实际货架并把对应 ITEM 状态交付入包，同时完成所有权与成交明细流水；任何一步失败则整笔销售不发生，不出现部分付款、部分扣货或部分入包；
- 实际扣货结果用于对应货架 Restock 检查。存档保存 Active 商品预留和 Pending 当前收银订单的商品、数量、锁定单价与关联 ID，不保存货架／堆叠引用或一次性扣货计划。读档先恢复真实 ITEM 与家具容器，再恢复预留、订单和 Flow 引用；收银原子节点只在结果已被 Flow 消费后允许快照，顺序见 [AI 决策系统架构 §7 存档](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md)。

### 2.2 NPC 私人背包固定槽位

- V1 `SlotCount = 16`，NPC 与玩家统一使用该固定值，运行中不扩缩容。背包保存固定长度槽位数组；槽位为空，或只保存一个 `ItemInstanceRef`，不直接保存另一份 `ItemId + Quantity`；
- `Quantity` 属于被引用的 ITEM 堆实例，单槽上限取静态 `MaxStackCount`。同一物品可占多个槽，超过单槽上限的余量可分到其他槽；HP、清洁度、品质等也都读取实例，槽位不复制；
- 采用 MC 式槽位规则：同种兼容物品可以同时存在多个未满槽，空槽始终可用，不要求历史同类槽全部满堆。NPC 自动入包先尝试合并兼容槽、余量再进入空槽，这只是当次插入顺序，不是背包合法性限制；
- 空槽没有有效实例引用。使用或丢弃使 `Quantity = 0` 时销毁对应堆实例并清空槽位引用，槽位可重新存放其他物品；
- `CanFitWholeBasket` 对实际待交付 ITEM 堆及其拆分结果做整单放置模拟：先使用兼容槽的 `MaxStackCount - Quantity` 剩余量，再使用空槽；所有物品都能完整放下才返回可行及放置计划。只比较商品总件数、空槽数或单件最大堆数都不是完整校验；
- Browse只形成1～3件待购清单，不因钱包或背包拒绝浏览；加入购物篮 / 锁价预留时用 `CanReserveBasket(BusinessEntityId, CreatureID, Basket)` 校验整单营业、现货、资金与容量，不足可缩篮子。收银按实际源堆重新生成放置计划并原子入包。此时放不下则整笔销售失败、释放预留，不做部分付款或部分入包；
- 存档保存固定槽位的 `FGuid ItemInstanceId`，并在 `UVoxelItemWorldSubsystem.ItemInstances` 中仅保存一次被引用实例的数量、HP、清洁度、品质及实际模块状态，不在槽位重复保存。读档先恢复实例登记和 ID→运行时索引，再恢复槽位引用；V1 不计算重量，后续追加由 NPC 力量等属性决定的总载重约束；
- 所有 ITEM 都有 float `HitPoints` 和静态 `MaxHitPoints`，`Integrity` 只派生。普通 ITEM 的 HP 归零时保留实例、不可使用且可维修；不同 HP 与清洁度同样按实际移动数量加权合并，拆分复制、纯移动不变，HP 不取整；
- 不同品质不能共槽、共堆；可放置能力不影响堆叠上限。花朵、罐子等可以同时可放置、可堆叠；
- `Cleanliness` 只在放置 OBJECT 中推进，ITEM 在背包／货架中只保存值。不同清洁度允许合并，按实际移动数量加权；拆分复制、纯移动不变，部分合并未移动的源堆保留原值；
- V1 不推进腐败，不产生不同新鲜度／到期时刻的自然变化。后续易腐字段与跨状态共槽规则由专项确定。

## 3. 物品侧配置

| 字段 | 位置 | V1 语义 |
|------|------|------|
| `MaxHitPoints` | ITEM 静态行 | 所有 ITEM 的 float HP 上限；实例保存当前 `HitPoints` |
| `ShelfLifeSec` | 物品行 | 保留保质配置；V1 不据此推进腐败或到期 |
| `Item.State.Spoiled` | 状态标签 | 后续变质结果；V1 不因时间推进自然打上 |
| `Disguise` | 物品/产出 | 外观伪装度 0–1，V1 默认 0（预留字段） |
| `PreserveFactor` | 储物设施配置 | 后续保质能力；V1 不修改到期时刻或腐败进度 |

## 4. 堆叠、FIFO 与后续腐败

- 容器槽位只引用 ITEM 堆实例；堆叠数量与状态由实例持有，不进顾客选品或预留数据结构；
- **先进先出**：消耗、补货上架、做菜取料和杂货销售履约均按既有库存 FIFO 从较早已入库的堆开始。FIFO 是库存操作顺序，不等于 V1 正在计算新鲜度；
- **V1 腐败边界**：不运行 `Freshness` 扣减、`ExpireAt` 到期、腐败进度推进或跨阶段转换；所有自然变质后果在 V1 不触发；
- **后续专项**：易腐状态最终字段、环境推进、保质设施作用、不同进度合并、是否允许跨阶段共槽均未确定；不得把旧的加权新鲜度草案或 RimWorld `RotProgress` 直接写成已确认规则；
- **可见性与伪装**：精确状态展示、顾客可见性和 `Disguise` 的效果随后续易腐／消费专项启用，不构成 V1 腐败模拟。

## 5. 后续：变质与处理（V1 不触发）

以下仅为后续功能入口，不是 V1 主动流程：

```text
后续腐败专项启用到期／阶段推进后：
  ├─ 丢弃：搬运/清洁工单丢到垃圾点，计入损耗支出
  ├─ 出售：是否允许及如何定价由经营规则决定
  └─ 加工：配方是否接受该状态由配方过滤决定
```

V1 不自然进入 `Spoiled`，不执行“到期打标＋品质折减”，也不生成对应出售、食用、加工或丢弃后果。

## 6. 后续：变质发现（V1 不触发）

```text
后续易腐与消费专项启用后：
购买/点单时的外观判断
使用入口的味觉发现、拒食／差评／退款
未发现时的效果折减与健康事件
事后归因到记忆、事件与店铺声誉
```

高伪装度掩盖外观与味道、健康事件延迟归因等均属后续设计；V1 不因自然变质进入这些分支。

## 7. 容量规则

- 后备储物家具与可售货架都有硬上限：`FStorageFuncFragment.MaxCell × 堆叠上限`，并受各自 `AllowItemTags` 过滤；区域和仓库子功能区本身不提供容量；
- 容量模拟同时读取目标槽所引用实例的数量与兼容状态，不能只按物品 ID 估算可合并空间；
- V1 即时采购只校验后备储物家具的兼容剩余容量，超容整笔拒绝，不扣款、不入库、不生成应付账款；
- V1 补货只向可售货架搬运；目标货架满时工单失败或等待，不允许落地上溢；
- 后续供应商版本才使用采购单容量预检、在途配送和“到货已满则配送失败并退货款”等规则，不回写成 V1 的即时采购流程。

---

## 8. 损耗

V1 不生成自然变质损耗。后续开启腐败后，变质丢弃再计入店铺损耗支出。

偷窃、打斗、灾害、搬运损坏等事件性损耗后续由事件系统直接写库存减少，库存系统只提供扣减接口，不建治安玩法。正常消费／销售的数量扣减不属于变质损耗。

盘点 V1 不做。
