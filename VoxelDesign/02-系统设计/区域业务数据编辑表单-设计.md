# 区域业务数据编辑表单 — 设计文档

**最后更新**：2026-11-04

## 0. 建造组合创建面板（引用）

组合创建的流程、原子集合、失败回滚、租约先行与子区域不建实体等业务规则，唯一信源见[区域店铺与商圈管理 §6.14](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。本文件只规定**面板采集哪些字段**与**字段级权限**，不重复业务规则。

- 采集字段：OperatorId（操作者上下文）、业态、名称、经营意图、父经营实体、空间草稿；不硬定请求 class。
- 产权人/经营人由有效授权、租约或任命确定，不能靠自由填写人名/ID 取得权利。
- 同一面板采集经营事实与范围信息，但分别发往实体业务与区域业务：UI → Controller → 业务门面 → 存储 → 事件 → UI。

## 1. 需求与范围

既有实体详情面板的「编辑业务」按钮打开普通资料表单，只允许修改经营实体的**名称、LOGO**；**仅子区域**可修改空间名称/类型。**所有人 Owner 与经营人 Manager 不在普通表单中修改**，也不在表单中直接选择；Shop 营业状态由独立营业按钮控制，不进普通资料保存。

### 权限规则（分字段）

| 字段 / 操作 | Owner | Manager | 其他人 |
|------|:---:|:---:|:---:|
| 名称 / LOGO | ✅ | ✅ | ❌ |
| 子区域类型（仅子区域） | ✅ | ✅ | ❌ |
| 主区域类型 | ❌ | ❌ | ❌ |
| **开业 / 停业** | 仅兼具经营人时 ✅ | ✅ | ❌ |
| 「编辑业务」按钮可见性 | ✅ | ✅ | ❌ |

- 无权限用户：详情面板隐藏「编辑业务」按钮。
- **产权不进普通表单**：购买/出售、继承或其他产权变更只走产权业务。Shop所依附铺位的产权按有效商圈产权/授权只读解析，不在区域或表单另存 Owner；租户建筑/家具按独立来源日志保留，不因范围包含继承商圈产权。不存在 Owner改变时自动同步 Manager 的普通字段联动。
- **经营关系不进普通表单**：Manager 的任命 / 分配、出租签约、终止或更换只走各自业务流程，由业务方法同步经营关系、租约与统一雇佣登记。表单不提供直接分配 Manager 的入口，经营人因此也不能通过表单修改自己作为乙方的合同。
- 开业 / 停业是独立业务操作，由营业按钮执行，不随名称 / LOGO 的普通保存提交；只有当前店铺经营人可执行，单纯产权人身份不代表能替经营人开关店。

### 类型切换约束（同层级互切）

- **判定标准**：同一直接父 GameplayTag（`GetDirectParent()` 相等）才允许互切。
- **层级节点过滤**：**有子类型的类型不可直接选**（若配置表中存在其他类型以其为直接父 Tag，则它是层级节点）。如 `Shop` 有子类（`Shop.Bakery` 等）故不可选，`Shop.Bakery` 无子类故可选。
- **注意**：`FAreaTypeBase.bAbstract` 是**重叠许可标志**（其他区域能否与其重叠），与类型层级无关，**禁止**用于此过滤。
- **后端校验**：提交时仍走 `CheckTypeConflict`，冲突拒绝并 Toast 原因。

### 所有人 / 经营人展示

- Owner / Manager 使用只读文本展示当前业务解析结果，不再使用可选择的 `ComboBoxString`。
- Shop所依附铺位的产权人按有效商圈产权/授权查询；不从在场生物生成候选，不在区域另存 Shop Owner，也不把租户家具/建筑产权覆盖为商圈产权。
- Manager 显示当前有效经营关系中的经营人；没有有效经营关系时显示空 / 未任命。后续任命、出租或产权交易完成后，详情面板通过数据广播刷新展示。

### 营业状态

- 不再提供 `EAreaStatus` 全枚举 ComboBoxString；Shop 按 `bOpen / bOperating` 显示停业、打烊或运营中，非 Shop 不显示该字段。
- 开业 / 停业通过独立业务操作提交，只写 `bOpen`：开业置 `bOpen=true`，停业置 `bOpen=false`；开业**不校验任何设施**，也不校验入口或导航可达性（05 决策29），缺少设施、员工或库存由运行期提醒与经营结果自然反映。
- `bOperating = bOpen && 当前处于有效营业时段（含延长覆盖）`，是派生状态：不单独手动写入、不由营业循环另存，读档后由 `bOpen` 与营业时段重建。表单中只读；实际接客直接读 `bOperating`，不存在 `bOpen=false、bOperating=true` 的合法状态。

## 2. 交互形态

**独立弹出对话框**（CommonActivatableWidget，含遮罩）：
- 可编辑字段：名称（EditableText）/ LOGO（图标选择）；子区域额外提供子区域类型（ComboBoxString）。
- 不在表单中出现：所有人、经营人、主区域类型、营业状态；这些由业务流程或营业按钮维护。
- 「保存」「取消」按钮。
- 打开时按当前玩家权限**逐字段禁用**不可编辑控件；Owner / Manager 不因玩家身份变成可编辑。
- 详情面板「编辑业务」按钮 → `Layout->PushModal(EditDialogClass)`

## 3. 数据流

```text
普通资料表单（不直改数据）
  → Controller → 业务门面，按目标身份分发：
      ├─ BusinessEntityId：名称/LOGO → 经营实体资料存储
      └─ AreaRef：子区域名称/允许的功能类型 → 区域空间存储
  → 校验有效经营关系/授权；请求不含 Owner/Manager/合同/bOpen 可写字段
  → 成功：资料事件 → ViewModel/详情面板刷新 → 关闭表单
  → 失败：显示业务原因，保留表单

Shop 开业 / 停业按钮（独立于普通保存，仅有效经营人）
  → Controller → 业务门面 → 经营实体营业模块，只写 bOpen 并入档
  → 开业不校验任何设施、不校验入口/可达性，不做自动复检
  → 状态事件 → UI；bOperating 由 bOpen 与有效营业时段纯派生

产权购买/出售、经营人任命/出租/终止（不经过普通资料表单）
  → Controller → 专用业务门面 → 有效授权/合同/资产/经营登记
  → 关系事件 → 只读刷新 Owner/Manager，区域不保存关系副本
```

## 5. 关键实现细节

### 5.1 同层级类型筛选

```cpp
// 收集全部出现过的「直接父 Tag」→ 拥有子类型的类型集合
TSet<FGameplayTag> ParentTags;
for (const FAreaTypeBase* Type : AllTypes)
{
    ParentTags.Add(Type->AreaTypeTag.GetDirectParent());
}

// 筛选：同一直接父 Tag 且自身无子类型（叶子类型才可直接选）
FGameplayTag CurrentDirectParent = CurrentTypeTag.GetDirectParent();
for (const FAreaTypeBase* Type : AllTypes)
{
    if (ParentTags.Contains(Type->AreaTypeTag)) continue; // 有子类型 = 层级节点，不可选
    if (Type->AreaTypeTag.GetDirectParent() == CurrentDirectParent)
    {
        Candidates.Add(Type);
    }
}
```

### 5.2 权限判定

- ViewModel 通过业务查询当前经营实体的有效产权/经营关系及授权，决定名称/LOGO编辑与营业按钮是否可用，不调用 AreaBase.IsOwner/IsManager 读取区域权属。
- Owner/Manager 始终只读；经营人与店铺铺位产权由对应有效关系解析，没有关系时显示未设定。子区域仅展示关联主体信息，不能设独立 Manager。
- 子区域功能类型编辑校验相应空间授权与类型约束；公开准入不等于可编辑或可经营。
- 开关店仅有效经营人调用专用业务；只读取实体营业模块 bOpen，bOperating 纯派生。后端各业务复核授权，不信任前端显隐。

### 5.3 保存组装

| 目标 | 请求内容 | 提交业务 |
|---|---|---|
| 经营实体普通资料 | BusinessEntityId、名称、LOGO | 实体资料业务 |
| 子区域普通资料 | AreaRef、空间名称、允许切换的功能类型 | 区域空间业务 |
| 开业 / 停业 | BusinessEntityId、目标 bOpen | 独立营业业务 |
| 产权 / Lease / 任命 | 专用业务所需授权与条款 | 相应合同/产权业务，不复用普通资料请求 |

普通资料不携带保持不变的合同/权属/范围快照，不在 UpdateBaseAreaInfo 映射 Owner/Manager/bOpen。经营事实和空间信息即使同面板采集，也按目标存储分别提交，成功后通过事件刷新。
