## 1. 口碑与店铺统计

### 1.1 个体层（V1 不实现）

完整版本中，综合满意度经事件系统上报与解读管线写入个体记忆，并通过 MemoryMod 影响复购评分。**V1 不启用这条链路**：综合满意度只形成 `Shop.ExperienceReported`，直接写入店铺统计，不创建个人记忆条目，也不经记忆附带店铺 ID。

### 1.2 店铺层：V1 五组统计

V1不做完整「维度×群体」矩阵，也不另设「全局」组。以下五组唯一归店铺经营实体，随稳定BusinessEntityId走，不存区域镜像：

1. **服务**：服务速度、服务质量、商品丰富度、价格、环境氛围；上菜速度并入服务速度或服务质量。服务组聚合全部有效体验样本，就是 V1 的总体店铺声誉，不再复制一份全局列。
2. **种族**：按顾客所属种族统计来访人数、成交笔数、成交金额、客单价与满意度。
3. **职业**：按顾客职业统计同类客群构成指标。
4. **阵营**：按顾客所属势力统计同类客群构成指标。
5. **街区**：按顾客常驻街区统计同类客群构成指标。

种族 / 职业 / 阵营 / 街区四组只是**客群构成统计**，不把五个服务维度按群体再交叉一遍，也不形成群体声誉。完整 6 维 × 5 群体矩阵及独立全局组留后续版本。

### 1.3 有效声誉（贝叶斯收缩）

V1 对服务组的五个维度分别保存滚动聚合与有效样本数，并独立做贝叶斯收缩：样本越少越靠近中性先验，样本越多观测均值越主导。综合有效声誉由五个服务维度的收缩结果按展示权重合成；不存在另一份全局组声誉。

新店不会被两条差评直接打到极端值。四类客群构成组只展示实际统计，不参与这套服务声誉收缩。

### 1.4 声誉写入与读取（V1）

- `Shop.ExperienceReported` 按评价归因写入服务组；实际进店、成交与体验结果分别更新对应种族 / 职业 / 阵营 / 街区客群构成。
- `QualityScore` 只读取服务组合成的综合有效声誉；四类客群构成不作为另一套群体声誉输入。
- 统计页读取同一组数据，不另算 UI 专用口碑。
- V1 不经声誉产生个体记忆、口碑传播或动态知名度半径；普通路过发现只走 [NPC 卷 §5.2](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md) 的简化认知规则，完整感知系统与声誉驱动的认知发现后续再接入。

### 1.5 个体偏差（V1 不实现）

完整版本的个体偏差由 MemoryMod 表达，店铺有效声誉保持纯统计。**V1 的 MemoryMod 固定为中性值 1，不生成个人记忆输入**；不同 NPC 的选店差异来自既有需求、期望带、意愿和其他 V1 修饰器，不由消费后新建的记忆条目产生。

### 1.6 负面记录入口

以下情况也汇入本次消费流程的体验报告，不只成功消费后才评价：
- 排队超时离开；
- 被门禁拒绝（满员拒入队等）；
- 进店发现买不起 / 想买的缺货（Browse 揭示真实价格与库存，预留双门禁无法通过，见 §8.6（[空间卷](/VoxelDesign/02-系统设计/AI决策系统-店铺空间与消费流程-系统设计.md)））；
- 投诉未处理（突发状况自然消散的落地结果，见《AI决策系统-事件系统-系统设计.md》§10 突发状况口子）。

体验在消费流程结束、顾客实际离店时一次性上报；同一流程的各节点只累计评价内容，不分别重复上报。未完成消费的负面记录（离队 / 拒入 / 离店）权重显著低于完整消费差评。V1 只按评价写入规则影响服务统计，不产生个人记忆或长期记忆修正，单日集中差评保护由店铺统计侧统一执行。

### 1.7 评价归因与多维写入

体验报告携带归因字段（见§6.2（[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)））。一般店铺原因（服务失败、等待破底、缺货等）写服务组负样本，自身 / 环境原因不追责。**打烊门外未进店队列清退是已确认例外**：白跑结束上报一次负满意度样本，只进服务组声誉；未实际进店、不成交，故不计四类客群的来访 / 成交 / 客单价 / 满意度，不创建个人记忆。店内已锁价 / 收银排队 / 结账继续完成，不能把打烊当作其强退理由。

V1 的群体归属只决定客群构成统计桶，不把同一体验交叉写成多个群体声誉，也不启用“同一事件对不同群体列反向加减”的完整矩阵规则。

### 1.8 单日集中评价保护

同一店铺单日内的负面样本按序递减权重（第一条全量，后续逐条衰减）——防单日集中差评（如一次群体性服务事故）把声誉一次性击穿；保护只作用于单日内，跨日样本照常累计，慢性差评仍会如实反映。V1 该保护只作用于服务组。

### 1.9 店铺日志

V1 五组评价（§1.2）是经营实体统计，店铺日志是事件级业务数据：值得注意的事件条目归**店铺经营实体**，跟稳定 BusinessEntityId 走，不随区域或当前经营人迁移。

- 来源：重大服务事故、群体事件（种族拒客）、名人 / 精英到访、员工侧事件（集体辞职、被挖角）、玩家的显著经营动作；“是否写入日志”由店铺侧写入规则配置声明，不挂在事件类型上。
- 用途：话题素材（§16.6（[商圈卷](/VoxelDesign/02-系统设计/AI决策系统-商圈生态-系统设计.md)））、玩家统计页与情报玩法素材（§16.4（[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md)））；完整群体声誉与传播素材留后续版本。
- 量控：只记值得注意的事件（配置驱动），滚动上限，旧条目自然淡出。

### 1.10 V1 不做与后续扩展

- 完整售后（投诉入口、退款 / 免单 / 重做、协商多轮）V1 不做，只保留体验上报与声誉影响（见[营业循环卷](/VoxelDesign/02-系统设计/AI决策系统-营业循环-系统设计.md) §7）。
- 个体记忆、MemoryMod、完整感知系统、口碑传播、完整 6 维 × 5 群体矩阵与独立全局组均不进入 V1；普通路过发现只按 NPC 卷 §5.2 的简化认知规则执行。
- 已完成上报的原始体验样本不逐条入档；V1 只保存五组统计聚合、当日集中评价保护所需的最小状态，以及仍在消费流程内、尚未上报的在途体验报告。逐字段归属、聚合值与派生值边界、读档顺序见 [AI 决策系统架构 §7 存档](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md)。
- 后续版本可在同一体验报告上增加记忆解读、沿真实社交接触传播及群体声誉写入，不改变 V1 已确定的事件归因与店铺统计来源。

## 2. 经济循环

### 2.1 NPC 收支与职业流动

**消费意图与支付能力分层**：**选店评分不读个人钱包**，NPC 选不选这家由 WillingnessScore + 期望带决定；个人储蓄参与目标层预算与职业流动，但不在选店阶段充当价格硬过滤。顾客没钱也可以进店 Browse；加入购物篮 / 锁价预留时才调用唯一守卫 `CanReserveBasket(BusinessEntityId, CreatureID, Basket)`，同时校验营业与货页可售、聚合现货 `ΣOnHand − ActiveReserved`、钱包是否覆盖整单锁价金额、16 槽背包整单放置。买不起或放不下时可减少数量或放弃部分商品，直到通过校验；一件都无法预留则放弃购物离店。收银仍再次执行原子履约校验，余额或履约条件不足则整笔失败并释放预留，不扣货、不赊账、不形成负余额。销售收入从消费者个人钱包直接进入店铺资金责任人的经营账户：自营 / 承租归经营人，薪酬制归产权人；区域流水保留店铺经营统计。

**职业是三条正交逻辑，没有状态机、没有“员工类型”**：

1. **职业 —— NPC 的属性**：这个 NPC 是干什么的（跑堂、厨师、工匠……），决定能认领什么工单、技能往哪个方向积累，跟着 NPC 走，与在哪干活无关
2. **工作归属 —— Creature 上的劳动安排**：这个 NPC 在哪个用工区域干活、按什么排班权重和工作优先级劳动，都由 `FWorkAssignment` 决定。雇佣记录只表示合同与工资关系，不能代替劳动区域；劳动安排停用后，NPC 还是那个职业的他
3. **经营负责人 —— 经营实体的有效经营关系**：指向人物而非区域，身份与产生规则见[店主与商圈管理 §2](/VoxelDesign/02-系统设计/AI决策系统-店主与商圈管理-系统设计.md)。开店取得经营实体负责关系；停业只改 `bOpen`，不移除关系；退出按租约 / 雇佣终止流程办理。当过店主不改变职业，取得 / 失去的是经营负责关系，不是空间产权；再次招聘仍要求无有效合同。

**积累跟着NPC走**：个人储蓄、技能、经验、人脉不因关系变动丢失；取得 / 失去的是经营实体负责关系，不是区域产权。职业流动、员工攒钱另开同业态店等叙事留后续，不在V1生成换工 / 吞合同 / NPC招商政策。招聘仅无有效合同者，图外合同也有效，人数不足如实显示（叙事接口见§16.6（[商圈卷](/VoxelDesign/02-系统设计/AI决策系统-商圈生态-系统设计.md)））。

### 2.2 商品目录

`FShopProduct{ProductTag, LinkedItemId(可选实物), Price, Quality}`

- 定价粒度 = 单个商品：Price 逐商品定价，默认 = 物品基准价；
- 当前市场基本价直接取物品的 `FVoxelItemCirculateDataFragment.Value`，不另建市场价格表；V1 不做动态市场价、供需波动或区域行情；
- `Price` 与可交易物品的 `FVoxelItemCirculateDataFragment.Value` 均只接受**有限且 ≥0** 的数值，不设固定上限；0 元售价与 0 元基础价均合法。V1 食品／饮料为使用百分比价格体验，其基本价配置必须大于 0；其他零基础价物品不在本项扩展；
- 单商品 `PremiumRate = (Price - Value) / Value`，`PriceFavorDelta = -PremiumRate`。高于基本价 20% 则价格好感 −20%，低于基本价 20% 则 +20%，等于基本价不增减；这是消费者购买行为的价格体验，不直接修改人际关系。远程店铺价位档取当前已上架商品 PremiumRate 的平均值并即时派生，到店仍揭示真实货币价格；
- 负数、NaN、Infinity 或无法解析为合法数值的定价输入直接拒绝并保留旧值，不静默截断或按 0 保存；无效 `Value` 配置不得用于采购或上架，不自动修正为 0；
- 0 元销售仍走同一原子结账、扣货、整单入包、所有权转移与销售流水，金额为 0，不产生付款不足；0 元采购仍校验容量并记流水，只是货款为 0；
- 商品目录不声明固定购买体验。成交结果发布后，由买家 Flow 的购买行为方法根据该买家的当前需求、性格、特性与本次购买上下文结算 Shopping、Mood 等购买体验；`CheckoutSale` 与员工不计算买家体验。食物 / 饮料对 Hunger / Thirst 的使用基础作用从 `LinkedItemId` 的 `FConsumeFuncFragment.Effect` 读取，在实际使用时经统一需求入口应用，不在商品目录复制；
- **禁止“调价系数”概念**。

### 2.3 支付

- 加入购物篮 / 锁价预留时统一调用 `CanReserveBasket(BusinessEntityId, CreatureID, Basket)`：校验 `bOperating` 与货页可售、聚合现货 `ΣOnHand − ActiveReserved`、钱包 ≥ 整单锁价金额，以及 16 槽背包整单放置模拟；空间流程与经济流程不得各自实现半套门禁；
- 杂货可售量按**店铺范围**（主区域及其子区域链，口径见[库存与保质期 §2](/VoxelDesign/02-系统设计/AI决策系统-库存与保质期-系统设计.md)）内全部 `bForSale=true` 货车架聚合，预留只保存商品、数量与锁价，不绑定具体货架 / 堆叠，也不提前扣货或入包。买不起或放不下时允许缩篮子，减数量或放弃部分商品后重新校验；一件都无法预留才放弃购物；
- 顾客到收银台开始服务时，由收银业务入口创建 `Pending` 订单。收银先按 FIFO 生成实际源堆扣货计划及状态兼容的固定槽位放置计划，再由当前订单唯一 `CheckoutSale` 原子完成锁价全额转账、预留核销、实际扣货、保持实例状态的整单入包、所有权转移与销售流水；成功后订单转 `Completed`，任一必需步骤失败则转 `Failed / Cancelled`，整单不支付、不扣货、不部分入包并释放预留。源堆计划不回写预留，顾客 Pay 和员工 Cashier 不分别结算；
- 未付款放弃 / 中断 / 取消 / 失败、实际离店及退租经营终止时，关闭未完成 `Pending` 并释放整单预留；打烊先让店内已有锁价 / 收银排队 / 结账完成，再清理残余订单，不因接客灯灭提前取消。重新选品用新价；原子履约成功后无已付款未交货状态，不自动退款；
- 流水商品明细保存实际成交商品、数量、锁定单价与行金额，不能只记商品 Tag 而丢失历史成交价；
- 小费：店铺类型配置 bAllowTips；小费率 = f(本次满意度, NPC 慷慨个性)，满意才给。

### 2.4 店铺业务账与经营账户

V1 每个实际 / 抽象人物在创建时都有一个个人钱包和一个唯一经营账户，非经营者也有；其所有生意共享该经营账户。经营实体与区域都不另设资金账户或余额。店铺经营页按 `BusinessEntityId` 查询唯一流水，展示收入、支出、净额与按日聚合报表，流水保留商品明细、应付、小费、等待时长和时刻。

商圈 / 店铺 / 图外生意共享经营实体基础模型，注册于 Global `BusinessEntities`，并按类型组合模块。经营实体是经营资产与业务的唯一所有者，持产权 / 经营关系、营业意图 / 日程、目录 / 价格 / 订单 / 预留及声誉 / 客流；区域只持空间与校验，实际位置由经营实体区域组件关联 `AreaRef={SceneId,AreaId}`。子客房 / 仓库有空间ID但不是经营实体；抽象生意无实际区域且不造假区域。真实库存仍归家具 / 物品实例，FIFO队列与门锁仍归工作点 / 门实例，区域看板为不入档派生索引。详见[区域店铺与商圈管理 §2 / §9](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。

`BusinessEntityId` 是全局稳定经营 ID（GUID，规则见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)）；不再使用 `ShopId` 别名，也不能以 `Shop->GetAreaId()` 代替；Home / Work 与发生地点仍是空间引用。

- 自营 / 承租店：销售从消费者个人钱包进入经营人的经营账户，采购、工资等从该经营账户支出；
- 薪酬制店铺：资金责任人是产权人，销售收入进入产权人的唯一经营账户，授权经营支出也从该账户支付；受薪店长不能划转产权人的个人钱包或经营账户；
- 交易保存 `SourceBusinessEntityId / TargetBusinessEntityId` 表示源 / 目标业务归属，`OccurredAreaRef` 可空；租金是一笔唯一交易，源业务为 Shop、目标业务为 District。历史归属不随当前父关系回改，空间账仅作查询视图，不复制交易、不拆区域账户；
- 店铺产权通过经营隶属继承商圈产权人，不通过空间包含吞并租户资产。商圈易主只切换依赖产权人的资金链，自营 / 承租店的营收与工资不改，合同雇主经营实体不换；
- 初始顾客个人钱包由配置提供，不在本卷给数值。大多数NPC有图外真实工资合同，工资进入个人钱包；图外雇主为抽象账户（`bAbstract=true`，不计余额），支出直接发生、不补资（03A §5.9）。不按职业 / 阶层发兜底收入；失业且无其他实际收入时确实没钱。

**经营实体业务账没有独立划转页**，工资、租金、采购由对应业务方法写唯一流水；经营实体Owner / Manager按业务ID在统计页查询，实际AreaRef只作空间过滤，不给区域存业务账或权限镜像。资金展示读取责任人的唯一经营账户。账户所有人可在个人资产页对自己的个人钱包与唯一经营账户双向注资 / 提取，普通转出须源账户足额；个人之间付款只走双方个人钱包（[经营操作卷](/VoxelDesign/02-系统设计/AI决策系统-经营操作-系统设计.md) §3.7）。

### 2.5 工资

```
V1 只有固定月薪，不做班次底薪、工时工资或工单计件：
  完整月份应付 = MonthlySalary
  入职首月 / 离职末月应付 = MonthlySalary × 本月实际在职时长 ÷ 本月总时长
每个游戏月结束、进入下一月时，统一结算上一游戏月：
  在职覆盖完整月份 → 支付 MonthlySalary
  月中入职 → 按首月在职比例折算
  月中离职 → 不等月末，按当月在职比例立即结清，再移出有效雇佣登记
调薪立即修改 MonthlySalary；结算只读当前值，不保留旧薪分段、不追溯调薪前差额
从雇主业务解析出的经营账户原子转账到员工个人钱包：
  自营 / 承租店铺员工从经营人的经营账户发；薪酬制店铺、商圈雇员 / 薪酬制经营人从产权人的经营账户发
  到期总是足额支付，允许源经营账户扣负；不做余额校验、不部分支付
  MonthlySalary=0 → 跳过当次工资流水
不设置 bWageUnpaid、欠薪金额或补发状态，不需要员工之间的工资竞争排序
工资配置（MonthlySalary）与 HireTime 存于统一雇佣记录
```

V1 不开放薪资周期配置，后续根据实际体验再评估。完整月份内只要雇佣关系有效，月薪不因出勤班次、实际工时、临时关门或工单数量变化；`RewardAmount` 不作为员工工资来源。玩家作为商圈受薪经营人时按同一月末规则从商圈产权人经营账户向自己的个人钱包领取月薪，不以退出面板、切换自主状态或完成工单为条件。V1 沙盒标准合同中玩家经营人的 `MonthlySalary=0`：仍保留薪酬制雇佣记录与月末结算规则，但只跳过工资流水；普通员工工资不受影响。工资不足不再造成 Loyalty 持续下降或自动离职。

**余额规则（V1）**：消费、即时采购、个人之间付款与本人两类账户普通互转必须先验证源账户足额，失败则整笔不执行且不扣负；只有经营贷款月供、店铺租金和工资允许源经营账户扣负并直接足额执行。贷款不记逾期，租金不记欠租 / 坏账，工资不记未领薪。V1 移除公共设施与公共维护费，设施维护统一走员工维修工单，不按日扣维护费。后续其他费用不能默认继承扣负权限，必须单独加入业务白名单。

### 2.6 中断效果结算与原子支付边界（PartialSettle）

```
节点声明允许按进度结算的需求回填量、体验分等效果，可按已完成进度比例结算
```

该规则只作用于节点允许的效果与体验，不是通用商品付款规则。V1 `CheckoutSale` 不调用 `PartialSettle` 计算商品款：任一必需步骤失败都整笔不支付、不扣货、不入包并释放预留；成功才一次完成全部资金与所有权变更。后续可分次履约的收费服务如需比例支付，必须在自己的业务节点中单独定义，不得套用 V1 商品收银。体验分与负面记录是否追责店铺由归因决定（[NPC卷](/VoxelDesign/02-系统设计/AI决策系统-NPC个体与决策-系统设计.md) §2.5 打断处理 / 本文 §1.7）。

### 2.7 不支付但记差评的情形

排队超时离开不支付，但产生负面口碑记录（见 §1.6）。
