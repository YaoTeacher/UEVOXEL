## 1. 现有模型与系统边界

### 1.1 业态沿用区域类型配置

当前项目没有独立 `BusinessType` 配置体系，也不新增一套重复模型。**业态与区域类型是两个独立的分类维度**，各自是 Tag 命名空间：

- **区域类型**按「空间作用」分类（`Area.Type.*`）：表达这块空间是什么用途，管放置约束、父子规则、覆盖与准入；具体取值由区域类型配置资产维护，本文不固定。
- **业态**按「经营业务」分类（`Business.Kind.*`）：表达这门生意做什么，管必需设施、模块组合、消费流程与允许经营的品类；具体取值由业态配置资产维护，本文不固定。
- 两者可复用同一套配置行结构（现有 `FAreaTypeBase`）以减少重复模型，但**分类语义不合并**：一个区域类型不等于一个业态，一个业态也不绑定唯一区域类型。
- 经营实体保存所选**业态**引用；区域实例只保存**区域类型**，不承担业态身份，也不持经营状态镜像。
- V1 的杂货为一条业态配置行，具体 Tag 取值见 §「目标配置内容」，由配置资产定义。

商圈 / Shop / 图外生意共享经营实体基础模型、按类型组合模块，唯一登记于 Global `BusinessEntities`。经营实体持资产与业务、产权 / 经营关系、`bOpen` / 日程、目录 / 定价 / 订单 / 预留、声誉 / 客流；区域只空间与校验，实体区域组件关联 `AreaRef={SceneId,AreaId}`。客房 / 仓库子区域只有空间ID并关联已有主体，抽象生意无实际区域且不造假区域。真实库存、FIFO队列与门锁归对应实例，区域看板为不入档派生索引。

`BusinessEntityId` 是全局稳定经营 ID（GUID，规则见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)）；不再使用 `ShopId` 别名。业态静态配置不复制运行时营业、目录、库存或经营关系。详见[区域店铺与商圈管理 §2 / §9](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md)。

### 1.2 负责

- 类型 / 业态身份、显示名、描述与视觉信息；
- 父区域约束、建造权限、必需与禁用设施；
- 允许经营的商品品类；
- 在**人工开业**时按当前类型配置执行设施硬校验并返回缺失清单；**保存并退出建造只做非阻断提醒**（列出缺失清单，不阻止退出、不锁在建造模式）。营业时段切换与延长营业不重复校验，`bOperating` 只按 `bOpen` 与生效时段派生。

### 1.3 不负责

| 内容 | 正确归属 |
|---|---|
| 收银台 / 前台等实际服务点、队列绑定、排队站位 | 家具实例、区域运行时服务点与工作点队列配置（队列线 / 等待区） |
| 工单类型与工单生成 | 设施状态与服务流程节点；由工单索引器派生并维护区域看板 |
| 员工工种优先级 | Creature 上的劳动安排与人员页配置 |
| 仓库布局与实际库存 | 仓库子功能区、后备储物家具与可售货架实例 |
| 营业时间与营业状态 | 经营实体的日程与 `bOpen`；`bOperating`纯派生 |
| 装修与初始布局 | 经营实体资产归属与租约关联；V1玩家自由装修 |
| 实际上架商品、售价 | 店铺经营实体经营数据 |
| 补货阈值 | **店铺商品目录级**配置（含补货量）；经营操作按商品修改。**判定基数是全仓库合计**（货架+后备，不分 `bForSale`），不复制库存 |
| FlowConfig 节点编排 | 统一流程配置，按 `FlowTypeTag` 索引 |
| 活动玩法、评价权重、岗位定义 | 各自业务模块 |

## 2. 配置字段

### 2.1 沿用现有字段

| 字段 | 用途 |
|---|---|
| `AreaTypeId` | 现有数值标识，实施阶段按当前数据规则维护 |
| `AreaTypeTag` | 类型 / 业态的唯一 GameplayTag |
| `DisplayName` / `Description` | 显示与说明 |
| `bAbstract` | 沿用现有区域重叠许可语义，不改作类型层级判断 |
| `AssetFragment` | 图标等视觉配置 |
| `ForbiddenFurnitureType` | 禁止放置的家具型别 |
| `RequiredParentTypes` / `AllowedParentTypes` | 父区域约束 |
| `BuildLimit` | 建造权限 |

### 2.2 设施需求结构（已确认，待实施）

现有 `TArray<int> RequiredFurnitureType` 只能表达家具型别列表，不能完整表达“功能能力 + 参数条件 + 数量”。目标结构为：

```text
FacilityRequirement
├─ 功能片段类型
├─ 参数条件（可选，例如 Storage.ForSale = true）
└─ MinCount
```

规则：

- 校验读取店铺实际设施索引，不要求玩家使用某一个指定外观或资产。
- 同一功能片段的不同参数可形成不同要求，例如可售货架与普通储物柜不能混用。
- V1 杂货店两类必需设施的数量下限均为 1，作为**运行期提醒项**；货架与收银设施按家具能力检查；入口不进入任何检查。
- 原 `RequiredFurnitureType` 如何在实施时迁移到该结构，由后续架构与数据维护处理；本次不修改模型和实际资产。

### 2.3 允许经营品类（已确认，待实施）

业态配置增加“允许经营品类”集合，用物品既有品类 Tag 表达：

```text
AllowedProductCategoryTags = { ... }
```

它只约束该业态允许上架哪些商品：

- 不保存实际商品目录；
- 不保存价格、库存、补货阈值；
- 不决定 NPC 的需求或购买意愿；
- 不要求开店时自动生成商品或初始库存。

店铺经营实体只能从所引用业态允许品类中上架商品；目录与售价归实体，实际库存仍由实际空间内合法所属的后备储物家具 / 可售货架承载，区域不持业务镜像。

## 3. V1 杂货店配置

以下是**目标配置内容**，不是已经写入资产的记录：

| 配置项 | V1 杂货店 |
|---|---|
| 业态 Tag | `Business.Kind.*` 下的杂货业态行（具体取值由业态配置资产定义） |
| 必需区域类型 | 店铺空间类型（父类型为商圈范围类型） |
| 建造权限 | 允许玩家按当前区域权限创建 / 编辑 |
| 必需设施（**运行期提醒项，不是开业门槛**） | 可售存储能力 ≥1；收银台家具（`FCashierFuncFragment`）≥1 |
| 允许经营品类 | 食品、饮料 |
| 禁用设施 | V1 无额外业态级禁用清单 |
| 仓库要求 | 不强制独立仓库子功能区；后备储物是采购前置条件，不进入业态设施提醒项 |
| 活动 | V1 无 |

收银台通过 `FCashierFuncFragment` 识别，运行期提醒按收银台家具能力计数；`slot_staff_cashier` 属于家具内部的员工交互点，不另设检查项。顾客队列和 Cashier 工单不写入业态配置。入口不进入任何检查：无门、被墙封死或导航不可达都允许开业，NPC 进不来自然没有客流，只向玩家给出去重、带冷却的提醒。食品 / 饮料对应的实际物品 Tag 在后续消费链配置中确定。

## 4. 必需设施检查与运行期提醒

```text
读取店铺经营实体的业态配置引用
  → 经 ConfigDataSubsystem 找到当前业态配置
  → 读取 FacilityRequirement 列表
  → 经实体区域组件关联的实际空间查询设施功能片段、参数条件与数量
  → 汇总缺失项
  → 按调用场景处理：
       保存并退出建造：只列缺失清单作提示，不阻断退出、不锁模式
       人工开业：不校验，直接允许 bOpen = true
       营业中：按状态变化或周期检查，缺失时去重、带冷却提醒；不关店、不改 bOpen
       时段切换 / 延长营业：不调用设施校验，只由 bOpen 与当前有效时段派生 bOperating
```

- 人工开业**不做设施校验**，`bOpen` 直接可置（05 决策29，取代决策24 的硬校验部分）；时段切换与延长营业不调用检查，`bOperating=bOpen&&当前有效营业时段` 纯派生、不入档。
- 必需设施改为**运行期提醒项**：缺收银台、缺可售货架等由营业中的检查给出提示，不阻断开业、不系统关店；实际后果由服务自然劣化体现（结不了账、无货可卖）。建造退出只做非阻断提醒。
- 未选业态或找不到配置时**仍允许开业**，只给提醒；业态是运行期检查与消费流程的前提，不作准入闸门。
- 校验的是设施能力，不是服务点、队列或工单的配置完整性。
- 不硬校验员工和库存；缺员工、缺商品或货架无货按经营提醒与自然服务劣化处理。
- 不要求独立仓库。
- 设施运行期被拆除不系统关店、不修改 `bOpen` 或给 `bOperating` 增加设施条件；告警与服务失败按已有设施 / 消费规则处理，不新增安全机制或状态机。

## 5. 与流程、服务点和工单的关系

### 5.1 流程

`FlowConfig` 按 `FlowTypeTag` 统一索引，消费与工作共用流程模型。废弃“每店铺类型内嵌或独占一份 FlowConfig”的做法。业态配置不保存流程节点，也不负责选择具体队列实体。

### 5.2 服务点与工作点队列

- 家具提供实际服务能力、员工位、消费者位和排队槽位。
- 工作点可配置队列线或关联等待区；未配置时按空间规则自动生成默认队列线，不需要独立的排队区资产。
- `QueueAt(PointTag)` 只声明目标服务点语义，实际服务点、队列与站位在店铺运行时解析。
- 业态表中的“收银设施 ≥1”只是开业设施要求，不等于配置队列位置。

### 5.3 工单

- 设施状态跨阈、服务流程节点等产生事件；
- 工单索引器据业务状态派生 Work 意图并维护所属区域看板；
- 员工按自己的工种优先级与任务紧急度认领；
- 业态配置不声明该店能产生哪些工单，也不初始化员工优先级。

## 6. V1 范围

**做**：

- 沿用现有区域类型配置注册杂货业态；
- 设施需求结构的目标设计；
- 允许经营品类的目标设计；
- 人工开业的设施校验及缺失清单（保存并退出建造只做非阻断提醒）；
- 商品上架时按允许经营品类约束。

**不做**：

- 服务点 / 工作点队列 / 工单的业态级配置；
- 业态级营业时间、装修模板、仓库或实例商品目录；
- 每业态独占 FlowConfig；
- 活动玩法、评价权重、岗位定义、自动装修与自动进货。

**实施状态**：以上新增字段与杂货配置行目前仅为设计决议，后续另行修改数据模型和配置资产。
