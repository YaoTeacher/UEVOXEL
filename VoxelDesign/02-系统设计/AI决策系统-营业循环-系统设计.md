## 1. 系统边界

**负责**：
- 营业状态切换（营业时段 + 玩家手动经营意图）
- 打烊后消费收尾、无消费者离店与日结快照
- 手动开关门时的员工响应规则

**不负责**：
- 顾客消费流程（空间卷 §8）
- 员工排班与工单认领（[员工与工作执行](/VoxelDesign/02-系统设计/AI决策系统-员工与工作执行-系统设计.md)）
- 生成日报后的经营决策（[店主与商圈管理](/VoxelDesign/02-系统设计/AI决策系统-店主与商圈管理-系统设计.md)）
- 打烊后活动玩法（V1 不做，见 §6）

---

## 2. 一天的三段

```
开店前（Prep）—— V1 不做
营业中（Open）
  正常服务；缺货/脏污/故障继续走现有自动工单（不需要开店前备货）
打烊（Close）
  停止接客 → 已进入消费流程的顾客服务到完成 → 无消费行为的在场者引导离店
  内部工单继续；员工离开时机由自己的劳动安排决定
日结（固定时刻，全局）
  冻结当日账目 → 生成日报 → 触发店主经营决策循环
```

V1 只做**打烊与日结**：开店准备、盘点、备货清单不做；补货与清洁本来都是营业中的持续工单，不依赖开店准备。

## 3. 营业状态切换

### 3.0 状态字段

- **数据宿主**：营业意图与日程归 Global `BusinessEntities` 中的经营实体，而非区域。商圈 / 店铺 / 图外生意共享基础模型并按类型组合模块；区域只空间与校验，实体区域组件可关联 `AreaRef={SceneId,AreaId}`，抽象生意无实际区域且不造假区域。身份类型与分工见[总纲 §2.7](/VoxelDesign/02-系统设计/AI决策系统-系统设计.md)。Home / Work 仍空间，工作点 FIFO 与门锁在对应实例，区域看板为不入档派生索引。
- **`bOpen`（经营人的开业 / 停业意图）**：经营实体创建默认 false，只由开业、停业业务方法修改，并入档。创建 / 签约成功不等于开业；临时停业只改 `bOpen`。
- **`bOperating`（实际接客状态）**：纯派生值为 `bOpen && 当前处于有效营业时段`，不单独手动改写、不入档、不复检设施。`bOperating=true` 才允许新顾客进入消费；变为false不阻断店内已锁价预留、收银排队或结账的既有履约需求。
- **营业时段**：店铺经营实体保存 N 天 × 24 格，允许多段与跨夜，并入档；与劳动安排复用小时格结构，但语义独立，不能用排班代替接客开关。
- 开业**不校验任何设施**（05 决策29），也不做入口存在性或导航可达性校验，不查员工或库存。业态必需设施改为营业中的提醒项：缺失时给去重、带冷却的提示，不关店、不改 `bOpen`。NPC 找不到路就不来消费，同样只给提醒。

### 3.1 自动

时间系统推进到营业时段边界时，Shop经营实体按当前 `bOpen` 与有效 `BusinessSchedule` 纯派生 `bOperating`，并广播 `Shop.StateChanged`；时段变化本身不改 `bOpen`。延长营业形成的有效时段覆盖也参与同一派生，不另设手工运营状态。

员工与经营人的劳动安排独立于接客状态。营业时段变化不召回班次外人员，也不强制在场人员离店；清洁、补货、维修等内部工单是否执行由劳动者自己的排班权重与找活决策决定。

### 3.2 玩家手动覆盖

玩家通过开业 / 停业业务方法临时开门或关门，通过营业时段编辑、延长营业业务方法改变有效营业时段；UI 不直写 `bOperating` 或店铺业务数据。V1 不做班次外召回、加班合同、加班意愿或加班费。

**手动打烊 = `bOpen=false`**：只关闭经营意图，`bOperating` 随即按统一公式派生为 false。重新开业只把 `bOpen` 改为 true，是否立即接客仍取决于当前是否在有效营业时段内。停业期间雇佣关系、工资与租金规则不变，亏损由经营人承担。

**延长营业**只扩展有效营业时段，不能覆盖 `bOpen=false`；取消延长后恢复按普通营业时段派生。员工仍按自己的劳动安排行动，延长营业不自动召回人员或改变其排班。

### 3.3 打烊后的消费收尾与人员处理

`bOperating` 从 true 变为 false 时，店铺停止接客并广播 `Shop.StateChanged`：

1. 不再允许新顾客进店或加入新的消费队列；不得为新客产生接客需求，但可为店内既有锁价 / 收银排队顾客继续派生并执行履约工单。
2. **店内既有消费服务到完成**：已锁价预留、在店内收银排队或正在结账的顾客继续结账、拿货与离店，不得因打烊硬清场或中断收银原子段。Cashier / Serve需求保留到对应消费完成；工作点FIFO仍归实例，不复制到经营实体或区域。
3. **外部门口未进店队列清退**：这些顾客不属于店内收尾，按退出意图离队离开；本次白跑结束时只上报一次负满意度体验样本，写服务组声誉，不记来访 / 成交客群，不新增个人记忆或首客保护。
4. 店内无任何消费行为的在场者按 `Shop.ExitRequested` 引导离店。`ExitRequested` 只是意图，不能冒充实际离店事实；实际跨出店铺空间后才发布 `Presence.Exited`，空间在场、槽位、预留、工单认领、裁决与统计等订阅者分别处理自己的状态；门外未进店者不伪造一次进店 / 离店。
5. 清洁、补货、维修等内部工单继续保留并可执行。员工与经营人的离开时机由自己的劳动安排决定，打烊不统一强退、不取消内部工单。

店内消费流程结束或实际离店时，未完成的 `Pending` 订单按业务结果转为 `Completed / Failed / Cancelled`；失败、取消及离店清理释放预留并关闭订单，不能仅因打烊提前取消已有结账。店内继续履约不因打烊直接追责；门外未进店队列被清退的白跑按既定例外上报一次负满意度服务组样本，不计来访 / 成交客群。

## 4. 打烊

```
bOpen=false 或离开有效营业时段 → bOperating 派生为 false
→ 经营实体广播 Shop.StateChanged，拦截新顾客、新消费入队与新接客需求
→ 店内已锁价预留 / 收银排队 / 正在结账继续履约并实际离店
→ 门外未进店队列清退，白跑一次负满意度样本只进服务组声誉、不计来访成交
→ 店内无消费行为者接收 ExitRequested，实际越界后发布 Presence.Exited
→ 清洁 / 补货 / 维修等内部工单继续；员工与经营人按自己的劳动安排决定去留
```

固定月薪只在月末或离职时结算（见[员工与工作执行](/VoxelDesign/02-系统设计/AI决策系统-员工与工作执行-系统设计.md)），打烊不触发工资重算。未完成的内部工单不因打烊清空，也不要求保留到下一营业日才能认领；只要对应劳动者仍按其排班工作，就可继续认领与执行。

---

## 5. 日结

- **每日固定时刻统一执行**，与各店营业/打烊时间解耦；
- 内容：冻结当日账目 → 生成日报（收入/支出/客流/评价/缺货/维护）→ 重置日计数 → 触发店主经营决策循环；
- 日报是玩家面板与 NPC 店主决策的共同输入；固定月薪只在游戏月月末统一结算，不并入日结。

---

## 6. 打烊后活动（V1 不做）

不同业态可有打烊后活动（餐厅试菜、零售盘点、大扫除…）。这类内容是**独立玩法模块**，不是业态模板能定义的东西——例如试菜包含切菜熬汤的多步交互、邀请员工/好友/其他店主、评分与关系变化。

接口预留：

- 业态模板声明 `ActivityTags`（该业态可用活动 ID 列表）；
- 活动模块自行实现流程与结算，通过事件/关系/评价系统接入；
- V1 不实现任何活动模块。

---

## 7. 售后（V1 范围）

V1 售后只保留**声誉影响阶段**：服务失败/体验差 → 差评与声誉变化（沿用[店铺经营 §1](/VoxelDesign/02-系统设计/AI决策系统-店铺经营-系统设计.md)）。

完整售后（投诉入口、退款/免单/重做、协商）后续版本再做；届时以服务失败事件为入口，补偿走账本冲销与事件记录。
