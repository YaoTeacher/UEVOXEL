## 1. 系统上下文

### 1.1 系统边界

**AI 决策系统负责**：
- NPC 个体画像（社会阶层 / 品类消费意愿 / 期望带 / 店铺认知）的定义与生成规则
- NPC 日程系统（周节律模板 / 日历覆盖层 / 需求微观填补）与出场判定
- NPC 动机（Motivation）的生成与决策：消费决策走 Utility 加法核评分，工作决策走员工优先级表 × Priority 分带两层扫描
- 硬过滤漏斗（营业状态 → 认知 → 价格上限）
- 需求衰减驱动决策触发（纯事件驱动，无轮询）
- 道具/区域的功能（FunctionDef）与状态（FunctionState）管理
- 区域任务看板（TaskBoard）的任务推送、领取（租约制）、完成
- FActionJob 流程解释器（按 FBusinessFlowConfig 逐节点执行消费/工作流程）
- 评价体系（期望带模型）与口碑双层模型（个体记忆 / 店铺声誉）
- 经济循环对接（商品目录 / 店铺账本 / 工资 / 小费 / 按比例结算）
- 排队区系统（队列数据与物理站位分离、叫号制、等待区设施、队列引导工单）
- 员工体系（雇佣记录、工作优先级表、熟练度、员工状态需求、待机与偷懒、排班与交接、工单租约制）
- 店主决策系统（经营记录、性格驱动的低频经营决策循环）
- 招聘系统（人力市场 / 店主引入 / 熟人邀请）
- 店铺活动与知名度（FShopCampaign 标准活动模型、广告触达）
- 供应链（三通道货源、采购单、缺货后果链）
- 行为外化事件与玩家侧 NPC 档案
- SpawnArea 流量分布与出场映射
- 决策 LOD（三档分级）
- NPC 记忆复用现有事件系统的回闪与性格塑变
- 战斗模式的配置切换（同框架不同配置）

**AI 决策系统不负责**：
- NPC 身体组装与视觉重建（由 VoxelNpcBaseInstance 负责）
- 对象池生命周期管理（由 VoxelCreatureWorldSubsystem 负责，本系统只提供出场/回收判据）
- 生物数据生成（由 CreatureGeneratorUtils 负责）
- 导航寻路底层（由 NavigationSystem 负责）
- 区域数据管理（由 VoxelAreaWorldSubsystem 负责）
- 配置数据加载（由 ConfigDataSubsystem 负责）
- 时间/历法底层（由时间系统 VoxelTimeDataBase 负责，本系统只消费其周期与日历）
- 经营面板 UI 呈现（本系统只提供 FShopLedger / FShopReputation 数据源）
- 任务系统的可接取任务实现（突发状况只留"可转任务"的事件结构口子）
- 天气系统本体（只预留 WeatherMod 修饰器接口）
- 情报玩法机制（万事屋/侦探所等店铺核心玩法，只留玩家侧 NPC 档案记录）
- 行为外化的动画演出（只发 FExternalizeEvent，演出归动画系统）

### 1.2 外部依赖

**依赖的系统**：
- **UVoxelCreatureWorldSubsystem**：NPC 实例管理、生成与回收、对象池衔接 LiveTime
- **UVoxelAreaWorldSubsystem**：区域查询、位置查询、区域营业状态（EAreaStatus）、SpawnArea 查表
- **UConfigDataSubsystem**：事件资产、区域类型、评分配置、阶层基准配置表、特质修正表、AspectTag 维度表、TimeMod 时间窗、阵营关系表 DT_FactionRelations、熟练度定义表、店铺活动配置表、供应商目录等全部新配置表
- **UCreatureGeneratorUtils**：需求规则合并、事件解析逻辑（CheckAllConditions、ResolveEventOutcome、ApplyEventOutcome）、需求衰减 Tick（UpdateDynamicAttributes，含跨阈值事件发射）
- **UNavigationSystemV1**：寻路（ProximityAtten、IsPathReachable 预估、排队格动态高成本区）
- **UVoxelFunctionAreaComponent**：功能挂载点、任务看板归属、队列点/账本/声誉/订单队列/店铺活动/经营记录挂载
- **时间系统（VoxelTimeDataBase）**：昼夜时刻、周节律周期长度、日历（节日占位）

**被依赖的系统**：
- **AVoxelIntelligentCreatureInstance**：持有决策组件
- **ACreatureAIController**：执行移动指令
- **NPCUI 系统**：显示 NPC 当前动机与执行状态
- **经营面板 UI**：读取店铺账本与声誉数据
- **招聘界面 UI**：读取人力市场候选与雇佣记录
- **动画系统**：消费 FExternalizeEvent 做演出

### 1.3 输入输出

**输入**：
- NPC 需求当前值（FCreatureRuntimeState::Dynamics）
- NPC 个性数值（FCreatureSaveData::PersistentBasicValues）与特质（FTrueCreatureData::TraitTags）
- NPC 个体画像（SocialClass / ActivityWillingness / Expectations / KnownShopIds）
- NPC 日程（周节律模板 + 日历覆盖层）与当前 RoleContext
- NPC 记忆（LifeHistory + SocialMemories）
- 场景内所有道具/区域的 FunctionState、店铺经营数据（声誉 / 商品目录 / 订单队列 / 店铺活动）
- 所属区域的 FAreaTaskBoard 任务列表
- 外部事件（日程时段切换、代办日程触发、被攻击、强制指令）
- 评分器配置（UUtilityEvaluatorConfig DataAsset）
- SpawnArea 流量数据（FSpawnArea）
- 全局天气状态（接口预留）

**输出**：
- 当前 FMotivation 与 FActionJob 状态（含流程断点）
- 需求值回填（Consume / Pay 节点结算）
- 看板任务状态变更（领取 / 完成 / 租约释放）
- FunctionState 队列变更
- FExperienceReport → 店铺声誉滚动统计、个体履历（FLifeHistoryEntry）
- FTransactionRecord 流水写入店铺账本
- 性格塑变（长期记忆回闪）
- 行为外化事件（FExternalizeEvent）
- 采购单（FPurchaseOrder）与店铺活动投放（FShopCampaign）
- 店铺经营决策结果（BusinessSchedule 改写 / 逐商品调价 / 招聘需求）

## 2. 核心概念

### 2.1 基础概念（四层分离）

系统严格分离四个不同层次的概念，每个层次有明确的数据归属：

**功能（Function）—— 道具/区域的静态配置**
- 定义：可交互对象固有的"它能做什么"
- 数据：`FFunctionDef`
- 归属：写在道具/区域蓝图配置里，运行时不变
- 示例："这张床能让人睡觉，回填精神 60，单次 8 小时"

**状态（State）—— 道具/区域的运行时实例数据**
- 定义：当前这个具体实例的运行情况
- 数据：`FFunctionState`
- 归属：跟着实例走，与 Def 通过 FunctionID 配对
- 示例："这张床现在有 1 人在用，0 人排队"

**任务（Task）—— 区域级的工作分配**
- 定义：道具/子区域/消费流程上报的"需要在岗 NPC 来做的事"
- 数据：`FTaskItem`，归集到 `FAreaTaskBoard`
- 归属：每个区域一份看板，统一管理增删领取（租约制）
- 示例："3 号桌客人点了餐，需要服务员上菜，优先级 0.9"

**动机（Motivation）—— NPC 内部的决策结果**
- 定义：NPC 决策后产生的"我要做什么"
- 数据：`FMotivation`
- 归属：属于 NPC 自己
- 示例："去 5 号餐厅吧台吃饭"

### 2.2 NPC 个体数据模型

**角色是时段属性，不是身份属性**：员工/顾客是同一 NPC 在不同时段扮演的角色，不存在"员工 NPC 类"和"顾客 NPC 类"。

**FTrueCreatureData 扩展**：

| 字段 | 类型 | 说明 |
|------|------|------|
| SocialClass | FGameplayTag（Creature.SocialClass.Poor/Worker/Middle/Elite） | 社会阶层 |
| ActivityWillingness | TMap<需求Tag, float[0,2]> | 品类消费意愿 |
| Expectations | TMap<AspectTag, FExpectationBand{Min,Max}> | 评价尺子（见第 6 章） |
| KnownShopIds | TSet<int32> | 认知的店铺集合 |
| 收支统计字段 | （占位） | 供未来阶层漂移使用 |

**复用现有字段**：
- PersistentBasicValues（个性）
- TraitTags（爱好）
- LifeHistory + SocialMemories（记忆）

**HomeAreaID 语义定为"住所"**：
- 有家 → 出场从住所绑定的 SpawnArea 刷出（住所与 SpawnArea 的绑定见第 17 章；本市其他城区居民同样经住所绑定点通勤进图）
- 住店 → HomeAreaID = 被分配的客房子区域（子功能区，非旅店商铺本身），从该区域绑定的出场点刷出；长期租住旅店的冒险者等属此类，不算外来 NPC
- 定期来客 / 一次性游客（"外来 NPC" 专指此类）→ 从城门等 SpawnArea 直接出场，消费/停留后原路离图
- 以上皆无 → 不刷出
- 员工归属**不用** HomeAreaID，走雇佣记录（FEmploymentRecord，见 11.2）

**生成画像（NPC 生成时一次 roll 定，运行时只读）**：
```
阶层 / 意愿 / 期望 = 阶层基准配置表 + 个性/爱好修正 + 个体噪声(±0.1)
```
噪声必须存在：同阶层 NPC 的要求互不相同，这是"推测客人"玩法的信息量来源。

### 2.3 日程系统（三层叠加）

**第 1 层：周节律模板**
- 24 小时 × N 天的时段表，周期长度由时间系统配置（不绑定 7 天/30 天——幻想历法）
- 每格填活动意图：`Sleep` / `Duty`（参数=雇主店铺+岗位）/ `Free` / `Any`
- 由种族/职业模板生成 + 个体扰动
- 是**偏好层**不是强制脚本：需求可以压倒模板（如 RimWorld）

**第 2 层：日历覆盖层**
- 一次性代办日程：`FAppointment{触发(时间点或事件Tag), ActionTemplate, Deadline/GracePeriod, RelatedOrderId}`，覆盖当天模板
- **FAppointment 语义是"代办日程"（义务/待办事项），不是社交约会**——日程上挂着的一件待办，有触发条件（到点/事件）和期限。典型：定制订单下定金后休眠 → 订单完成事件唤醒 → 到店验货付尾款
- 逾期未办 = 超宽限期仍未完成（不称"爽约"）
- 节日/事件日整张替换模板（本版只留占位，后续版本实现）

**第 3 层：需求微观填补**
- 时段只决定"在哪、什么角色（RoleContext）"
- 具体行为由需求 + 决策产生

**出场规则（唯一刷新判据，事件驱动不轮询）**：
```
无激活时段         → 不在图 / 回收对象池（零计算）
有激活 + 不在图    → 按 2.2 出场点分层判据刷出（住所 / 客房子区域 / 城门 SpawnArea），通勤到目标
有激活 + 在图      → 切换 RoleContext，触发重决策
```

**RoleContext（时段角色上下文）**：

| RoleContext | 决策方式 |
|-------------|---------|
| Duty | 员工决策（优先级表 × Priority 分带两层扫描，见 5.4） |
| Free | 消费者决策（Utility 加法核，见 5.3） |
| Sleep | 居家低耗态 |

**RoleContext 延迟生效**：时段切换只打标记、不强制换脑——变更在当前 Job 自然结束时生效，仅 Critical 需求/外部强制事件可提前引爆重决策。消除"角色已切但还在干旧活"的状态分裂。

**饭点/高峰涌现设计**（不硬编码"几点吃饭"，靠参数对齐涌现）：
- 起床窗口对齐
- 饥饿衰减调参（起床后 4-5 小时过阈）
- TimeMod 饭点窗口加成
- 个体 ±30min 扰动

### 2.4 组合概念

**双源候选模型（按 RoleContext 分流）**
```
Duty 时段（员工决策）:
  候选 = 所属店铺看板 FTaskItem（工单）
  决策 = 员工优先级表 × Priority 分带两层扫描，不走评分公式

Free 时段（消费者决策）:
  候选 = 店铺/道具的 FunctionState + 店铺商品目录
  先过硬过滤漏斗（营业状态 → 认知 → 价格上限）
  决策 = Utility 加法核评分

两源不混合评分；Critical 个人需求在任意 RoleContext 下都优先
```

**任务上报机制**
```
道具/子区域/消费流程节点状态变化（事件驱动）
  ↓
更新自身 FFunctionState（如 bAvailable=false）
  ↓
向所属区域 TaskBoard.AddTask(FTaskItem)
  ↓
看板去重（同 SourceObject + 同 TaskType 只保留最高优先级）
  ↓
Duty 时段员工扫描到 FTaskItem
  ↓
ClaimTask → 标记 Locked + 获得租约（默认 X 秒，执行中自动续约）
  ↓
完成后 → CompleteTask → 移除任务，恢复 FunctionState
  ↓
（过期未续约 / NPC 回收 / 下班 / 死亡 → 租约释放，任务自动回 Unclaimed）
```

**FActionJob 流程解释器**
```
消费/工作流程不再写死固定阶段:
  FActionJob 加载目标店铺类型的 FBusinessFlowConfig
  逐节点（FFlowNode）执行: Browse / QueueAt / ClaimSeat / Order / Pay / Consume / ...
  每个节点内部 = 五原语段骨架（Goto/Acquire/Advance/Settle/Release，见 8.2）
流程实例可休眠持久化:
  中断于（节点 i, 原语段 j, 子进度 k）→ 持久化断点 → 事件唤醒后从断点恢复
  （典型：定制订单下定金后休眠，订单完成事件唤醒验货付尾款——一条代办日程）
```

**记忆与事件复用**
```
结算时（消费完成/工作完成/异常/负面体验）
  ↓
匹配对应 UCreatureEvent（复用现有事件资产）
  ↓
复用 UCreatureGeneratorUtils 的 CheckAllConditions / ResolveEventOutcome / ApplyEventOutcome
  ↓
追加 FLifeHistoryEntry 到 LifeHistory（不扩展字段，记忆附带店铺 ID = 认知来源之一）

定期回闪
  ↓
触发 UEventOutcome_Chain（复用现有 Outcome 类型）
  ↓
UEventOutcome_Instant::PersonalityShift（永久改性格）
```

### 2.5 行为概念

**决策触发模型**
```
事件驱动触发，无周期轮询:

需求衰减跨阈值（Urgent 或 Critical，由 UpdateDynamicAttributes 每秒 Tick 内做跨阈值检测后发射）
当前 Job 完成 / 失败 / 排队离队
日程时段切换（RoleContext 变化）
代办日程触发（到点 / 订单完成等事件 Tag）
区域看板新任务通知（Duty 时段）
外部事件（被攻击 / 强制指令）

不触发:
Execute 阶段 + 非 Critical 新需求 → 等当前节点完成
无激活时段 → NPC 不在图，零开销
```

**决策递归护栏**（事件驱动不失控的四条规则）：
```
1. 重决策请求一律进下一 Tick 决策队列：每 NPC 每 Tick 最多执行一次重决策，同 Tick 多触发源合并（优先级：Critical > 外部事件 > Job 状态 > 新需求），杜绝一帧内同步递归
2. 失败源冷却：Job 失败按原因分类（不可达 / 资源被占 / 破底放弃 / 外部打断），同需求同原因失败的候选写 FCandidateCooldown 降权
3. 连续失败计数器：任何节点成功完成或需求被回填即清零；达 N 次走兜底链（见 5.5）
4. 级联上限：单次触发链最多级联 3 次重决策，之后强制兜底——数学上保证收敛
```

**Critical 强制覆盖**
```
任一需求达到 Critical 阈值时:
- 员工决策: Critical 个人需求优先于一切工单，立即放下手上工作（无"做完再走"特例；被撂下的顾客由等待段机制接管，见下）
- 消费决策: 硬过滤的价格上限 ×1.5 放宽（饿极了贵的也吃）；MemoryMod 下限从 0.1 放宽到 0.3（恨意打折但不忘）
- 强制打断只发生在原语段边界（节点骨架见 8.2）：自驱段立即停并按 PartialSettle 比例结算；服务驱等待段直接离开、走放弃分支
- 员工被打断时手上工单按 bPausable 处理（11.7）：可暂停 → 进度留存；不可暂停 → 进度清零、租约释放、工单回 Unclaimed
```

**Execute 阶段重评估规则**
```
不重评估:
- 同一需求的其他候选（不换餐厅）
- Urgent 级别新需求（等当前节点完成）

强制打断:
- Critical 新需求（吃饭中途上厕所）
- 外部强制事件（被攻击/着火）

打断处理:
  ① PartialSettle 按比例部分回填需求、同比例支付、体验分按进度打折
  ② 释放当前预留资源
  ③ 流程类 Job 记录断点（节点 i + 原语段 j + 子进度 k，骨架见 8.2），可休眠持久化
  ④ 触发紧急决策
```

**服务等待段（统一等待模型，并入期望带）**
```
任何节点进入"阻塞等待外部服务"状态（排队前进 / 等工单履约）即开启等待段
（QueueAt 只是它在排队场景的标准实例，节点骨架见 8.2）:

  ① 等待体验值随时长衰减，减缓因子按场景配到节点:
     站排=等待区设施 Comfort；坐等上菜=用餐区 Luxury/Environment；引导员在岗减速（9.7）
  ② 跌破预警线（Expectations[Service].Min + 预警边距，节点可配）:
     → 触发投诉事件（19.5 口子）+ 外化事件（敲桌/看表/招手，16.2）
     → 关联工单 Priority 提升到紧急带（顾客催单自然插队，复用分带扫描）
     → 玩家/店主可介入安抚，消掉本次负面记录
  ③ 跌破 Expectations[Service].Min → 按承诺程度三分支放弃:
     未承诺（未下单未付钱）→ 离队/离店 + 轻负面记录（7.6）
     已承诺未支付 → 起身离店 + 按已履约部分 PartialSettle + 差评
       + 作废关联工单（半成品记库存损耗）；等买单阶段破底 = 跑单
     已支付（预付/定金）→ 离店 + 自动退款 + 差评（权重更高，店违约在先）
  ④ 放弃后写候选冷却（FCandidateCooldown）→ 触发重决策
  ⑤ 一次消费多段等待：Service 维度按时长加权平均上报 FExperienceReport；
     任何一段破底 → 本次消费 Service 单独记负面（服务失败主导评价）

估算等待统一入口（评分与等待中重估调同一函数）:
  估算等待 = WaitingQueue.Num() × UsageDuration / MaxConcurrency
  防蜂拥: 评分读队列长度用信息快照（低频刷新约 30s）+ 个体 ±20% 估算抖动
```

**角色统一性**
```
店员和顾客是同一 NPC 在不同时段的 RoleContext:
  Duty 时段: 员工决策（优先级表 × Priority 分带），雇佣记录决定雇主店铺
  Free 时段: 消费者决策（Utility 加法核评分）
  Sleep 时段: 居家低耗态
  Critical 个人需求: 任意时段都优先

无身份切换逻辑，时段切换即角色切换
```

**兜底行为链**
```
无高分消费候选 → 闲逛（Leisure 需求的合法满足途径，正常行为非异常）
连续 N 次候选失败 → 回家（居民）/ 离场（游客经 SpawnArea 离图）——防"鬼打墙"的总出口
全需求满足     → 回家（回居家态，可被对象池回收）

无"空闲超时"字段——兜底语义由 闲逛 → 回家/离场 链自然接管
```

## 3. 设计原则

### 3.1 架构原则

**四层概念严格分离**
- 功能（静态配置）/ 状态（运行时实例）/ 任务（区域级分配）/ 动机（NPC 决策结果）
- 每层有明确数据归属，不混淆

**硬过滤先于评分**
- 营业状态、认知、价格上限是绝对约束，不进评分公式
- 过滤不通过的候选直接出局，不参与打分

**消费/工作决策分流**
- RoleContext 决定算法：Duty 走优先级表 × Priority 分带（RimWorld 式），Free 走 Utility 加法核（Sims needs-based 结构，随机效用理论背书）
- 不按身份建系统——同一 NPC 时段切换即角色切换

**环境驱动**
- 道具/区域声明自己能做什么（FunctionDef）
- 状态变化主动上报任务（FTaskItem）到所属区域看板
- 消费流程节点按需抛工单（点餐 → AI.Work.Serve，退房 → AI.Work.Clean）
- NPC 只感知不判断——"这个对象能做什么"由对象声明

**决策与执行分离**
- 决策层只产出 FMotivation（"做什么、去哪做"）
- 执行层按 FBusinessFlowConfig 解释执行（"怎么一步步完成"）
- 两层解耦，决策不关心流程细节，执行不参与选择

**事件驱动决策**
- 无周期轮询，无定时刷新
- 需求衰减跨阈值才触发决策
- 日程时段切换 / 代办日程 / Job 状态变化才触发决策
- 无激活时段的 NPC 不在图，零开销

**认知与到访分工**
- 店铺活动/广告只负责把店铺写入 NPC 认知（KnownShopIds）
- 来不来由现有评分公式决定（好奇 = PersonalityMod 探索特质、声誉 = QualityScore），距离衰减自然筛选
- 广告没有"强制到访"特权

### 3.2 接口设计原则

**按需缩小候选范围**
- 哪个需求触发就只评该需求相关候选
- 硬过滤漏斗先砍掉出局候选，再进评分
- 空间优先级逐层扩展（当前区域 → 附近 → 全局），找到 N 个即停

**流程配置化**
- 消费流程不写死在代码里：FBusinessFlowConfig 每店铺类型一份（DataAsset）
- 节点类型集由代码各实现一次，编排完全交给配置
- 加新店铺类型 = 加一份 FlowConfig + 商品目录，零代码

**同一把尺**
- 排队：选店时的 QueueFactor 预估与入队后的忍耐实判，共用 Expectations[Service] 带
- 价格：选店硬过滤的价格上限与结账时的价格满意度，读同一份 Expectations[Price] 带
- 估算等待统一入口：评分与入队后重估调同一函数

**异步双机制解耦主流程**
- 店铺侧订单队列（FBillOrder，RimWorld 式 Bill）：生产与交付异步
- NPC 侧代办日程（FAppointment）：到点/事件触发后注入候选池参与评分，非强制

### 3.3 数据管理原则

**全复用现有数据模型**
- 需求系统：直接用 Dynamics + CachedDemandRules + DemandRule 系列
- 性格系统：直接用 PersistentBasicValues + TraitTags
- 事件系统：UCreatureEvent + UEventOutcomeBase 体系完全复用
- 履历系统：FLifeHistoryEntry 即记忆条目，不扩展字段
- 属性管线：熟练度与员工 BUFF 直接接入现有四层属性管线（FCreatureRuntimeState），不新建数值系统

**记忆即履历**
- 不新建记忆结构
- 复用 FLifeHistoryEntry，情感/关联目标等数据从 SourceEvent 的 Outcome 读取
- 记忆附带店铺 ID = 店铺认知来源之一
- 如需回闪运行时状态（如回闪次数），建独立轻量表用 EventId 索引，不污染履历本身

**需求与期望彻底分离**
- 需求 = 会衰减的驱动值（Dynamics / CachedDemandRules，不动）
- 期望 = 不衰减的评价基准线（Expectations，评价尺子）
- 需求驱动行为，期望评判体验——两套字段互不引用

**数据驱动配置**
- 评分曲线和权重在 UUtilityEvaluatorConfig DataAsset 配置
- 功能定义在道具/区域蓝图配置
- 事件和记忆结果在事件资产配置
- 阶层基准 / 特质修正 / AspectTag 维度 / TimeMod 窗口 / 熟练度公式 / 店铺活动 / 偷懒概率等全部由 ConfigDataSubsystem 承载

**全 Tag 化**
- 不引入新枚举来分类业务（旧 EDemandEnum 迁移到 Creature.Demand.* Tag）
- 需求类型用 Creature.Demand.* Tag
- 动作类型用 Creature.Action.* Tag
- 工作类型用 AI.Work.* Tag
- 社会阶层用 Creature.SocialClass.* Tag
- 评价维度用独立的 AspectTag 体系（与需求 Tag 解耦，各自演化）
- 店铺活动/雇佣角色/外化事件用 Campaign.* / Employment.Role.* / Externalize.* Tag
- 只有纯运行时状态机（如 EJobState、ERoleContext、EDecisionLOD）和代码固定实现的节点类型集（EFlowNodeType）保留 enum

### 3.4 性能原则

**零无效开销**
- 无激活时段的 NPC 不在图（回收对象池），零计算
- 没需求的 NPC 不决策
- Execute 阶段不重评估（除 Critical）
- 缺货信息不缓存，店内执行阶段直接查 FunctionState.bAvailable（候选过滤不查库存，见 5.1 认知边界）

**事件驱动非轮询**
- 需求突破阈值才触发，不是每帧检查
- 对象状态变化才推送看板，不是定时扫描
- 出场判定由日程时段切换事件驱动，不是轮询日程表

**固定槽位防爆炸**
- 看板任务支持去重 + 过期清理
- 候选数控制在 3-10 个

**长流程休眠**
- 跨时段/跨天的流程实例（如定制订单）休眠持久化，不占 Tick
- 事件唤醒后从断点恢复

**决策 LOD 分级**
- 事件驱动的基础上，按重要度对决策深度与频率分三档（见第 18 章）
- 玩家关注点（玩家店铺 / 熟人 / 被注视目标）始终全量计算

## 4. 系统约束

### 4.1 技术约束

**数据结构**
- 需求值：`TMap<FGameplayTag, float>`（Dynamics）
- 履历：`TArray<FLifeHistoryEntry>`（LifeHistory）
- 功能定义：`TArray<FFunctionDef>`（挂在组件上）
- 功能状态：`TArray<FFunctionState>`（与 Defs 通过 FunctionID 配对）
- 任务看板：`FAreaTaskBoard`（每个区域组件一份）
- 消费意愿：`TMap<FGameplayTag, float>`（ActivityWillingness，[0,2]）
- 期望带：`TMap<FGameplayTag, FExpectationBand>`（Expectations，AspectTag 索引）
- 店铺认知：`TSet<int32>`（KnownShopIds）
- 流程模板：`TArray<FFlowNode>`（FBusinessFlowConfig，每店铺类型一份）
- 雇佣记录：`FEmploymentRecord`（每雇佣关系一份）
- 店铺活动：`TArray<FShopCampaign>`（挂店铺区域组件）
- 采购单：`FPurchaseOrder`
- 地图切换点：`FSpawnArea`（区域配置）

**线程模型**
- 需求衰减：游戏线程 Tick（每秒，含跨阈值检测发射）
- 决策触发：游戏线程事件回调
- 寻路：NavigationSystem 异步

**事件系统集成**
- 运行时事件触发完全复用 GenerateBackstory 的候选筛选逻辑
- 记忆回闪复用 UEventOutcome_Chain 机制
- 性格塑变复用 UEventOutcome_Instant::PersonalityShift
- 行为外化事件与突发状况事件复用 UCreatureEvent 事件总线

### 4.2 性能约束

**决策开销**
- 每次决策只评触发需求相关候选（非全量）
- 候选数控制在 3-10 个
- 评分计算为纯数值运算，无 I/O
- LOD 1/2 档位降低决策深度与频率（见第 18 章）

**执行开销**
- 节点内移动调用 AIController 异步寻路
- 执行类节点按 DeltaTime 推进 Progress，无密集计算
- 结算节点一次性回填，无重复计算
- 休眠流程不占 Tick

**任务推送开销**
- 仅状态变化时推送，非每帧
- 看板去重避免重复任务
- 过期清理与租约到期回收释放内存

### 4.3 设计约束

**Execute 阶段约束**
- 仅 Critical 新需求可打断
- 同一需求的其他候选绝不换
- 打断时按 PartialSettle 比例结算；流程类 Job 记录断点，可休眠恢复

**角色约束**
- 角色是时段属性：不为员工和顾客分别建决策系统
- Duty 走优先级表 × Priority 分带两层扫描、Free 走 Utility 评分，由 RoleContext 分流
- 员工归属走雇佣记录，不用 HomeAreaID

**战斗模式约束**
- 不新建独立战斗 AI 系统
- 同一评分框架，加载 Combat 配置
- 通过 BehaviorContext 切换

**经济约束**
- NPC 无钱包余额：消费意愿模型替代支付能力，收支只记统计
- 定价粒度 = 单个商品（FShopProduct.Price 逐商品定价），禁止"调价系数"概念
- 店铺账本余额动用权限 = 仅玩家主角色

**Tag 化约束**
- 决策层数据完全 Tag 化
- 不引入新枚举来分类业务概念
- 仅纯运行时状态机与代码固定实现的节点类型集用 enum

## 5. 决策架构（三段式）

RoleContext 把 NPC 的决策分流为三段：Duty → 员工决策（5.4），Free → 消费者决策（5.3），Sleep → 居家低耗态。消费决策在评分前先过硬过滤漏斗（5.1）。

### 5.1 硬过滤漏斗（绝对约束，不进评分）

**认知边界（NPC 信息可得性规则）**：
- 远程可知：店铺类型 / 价位档（模糊消费水平，由声誉与记忆推算）/ 营业状态 / 队列长度（QueueFactor 预估依据）
- 到店才知：具体商品目录 / 实时库存 / 精确价格（在 Browse 节点揭示，见 8.6）

```
① 营业状态: EAreaStatus = 运营中 的店铺才可选
   （FunctionState.bAvailable 管店内具体功能点，不管整店）
        ↓
② 认知: KnownShopIds 命中（NPC 不知道这家店就不会去）
        ↓
③ 价位档: 店铺价位档 ≤ Expectations[Aspect.Price].Max
   （按 NPC 对该店的模糊认知判定；Critical 需求时上限 ×1.5 放宽；
     期望带方向倒置时此处过滤下限，见 6.1 Direction）
        ↓
【占位】节日/信仰/禁忌: 未来按其语义逐个定性为过滤或因子后接入，本版不实现
```

### 5.2 认知增长机制

NPC 的 KnownShopIds 通过四条途径增长：
- **路过发现**：店铺知名度半径 × 招牌等级决定被发现半径；认知写入与"NPC 是否在图"解耦——图内路过真实感知，图外按流量池抽象结算（同指路牌双层感知，见 14.3）
- **口碑记忆**：个体记忆附带店铺 ID（体验过的店自然进入认知）
- **开局老店预设**：世界生成时老牌店铺直接写入附近居民认知
- **广告触达**：店铺活动 Reach 效果每日触达人群，按转化率直接写入（见第 14 章）

```
知名度 = 基础声誉 × 招牌等级系数 → 决定被发现半径
```

深巷设定下的关键分工：路过发现依赖"有人经过"，深巷店铺没有过路流量，必须靠广告触达写入认知；认知之后的到访与留存交给评分公式（见 3.1 认知与到访分工）。

### 5.3 消费决策（Utility 加法核评分）

Sims needs-based AI 结构，随机效用理论背书：

```
FinalScore = ( w₁·NeedScore + w₂·QualityScore + w₃·WillingnessScore )   ← 加法核，可互相补偿
           × ProximityAtten × QueueFactor                                ← 衰减器 [0,1]
           × PersonalityMod × DutyMod × TimeMod × WeatherMod
           × MemoryMod × ClienteleMod                                    ← 修饰器（中性 1.0，[0.1,2.0]）
```

**加法核**（可互相补偿——便宜能补远，急需能补次）：

| 分量 | 输入 | 说明 |
|------|------|------|
| NeedScore | 需求当前值 + 阈值 | 沿用需求衰减曲线差值（非线性衰减，越低越急） |
| QualityScore | 功能品质 × 店铺有效声誉 | 有效声誉见第 7 章（贝叶斯收缩）；**纯店铺层统计，个体记忆不掺入**（个体偏差唯一入口是 MemoryMod，见 7.5） |
| WillingnessScore | 品类意愿 × 价格在期望带内位置 | 意愿 [0,2]，价格位置读 Expectations[Price] 带 |

**衰减器 [0,1]**：

| 因子 | 输入 | 说明 |
|------|------|------|
| ProximityAtten | 路径距离 | 距离衰减，**柔性曲线（如 1/(1+d/k)，永不为零）**——"远"是"不太愿意"而非"绝不"，加法核允许急需补偿；不可达在硬过滤/候选收集阶段已剔除 |
| QueueFactor | 估算等待 vs Expectations[Service] 底线 | 预估排队压力；估算等待 = WaitingQueue.Num() × UsageDuration / MaxConcurrency（与等待段实判调同一函数）；读信息快照（低频刷新）+ 个体 ±20% 估算抖动，防蜂拥 |

**修饰器（中性 1.0，范围 [0.1,2.0]）**：

| 因子 | 输入 | 说明 |
|------|------|------|
| PersonalityMod | 个性维度 + 特质 | 贪婪→奢饰品偏好，探索→陌生店偏好（好奇）等 |
| DutyMod | 当前 RoleContext | Duty 时段的消费候选打折扣（配置） |
| TimeMod | 当前游戏时间 + ActionTag | 深夜睡眠加成 / 饭点餐饮加成 |
| WeatherMod | 全局天气状态 | 接口预留（见 17.5），本版恒 = 1.0 |
| MemoryMod | LifeHistory 中相关记忆（个体偏差唯一入口，见 7.5） | 1.0 + Σ(Emotion × Importance × 时效衰减)，Clamp [0.1, 2.0]；Critical 需求时下限放宽到 0.3 |
| ClienteleMod | 店铺客群阵营统计 | 近期顾客 FactionTag 分布滚动统计：本阵营高 → >1，对立阵营高 → <1；DT_FactionRelations 配置；样本不足 = 1.0 |

**选择器**：
```
1. 过滤 FinalScore = 0 的候选
2. 排序降序
3. 最高分 < MinActionThreshold → 兜底闲逛
4. Top-3 按分数加权随机（≈softmax，避免挤同店）
5. 输出选中候选 → 生成 FMotivation
```

### 5.4 工作决策（员工，优先级表 × 任务分带两层扫描）

RimWorld 式两层模型：员工侧工作优先级表（意愿）× 任务侧 Priority 分带（紧急度），**不走评分公式**：

**员工工作优先级表**（FEmploymentRecord.WorkPriorities）：
```
TMap<AI.Work.* Tag, uint8>，取值 0-4:
  0 = 禁止（绝不干，如怕火的员工禁灭火）
  1-3 = 普通偏好梯度
  4 = 灭火级（有活就抢着干）
"岗位"概念由优先级表吸收：招聘时按岗位给预设模板，玩家之后可逐格调整
```

**扫描流程**：
```
① Critical 个人需求优先（先去吃饭/上厕所）
② 按员工优先级从高到低遍历工种（优先级 0 的工种跳过）
③ 该工种看板有可领工单 → 进入（工种内按任务侧 Priority 分带: 紧急 → 常规 → 低优）
④ 同带 tie-break: 就近 + 先到先得
⑤ 全表扫完无工单 → 待机状态（待机/偷懒分流见 11.6）
```

交接约束（详见 11.7，含工单可暂停/不可暂停分带）：
- 不可暂停工单做完才离岗；可暂停工单下班时进度随工单留存、下一班可换人续做
- 临近下班只认领"预估工期 ≤ 剩余班次时间"的不可暂停工单（班次末尾"只接小活"是自然涌现）
- 无人接的工单留在看板

### 5.5 兜底行为链

```
无高分消费候选 → 闲逛（Leisure 需求的合法满足途径，正常行为非异常）
                ↓
连续 N 次候选失败 / 闲逛需求已回填 → 回家（居民）/ 离场（游客）——防"鬼打墙"的总出口（连续失败计数器重置条件见 2.5 递归护栏③）
                ↓
全需求满足     → 回家（回居家态，可被对象池回收）
```

无"空闲超时"字段，兜底语义由该链自然接管。同一店铺当日由 FCandidateCooldown 防立刻重选，跨日由个体记忆抑制复购（排队离队写入的记忆权重低于完整消费差评，见 7.6/19.4）。

## 6. 评价体系：期望带模型（SERVQUAL 期望差）

**需求驱动行为、期望评判体验——两套字段彻底分离。** 需求是会衰减的驱动值（Dynamics，不动）；期望是不衰减的评价基准线（Expectations，评价尺子）。

### 6.1 期望带

`FExpectationBand{Min, Max, Direction}`：每个评价维度一个满意带。

- Direction: `HigherBetter`（默认，体验值越高越好）/ `LowerBetter`（如常人对价格：越便宜越好）
- 方向与带值由生成画像时特质修正写入，运行时决策代码零分支。例："势利"特质把 Price 翻成 HigherBetter + 高 Min（太便宜 = 破底线，硬过滤③随之变为价格下限）；"异食癖"把 Environment 翻转（越脏体验越高）
- 特殊服务需求同理：特质可向 NPC 的 Expectations 增加非常规 AspectTag 维度，店铺侧能产出该维度体验值即闭环

AspectTag 维度集：`Service / Quality / Luxury / Environment / Price`。加维度 = 配置加行，零代码。

### 6.2 体验报告

`FExperienceReport{Aspects: TMap<AspectTag, 体验值[0,1]>}`：由消费流程节点产出。

| 节点 | 上报维度 |
|------|---------|
| QueueAt | 服务速度（Service） |
| Consume | 品质（Quality） |
| （店铺装修/卫生/拥挤注入） | Luxury、Environment |
| Pay | 实际价格（Price） |

### 6.3 单维度满意度

```
HigherBetter 维度:
  单维度满意度 = MapTo[-1,+1](体验值, Min, Max)
    体验值 < Min → 负分（破底线）
    体验值 > Max → 封顶 +1（过满分线不再加分）

LowerBetter 维度（如常人对价格）:
  单维度满意度 = (Max − 体验值) / (Max − Min)
    体验值 > Max → 负分；< Min → 封顶 +1
```

### 6.4 综合满意度

```
综合满意度 = Σ(满意度ᵢ × 在意度ᵢ) / Σ在意度ᵢ
```

在意度 = 底线值：HigherBetter 维度取 Min（底线高 = 在意）；LowerBetter 维度取归一化上限的反向位置 (1 − Max_norm)（价格上限压越低 = 对价格越敏感）。天然加权，免配权重表。

### 6.5 带宽即性格

- 挑剔贵客 = 高底线 + 窄带（难伺候）
- 随和顾客 = 低底线 + 宽带（好打发）

带宽与底线都来自生成画像（阶层基准 + 个性修正 + 个体噪声），无需单独的性格→忍耐映射。

### 6.6 关键一致性

选店硬过滤的"价位档"与结账评价的"价格满意度"读**同一份** Expectations[Price] 带——价位档超上限的店不去（精确价格到店 Browse 才揭示，见 5.1 认知边界），贴上线的店打分低。同一把尺，无两套价格逻辑。

### 6.7 等待忍耐并入（服务等待段）

- 所有"阻塞等待外部服务"统一走等待段模型（定义见 2.5，节点骨架见 8.2）：等待体验值随时长下降，减缓因子按场景（等待区设施/用餐环境/引导员）
- 预警档：跌破预警线 → 投诉事件 + 外化 + 关联工单提带，玩家/店主可安抚消负面
- 跌破 Expectations[Service].Min → 按承诺程度三分支放弃（2.5）
- 选店时 QueueFactor 用"估算等待 vs Service 底线"预估——预估与实判同一把尺

### 6.8 漂移接口预留

期望带 Min/Max 可向体验值缓移（期望被现实驯化/由奢入俭难），首版关闭，但漂移字段（方向/速率/边界）首版即定死进 FExpectationBand 数据结构，第二阶段启用——避免届时改存档结构。

## 7. 口碑双层模型

### 7.1 个体层

综合满意度 → 写个体记忆（FLifeHistoryEntry 情感化，复用现有事件体系）：
- MemoryMod 影响自己的复购评分
- 记忆附带店铺 ID = 店铺认知来源之一

### 7.2 店铺层

`FShopReputation`（挂店铺经营数据）：

| 字段 | 说明 |
|------|------|
| RollingScore | 滚动窗口均值 |
| SampleCount | 样本数 |
| StarRating | 0-5 星（对外展示） |
| 分维度细分 | 按 AspectTag 拆分统计 |

### 7.3 有效声誉（贝叶斯收缩）

```
有效声誉 = (RollingScore × SampleCount + 中性先验 × 收缩强度) / (SampleCount + 收缩强度)
```

新店不会被两条差评打死；样本越多，观测均值越主导。

### 7.4 声誉传导

有效声誉是四条通路的输入：
- QualityScore（选店评分）
- 知名度半径（认知发现，见 5.2）
- 高声誉 → 精英阶层 WillingnessScore 加成
- 经营面板 UI 数据源

### 7.5 个体偏差

有效声誉是**店铺层纯统计**，不掺个体记忆。个体偏差的唯一入口是评分修饰器 MemoryMod（5.3/19.4）——同一家店，不同人因 MemoryMod 不同而打出不同的分。双层模型各司其职：店铺层管传播（QualityScore / 知名度半径），个体层管复购（MemoryMod）。

### 7.6 负面记录入口

以下情况也产生负面评价记录（不只消费完成后才评价）：
- 排队超时离开
- 被门禁拒绝（满员拒入队等）
- 进店发现买不起 / 想买的缺货（Browse 揭示真实价格与库存后离店，见 8.6）
- 投诉未处理（突发状况自然消散的落地结果，见 19.5）

未完成消费的负面记录（离队/拒入/离店）重要性权重显著低于完整消费差评——只抑制短期复选，不长期压制 MemoryMod（19.4）。

### 7.7 不做

NPC 间实时口口相传模拟——数据结构已留（SocialMemories），后续版本再接。情报集散地是剧情概念，玩法载体（万事屋/侦探所等）后续按店铺核心玩法单独设计，本系统只留玩家侧 NPC 档案记录（见 16.4）。

## 8. 消费流程：业务模板配置化

### 8.1 流程模板

`FBusinessFlowConfig`（每店铺类型一份，DataAsset）：`FlowNodes` 有序节点列表。

`FFlowNode{NodeType, Params, LocationHint, OnFail}`：
- OnFail 策略：放弃 / 重试 / 跳节点
- 等待段参数（配在节点上，仅服务驱 Advance 生效）：衰减率 / 减缓来源（AspectTag 或设施）/ 预警边距；放弃分支由流程上下文自动推导（当前节点在 Pay 之前还是之后、PayTiming），零手配

**节点类型集**（代码各实现一次，编排靠配置）：

| 节点 | 职责 |
|------|------|
| Browse | 进店浏览商品目录 |
| QueueAt(PointTag, QueuePolicy) | 到指定服务点排队 |
| ClaimSeat | 找座位 |
| Order | 下单（抛对应工单） |
| Pay(时机) | 支付；时机：预付 / 定金 / 尾款 / 日结 / 月结 / 离店结 |
| Consume | 消费回填需求（支持子进度序列：多品项逐道"等待→食用"） |
| AcquireResource | 拿货/取资源 |
| Release | 释放占用（座位/房间等） |

### 8.2 FActionJob = 流程解释器与节点骨架

- 加载目标店铺类型的 FlowConfig，逐节点执行
- **每个节点内部是同一条五原语段流水线**：① Goto（移动到 LocationHint）→ ② Acquire（占用资源：锁座位/占队列位/预留商品）→ ③ Advance（推进节点进度，核心段）→ ④ Settle（计价/回填需求/体验上报/抛工单）→ ⑤ Release（释放占用）；各段可跳过，节点类型 = 骨架的不同填充组合
- **Advance 只有两种驱动方式**：自驱（NPC 自己做事，进度随时间推进，速率受属性修正）/ 服务驱（等外部交付推进：服务点空位、工单履约、叫号）；**等待段只挂在服务驱期间**（2.5）——排队与等上菜是同一个逻辑
- **多品项由 Advance 子进度序列承载**（非新节点类型）：如 Consume 的品项清单按"等菜 i（服务驱）→ 吃菜 i（自驱）"交替推进，节点完成 = 子进度全部完成
- 流程实例可休眠持久化：断点 = (节点 i, 原语段 j, 子进度 k)，事件唤醒后从断点恢复

### 8.3 典型编排

| 店铺类型 | FlowNodes 编排 |
|---------|---------------|
| 餐厅 | 门口等位 → 找桌位 → 点餐(抛 Serve 工单，N 品项一单) → 逐道等菜/吃(Consume 子进度) → 等买单 → 离店结账 |
| 装备现货 | (满员时门口排队) → 选品 → (橱窗并发受限才排队) → 收银台排队 → 付全款 → 拿货 |
| 装备定制 | 下定金+交材料 → 流程休眠+代办日程入 Agenda → 订单完成事件唤醒 → 验货付尾款 |
| 旅店 | 前台排队 → 付款(日/月/全) → 房客登记(HomeAreaID=旅店) → 居住 → 到期退房 |

注：店门容量 = 并发数为 MaxUser 的服务点——"满员"就是门口等待段的排队/破底，不需要独立的满员拒入队配置。

### 8.4 异步双机制

**店铺侧订单队列 Bill Queue（RimWorld 式）**：
`FBillOrder{商品, 材料需求, 工期, 客户ID, 已付定金, 交付期限, 优先级}` 挂店铺生产队列；店主可排序插单；员工认领生产；完成 → 可交付 → 通知客户事件。

**NPC 侧代办日程 Appointment**：
FAppointment 语义是代办日程（义务/待办，非社交约会）。到点/事件触发 → 注入候选池参与评分（非强制，可逾期未办），并携带**临期权重斜坡**：`AppointmentBoost = 基础加成 × (1 + 已耗时长/总期限 × K)`——越临近截止加成越高，宽限期过半后足以压过普通需求（"最后一刻赶去取货"自然涌现）；超宽限期 → 违约结算：定金没收 + 差评 + 订单取消。

**玩家委托 = FAppointment 的一种来源**：玩家对 NPC 的指派/委托统一走代办日程通道——Duty 员工的店内工单指派 = 扫描时置顶（雇主指令强制力最高，见 11.9）；Free 时段 NPC 的委托（办事、外派探索采集经 SpawnArea 出城，见 15.2/17.2）= 注入 Appointment 按关系度评估接受。店内工单只是指派的最低级形态，外出任务与剧情任务同一通道，不新增机制。

### 8.5 流程节点抛工单（与员工解耦的关键）

| 触发 | 抛出工单 |
|------|---------|
| Order(点餐) | AI.Work.Serve |
| Order(定制) | AI.Work.Craft |
| 退房 | AI.Work.Clean |
| 现货拿走，库存低于阈值 | AI.Work.Restock |

顾客流程不直接调用员工，只往看板抛工单；员工按优先级表 × Priority 分带认领——两侧完全解耦。

### 8.6 店内选品逻辑

```
进店读商品目录（认知边界：真实价格与库存在此揭示，见 5.1）
  → 过滤: 满足当前需求Tag 且有货 且 Price 在 Expectations[Price] 期望带内
  → 按 回填量(SatisfactionAmount) × WillingnessScore 选一项
  → 无承受带内商品（缺货 / 真实价格超带）→ 离店 + 轻微负面记录（见 7.6）
```

### 8.7 组团消费

几个 NPC 结伴消费（与代办日程是不同概念：代办日程是义务/待办，组团是社交结伴）：

```
发起: 某 NPC 产生消费需求 + 有社交意愿
      → 从 SocialMemories 里挑亲密度高的同伴发起邀请
成团: 每个被邀者独立评估（当前需求 + 时段是否 Free + 对发起者亲密度）
      → 接受者入团，拒绝者不去（团可大可小，1 人也成立 = 单独消费）
选店: 发起者跑一遍正常评分选候选
      → 同伴对候选有否决权（该店对自己评分过低 → 退出团）
      → 剩下的成员同行
执行: 同店同流程，座位/排队按团整体处理
      → 消费中触发社交互动（聊天/拼桌），回填 Social/Leisure 需求

互斥: 处于"已发起待响应 / 受邀评估中 / 已在团"状态的 NPC 不发起新邀请、不响应新邀请（组团状态锁）
退团: 同伴否决退出 → 对该店写短期候选冷却（防止退团后自己又评出同店走回去）
```

收益：涌现"朋友聚餐"场面；社交需求有了合法满足途径；团内成员互相影响对店的记忆（口碑载体）。

### 8.8 等待社交

服务驱等待段期间，NPC 可与邻近 NPC 概率触发互动配置池（Social 需求的合法满足途径之一；等待场景天然是观察热点，外化素材密度与玩家注意力对齐）：

| 互动 | 条件 | 效果 |
|------|------|------|
| 闲聊 | 任意两 NPC 邻近 | 双方 Social 回填 + 等待体验衰减减缓（聊天让等待不那么难熬）+ 外化 |
| 熟人打招呼 | 双方有 SocialMemory | Affinity+，影响组团邀请成功率（8.7 闭环） |
| 拼桌 | 餐厅满座且双方都等位 | 合并座位 + 社交回填 + 关系变化 |
| 抱怨队伍 | 等待体验值已较低 | 双方 Mood 微升（宣泄），但对店记忆微降——负面情绪会传染，排队区怨气是真实经营风险 |

## 9. 排队区系统

### 9.1 数据/物理分离

- `FFunctionState.WaitingQueue` 记队列顺序（谁排第几）
- `FQueueArea.QueueSlots` 记物理站位（站哪一格）
- 队首在前：第 i 位 → Slots[i]；前进 = 整体顺移，走导航不瞬移

### 9.2 队列绑定服务点，不绑定店铺

`FQueuePoint{PointTag(门口/收银台/取餐口/前台…), QueuePolicy(站位排|叫号制), Line, Comfort}`

一个店铺可多服务点、多队列；QueueAt 节点参数 = PointTag。QueueAt 不是特殊节点，是"Advance 服务驱 + 等待段"在排队场景的标准实例（见 8.2）。

### 9.3 排队位三级来源

1. **玩家划定排队区**：建造域画区对象，挂店铺；格位按距服务点由近及远蛇形排序成 Slots；区内放座椅/遮阳/娱乐 = 装修等待区
2. **排队桩家具**：逐个摆放，放置顺序 = 队列顺序
3. **门口自动排队线兜底**：无玩家设计时，沿可达方向自动延伸 N 格

### 9.4 动线影响

排队格对其他 NPC 的导航标记为动态高成本区——队伍挡路会迫使绕行。排队区选址是玩家的动线设计环节。

### 9.5 叫号制

```
取号入队（不占站位格）
  → 等待区坐着 / 附近活动
  → Release 事件叫号 → 走到服务点
  → 过号超时 → 跳过重排 + 轻微差评
```

### 9.6 等待区设施

有座 / 遮阳 / 娱乐 → Service 维度等待体验扣分减缓。**装修等待区 = 购买顾客忍耐度**（FQueuePoint.Comfort 汇总设施加成）。

### 9.7 队列引导

队长超引导阈值 → 自动抛 AI.Work.Guide 工单 → 引导员到岗后：
1. 队中顾客等待不满累积减速
2. 沿队列预登记（提前完成 Order 节点）→ 服务点吞吐提升

### 9.8 阈值配置

- 引导阈值（队长超过则抛 Guide 工单）
- 服务点并发数（店门容量即门口服务点并发数；满员 = 门口等待段排队或破底）
- 个体忍耐（服务等待段模型，见 2.5/6.7）

### 9.9 不做

插队、黄牛、付费优先队列（QueuePolicy 留扩展位）、排队社交（组团消费的消费中社交另见 8.7）。

## 10. 经济循环

### 10.1 NPC 无钱包余额

消费意愿模型替代支付能力：NPC 能不能消费由 WillingnessScore + 期望带决定，不查余额。收支只记统计（占位字段，供未来阶层漂移）。

### 10.2 商品目录

`FShopProduct{ProductTag, LinkedItemId(可选实物), Price, SatisfyDemandTag+SatisfactionAmount, Quality}`

- 定价粒度 = 单个商品：Price 逐商品定价，默认 = 物品基准价
- **禁止"调价系数"概念**

### 10.3 支付

- Pay 节点按商品明细逐项计价
- 小费：店铺类型配置 bAllowTips；小费率 = f(本次满意度, NPC 慷慨个性)，满意才给

### 10.4 店铺账本

`FShopLedger`（挂店铺区域）：余额 + 流水（`FTransactionRecord{NPC, 商品明细, 应付, 小费, 等待时长, 时刻}`）+ 按日聚合报表。

余额动用权限 = **仅玩家主角色**（GetMainCharacterId() 校验；玩家扮演的店员/店主角色只能做业务操作，不能动账）。

### 10.5 工资

```
工资 = 出勤底薪（班次结束结算）+ 工单计件（RewardAmount 完成即发）
从店铺 Ledger 扣，允许负余额记账（后果系统后续版本接）
工资配置（底薪/计件系数）存于雇佣记录（FEmploymentRecord.WageConfig），招聘议价时确定
```

### 10.6 中断按比例结算（PartialSettle）

```
回填量 = SatisfactionAmount × Progress
支付   = 应付 × Progress
体验分 = 按进度打折
```

### 10.7 不支付但记差评的情形

排队超时离开不支付，但产生负面口碑记录（见 7.6）。

## 11. 员工体系

### 11.1 排班表

排班表 = 周模板的 Duty 时段（参数=雇主店铺），**独立于营业时间**——可以有开店前准备班、打烊后清洁班。

**玩家角色同样进排班**（与员工同一张周节律表）：Duty 时段 = 在岗，不领工资、不被 AI 决策接管（玩家自己演这个角色）；在岗期间监督光环生效（11.6 偷懒概率 −0.2）；不在岗无违约惩罚（玩家不是 AI），但员工偷懒概率自然上升。

### 11.2 雇佣记录

```
FEmploymentRecord{
  ShopAreaID, CreatureID,
  RoleTag,              // Employment.Role.Staff / Employment.Role.Shopkeeper
  WorkPriorities,       // 0-4 工作优先级表（按岗位模板初始化）
  WageConfig{底薪, 计件系数},   // 对接 10.5 工资
  ShiftTemplate,        // 写入该 NPC 周模板的 Duty 时段
  HireSource            // 人力市场 / 店主引入 / 熟人邀请 / 剧情
}
```

雇佣 = 改写目标 NPC 周模板的 Duty 时段（现有日程模型的天然落点，无新机制）。产生途径与招聘流程见第 13 章。

### 11.3 工作优先级表（RimWorld 式）

员工侧意愿表，与任务侧 Priority 分带正交（扫描流程见 5.4）：

```
WorkPriorities: TMap<AI.Work.* Tag, uint8>，取值 0-4:
  0 = 禁止（绝不干）
  1-3 = 普通偏好梯度
  4 = 灭火级（有活就抢着干）
```

- 招聘时按岗位给一份预设模板（如服务员 = Serve 4 / Clean 2 / Craft 0），玩家之后可逐格调整
- 原"岗位匹配" tie-break 删除，由优先级表表达
- 管理界面 = RimWorld 标志性优先级矩阵（行=员工，列=工种，格=0-4），**点击格子循环 0→4**
- 玩法深度：玩家故意把某员工某工种设 0 制造排班缺口、紧急时手动拉高某人优先级救火

### 11.4 熟练度（与战斗数值同源）

工作熟练度接入现有属性管线（FCreatureRuntimeState 四层管线），不新建数值系统：

```
一级能力 (Creature.Attribute.Primary, 基础六围)
    ├─→ Combat 公式 → Creature.Attribute.Combat.*   (战斗，已有)
    ├─→ Social 公式 → Creature.Attribute.Social.*   (经营通用，WorkEfficiency)
    └─→ 工作熟练度公式 → Creature.Attribute.Skill.*  (新增，每工种一条)
```

**熟练度定义表**：`AI.Work.* Tag → FDerivedAttributeDef`，声明该工种吃哪些一级能力。例：
- `AI.Work.Serve = Cha×0.6 + Int×0.2`
- `AI.Work.Craft = Str×0.3 + Int×0.5`

复用现有 FDerivedAttributeDef 公式结构，加工种 = 加配置行。

**特质修正自动生效**：特质的 AttributeConfigs 本就作用于属性管线（加/乘修正），无需额外机制。

**后天经验**：
```
FCreatureSaveData 新增 WorkExperience: TMap<AI.Work.* Tag, float>
完成工单按量增长，对数收敛、有上限（前期成长快、后期趋缓，避免数值失控）
最终熟练度 = 公式(一级能力) + 收敛映射后的经验值
```

**作用点**：`工单工期 = 基准工期 ÷ (熟练度 × WorkEfficiency)`。

**战斗联动**：战斗与工作读同一份 Primary——培养员工工作能力同时投资战斗能力（"全员皆兵"设定的兑现点，见第 20 章）。

### 11.5 员工状态需求（精力/情绪/忠诚度）

新增三个需求，全部复用现有 Dynamics + 阈值规则管线：

| 需求 Tag | 方向 | 驱动 |
|---------|------|------|
| Creature.Demand.Energy（精力） | 工作中消耗、睡眠/休息回填 | 工单执行按时间扣，与睡眠时段天然衔接 |
| Creature.Demand.Mood（情绪） | DecayRate=0，纯事件驱动 | 正面体验（好评/小费/被夸奖）+，负面（被骂/环境脏乱）− |
| Creature.Demand.Loyalty（忠诚度） | 缓慢衰减 + 事件驱动 | 工资兑现/被重视 +，训诫/欠薪 −；低忠诚 → 辞职事件（对接招聘补员） |

用"精力"而非"疲劳"，贴合现有模型"值越低越紧急"的方向，零特判。

**BUFF 全部走 FDemandThresholdRule.EffectModifiers（现有字段）**，需求跨阈值自动应用属性修正：

```
精力 < 40        → WorkEfficiency ×0.7（疲惫）
精力 Critical    → "休息"压倒一切工单（现有 Critical 优先规则直接覆盖）
情绪高           → WorkEfficiency ×1.2 + 小费率提升
情绪低           → 效率下降 + 偷懒概率提升（接 11.6）
忠诚度低         → 偷懒概率提升 + 辞职风险
```

作用点统一：修正 `Creature.Attribute.Social.WorkEfficiency`（已有占位），工单工期公式一处生效全链路。需求变化本身即产生 BUFF——跨阈值检测发射事件时同步应用修正。

### 11.6 待机与偷懒

优先级表全表扫完无工单 → 进入**待机态**，按概率分流（纯配置表驱动，不走需求阈值）：

```
偷懒概率 = 基础值(0.3)
         + 性格修正（懒惰特质 +0.3 / 勤劳特质 −0.3）
         + 状态修正（情绪低 +0.2 / 忠诚度低 +0.2 / 精力低 +0.2）
         − 监督修正（店主或玩家角色在附近 −0.2）
```

**偷懒行为池**（按场景配置，复用 FunctionDef）：
- 坐下休息（占用座位但**不锁座位**——顾客来了要让）
- 闲聊（两个偷懒员工凑一起 → 社交需求回填，行为外化素材）
- 打盹（精力微量回填）
- 摸鱼道具（酒馆场景 = 自己喝一杯，店铺库存 −1 = 库存漏洞，玩家可发现）

**任务程度分带（通用工作处理逻辑，Tidy 杂务是其实例）**：
- 任务按程度映射 Priority 分带：重度（重污染/急单）→ 紧急带，正常优先级扫描即被抢走；轻度（如轻微脏污的 `AI.Work.Tidy` 擦桌/整理货架）→ 低优带挂看板，员工扫完所有真正任务仍空闲才处理
- 程度由上报方随 FTaskItem 给出（如脏污度跨档），看板不自动生成任务
- 员工优先级表里 Tidy 设 0 → 该员工连杂务都不干，纯偷懒
- 杂务微抬店铺 Environment 维度 → 顾客体验受益，形成"养闲人也有用"的权衡

**偷懒的后果**（保持轻量）：
- 偷懒只影响工作进度
- 被顾客指派的任务期间被看到偷懒 → 该顾客 Service 体验扣分（普通工作不会）
- 被店主/玩家抓到 → 处置方式由店主或玩家决定（训诫 / 扣工资 / 辞退），无自动加速辞职判定

### 11.7 交接规则

**工单按工种分可暂停/不可暂停**（工种配置表声明 bPausable）：
- 可暂停（Craft / Bill 定制生产等长工期）：进度存工单，下班留存、下一班可换人续做
- 不可暂停（Serve / Clean / 收拾桌面等短工）：中断即进度清零，必须当班一次做完

1. 不可暂停工单做完才离岗；可暂停工单下班时进度随工单留存
2. **加班意愿**（性格调制，配置表驱动）：`加班意愿时长 = 基础值 × 勤劳特质修正 × 忠诚度修正 × 情绪修正`（懒惰/低忠诚/低情绪 → 趋近 0，到点就走）
   - 认领放宽：临近下班认领条件 = 预估工期 ≤ 剩余班次 + 加班意愿——责任心强的员工会接下略超时的活，按时下班型不接（班次末尾"只接小活"仍是低加班意愿者的自然涌现）；可暂停工单不受此限
   - 到点离岗：愿加班 → 做完当前工单再走（RoleContext 延迟生效，见 2.3）；不愿 → 到点即走，手上不可暂停工单强制清零回 Unclaimed（认领判定已拦过一轮，走到这步的都是预估失误，白干一单是涌现的经营损耗）
   - 加班员工发"主动收尾"外化（16.2 工作状态类）——玩家观察得到，是涨薪决策依据（涨薪 → 忠诚 → 更愿加班，正循环）
3. 执行中超时兜底：实际执行超过预估 ×K（K 可配，默认 2）→ 强制失败：进度清零、租约释放、工单回 Unclaimed——堵寻路卡死/资源被占导致永不下班的残余死锁
4. 无人接的工单留在看板（等下一班）

### 11.8 工单租约制（修补死锁）

```
ClaimTask → 获得租约（默认 X 秒）
执行中自动续约
过期未续约 → 任务自动回 Unclaimed
NPC 回收 / 下班 / 死亡 → 显式释放名下锁定
```

租约自动回收 + 显式释放 = 双保险，杜绝"认领人消失、工单永久锁死"。

### 11.9 玩家即时指令与亲自上工

| 指令 | 性质 | 目标 | 效果 |
|------|------|------|------|
| 指派工单 | 软、即时 | 员工 × 具体工单 | 该员工下次扫描时此工单置顶（个人指派标记，不打断当前原语段）；委托通道见 8.4 |
| 驱赶 | 硬、即时 | 顾客/闲杂 NPC | 目标放弃当前流程离店（无差评——店主权利），可封禁当日 |

- 优先级：玩家指派 > Critical 个人需求 > 常规工单；强压 Critical 时员工发"面露难色"外化，后果由玩家承担
- 长期手段 = 优先级矩阵调表（11.3），即时手段 = 本表两件
- 玩家亲自干活 = 特殊员工：开始交互即认领该工单（玩家租约无过期，离开交互即释放），AI 员工扫描跳过玩家锁定单；产出走同一结算（消耗库存/服务体验照算）
- 附身玩法留口子：玩家角色与实体的控制绑定抽象为 ControlBinding 层，首版只绑主角色

## 12. 店主决策系统

### 12.1 店主身份与产生

店主不是新"类"，仍是时段角色模型的 NPC，只是多挂一份经营记录：

```
FShopOwnership{ShopAreaID, OwnerCreatureID, 任命来源, 就任时间}
```

三种产生途径（都写同一份记录）：
1. **玩家邀请** → 招聘界面选中 NPC → 任命为店主（见第 13 章）
2. **剧情指派** → 剧情事件写入
3. **商圈邀请** → 商圈代理人系统邀请外来 NPC 开店

### 12.2 双层结构（个人层/经营层完全分离）

| 层 | 频率 | 内容 |
|---|------|------|
| **个人层** | 实时 | 店主自己的需求/日程，可亲自上岗领工单（走第 11 章优先级表） |
| **经营层** | 低频（按性格） | 店铺级参数决策（UShopkeeperDecisionComponent，挂店铺区域 Actor） |

两层完全分离：店主作为 NPC 正常过日子（会饿、会休息、能亲自干活），经营决策是独立后台循环——**店主在睡觉/离店时店铺照常运转**（由排班员工顶着）。店铺是持续经营体。

### 12.3 经营决策循环（性格驱动周期）

```
决策触发 = 周期到点 ∪ 关键事件
  周期长度 = 基准周期 × 性格修正:
    勤快/进取性格 → 短（每日）
    懒散/保守性格 → 长（每周）
  关键事件（不等周期，立即触发）:
    库存告急 / 资金低于警戒 / 差评激增 / 员工集体辞职
```

性格不只影响**周期**，还影响**决策倾向**：进取店主敢涨价敢投活动，保守店主求稳。

### 12.4 经营决策项

| 决策项 | 依据 | 输出 |
|--------|------|------|
| 营业作息 | 客流时段统计 + 性格 | 改写 BusinessSchedule（开门/打烊时段） |
| 招聘/裁员 | 工单积压量 + 资金 | 发起招聘需求（委托制，见 13.2）/ 解雇 |
| 商品定价 | 销量 + 声誉 + 性格风险偏好 | 逐商品调价（复用逐商品定价，禁止调价系数） |
| 进货 | 库存水位 + 销量预测 | 下采购单（见第 15 章） |
| 活动/广告 | 知名度 + 资金 + 性格 | 投放店铺活动（见第 14 章） |

**自治边界（分域）**：
- 定价 / 作息 / 活动投放 / 采购：店主自主执行（默认自动），玩家看报表与结果
- 招聘 / 解雇（人员流动）：**永远需玩家同意**——商圈人事权归玩家（13.2 委托制）
- 关系度解锁商量：关系度低 = 店主按自己性格独立干；关系度高 = 店主决策前会来问玩家（FShopProposal 提案询问，玩家获得介入窗口）。关系度即影响力（16.5）
- 辞退店主：玩家随时可行（最高权力）

### 12.5 数据归属

经营决策需要的店铺数据（账本/声誉/库存/客流）全挂在 `UVoxelFunctionAreaComponent`，店主决策只读不新增存储；决策结果写回这些字段。

### 12.6 无主经营态

OwnerCreatureID 死亡/辞职 → 店铺进入无主经营：经营决策循环挂起（参数冻结维持现状），员工排班照旧运转（持续经营体不断气），玩家收事件通知 → 任命新店主 / 自己兼管 / 歇业。

## 13. 招聘系统

### 13.1 三条来源（前期以人力市场为主）

| 来源 | 机制 |
|------|------|
| **人力市场**（主路径） | 双点博物馆式招聘界面：市场刷新陌生候选人列表，直接展示属性面板（市场提供简历，不受脸盲限制），选中即谈 → 议价 → 签约。入职后该 NPC 与玩家角色仍是陌生人（关系度低），靠共现与互动认识（双向关系度，见 16.5） |
| **店主引入** | 玩家从市场引入陌生店主开店：店主**自带店铺/房间模板**，引入后玩家布置落位；**布局修改权限与关系度挂钩**（熟了才能帮他改） |
| **熟人邀请**（次要） | 玩家问熟人是否愿意来当店主/店员，按亲密度判定接受 |

### 13.2 店主自主招聘 = 委托制

店主向玩家提出招聘需求（岗位/人数/预算），由玩家代为在招聘界面安排——玩家始终是招聘的操作者，店主只提需求。

### 13.3 议价

邀请/报价被拒 → 对方还价 → 玩家接受还价 / 再谈 / 放弃。议价结果写入 FEmploymentRecord.WageConfig。

### 13.4 招聘界面信息分层（脸盲玩法）

| 对象 | 界面可见信息 |
|--------|------------|
| 人力市场候选 | 属性面板（市场简历） |
| 低关系度 NPC | 素体剪影 + 玩家自己的记事本备注（玩家起的外号） |
| 中关系度 NPC | 真名 + 职业倾向（模糊描述） |
| 高关系度 NPC | 完整属性面板（一级能力/特质/期望带） |

注：员工管理界面（优先级矩阵，11.3）以"工牌编号 + 玩家备注名 + 关系度分层"显示——脸盲下玩家仍需区分员工，给新员工起备注名是开店的必要动作。

信息不对称即玩法：低关系度招人 = 赌，高关系度招人 = 稳。

## 14. 店铺活动（广告与知名度）

### 14.1 深巷设定与系统职责

主地图本身客流量不小，问题只是玩家商业街位于深巷、没人路过。现有认知模型靠"路过发现"（5.2），深巷没有过路流量，半径再大也没用。**店铺活动的职责：绕过"必须路过"的前提，主动把店铺塞进 NPC 的 KnownShopIds。**

同时深巷的距离会被 ProximityAtten 惩罚——知道了也未必愿意专程来。因此分工明确：
- 活动只负责**写入 KnownShopIds**（认知）
- 来不来 = 现有评分公式：PersonalityMod（探索特质 → 陌生店好奇）+ QualityScore（有效声誉），距离衰减自然筛选
- **活动没有"强制到访"特权**——留不留客全看声誉和体验

### 14.2 标准店铺活动模型

凡需要商店持续投入的活动统一为 `FShopCampaign`（不止广告）：

```
FShopCampaign{
  CampaignTag,          // Campaign.Ad.Flyer / Campaign.Ad.Bard /
                        // Campaign.Promo.Tasting / Campaign.Promo.Opening ...
  DailyCost,            // 日开销（从 FShopLedger 扣，余额不足自动中止）
  Duration,             // 持续天数（-1 = 长期，如招牌维护费）
  Effects: TArray<FActivityEffect>   // 效果条目，全配置化
}

FActivityEffect{
  EffectTag,            // Campaign.Effect.Reach / ReputationBoost /
                        // ExperienceBuff / FootTraffic ...
  Params: TMap<FGameplayTag, float>
}
```

加活动类型 = 加配置行，零代码：

| EffectTag | 作用 |
|-----------|------|
| Reach | 每日触达 N 人，按转化率直接写入 KnownShopIds |
| ReputationBoost | 声誉滚动值加成（吟游诗人/促销） |
| ExperienceBuff | 活动期间到店消费者体验值加成（试菜/酬宾） |
| FootTraffic | 物理引流（指路牌：等效延伸发现半径到指定位置） |

### 14.3 渠道

| 渠道 | 机制 | 特点 |
|------|------|------|
| 招牌/指路牌 | 物理建造物，玩家摆放在街道任意位置（FootTraffic）；**双层感知**：图内 NPC 进半径真实感知，图外按牌位流量（街道流量属性 × 距 SpawnArea 衰减）抽象结算——认知写入与"谁在图"解耦 | 空间策略——深巷店靠主街指路牌引流，同条街不同路段效率不同 |
| 传单派发 | 雇 NPC 到 SpawnArea/主街派发（Reach） | 一次性、可控成本、见效快 |
| 吟游诗人/说书人 | 表演（Reach + ReputationBoost） | 贵，认知+口碑双收 |
| 促销活动（试菜/开业酬宾） | 限时活动（Reach + ExperienceBuff） | 接每店核心玩法（如酒店试菜） |

### 14.4 归属与接口

- 活动列表挂 `UVoxelFunctionAreaComponent`（与 Ledger/Reputation 同级）
- 投放决策进店主经营循环（12.4）；玩家也可手动投放，共用同一接口
- 触达转化直接写入 KnownShopIds（5.2 第四途径）

## 15. 供应链

### 15.1 全链路闭环

```
外部货源 → [采购] → 店铺仓库 → [Restock 工单，已有] → 服务点/货架 → 消费者
```

### 15.2 三通道货源

| 通道 | 说明 |
|------|------|
| **外部市场/供应商**（主） | 抽象货源点（批发市场/商队），提供商品目录 + 批发价 + 供货量；不在图内模拟，纯数据接口 |
| **街区店铺互供**（辅，B2B） | 商业街内店铺互相供货（如面包店给酒馆供面包），复用店铺商品数据，形成街区经济内循环 |
| **探索获取**（素材类） | 玩家亲自出城探索 / 委托店员·冒险者外出采集；与"全员皆兵"战斗冒险设定联动（素材产出与冒险风险挂钩）；委托机制复用任务系统接口（见 19.5 口子） |

探索素材与商品采购分开：商品走市场定价，素材走冒险产出，两条链不混。

### 15.3 采购单

```
FPurchaseOrder{
  ShopAreaID,
  Items: TArray<{ItemTag, 数量}>,
  SupplierTag,          // 外部市场 / 某店铺
  TotalCost,            // 从 FShopLedger 扣
  State                 // 待配送 / 在途 / 已入库
}
```

- 店主决策循环按库存水位 + 销量预测自动下单（12.4）；玩家可手动下单/改单
- **配送方式 = 供应商配送**：下单后延迟 N 时段自动入库，只扣货款 + 配送费，不占员工
- 入库 → 仓库库存增加 → 触发 Restock 工单链（已有机制，零新增）

### 15.4 缺货后果链

```
仓库断货 → 服务点无货可卖 → 抛 Restock 工单（已有链路）
        → 消费者到店 Browse 发现缺货（库存到店才知，见 5.1 认知边界）
        → 离店 + 差评（"想买的没有"，见 8.6/7.6）→ 客流损失
        → 触发店主紧急决策（12.3 关键事件：库存告急）
```

## 16. 行为外化与情报记录

### 16.1 两层信息分离（脸盲约束）

脸盲限制的是"这是谁"，不限制"他在干什么"——素体也做动作，行为正是脸盲玩法的观察通道：

| 层 | 内容 | 门槛 |
|---|------|------|
| **身份层** | 脸/名字/属性面板 | 关系度达标才显示；否则统一半透明素体 |
| **行为层** | 动作/反应/情绪演出 | 永远可见（素体也演） |

### 16.2 外化事件模型

决策/评价结果之后加一级外化事件分发：

```
决策/评价结果 → FExternalizeEvent{EventTag, ActorID, Intensity} → 动画/表情演出
```

事件分三类（全配置化，Tag 驱动），**只在关键节点发**（决策失败/差评/离队等显著结果，不全量发）：

| 类别 | 例子 | 玩法作用 |
|------|------|---------|
| 情绪反应 | 嫌贵皱眉、吃到差评摇头、被服务好评点头 | 玩家观察 → 推测该店问题所在 |
| 行为线索 | 看别家队伍、排队中途离队指店、橱窗张望 | 玩家观察 → 推测客流流失原因 |
| 工作状态 | 员工忙碌/偷懒/打盹的演出 | 接 11.6 偷懒的可见性 |

### 16.3 系统挂接

- 事件源复用 UCreatureEvent 事件总线，外化事件作为一种事件类型
- 演出层走动画系统（蒙太奇/表情）；AI 侧只负责发事件，不管怎么演
- 玩家记事本可记录观察到的外化事件（脸盲玩法的线索沉淀）

### 16.4 玩家侧 NPC 档案（情报记录口子）

玩家对 NPC 的观察/认知数据（关系度、记事本备注、观察到的外化事件）统一存在**玩家侧 NPC 档案**，作为未来情报玩法（万事屋/侦探所等店铺核心玩法）的数据底座。本版不设计传播/交易/情报价值机制。

### 16.5 关系度（玩家角色 ↔ NPC，双向）

- 关系度是**玩家角色与 NPC 之间的双向关系**（复用 FSocialMemory{TargetID, Affinity, MemoryTags}，玩家角色是社会关系网中的一个节点），对全体 NPC 适用：顾客、店员、店主、邻居——主角对所有人脸盲
- 增长通道：被动眼熟（反复共现低速缓涨：常客/店员天天见自然脸熟）+ 主动互动（搭话/服务/安抚快涨）
- 解锁分层（即 13.4 信息分层）：低 = 素体剪影；中 = 真名 + 职业倾向；高 = 完整面板（一级能力/特质/期望带）
- 双向收益：NPC 认得老板 → 常客对玩家角色的亲密度影响复购（MemoryMod 的人情分项）、小费、忠诚——老板亲自站店 = 攒关系 = 锁熟客
- 玩家单方备注与之并行：关系度不够时可在记事本给素体钉观察记录（玩家起的外号），认得后归并到真名档案。单方笔记是玩家的，关系度是世界的，两层不混

## 17. SpawnArea 与流量分布

### 17.1 设定基调

主地图本身客流量不小，问题只是玩家商业街位置偏。因此**人口总量静态**（大城市背景），不做移民/流失模拟；要模拟的是**"流量分布"**——与第 14 章活动系统咬合：广告的本质就是把主街流量引进深巷。

### 17.2 SpawnArea = 地图切换点

```
FSpawnArea{
  AreaID,
  Location,              // 图内入口位置（城门/地铁口/街口）
  LinkedAreas: TArray<FAreaLink>,   // 对接的其他区域（类似 MMO 地图切换点）
  TrafficWeight,         // 流量权重（单位时间通过人数）
  TimeCurve              // 时段曲线（早晚高峰/饭点加成）
}
```

一套切换点数据，NPC 寻路、玩家探索、流量分布全复用：
- **NPC 用途**：居住区配置绑定对接的 SpawnArea（配置表显式绑定），生成时直接查表——进场从该点刷出、退场回该点消失
- **玩家用途**：探索模式下通过 SpawnArea 切换到目标区域（城外探索/素材采集的出口，接 15.2 探索通道）

### 17.3 进场与退场

```
进场: 日程段需要进图 → 从对应 SpawnArea 刷出 → 寻路到目的地
退场: 日程结束离图 → 寻路回对应 SpawnArea → 消失
```

NPC 来去方向符合直觉（住城东的人从东门进），组团消费有自然的汇合点。

### 17.4 图内人口

在场人数由"日程出场判据"（2.3）自然决定，不需要额外人口系统。玩家不开店也不影响人口——影响的是**流量去向**，不是流量总量。

主街流量 = SpawnArea 权重 × 时段曲线（天然存在）；深巷没流量 = 没有路径经过 → 指路牌（FootTraffic）把部分流量引入深巷路径；传单投放点 = 直接选 SpawnArea（在人流入口发）。

### 17.5 天气接口（预留）

评分公式在 TimeMod 同模式上加天气修正窗（见 5.3 公式的 WeatherMod 槽位）：

```
WeatherMod 由全局天气状态驱动（雨天: 室外队列忍耐加速衰减 / 客流系数下降）
```

本版只定义接口（WeatherMod 槽位 + 天气状态查询函数），数值与天气系统本体等环境系统实现时再填。

## 18. 决策 LOD

现有决策已是事件驱动非 tick，LOD 解决的是**决策深度与频率的分级**——饭点全员在场时，把算力集中在玩家看得见的地方。

### 18.1 三档 LOD

| 档位 | 判定 | 决策行为 |
|------|------|---------|
| **LOD 0 全量** | 玩家店铺内 / 玩家附近 / 高关系度目标 | 完整评分（全候选 Top-3 加权随机）、正常重评估频率、全动画外化 |
| **LOD 1 简化** | 图内但远离玩家 | 评分只取最高分（跳过 Top-3 加权）、重评估频率减半、只发关键外化事件 |
| **LOD 2 休眠** | 不在图内 / 屏幕外远端 | 只跑 Critical 需求与日程切换，需求衰减按粗粒度批量结算，无动画 |

### 18.2 重要度优先定档

```
重要度 = 玩家店铺员工/顾客(+高)
       + 玩家高关系度 NPC(+高)
       + 当前被玩家注视/交互(+高)
       + 距离衰减(−)

基础档位由重要度定，再按距离微调
```

**玩家店铺永不休眠**：玩家经营的店，其员工与在场顾客锁定 LOD 0/1（玩家观察的核心）。

### 18.3 升降档与连续性

- 档位可升降：玩家走近 → 升档补算；走远 → 降档。升降时补一次决策避免行为断层
- 休眠不是删除：LOD 2 的 NPC 日程/需求照常推进（离线结算），只是不演出、不精细决策——回来时状态连续
- **LOD 只降决策精度与演出，数据层永不降档**：租约续约、看板状态流转、需求衰减（粗粒度批量）、体验结算、账本、声誉滚动统计、店主经营循环，全部照常推进——玩家远离时世界照常运转，回来账本声誉对得上
- LOD 2 员工认领工单用粗略轮询代替完整优先级扫描

## 19. 记忆与事件系统

### 19.1 记忆即履历

记忆**不新建结构**，复用 `FLifeHistoryEntry`：

| 现有字段（不动） | 含义 |
|----------------|------|
| OccuredAge | 发生时年龄 |
| SourceEvent | 事件资产软引用 |
| EventId | FPrimaryAssetId |
| SelectedChoiceIndex | 选择的选项索引 |
| SnapshotOutcomeText | 结果文本快照 |
| GainedTraitTag | 获得的特质 |

情感强度、关联目标等数据从事件资产的 Outcome 配置读取，不在条目里冗余存储。消费体验记忆附带店铺 ID（经 SocialMemories / 事件参数传递），是店铺认知来源之一。

如需运行时回闪状态（次数/时间/晋升），单独建一个 `TMap<FPrimaryAssetId, FMemoryRecallState>` 表外挂存储，不修改 FLifeHistoryEntry。

### 19.2 运行时事件触发

复用现有 `UCreatureGeneratorUtils` 的事件解析逻辑：

```
运行时触发条件:
- 结算时（消费完成/工作完成/异常）
- 排队离队 / 被门禁拒绝 / 进店买不起（负面体验）
- 代办日程履约/逾期未办
- 社交互动
- 被攻击
- 定期回闪检查

触发流程（完全复用 GenerateBackstory 中的逻辑）:
  ① Config->GetAllLifeEvents() 获取候选事件
  ② CheckAllConditions() 筛选（年龄/Tag 条件）
  ③ 优先级互斥 + 加权随机
  ④ ResolveEventOutcome()（含性格检查）
  ⑤ ApplyEventOutcome()
  ⑥ 追加到 LifeHistory
```

### 19.3 记忆回闪与性格塑变

```
短期记忆（外挂表标记 RecallCount/LastTime 未晋升）:
  定期回闪 → UEventOutcome_Chain 触发链事件
  → 产生情绪波动（影响 Dynamics）
  → 强度足够 → 标记为长期记忆

长期记忆（外挂表标记已晋升）:
  周期性回闪 → 触发 UEventOutcome_Instant::PersonalityShift
  → 永久改变 PersistentBasicValues 中性格维度数值
  → 被更强记忆覆盖才释放槽位
```

### 19.4 记忆影响评分

```
评分某候选时:
  ① 按 SourceEvent 关联（含店铺 ID）筛选 LifeHistory
  ② 按重要性 × 时效性 × 情感强度排序
  ③ 取最相关 1-2 条
  ④ MemoryMod = 1.0 + Σ(Emotion × Importance × 时效衰减)
     Clamp [0.1, 2.0]
```

### 19.5 突发状况事件（任务系统口子）

突发状况（投诉/打翻汤/插队争执/醉酒闹事…）统一生成为 UCreatureEvent，携带标准字段：

```
{EventTag, SourceCreatureID, ShopAreaID, Severity, Deadline, 处置结果(预留)}
```

- 本版：店铺侧自动处理或自然消散（如投诉不处理 → 差评落地，走 7.6 现有路径）
- 未来任务系统上线：同一事件结构直接转成可接取任务，AI 侧零改动
- 口子 = 事件结构按"可转任务"设计（带 Severity/Deadline/处置结果字段），但不实现任务接取
- 探索采集委托（15.2）同样走此事件结构

## 20. 战斗模式（愿景附录）

> 定位：战斗为探索模式的**回合制 3D 战棋（非网格）**。可复用的是评分器框架与连续空间距离因子（ProximityAtten 映射为距离/AP 消耗，与日常连续寻路同源）；**回合时序执行层另设**，不属于本系统交付范围。本章仅为方向性参考，不构成实现承诺。

### 20.1 同框架不同配置

战斗不新建独立系统，通过 `BehaviorContext` 切换：

| 维度 | Daily 配置 | Combat 配置 |
|------|----------|-----------|
| 决策触发 | 需求阈值 / 日程时段 / Job 完成 | 回合开始 / 被攻击 |
| 候选来源 | 店铺 FunctionState + 商品目录 / 看板工单 | 技能 + 格子 + 道具 |
| NeedScore 输入 | 需求值 | 血量 / AP / 友军血量 |
| QualityScore | 功能品质 × 有效声誉 | 伤害值 × 命中率 |
| ProximityAtten | 距离衰减 | 移动范围 + 攻击范围 |
| 执行模式 | 流程节点 + 连续寻路 + 动画 | 回合制 3D 战棋（非网格）+ AP 消耗；回合时序执行层另设 |
| 玩家控制 | 无 | 挚友完全受控 / 陌生盟友 AI 评分 |

**一级能力同源**：战斗数值与工作熟练度读同一份 `Creature.Attribute.Primary` 基础六围（见 11.4）——培养员工的工作能力同时投资战斗能力（"全员皆兵"设定）。

### 20.2 玩家控制

- **挚友**（完全控制）：候选只有玩家指令，分数固定最高
- **陌生盟友**（AI 控制）：正常 Combat 配置评分
- **同一框架**：只是候选来源不同，评分器本身不变

## 21. 完整逻辑链

### 21.1 主循环

```
时间推进
  │
  ├─ 每秒: 需求衰减 Tick
  │         Dynamics 按 DecayRate 衰减
  │         跨阈值检测 → 突破则发射 OnTriggerEvent（同步应用阈值规则 EffectModifiers）
  │
  ├─ 日程时段切换（事件）
  │         无激活时段 → 回收对象池
  │         有激活 + 不在图 → 从住所绑定 SpawnArea 刷出通勤
  │         有激活 + 在图 → 切 RoleContext 重决策
  │
  ├─ 代办日程触发（到点 / 订单完成事件）
  │         → 注入候选池 / 唤醒休眠流程
  │
  └─ 环境事件（对象状态变化）
           家具脏污度超阈 → 推送看板 + 更新 FunctionState
           货架库存低于阈值 → 推送看板(AI.Work.Restock) + bAvailable=false
           营业时间变化 → EAreaStatus 切换（影响硬过滤）+ 打烊事件清场:
               排队/等待段顾客 → 放弃离开（无差评，非服务失败）
               自驱段顾客（正在吃）→ 完成当前子进度后自然收尾，不再开新子进度
               已下单未履约 → 免单无差评，关联工单作废
           店主经营决策循环到点/关键事件 → 经营决策（第 12 章）
```

### 21.2 决策周期

```
决策触发时:

  ① 确定触发源（哪个需求 / 哪个事件 / 哪个时段切换）

  ② RoleContext 分流
       Duty  → 员工决策（转 ④）
       Free  → 消费者决策（转 ③）
       Sleep → 居家低耗态，不决策

  ③ 消费者决策
       硬过滤漏斗: 营业状态 → 认知(KnownShopIds) → 价格上限(Critical ×1.5)
       收集候选（空间优先级 Layer 1/2/3）
       加法核评分:
         (w₁·NeedScore + w₂·QualityScore + w₃·WillingnessScore)
         × ProximityAtten × QueueFactor
         × PersonalityMod × DutyMod × TimeMod × WeatherMod
         × MemoryMod × ClienteleMod
       过滤 0 分 → 最高分 < MinActionThreshold → 闲逛
       Top-3 加权随机（LOD 1 只取最高分）

  ④ 员工决策
       Critical 个人需求 → 优先转消费者路径处理
       员工优先级表从高到低遍历工种（0 跳过）
       工种有工单 → 工种内任务侧 Priority 分带（紧急 → 常规 → 低优）
       同带 tie-break: 就近 + 先到先得
       无工单 → 待机状态（待机/偷懒分流，见 11.6）

  ⑤ 生成 FMotivation → 创建 FActionJob（流程解释器）
       关键节点结果 → 发 FExternalizeEvent（行为外化）
```

### 21.3 执行周期

```
FActionJob 按 FlowConfig 逐节点推进:

  Browse   → 读商品目录 → 选品（回填量 × WillingnessScore）
  QueueAt  → 入队（WaitingQueue + QueueSlots）
           → 等待体验值跌破 Expectations[Service].Min → 离队+差评+写冷却
  ClaimSeat→ 锁定座位
  Order    → 下单 → 抛工单（Serve/Craft）/ 定制单入 Bill Queue
  Pay      → 逐项计价 + 小费 → 写 FShopLedger 流水
  Consume  → 回填需求（中断按 PartialSettle 比例结算）
  AcquireResource / Release → 拿货 / 释放

  节点失败 → 按 OnFail 策略（放弃/重试/跳节点）
  定制流程 → 休眠持久化（断点）→ 订单完成事件唤醒

  节点产出 FExperienceReport → 期望带评价（第 6 章）
    → 写个体记忆 + 更新店铺声誉（第 7 章）

  流程结束 → 触发下一轮决策
```

### 21.4 记忆周期

```
事件触发（运行时）:
  结算 / 排队离队 / 买不起 / 被拒绝 / 社交 / 被攻击
    ↓
  匹配对应 UCreatureEvent
    ↓
  复用 GenerateBackstory 解析逻辑
    ↓
  追加 FLifeHistoryEntry 到 LifeHistory（附带店铺 ID）
    ↓
  外挂表登记为短期记忆

定期回闪:
  每游戏日检查
    ↓
  遍历 LifeHistory + 外挂表
    ↓
  短期触发 Chain → 情绪波动 → 可能晋升长期
  长期触发 PersonalityShift → 永久改性格

评分时:
  按相关记忆计算 MemoryMod + 个体声誉偏差
    ↓
  影响候选评分
```

## 24. 关键场景走查

### 24.1 店员工作到一半饿了

```
14:00  Duty 时段, Hunger=72 (>Urgent=60 未达 Critical)
       → 员工决策: 优先级表扫描, Serve=4 最高且看板有收银工单(紧急带) → 继续收银
15:10  Hunger=35 (<Critical=40), 饭点 TimeMod 加成
       → Critical 个人需求优先: 段边界强制打断（收银工单不可暂停 → 进度清零、租约释放、回 Unclaimed）
       → 转消费者路径去员工餐厅（被撂下的收银台：顾客等待段预警，工单留看板）
15:20  吃完 Hunger=85 → Critical 解除 → 回 Duty 决策
       → 看板任务还在(无人接留看板), 重新优先级表扫描认领收银
```

### 24.2 吃饭中途上厕所

```
Consume 节点（餐厅流程）吃饭进度 15/30
Spirit 突破 Critical → 强制打断当前节点
  → PartialSettle: Hunger += SatisfactionAmount × 50%
  → 支付同比例, 体验分按进度打折
  → 释放吧台座位, 流程记录断点
  → 紧急决策

空间优先级扫描 Layer 1: 当前餐厅
  → 餐厅内有洗手间 → 生成候选, 停止扩展

去洗手间 → 上完 Spirit=90 → Hunger 仍低
  → 重决策 → 可从断点恢复餐厅流程继续吃
```

### 24.3 缺货自动处理（含供应链）

```
货架 A 现货被拿走, 库存低于阈值:
  → FFunctionState.bAvailable=false
  → 向区域 TaskBoard.AddTask(AI.Work.Restock)

顾客:
  库存远程不可知（认知边界 5.1）→ 正常到店
  → Browse 发现货架 A 无货 → 离店 + 负面记录（7.6）

店员（Duty 时段）:
  优先级表扫描 → Restock 工单落入对应优先级带
  → 认领(获得租约) → 去仓库取货 → 货架 A 补货
  → 完成 → 货架 A bAvailable=true, 看板移除任务
  → (若认领中途下班/死亡 → 租约过期, 任务自动回 Unclaimed)

仓库也空了:
  → 仓库库存低于水位 → 店主经营决策下采购单（供应商配送, 延迟入库）
  → 入库后 Restock 链恢复；断货期间顾客候选被硬过滤 → 客流损失+差评
```

### 24.4 排队太长离队换店

```
餐厅 A 门口 QueueAt 节点:
  WaitingQueue=4 人, 估算等待 8 分钟
  等待体验值随等待时长下降（无等待区设施, 无减缓）
  → 跌破 Expectations[Service].Min（该 NPC 挑剔, 底线高）
  → 离队 + 差评 + 写候选冷却（餐厅 A 冷却期内评分 ×0.1）
  → 发 FExternalizeEvent（行为线索: 离队指店）
  → 触发重决策
  → 餐厅 B（队列 0 人, QueueFactor 高）评分更高 → 选餐厅 B

同场景换随和顾客（Service 底线低, 带宽）:
  → 体验值仍在带内 → 继续排队
```

### 24.5 记忆影响评分与个体偏差

```
NPC 甲评分餐厅 A:
  有效声誉 0.6 × 个体记忆修正（"上次在 A 吃坏肚子" Emotion=-0.8）
  MemoryMod → Clamp(0.1) → QualityScore 分项与修饰双低
  → 几乎不会选餐厅 A

NPC 乙评分餐厅 A:
  无相关记忆 → MemoryMod = 1.0
  → 按有效声誉 0.6 正常评分 → 可能选中

同一家店, 不同人不同的分（个体偏差）
```

### 24.6 装备定制全流程（异步双机制）

```
顾客: 进店 → Browse 选定制款 → Order(定制) → Pay(定金) + 交材料
  → 店铺 BillQueue 新增 FBillOrder(客户ID, 已付定金, 交付期限)
  → 顾客流程休眠持久化, FAppointment 代办日程(事件Tag=订单完成, GracePeriod) 入 Agenda
  → 顾客离开, 正常过日子

店铺: 工匠 Duty 时段优先级表扫描 → 认领 BillOrder 对应 Craft 工单 → 生产
  → 完成 → 可交付 → 发射"订单完成"事件

顾客: 代办日程事件触发 → 唤醒流程, 从断点恢复 → 到店验货 → Pay(尾款) → 拿货

逾期未办分支: 超 GracePeriod 未到店 → 违约结算: 定金没收 + 差评 + 订单取消
```

### 24.7 深巷店铺用活动引流

```
玩家商业街在深巷, 无过路流量 → 路过发现失效:
  → 主街高流量点立指路牌（Campaign.Effect.FootTraffic, 发现半径延伸到主街位置）
  → 投传单派发（Reach: 每日触达 N 人, 按转化率直接写入 KnownShopIds）
  → NPC 认知到店, Free 时段决策:
      PersonalityMod（探索特质 → 陌生店好奇）+ QualityScore（有效声誉, 新店贝叶斯收缩保护）
      → 部分人专程前来
  → ProximityAtten（深巷远）自然过滤低意愿顾客——认知与到访分工
  → 到店体验 → 声誉积累 → 口碑记忆（5.2 第二途径）接力
```

### 24.8 店主经营决策循环

```
酒馆店主（保守性格, 每周决策）:
  周一决策点到 → 评估:
    库存: 麦酒低于警戒水位 → 下采购单（外部市场, 供应商配送）
    资金: 余额充足 → 不调价（保守倾向）
    工单积压: 饭点 Serve 工单积压 → 提招聘需求（委托玩家安排）
    知名度: 低 → 不投活动（保守倾向）

  突发事件: 连续三条差评 → 不等周期立即触发 → 调价 / 店主亲自顶岗服务
```

### 24.9 组团消费

```
NPC 甲 Hunger 急 + 社交意愿高:
  → 从 SocialMemories 挑两个好友乙、丙发起邀请
  → 乙: Hunger 也低 + Free 时段 + 与甲亲密度高 → 入团
  → 丙: Duty 时段（在上班）→ 拒绝
  → 甲跑评分选餐厅 X → 乙对 X 的评分高于否决线 → 同行
  → 同店消费（座位按团整体处理）→ 聊天互动回填 Social 需求
  → 两人各自写记忆 + 店铺声誉样本 +2
```

## 25. 设计决策总结

| 决策 | 选择 | 理由 |
|------|------|------|
| 消费决策机制 | Utility 加法核（可补偿）+ 衰减器 + 修饰器 | Sims needs-based 结构，随机效用理论背书；连乘被零值一棍子打死，加法核允许补偿 |
| 工作决策机制 | 员工侧 0-4 优先级表 × 任务侧 Priority 分带两层扫描，不走评分公式 | RimWorld 式，可靠可控；员工意愿与任务紧急度正交；"岗位"概念由优先级表吸收 |
| 工作优先级交互 | 优先级矩阵点击格子循环 0→4 | RimWorld 原版交互，直接点击切换档位 |
| 工作熟练度 | 接入现有属性管线（Creature.Attribute.Skill.* 命名空间），一级能力 × 特质修正 + 对数收敛经验 | 与战斗数值同源（全员皆兵）；复用 FDerivedAttributeDef/AttributeModifier 零新机制；对数收敛避免数值失控 |
| 员工状态 | 精力/情绪/忠诚度三需求走 Dynamics + 阈值规则 EffectModifiers | 需求变化本身即产生 BUFF，全配置化；作用点统一为 WorkEfficiency |
| 待机/偷懒 | 纯配置表概率分流（性格+状态+监督修正）+ AI.Work.Tidy 杂务工单 | 偷懒只影响进度；被顾客指派任务时被抓才扣分；处置由玩家/店主决定，无自动加速辞职 |
| 店主决策 | 双层分离（个人层实时 / 经营层低频），性格驱动决策周期与倾向 | 店铺是持续经营体，店主休息不瘫痪；UShopkeeperDecisionComponent 挂店铺区域 |
| 招聘 | 人力市场为主（双点式直接选陌生人）+ 店主引入自带模板 + 熟人邀请；店主招员工走委托制 | 前期主要直接招聘陌生人；修改权限与关系度挂钩咬合脸盲玩法；议价可协商 |
| 消费/工作关系 | RoleContext 分流，不混合评分 | 角色是时段属性；两套算法各取所长 |
| 硬约束处理 | 硬过滤漏斗先于评分 | 营业状态/认知/价格上限是绝对约束，不该被分数补偿掉 |
| 决策触发 | 纯事件驱动 + 日程时段切换 | 没需求的 NPC 零开销；无激活时段不在图 |
| 候选范围 | 硬过滤 + 按触发源 + 空间优先级缩小 | 高效，不全量评 |
| 四层分离 | 功能/状态/任务/动机分开 | 概念清晰，数据归属明确 |
| 任务归属 | 区域看板统一管理 + 租约制 | 道具/流程上报，看板分发；租约修补认领人消失死锁 |
| 消费流程 | FBusinessFlowConfig 配置化 + FActionJob 流程解释器 | 新店铺类型零代码；流程可休眠持久化支撑定制等长周期业务 |
| 代办日程语义 | FAppointment = 义务/待办（非社交约会），逾期称"逾期未办" | 避免"约会/爽约"歧义；组团消费另行设计（8.7） |
| 组团消费 | 发起者选店 + 同伴否决权 | 发起者是"组局的人"，最自然；社交需求合法满足 + 口碑载体 |
| 评价体系 | 期望带模型（SERVQUAL 期望差） | 需求驱动行为、期望评判体验彻底分离；权重=底线免配权重表 |
| 排队忍耐 | 并入期望带（Service 维度） | 预估与实判同一把尺；废弃 QueueTimeoutSec 常量 |
| 口碑 | 双层模型 + 贝叶斯收缩 | 个体记忆管复购，店铺声誉管传播；新店不被两条差评打死 |
| 经济 | 无钱包余额 + 逐商品定价 + 店铺账本 | 意愿模型替代支付能力；禁止调价系数；账本服务经营玩法 |
| 广告/知名度 | FShopCampaign 标准活动模型（凡持续投入的活动统一），触达直接写入认知 | 认知与到访分工：广告无强制到访特权，留客靠声誉与体验；深巷设定下绕过"必须路过" |
| 供应链 | 三通道货源（外部市场配送 / 街区 B2B / 探索素材）+ 供应商配送 | 简单起步不占员工；探索素材与战斗冒险设定联动；缺货后果链接店主紧急决策 |
| 行为外化 | 两层信息分离（身份按关系度门槛 / 行为永远可见）+ 关键节点才发 | 脸盲限制"这是谁"不限制"在干什么"；素体也演，行为是观察玩法通道 |
| SpawnArea | 地图切换点（MMO 式），NPC 出场与玩家探索共用一套数据 | 居住区显式绑定查表；人口总量静态，模拟流量分布 |
| 决策 LOD | 三档（全量/简化/休眠）+ 重要度优先定档 | 玩家关注点永远全量；玩家店铺永不休眠；休眠不是删除 |
| 出场刷新 | 日程出场规则为唯一判据 | 事件驱动不轮询；无激活时段零计算 |
| 兜底行为 | 闲逛 → 回家链 | 闲逛是 Leisure 合法满足途径；废弃"空闲超时"字段 |
| 记忆系统 | 复用 FLifeHistoryEntry 不加字段 | 信息已在事件 Outcome 里；记忆附带店铺 ID 即认知来源 |
| 战斗模式 | 同框架换 Config | 不建独立系统 |
| 突发任务/天气/情报 | 只留口子不实现 | 突发事件按"可转任务"结构设计；天气只留 WeatherMod 槽位；情报只留玩家侧 NPC 档案 |
| Tag 化 | 业务概念全 Tag | 不引入新 Enum 来分类；AspectTag 与需求 Tag 解耦 |
| 等待模型 | 服务等待段统一原语（预警档 + 按承诺度三分支放弃），QueueAt 是其排队实例 | 所有等待一个逻辑；预估与实判同一把尺；投诉→工单提带闭环 |
| 节点骨架 | 五原语段（Goto/Acquire/Advance/Settle/Release），Advance 自驱/服务驱双驱动，子进度序列承载多品项 | 断点粒度=节点+段+子进度 |
| 记忆计数 | 个体记忆只走 MemoryMod，有效声誉保持店铺层纯统计 | 消除双重计数；双层模型各司其职 |
| 店主自治 | 分域自治：经营四域店主自主，人事归玩家；关系度解锁商量 | 关系度即影响力；商圈人事权归玩家 |
| 关系度 | 玩家角色↔NPC 双向（FSocialMemory），全体 NPC 适用；被动眼熟+主动互动+单方备注并行 | 破脸盲冷启动悖论；老板站店有经营收益 |
| 玩家指令 | 指派工单/驱赶两件套 + 委托/外派统一走 FAppointment；玩家角色进排班不领工资 | 即时救火与长期调表分层；指令体系不新增机制 |
| 递归护栏 | 决策异步队列 + 失败源冷却 + 计数器重置 + 级联上限 3 次 | 事件驱动数学上保证收敛 |
| LOD 切割 | 只降决策精度与演出，数据层永不降档 | 远离时世界照常运转，回来账本声誉对得上 |
| 打断与边界 | Critical 段边界强制打断；RoleContext 延迟生效；加班意愿性格调制；工单预估×K 强制失败；打烊事件清场 | 一套段边界语义覆盖打断/下班/打烊 |
| 等待社交 | 服务驱等待段触发互动池（闲聊/拼桌/打招呼/抱怨传染） | 等待有内容；外化密度对准观察热点 |
| 认知写入 | 与"在图"解耦：图内真实感知 + 图外流量池抽象结算；指路牌物理摆放+双层感知 | 深巷引流真正生效；ProximityAtten 柔性曲线 |
