## 核心原则

### 1. 唯一性原则
- 每个主题只能有一个**主文档**
- 避免文档内容重复和版本分散

### 2. 层级原则
- 清晰的层级关系：总览 → 分类 → 详情
- 单一职责：每个文档只负责一个明确主题

### 3. 可发现性原则
- 通过统一的命名和索引，快速定位文档
- 减少查找时间

### 4. 可维护性原则
- 文档结构稳定，避免频繁重构
- 修改时影响范围最小化

## 命名规范

### 基本命名格式

```
[前缀-][主题-][子主题-][类型.]md
```

### 命名规则详解

#### 1. 前缀规则（可选）

| 前缀 | 用途 | 示例 |
|------|------|------|
| `Phase[数字]-` | 阶段标识 | `Phase1-测试指南.md` |
| `v[数字]` | 版本标识 | `v2.0-架构设计.md`（仅用于历史归档） |
| `[YYYYMMDD]-` | 日期标识 | `20260112-会议记录.md`（临时文档） |

**注意**：主文档不使用版本前缀，版本前缀仅用于归档。

#### 2. 主题命名规则

**中文文档**：
- 使用中文描述性名称
- 避免英文混用（专有名词除外）
- 使用 `-` 分隔多个词汇

**示例**：
```
✅ 正确:
- 编辑系统架构.md
- 体素位置传输规范.md
- 自然环境系统设计.md

❌ 错误:
- Voxel编辑系统.md
- 编辑系统-架构-v2.md
- EditingSystemArch.md
```

**英文文档**：
- 使用 PascalCase 或 kebab-case
- 优先使用 kebab-case（小写+连字符）

**示例**：
```
✅ 正确:
- world-subsystem-design.md
- voxel-position-spec.md

❌ 错误:
- WorldSubsystemDesign.md
- world_subsystem_design.md
```

#### 3. 文档类型后缀（推荐）

| 类型后缀 | 用途 | 示例 |
|---------|------|------|
| `-设计.md` | 系统设计文档 | `预览系统-设计.md` |
| `-规范.md` | 规范类文档 | `命名规范.md` |
| `-指南.md` | 操作指南 | `测试指南.md` |
| `-报告.md` | 分析/测试报告 | `性能分析报告.md` |
| `-清单.md` | 检查清单 | `代码审查清单.md` |
| `-总结.md` | 总结文档 | `Phase1-总结.md` |
| `-参考.md` | 快速参考 | `API快速参考.md` |

### 特殊文档命名

#### 索引文件（固定命名）
```
README.md       # 目录入口和总览
INDEX.md        # 仅用于大型子目录的文档索引
```

#### 模板文件
```
_template-报告.md    # 报告模板
_template-计划.md    # 计划模板
```

## 颗粒度规范

### 文档粒度层级

```
层级 1: 总览文档（1000-5000 字）
├── 描述整体架构、流程、概览
├── 包含导航和快速链接
└── 示例：README.md、项目概览.md

层级 2: 分类文档（3000-10000 字）
├── 描述一个主要分类/模块
├── 包含多个子主题的概览
└── 示例：编辑系统架构.md、测试指南.md

层级 3: 详情文档（5000-20000 字）
├── 详细描述一个具体主题
├── 包含完整的技术细节、代码示例
└── 示例：预览系统-设计.md、撤销重做系统-实现.md

层级 4: 专项文档（1000-5000 字）
├── 针对某个具体问题的文档
├── 示例：特定Bug分析、性能优化记录
└── 示例：20260112-内存泄漏分析.md
```

### 文档拆分原则

#### 应该拆分的情况

**情况 1: 文档过长（>20000 字）**
```
原: 编辑系统-设计.md (25000 字)
↓ 拆分为
├── 编辑系统-架构.md        # 架构设计 (8000 字)
├── 编辑系统-组件设计.md    # 组件详细设计 (10000 字)
└── 编辑系统-交互流程.md    # 交互和API (7000 字)
```

**情况 2: 多个独立主题**
```
原: Phase1-文档集.md
↓ 拆分为
├── Phase1-测试指南.md
├── Phase1-测试报告.md
└── Phase1-总结.md
```

**情况 3: 不同受众**
```
原: 测试文档.md (包含测试指南和测试报告)
↓ 拆分为
├── 测试指南.md        # 给测试人员
└── 测试报告模板.md    # 给填写报告的人
```

#### 不应该拆分的情况

**情况 1: 内容高度关联**
```
❌ 错误拆分:
├── 变量命名规范.md
├── 函数命名规范.md
└── 类命名规范.md

✅ 正确合并:
└── 命名规范.md        # 包含所有命名规则
```

**情况 2: 每个部分都很短（<3000 字）**
```
❌ 错误拆分:
├── 编辑系统-概述.md       (1000 字)
├── 编辑系统-架构.md       (1500 字)
└── 编辑系统-接口.md       (1200 字)

✅ 正确合并:
└── 编辑系统-设计.md       (3700 字)
```

## 索引文件规范

### README.md 规范

**用途**：目录入口和总览

**必须包含**：
```markdown
# [目录名称]

本目录包含 [说明]

---

## 目录结构

## 快速导航

## 使用指南

## 相关文档
```

**每个一级子目录都应该有 README.md**

### INDEX.md 规范

**用途**：大型子目录的文档索引（可选）

**使用条件**：
- 子目录下有 **5个以上** 的文档
- 或者文档层级超过 **2层**

**必须包含**：
```markdown
# [主题] 文档索引

## 文档列表

## 快速查找

## 相关链接
```

### 索引文件决策树

```
子目录有文档吗？
├── 否 → 不需要索引文件
└── 是 → 文档数量 > 5 或 层级 > 2？
    ├── 是 → 创建 INDEX.md
    └── 否 → 依赖上级 README.md
```

## 文档合并决策规则

### 合并检查清单

在合并文档前，检查以下问题：

#### 1. 内容相关性检查

**问题**：这些文档是否描述同一个主题？

| 相关性 | 决策 |
|-------|------|
| 完全相同主题 | ✅ **应该合并** |
| 高度相关（同一主题的不同方面） | ⚠️ **评估后决定** |
| 中度相关（同一大类下的不同主题） | ❌ **不应该合并** |
| 低度相关（只是类别相同） | ❌ **绝对不应该合并** |

**示例**：

```
✅ 应该合并:
├── Phase1-测试指南.md
├── Phase1-测试指南-Revised.md
└── Phase1-测试指南-Scene1.md
→ 合并为: Phase1-测试指南.md

❌ 不应该合并:
├── 预览系统-设计.md
├── 选择系统-设计.md
└── 编辑系统-设计.md
→ 保持分离（三个独立系统）
```

#### 2. 内容重复度检查

**问题**：文档之间有多少内容重复？

| 重复度 | 决策 |
|-------|------|
| > 70% | ✅ **必须合并**（选择最完整的版本） |
| 30-70% | ⚠️ **考虑合并**（提取公共部分） |
| < 30% | ❌ **不需要合并**（保持独立） |

#### 3. 维护成本检查

**问题**：分开维护会导致一致性问题吗？

```
评估场景:
├── 如果文档A更新，文档B也需要更新吗？
├── 是否经常出现版本不一致的问题？
└── 用户是否经常混淆这两个文档？

如果 2 个以上答案是 → 考虑合并
```

#### 4. 受众差异检查

**问题**：文档的目标受众是否不同？

```
不同受众 → 考虑分开:
├── 测试指南.md     → 测试人员
└── 测试报告模板.md → 项目经理

相同受众 → 考虑合并:
├── 架构设计-v1.md
└── 架构设计-v2.md
→ 合并为最新版本，旧版本归档
```

### 合并决策流程图

```
开始合并评估
    ↓
是否同一主题？ ──否→ ❌ 不合并
    ↓ 是
重复度 > 70%？ ──否→ ↓
    ↓ 是              受众是否不同？
选择最完整版本           └── 是 → ❌ 不分开文档
    ↓                   └── 否 → ⚠️ 评估
合并到主文档                      ↓
    ↓                    维护成本高？
标记旧版本为归档                   └── 是 → ✅ 合并
    ↓                          └── 否 → ❌ 不合并
完成
```

### 实际合并案例

#### 案例 1: 版本重复

```
现状:
├── 编辑系统-架构.md
└── 编辑系统-架构-v2.md

分析:
- ✅ 同一主题
- ✅ 重复度 > 70%
- ✅ 相同受众
- ✅ 维护成本高（需要同步更新）

决策: 合并

操作:
1. 比较 v1 和 v2，保留最新内容
2. 合并到: 编辑系统-架构.md
3. 归档 v2 为: _archive/编辑系统-架构-v2-旧版.md
```

#### 案例 2: 内容拆分过度

```
现状:
├── 变量命名规范.md
├── 函数命名规范.md
└── 类命名规范.md

分析:
- ✅ 高度相关（同一主题的不同方面）
- ✅ 每个文档都很短（<3000 字）
- ✅ 相同受众（开发者）
- ✅ 需要统一查看

决策: 合并

操作:
1. 创建新文档: 命名规范.md
2. 整合三个文档的内容为章节
3. 删除原有文档
```

#### 案例 3: 测试文档重复

```
现状:
├── Phase1-TestGuide-Revised-Scene1.md
└── 测试计划/Phase1测试指南.md

分析:
- ✅ 同一主题（Phase1 测试）
- ✅ 重复度 > 50%
- ✅ 相同受众
- ✅ 造成混乱

决策: 合并

操作:
1. 合并内容到: 测试计划/Phase1测试指南.md
2. 删除顶层重复文档
3. 在 README.md 中更新链接
```

## 文档新建决策规则

### 新建检查清单

在创建新文档前，回答以下问题：

#### 1. 必要性检查

**问题**：这个内容是否真的需要独立文档？

```
不需要新建文档的情况:
❌ 只是临时笔记 → 使用项目管理工具（Tasks, Notion等）
❌ 一次性的讨论 → 使用会议记录或 Issue 跟踪
❌ 可以放入现有文档 → 扩展现有文档
❌ 代码注释 → 使用代码文档工具（Doxygen）

需要新建文档的情况:
✅ 独立的主题，不适合放入现有文档
✅ 需要长期维护和更新
✅ 多人协作编写
✅ 需要独立版本管理
✅ 内容超过 3000 字
```

#### 2. 位置检查

**问题**：文档应该放在哪里？

```
决策流程:
1. 确定文档类型（设计/规范/测试/报告）
2. 查找对应的目录（03-系统设计/ 05-开发规范/ 等）
3. 检查是否已有类似文档
4. 决定是否新建或扩展现有文档
```

#### 3. 命名检查

**问题**：文档名称是否符合规范？

```
✅ 检查项:
- [ ] 使用中文描述性名称
- [ ] 避免版本号（主文档）
- [ ] 包含类型后缀（如果适用）
- [ ] 与同类文档命名一致

示例:
✅ 预览系统-设计.md
✅ Phase2-测试指南.md
❌ 预览系统设计-v2.md
❌ PreviewSystem.md
```

#### 4. 颗粒度检查

**问题**：文档的颗粒度是否合适？

```
评估:
- [ ] 文档预计长度是否在 3000-20000 字之间？
- [ ] 是否是单一明确主题？
- [ ] 是否与现有文档内容重复？
- [ ] 是否可以拆分为多个更小的文档？

如果预计 < 3000 字 → 考虑合并到相关文档
如果预计 > 20000 字 → 考虑拆分为多个文档
```

### 新建决策流程图

```
需要记录新内容？
    ↓
是否适合现有文档？ ──是→ ❌ 不新建，扩展现有文档
    ↓ 否
内容长度 > 3000 字？ ──否→ ❌ 不新建，使用笔记或 Issue
    ↓ 是
确定文档类型（设计/规范/测试/报告）
    ↓
检查目标目录
    ↓
是否有类似文档？
    ↓ 是
检查内容重复度 ──< 30% → ✅ 新建文档
    ↓ ≥ 30%
考虑合并 ──不合适 → ✅ 新建文档
    ↓ 合适
❌ 不新建，更新现有文档
```

## 版本管理规范

### 版本号规则

**主文档不使用版本号**，保持简洁。

版本号仅用于：
1. **归档旧版本**：`_archive/[原名称]-v[版本].md`
2. **区分阶段性文档**：`Phase[数字]-[文档名].md`

### 文档更新流程

```
文档需要更新
    ↓
更新内容到主文档
    ↓
在文档末尾的"更新日志"中记录
    ↓
如果改动很大（>50% 内容变化）
    ↓
保存旧版本到 _archive/
文件名: _archive/[文档名]-v[旧版本]-[YYYYMMDD].md
    ↓
完成更新
```

### 文档状态标记

在文档开头添加状态标记：

```markdown
**文档状态**: ✅ 最新版本 | ⚠️ 更新中 | 🔄 需要更新 | ❌ 已废弃
**最后更新**: 2026-01-12
**维护者**: [姓名]
```
