# 经营系统-最小版本设计逻辑清单-设计计划

**版本**: 0.50（讨论维护中）
**创建日期**: 2026-10-20
**最近更新**: 2026-11-04
**状态**: 设计逻辑清单；本清单只定义 V1 范围与验收，不含实现排期与 UI 细节（UI 后续原型探讨）。规则冲突以 [02 系统设计](/VoxelDesign/02-系统设计/AI决策系统-区域店铺与商圈管理-系统设计.md) 为规范，[03 架构设计](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md) 为运行时 / 存档依据。
**目标**: V1 只做沙盒，把「开店 → 经营 → 顾客消费 → 员工工作 → 账本/统计 → 租金/工资/贷款」这条基础流程完整跑通；不做主线，不做酒店/餐厅，不做多店与并购。

## 1. 世界与开局

- **地图**：只有玩家的商圈是实际内容，商圈外都是平地；地图大小不限制，按需要放。
- **商圈初始**：只有道路和空地；没有店铺、没有公共预算、没有其他 NPC 店铺。
- **NPC 来源**：开局生成一套有限的固定名册，顾客与员工都来自同一名册并使用稳定 `CreatureID`；`FactionTag` 等基础身份字段在名册生成时确定，阵营与种族、职业一样可直接用于客群统计，不依赖关系系统。NPC 从地图边缘 / 抽象住所进出，离场只回收实体、不删除名册数据，不做实体住宅。V1 名册中的普通居民与员工都使用抽象住所，普通居民的 `HomeAreaRef`（`{SceneId,AreaId}`）直接保存其抽象住所对应的 `SpawnArea.AreaId`，进图与回住所共用该点，不新增住所配置表或抽象住宅区域。V1 不做季节游客、行商、背景人或按流量临时刷人。
- **经营实体与区域**：经营实体是资产与经营业务的唯一所有者，由 Global `BusinessEntities` 唯一登记；商圈、店铺与图外生意共用同一基础模型，按类型组合业务模块（经营关系、`bOpen` / 营业时段、目录 / 订单 / 预留、声誉客流、商圈租务）。区域不是资产、不是经营实体，只承担空间范围、关系与校验：子区域只有 `AreaId`、不成为经营实体，抽象经营实体可以没有实际区域。经营 ID 统一用逻辑名 `BusinessEntityId`（底层实现未定，且不等同于 `AreaId`），空间引用统一用 `AreaRef{SceneId, AreaId}`，`ShopId` 只作为店铺经营 ID 的别名；NPC 的 `KnownShopIds` 是 `TSet<BusinessEntityId>`，认知指向经营实体，路过 / 导航另用空间引用。家具真实库存、工作点 FIFO、门锁与队列仍归现场实例，区域空间与设施索引不存业务镜像。
- **玩家身份**：
  - 受薪的商圈经营人（V1 沙盒标准月薪为 0，仍保留薪酬制关系；零工资只跳过工资流水）；
  - 自己店铺的承租经营人（V1 标准月租为 0，仍保留承租关系；零租金不产生流水或负债）。
- **开局资金**：玩家主角个人钱包为 0，唯一经营账户为 0；商圈没有独立余额，商圈业务使用抽象产权人游商的唯一经营账户，玩家不能划转该账户。玩家必须申请**经营贷款**，放款进入自己的经营账户后开始店铺经营。
- **公共设施**：V1 不做专属公共设施，也不产生公共设施类维护扣费；商圈区域内放置的普通家具仍注册到商圈设施索引并产生保洁/维修工单，由普通员工认领。

## 2. 时间与日历

- **1x：1 游戏日 = 24 现实分钟**（1 现实秒 = 1 游戏分钟）。
- 速度：暂停 / 1x / 2x / 3x / 4x / 8x。
- 逻辑频率固定为 **30 tick/现实秒**，不随倍速增加；1x 下 **1 tick = 2 游戏秒**。
  - 倍速放大每 tick 推进的游戏时间：1x/2x/3x/4x/8x 分别推进 2/4/6/8/16 游戏秒；
  - 1 游戏小时 = 1,800 tick，1 游戏日 = 43,200 tick（均指 1x 逻辑频率下的换算）；
  - 业务时长统一使用游戏秒，随倍速缩放、随暂停冻结。
- 暂停是**游戏时间暂停**：需求、日程、营业切换、租约与贷款结算计时、NPC 经营模拟冻结；UI、镜头和建造操作不被禁用。
- 日历：**一周 6 天、一月 5 周 = 30 天、一年 12 个月 = 360 天**；周期长度进配置表，当前日期时间入档，V1 不支持同一存档运行中修改周期长度。
- 日界：**00:00**。
  - 日界不打断营业 / 班次 / NPC 行为；
  - 统计、日结按日历日切；
  - 月界用于月度统计与日历切换；租金按商圈配置的收租时间结算，贷款按各借据生成时写入的扣费时间结算，不要求二者统一在月界执行；
- 小时边界：营业时段、排班、班次在整点校验一次；其他系统按游戏时间连续推进。
- 日界、月界、整点、日程时段切换由时间系统统一发布事件。高倍速一次跨过多个边界时按时间顺序补发，但**补发受单帧预算约束**：单帧 tick 次数上限、墙钟预算（约 1000/22 毫秒）、超限时**丢弃剩余积压并让 `GameTimeSec` 直接前进**。允许跳过部分边界事件，不允许一帧爆量或长时间卡顿；业务侧必须能容忍边界事件缺失（以当前时间戳为准重新对齐状态）。
- 六条需求按带符号的配置变化率与游戏时间增量变化；行为回填和事件脉冲也走同一数值入口。比较变化前后值并按阈值声明方向检测实际跨阈，阈值事件才触发决策，不做每 tick 全量候选重算。**V1 例外：员工位于其有效雇佣关系对应的工作 Shop 区域内时，会导致需求下降的自然时间变化与工作负向增量均不应用；离开工作区域后恢复。已有需求值与 Critical 状态不清空，正向回填仍走统一入口。**

详见 [时间系统-系统设计](/VoxelDesign/02-系统设计/时间系统-系统设计.md)。

## 3. 贷款与资金

- **个人钱包与唯一经营账户分离**：每个实际 / 抽象人物都建一个个人钱包与一个唯一经营账户，同一经营者名下的所有生意共用该经营账户，不按区域拆分、不另设第二套账户。商圈、店铺、子功能区与图外生意都只是经营实体的业务模块或空间范围，不保存独立资金账户或余额；账本 / 统计视图只按唯一流水展示收入、支出与净额。
- **资金责任人**：每笔付款实时解析经营实体的资金责任人：产权人自营 / 承租经营的店铺使用经营人的经营账户，薪酬制经营的店铺 / 商圈使用产权人的经营账户；Shop 产权人继续继承商圈产权人。销售、采购、工资、租金与经营贷款都先按经营实体解析业务归属，再解析资金责任人的经营账户。
- **统一结算与唯一流水**：消费从消费者个人钱包进入店铺经营实体的经营账户，工资（含图外 NPC 的真实雇佣合同）从雇主经营实体账户进入员工个人钱包，租金在出租方 / 承租方两个经营实体账户之间划转；贷款、即时采购等抽象对手方业务使用系统单边入账 / 扣款记录，但不新增系统单边工资。一笔结算只保存一条流水，原子提交，不保存双方副本。
- **运行时存储**：世界经营注册表（Global 经济子系统）保存个人钱包、经营账户与唯一流水，经营实体由 Global `BusinessEntities` 唯一登记；人物保存 `PersonalWalletAccountId` 与 `BusinessWalletAccountId`（每个实际 / 抽象人物各一份），区域不存 `AccountId`。余额、价格、应付与成交金额使用 `int64` 整数金，数量仍用 `int32`；0 元销售 / 采购可记流水，普通手动划转金额必须大于 0。
- 一条流水同时保存 `SourceBusinessEntityId` / `TargetBusinessEntityId` 与可空的 `OccurredAreaRef{SceneId, AreaId}`：财务只记一次，商圈 / 店铺 / 图外生意按经营实体分别统计，区域只作发生位置。租金等双边业务两侧都记经营实体归属；区域改挂或经营实体易主都不回改历史流水，新流水按新归属记录；这些归属只用于业务账，不生成区域资金分账户。
- 经营实体的 Owner / Manager 可查看该实体业务流水和资金责任人的经营账户可用资金；受薪经营人不能查看产权人的个人流水，也不能划转产权人的个人钱包或经营账户。权限按当前经营关系与业务类型实时计算，不保存“可操作”标志，也不以是否为玩家主角色判定。
- **余额规则按业务类型确定**：
  - 消费、即时采购、个人之间付款与本人个人钱包 ↔ 经营账户的普通手动划转必须足额；源账户 `Balance >= Amount` 才执行，否则整笔失败且不扣负。消费仍在 Browse 与结账检查。
  - V1 只有**经营贷款还款、店铺租金、工资**允许源经营账户扣负；到期直接足额结算并执行对应业务，不做余额不足失败。该权限由业务结算器内部使用，不开放给普通划转 UI。
  - 贷款不生成逾期，租金不生成欠租 / 坏账或连续失败次数，工资不生成未领薪状态或欠薪债务。负余额本身不触发破产、收资产、收铺或离职；后续其他费用若需扣负必须单独加入业务白名单。
  - 不同业务按计划时间先后执行；计划时间完全相同时，先执行必须验足额的费用，再执行允许扣负的白名单费用。例：经营账户 1000，同时应付采购 800、工资 500，先付采购成功，再发工资，最终余额 -300。
- 玩家作为承租经营人，店铺收支使用自己的唯一经营账户；本人可在个人钱包与经营账户之间双向手动注资 / 提取，普通转出仍须源账户足额。该账户不按 Shop / 商圈拆分。
- 玩家作为受薪商圈经营人可查看商圈业务流水和经营账户可用资金，并执行授权经营支出；扣款来自商圈产权人游商的经营账户，不从玩家个人钱包支出，也不允许玩家借此划转游商资金。玩家自己的月薪从游商经营账户进入玩家个人钱包。
- 工资从雇主业务对应的经营账户足额转入员工个人钱包，允许经营账户因此为负；不再设置 `bWageUnpaid`、未领薪忠诚衰减或工资不足自动离职，也不需要员工之间的工资竞争排序。
- NPC 与玩家复用同一账户基础模型；每个实际 / 抽象人物都建个人钱包与唯一经营账户。V1 实现初始资金、真实经营收入、个人工资入账、个人消费扣款、经营支出和存档。V1 **选店评分不读个人钱包**，只由意愿 + 期望带决定是否选店；到店 Browse 揭示真实价格后检查个人钱包，买不起则不生成预留并按既有规则离店；结账再次校验真实余额，不足则整笔失败。不按职业 / 阶层定期生成收入；失业且没有其他实际收入时收入为 0（真没钱）。非主地图雇工按真实雇佣合同与工资条款把工资回流到个人钱包，不因工作生成 Actor、工单或寻路执行；图外雇主为抽象账户（`bAbstract=true`，不计余额），支出直接发生、不补资（03A §5.9），工资付款实时解析经营实体资金责任人，不新增系统单边工资。
- 贷款是玩家主角的**经营债务**，债务主体仍是主角，不按店铺或商圈分债；V1 放贷方为**抽象银行**，放款与还款都走主角唯一经营账户。
- V1 贷款产品不做固定档位：抽象银行每次向玩家展示 **5 个全随机报价**，每个报价由本金、名义年利率和期限三项独立随机生成：
  - 本金从 200,000～8,000,000 中按 10,000 步长取整数档；
  - 名义年利率从 3%～15% 的整数百分点中取；
  - 期限从 12～360 的整数月中取。
- 报价生命周期：
  - 新游戏首次打开贷款页生成 5 个报价；
  - 借走一个后该位置保持空缺，不立即补位；每个游戏月开始时只把空缺补满至 5 个，不替换尚未借走的报价；
  - 最多同时持有 5 笔贷款，不提供手动刷新；重新打开界面、暂停恢复或读档都不能重摇报价；
  - 报价与借据都保存生成时的实际本金、利率、期限和固定月还本金，后续生成参数变化不回写存量。
- **等额本金月供**：
  - 设本金为 `P`、名义年利率为 `R%`、期限为 `n` 月，月利率 `r = R / 100 / 12`。固定月还本金 `B = RoundHalfUp(P / n)`；`RoundHalfUp` 对非负数表示 `floor(x + 0.5)`，结果为整数金。
  - 常规期应还本金为 `B`；当期利息 `I = RoundHalfUp(剩余本金 × r)`；当期扣款 = 应还本金 + 当期利息。最后一期应还本金改为全部剩余本金，用于结清取整尾差。
  - 每笔借据从各自放款成功时刻起按月扣费，不统一挂在全局月界；多笔借据按各自下一扣费时间独立结算，高倍速跨期时按时间顺序逐期执行。
  - 月供从主角唯一经营账户直接足额扣除，允许因此变为负数；不记逾期、不部分扣款、不强制破产或收资产。
  - 可以提前还款；提前还款只结当时剩余本金，不再收未来利息，不设违约金。所有已产生月供均已直接结算，因此没有额外未付利息或逾期金额。
- 生成扩展口：V1 只从统一配置读取报价数量、本金上下限与步长、利率上下限、期限上下限、同时持债上限、补充周期和随机权重；后续再接入信用、收入、经营表现、放贷方、期限结构、浮动利率和附加条款修正器，不改借据快照边界。

## 4. 建造与开店

**流程**：

```
贷款 → 同一建造面板：**先选区域类型与业态 → 框选 Shop 区域** → 填信息 / 确认
→ 后台一次完成经营实体 + 空间 + 经营关系 / 标准租约 / 劳动安排 / 首期按比例结算
→ 继续装修
→ 招聘 / 进货 / 上架 → 开业（不做设施校验）
```

- **一次创建、先签约再建房**：开局由抽象产权人预先提供标准承租授权与条款；玩家在同一个建造面板拉区域、填信息、确认后，后台一次完成经营实体注册、空间区域、经营关系、标准租约（含首期按比例结算）与劳动安排，稳定 `LeaseId` 随即生效，成功后直接进入装修，不跳详情页补建、不手动绑定。有效租约必须先于真实租户的建造 / 家具写入，之后才允许玩家以租户身份建房、装修。
- 玩家不能凭商圈经营人权限批准或修改自己作为乙方的合同；该合同只能由产权人办理。玩家若同时具有产权人身份，才可按产权人权限处理。
- 每次新承租关系生成新 `LeaseId`，退租后重签不复用旧 ID；硬装改动日志与家具 `PlacedByLeaseId` 必须在落点时引用已生效租约。
- **建造 / 装修 V1 全免费**，先跑通流程，经济后续再加。
- 店铺区域归商圈；签约前已有结构仍归产权方，签约后玩家新建、改造的建筑和装修作为承租户资产归玩家。
- **业态**：V1 只做**杂货店**。业态与区域类型是两个独立分类维度——业态走 `Business.Kind.*`（具体取值由业态配置资产定义），区域类型只表达空间用途（店铺空间 / 子功能区），不承担业态身份；不新增重复 `BusinessType` 实例字段。**业态在组合创建面板选定（先选业态与区域类型，再框选区域）**；创建后变更须走**业态变更申请流程**（申请 → 审批 → 生效），不得用普通资料表单或简单 setter 直接改。配置表结构与杂货行后续实施，见 [AI决策系统-业态模板-系统设计](/VoxelDesign/02-系统设计/AI决策系统-业态模板-系统设计.md)。
- **开业不做校验**：人工开业不校验任何设施（05 决策29），`bOpen` 直接可置。业态的「必需设施」保留为**运行期提醒项**：V1 杂货店关注可售存储 ≥1、收银台（`FCashierFuncFragment`）≥1，缺失时给去重、带冷却的提醒，不关店、不改 `bOpen`。`slot_staff_cashier` 只是收银台内部的员工交互点；服务点、工作点队列和工单不在业态表中配置。入口同样只提醒：无门、被墙封死或导航不可达都允许开业，NPC 进不来自然没有客流。
- **保存并退出建造**：不阻断。退出时按当前业态的设施需求生成缺失清单作提醒，但不阻止退出、不锁在建造模式；开业同样不做设施校验，缺失项由运行期提醒给出。
- 仓库用 Shop 下的子功能区表达，内部放置非售储物家具。独立仓库是可选的空间组织方式，后备储物家具也可放在营业空间；V1 不做地面堆放区，仓库子功能区本身不持有库存或容量。
- 开业不查员工 / 库存 / 入口导航；缺员工 / 缺货是经营问题，服务自然劣化；运行期拆除必需设施不触发系统关店，只靠服务劣化与维修工单体现；商品目录无商品或货架无库存给提醒。
- 店铺状态只手动入档 `bOpen`（人工开业 / 停业总开关）；`bOperating`（运营中 / 打烊）是 `bOpen && 当前处于生效营业时段` 的纯派生值，不写入存档、不保存第二个布尔、不使用 `EAreaStatus`，也没有替代状态。实际接客要求 `bOperating` 为真；`bOpen=false` 时一律不接客。创建 / 签约 / 建成后默认 `bOpen=false`（只是建成，不是开业），手动点开业并通过硬校验才置 true。
- **开业入口**：UI 只调用 Controller 开业业务方法；业务方法校验权限与业态必需设施，失败直接返回缺失清单，成功才提交 `bOpen=true` 并发布 `Shop.StateChanged`。不新增 `Shop.OpenRequested` / `Shop.OpenRejected`，也不由 UI 直接写字段；`bOperating` 由营业时段派生，无需任何组件写入。
- **时段切换与营业派生**：进入 / 退出营业时段只切换时段事实，`bOperating` 随之派生，不再按当前必需设施重新校验、不设替代状态、不在中途自动补验；`bOpen=false` 时绝不自动开业。延长营业同样只改时段，不绕过 `bOpen`；运行期拆除必需设施不触发系统关店，只靠服务劣化与维修工单体现。

## 5. 商品、库存、采购

- **商品**：V1 只做**食品 + 饮料**。
  - 购买行为产生的 Shopping、Mood 等体验由消费者 Flow 在成交结果发布后，根据其当前需求、性格、特性与本次购买上下文结算；商品目录不设置固定购买效果字段，`CheckoutSale` 不负责买家体验。
  - 食品／饮料的使用基础作用只配置在 `LinkedItemId` 的 `FConsumeFuncFragment.Effect`：食品 `LinkedDemand = Hunger`，饮料 `LinkedDemand = Thirst`，实际食用／饮用时以正值 `EffectValue` 进入统一 `ApplyDemandDelta`，不在商品目录重复配置。
  - 食品 / 饮料作为杂货业态的允许经营品类进入业态配置；商品目录、售价和补货阈值属于店铺经营数据，实际库存按店铺归属存于家具实例。
- **价格**：
  - 当前市场基本价直接取现有物品配置 `FVoxelItemCirculateDataFragment.Value`，不是另建市场价格表；售价是玩家在店铺商品目录里手动调的运行时数据，默认取该基本价。
  - V1 食品／饮料的基本价必须大于 0 以使用百分比价格体验；其他物品 0 元基础价合法性不变，其百分比价格体验不在本项扩展。单商品 `PremiumRate = (Price - Value) / Value`，`PriceFavorDelta = -PremiumRate`：高于基本价 20% 则价格好感 −20%，低于基本价 20% 则 +20%，等于基本价不增减。价格好感由消费者购买行为结算，不直接修改人际关系。
  - 远程店铺价位档使用当前已上架商品 `PremiumRate` 的平均值，查询时派生，不另存店铺价格副本；个人 `Expectations[Price].Max` 比较的是可接受溢价率。到店仍揭示真实货币价格，成交评价使用实际商品的同一溢价率。V1 不做动态市场价、供需波动或区域行情。
  - `Price` 与可交易物品 `Value` 均只接受有限且 ≥0 的数值，不设固定上限；0 元采购与 0 元销售合法。负数、NaN、Infinity 的定价输入拒绝并保留旧值，无效 `Value` 配置不得采购或上架，不自动按 0 修正；
  - 0 元采购仍校验后备容量并原子入库、记流水；0 元销售仍走同一原子结账、扣货、入包与流水，金额为 0，不产生付款不足。
- **ITEM 实例与堆叠**：
  - 所有 ITEM 都有 float `HitPoints`，静态行保存 `MaxHitPoints`；`Integrity = HitPoints / MaxHitPoints` 只派生，不另存。普通 ITEM 的 HP 归零时保留实例、不可使用、可维修；消耗品使用消耗与堆数量耗尽按各自规则销毁实例，不要求先扣 HP；
  - 容器槽位只引用 ITEM 实例，数量与实例状态由 ITEM 持有，槽位不复制 `ItemId + Quantity + HP / Cleanliness / Quality`。纯移动不改变实例，数量耗尽后清空引用；
  - 不同品质不能共槽、共堆；可放置不妨碍堆叠，花朵、罐子等可以同时可放置、可堆叠；
  - 清洁度只在放置 OBJECT 中推进，ITEM 只保存收起时的值；重新放置恢复后续计算。不同清洁度合并时按实际移动数量加权，拆分复制、纯移动不变，部分合并未移动的源堆保留原值；
  - V1 不执行新鲜度扣减、腐败进度推进、到期判断或自然 `Spoiled` 转换，`ShelfLifeSec / PreserveFactor` 只作后续预留；不触发自然变质的出售、食用、加工、丢弃或损耗；
  - 所有 ITEM 有 HP 不代表 V1 给工具等物品种类新增消耗或损耗链；不同 HP 与清洁度采用同一实际移动数量加权合并规则，拆分复制、纯移动不变，HP 为 float、不取整，HP0 合并不另设例外。
- **采购**：V1 不做供应商、采购单或在途配送。玩家选择商品与数量，按物品基础价计算货款；校验店铺资金责任人的经营账户余额和兼容后备储存容量后，原子完成扣款、后备储存入库与店铺采购流水。余额或容量不足整笔失败，不生成应付账款。
- **库存**：
  - 真实库存只存在家具实例容器中：`bForSale=false` 为后备储存，`bForSale=true` 为可售货架；店铺库存是这些容器的聚合视图，不另存一份总库存；
  - 独立仓库子功能区只是后备储物家具的空间组织，继承店铺核算，不形成独立库存；
  - 即时采购只进入后备储存；**补货阈值按全仓库合计判定**（货架+后备），低于阈值且后备有货时理货员把后备商品搬到可售货架，顾客只能购买货架现货；后备为空只提醒库存不足；
  - 后备储存与可售货架分别按自身家具容量和物品过滤条件计算；采购校验后备容量，补货校验目标货架容量，不使用“仓库面积 + 货架容量”的虚拟总容量。
- 商品目录 / 上架 / 下架 / 定价由玩家操作。

## 6. 人力

- **招聘**：
  - 招聘板只从固定名册中当前**无有效雇佣记录**的 NPC 选取候选，每次最多展示 5 人；不足 5 人时如实显示实际人数，不生成或复制 NPC 补齐；图外就业同样是有效雇佣合同，不吞合同、不补造人口、不擅自决定换工政策；
  - V1 同时支持定期刷新和手动刷新，手动刷新免费；刷新只改变展示人选，不模拟人口流动。后续手动刷新可收费，不愿付费可等待定期刷新；
- **雇佣登记**：
  - 全部有效雇佣由 Global 统一登记管理；同一 NPC 同一时间最多一条有效记录，店铺、商圈与 NPC 不分别保存合同副本。雇佣记录只保存合同与工资，雇主一律用 `EmployerBusinessEntityId` 指向经营实体，招聘板直接查询无有效雇佣记录的名册 NPC；
  - 雇佣记录只保存合同与工资；劳动安排（排班 / 工作优先级 / 工作区）挂在 `Creature` 上，不写进雇佣记录，NPC 工作日程只引用 `Creature` 的劳动安排；离职即移出有效登记，V1 不保存履历，但保留后续接收终止记录、离职时间与原因的扩展口；
  - V1 不做加班逻辑或加班合同字段，不做班次外召回与加班费；延长营业只改变店铺时段，员工仍按 `Creature` 上的原排班离岗。
- **岗位 / 工单**：V1 开放**收银 + 补货 + 清洁 + 维修**四类工单。
- **员工行为**：员工在排班表 + 工作优先级矩阵下，按优先级抢收银 / 补货 / 清洁 / 维修工单。
- **工作区需求**：员工位于其工作 Shop 区域内时，六条需求不因自然时间或工作动作下降，离开工作区恢复；已有需求值与 Critical 状态不清空，不新增冻结字段。
- **员工休息 / 用餐 / 睡眠**：Rest、Dine、Sleep 均离店或回抽象住所，不使用员工专用设施或店内客座。V1 只有一个经营店铺，不开放员工去别家店消费，不生成跨店排队、付款、座位或销售流水；后续多店版本再评估。
- **设施维护**：清洁度或 HP 低于各自维护阈值时降低使用效果并自动产生对应工单，不直接停用设施；清洁度为 0 时降低 NPC 使用欲望，HP 为 0 时仍可使用但无功能效果。清洁 / 维修完成后恢复对应状态与效果。
- **收银工单与待机**：
  - 首位顾客完成选品并进入收银队列时生成 `AI.Work.Cashier`；以收银台实例去重，不按单个顾客生成，员工占用 `slot_staff_cashier` 后按 FIFO 连续服务；
  - 队列清空才完成工单；没有顾客时不生成常驻收银工单；
  - 只有除 Cashier 外其他工种优先级全部为 0 的单职责员工，完工后才留在原收银工位待机。待机不是工单、不产生额外薪资；启用其他工种的员工完工后重新扫描看板。
- **玩家角色**：
  - 也在排班表和工作优先级表里；每个角色有 `bAutonomyEnabled`，新游戏默认关闭，玩家可手动开关；
  - 自主开启且未被直接操控时，复用同一套 NPC 路径：Duty / Work 时段按优先级执行工单，Free / Sleep 等时段自动生活；V1 未做的功能不因此提前开放；
  - 自主生活可以自动消费，从玩家个人钱包按普通 NPC 规则付款，不逐笔询问、不赊账、不允许透支；
  - 玩家直接操控始终优先于普通自主决策，按原子步骤 / 结算边界安全中断；自动工作租约释放或回池，结束后若开关仍开启，就从当前位置和状态重新决策；
  - 自主关闭时不自动工作 / 生活，但需求、硬生理极限、时间和结算仍正常生效；打开经营管理界面不暂停自主行动；
  - 非受薪的玩家自主工作不领工资，也不产生工资流水；玩家作为商圈受薪经营人时按统一月薪规则从商圈产权人经营账户向自己的个人钱包领薪。
- **工资**：V1 只有固定 `MonthlySalary`，每个游戏月月末统一结算；不做班次底薪、工时工资或计件工资。
  - 完整月份按当前 `MonthlySalary` 支付；月中入职按当月在职时长比例折算，月中离职按当月在职比例立即结清；调薪立即生效，结算只读当前值；
  - 工资从雇主业务对应的经营账户原子转账到员工个人钱包：自营 / 承租店使用经营人的经营账户，薪酬制店铺与商圈使用产权人的经营账户；
  - 到期工资总是足额支付并允许源经营账户扣负，不做余额校验、不部分支付；没有 `bWageUnpaid`、欠薪金额、补发状态或员工工资竞争排序；
  - `MonthlySalary=0` 只跳过当次工资流水；工资不足不再造成 Loyalty 持续下降或自动离职。
- V1 不做辞职梯度 / 谈判 / 预告期 / 调岗；不另设“亲自顶岗”经营按钮，玩家工作统一走手动交互或自主排班；员工与薪酬制店主直接清退。

## 7. NPC 与消费

- **NPC 规模**：名册 30～50 人，图内常态 20～30 个实际 NPC。
- **NPC 类型**：V1 不区分居民 / 游客 / 行商，统一通用 NPC；收入只按实际工作、经营或其他真实业务流水计算，失业且没有其他实际收入时为 0，不按职业 / 阶层自动生成。非主地图雇工按真实雇佣合同与工资条款把工资回流到个人钱包，不因工作生成 Actor、工单或寻路执行。
- **需求与状态**：
  - 需求 6 条：`Creature.Demand.Hunger / Thirst / Energy / Leisure / Social / Shopping`；前五条通常负速率衰减，Shopping 正速率慢积累。规则字段为 `ChangeRatePerGameSecond / FinalMin / FinalMax / Thresholds{ThresholdValue, Direction, TriggerTag}`，行为回填与事件脉冲共用跨阈入口；旧 7 值 `EDemandEnum` 退出运行时；
  - 状态 5 条：Mood、Health、Hygiene、Comfort、Loyalty；
  - **V1 状态只算数值 / 展示，不驱动行为**；原员工未领薪导致 Loyalty=0 自动离职的例外已随工资直接扣负规则删除。
- **兜底**：所有需求如果场景里解决不了，就回家兜底；NPC **实际到达抽象住所并离场时**一次补满 6 条需求以及 Mood / Health / Hygiene / Comfort，Loyalty 不恢复。V1 不做图外时间补算或图外日程模拟；不在图只回收激活 Actor，名册需求 / 状态仍按 §9 入档。
- **目的队列**：有效需求与外部目的不设固定数量上限。每个事件按自己的合同携带业务数据并触发订阅者；裁决器统一新增、更新、完成、取消或删除目的，并负责排序与执行组合并。不能因数量丢弃目的，主 / 次槽的有限执行资源不等于目的队列容量。
- **候选冷却**：仅排队后因等待期望破底而主动放弃，才写该店持续至下一游戏日界的候选冷却，冷却期内评分 ×0.1；普通失败、路径不可达、Goto 超时、停滞或环境变化不写候选冷却。连续失败计数只触发原有兜底，不生成模板整体冷却或店铺候选冷却。
- **全局事件化**：先划界，Tick 管连续过程，事件管业务节点；不是每个 Tick 都发事件，也不是把计时器全部改成事件。业务与环境离散状态迁移在业务事务内提交，事务可由统一目录事件或外部业务方法启动；提交后按统一目录广播，后续影响由各订阅者事务执行。Tick 只推进需求、移动、动画、物理与执行进度等连续量，并发布到时、到达、碰撞或跨阈事件。所有事件统一登记事件 ID、载荷、发布时机、投递范围和订阅关系，不允许模块私有事件或绕过目录分发。事件不从属于发布者或载荷实体，所有订阅者分别在自己的事务中执行逻辑，内部允许普通函数调用；没有首域处理器或统一业务总控，需要新动作时再发布事件。UI 只调用 Controller 业务门面方法，由业务方法校验、提交并在成功后广播；校验失败直接返回 UI，不为每次 UI 输入额外增加 Request／Rejected 事件。禁止裸 Tick、裸 Flow 节点或 UI 直接写业务状态。V1 使用状态快照存档，不做事件溯源或读档重放。后续所有具体业务都按“输入／连续沿／既有事件 → 业务事务或目录事件 → 各订阅者事务 → 必要时下一事件”的同一逻辑设计和复核。
- **V1 事件目录**：只运行统一目录、分发与直接订阅，不启用长期社交事实库、感知、个人记忆或传播。当前已登记事件如下；不为事件预设总数，也不按“请求／事实”等标签分类：
  - `Time.DayBoundary`、`Time.MonthBoundary`、`Time.HourBoundary`（日界/月界/整点，供日结、月统计与营业时段派生）；
  - `Need.ThresholdCrossed`（载荷为 `DemandTag` 与该阈值的 `TriggerTag`）、`Schedule.BlockChanged`、`Command.Changed`；
  - `Flow.NodeSettled`、`Flow.Resulted`、`Work.ClaimInvalidated`；
  - `Facility.StateThresholdCrossed`、`Inventory.StockThresholdCrossed`、`Shop.QueueChanged`、`Shop.ExitRequested`、`Shop.PresenceChanged`、`Shop.StateChanged`；
  - `Shop.CheckoutCompleted`、`Shop.ExperienceReported`；
  - `Home.Arrived`、`Employment.Changed`、`Economic.SettlementResolved`。`Employment.LoyaltyZeroed` 随自动离职规则删除。
  每个事件只按自己的合同携带业务数据，订阅者不得直接修改目的。完整字段与订阅者见[事件系统](/VoxelDesign/02-系统设计/AI决策系统-事件系统-系统设计.md) §11。
- **背包**：
  - 只做私人背包，不做家庭库存。饿了先看背包有没有食物；没有就去地图找有食物的店；买完正饿就当场吃 / 喝，不饿就收进背包；
  - `SlotCount = 16`，NPC 与玩家统一使用该固定值，V1 不动态扩缩容；每槽只能为空或引用一个 ITEM 堆实例，实例 `Quantity` 的单槽上限为静态 `MaxStackCount`，超过单槽上限可分到其他槽，不同物品不得共槽；
  - 采用 MC 式槽位语义：同种兼容物品可同时存在多个未满槽，空槽随时可用；NPC 自动入包先合并兼容槽、余量再进空槽，但不要求历史同类槽全部装满；不同品质不共堆，不同清洁度按已确认规则加权合并；
  - 整单入包按实际源堆及其状态先模拟现有兼容槽的剩余堆叠空间，再使用空槽；任一物品放不下则整单不可入包，不能只比较总件数或空槽数；
  - V1 不计算重量，后续在槽位限制外追加由 NPC 力量等属性决定的总载重；后续易腐字段与共槽规则另定；
  - HP、清洁度、品质与 ITEM／OBJECT 生命周期统一按 §5 的实例规则执行；收银交付保持实际源堆状态，不能把物品重新生成为只有 `ItemId + Quantity` 的默认物。
- **购买决策**：
  - 需求与外部事件只携带事实并触发裁决器，由裁决器统一形成、更新和维护目的意图；仲裁对待执行目的排序并建立执行组合并关系，主槽取队首主行为链，次槽派发相容行为，不在主槽空时重新评分整个队列；
  - 执行组只合并执行安排，保留各目的完成条件；购买体验与物品使用基础作用分别结算。成交后由消费者购买行为方法按个体状态结算 Shopping、Mood 等体验，食物 / 饮料再通过实际使用满足饥饿 / 口渴，主目的不限制其他附带效果；
  - 按需求强度 + 背包已有物品与固定槽位可放置结果决定购买数量，整单 1～3 件；没有任何一件可装时不生成购买预留；
  - 选店评分阶段不读钱包，只按需求与价格期望带判断“想不想买”；到店 Browse 揭示真实价格与实际可售数量后，再检查钱包与整单可放置结果，买不起则不生成预留并离店；结账按锁价再次校验，余额不足整笔失败；
  - 需求驱动的购物清单 + 逛货架时临时加购；
  - 选品按**店铺范围**（主区域及其子区域链，口径见 [库存与保质期 §2](/VoxelDesign/02-系统设计/AI决策系统-库存与保质期-系统设计.md)）内全部 `bForSale=true` 货架的聚合现货建立整单预留，可售数量 = `Σ OnHand - ActiveReserved`；顾客不选择具体货架 / 堆叠，区域空间不另存库存副本；
  - 每条预留明细保存 `ProductTag + Quantity + LockedUnitPrice`；选品后调价不影响已预留订单，放弃后重新选品才使用当时新价格；
  - 收银台唯一执行 `CheckoutSale`：按锁价校验预留、钱包与聚合现货，再按 FIFO 生成实际源堆扣货计划和固定槽位放置计划；确认整单可交付后，原子完成全额付款、预留核销、实际扣货、保持实例状态的入包、所有权转移与成交明细流水；失败不发生任何部分结算，源堆计划不回写商品预留；
  - 未付款放弃 / 中断 / 取消 / 失败 / 离店释放整单预留，之后按当时现货与价格重新选品；真实扣货与对应货架 Restock 检查只在付款履约时发生。
- **杂货店动线**：
  - 进店 → 读取店铺范围内可售货架的聚合现货 → 选品、锁定单价并预留 → 单收银台 FIFO 排队 → 收银员执行原子 `CheckoutSale` → 商品已入个人背包 → 按需使用 / 离开；
  - 实际进门检测链发布中性的 `Shop.PresenceChanged(Entered)`，所有订阅者各自启动逻辑；统计订阅者只对顾客角色累计进店人次，其他在场、坐位、消费、员工和裁决订阅者处理自己的状态。`FWorkPointQueue.Entries[0]` 是队首，只有队首可取得收银服务槽位，等待时长读取入队游戏时间；
  - 打烊（`bOperating` 转 false）时不再接新客：店内已锁价、收银台排队与正在结账的顾客服务到完成；店外未进店的门口队列清退，这一次白跑只产生一条负满意度样本进入服务组总体声誉，不计来访 / 成交、也不计客群构成。实际接客条件变为 false 时发布 `Shop.StateChanged`；店铺聚合订阅者从 `PresentPersons ∪ 门口队列` 找全接收人、按 `(PersonId, Role)` 去重，并逐个发布统一目录中的 `Shop.ExitRequested`。店内自驱段完成当前原子子进度后才发布 `Exited`，店外等待段顾客按清退处理；V1 不开放员工实体居住，员工按 `Creature` 上的劳动安排离岗，店外员工不召回。`Exited` 的区域、坐位、库存、工单、员工工作、裁决和统计等订阅者分别更新自己的状态，没有首处理器或统一清场；未付款退出不扣真实库存、不支付、不入包；
  - 没有收银员时顾客排队并保留预留与锁价，超过容忍时间离开同时释放预留；之后重新选品使用最新价格；
  - 付款履约后不存在已付款未交货状态，普通离店 / 中断不自动退款；
  - V1 消费只做入店购买，不做外带 / 外卖 / 送货 / 售后。
- **社会 / 休闲**：V1 不做专门满足场景；社交只做同场共处（不记关系），解决不了就回家兜底。

## 8. 商圈管理（V1 范围）

- 玩家作为薪酬制商圈经营人，可查看商圈业务流水、经营账户可用资金、客流 / 统计，并执行授权业务；支出从商圈产权人游商的唯一经营账户结算，玩家不能划转该账户。V1 标准初始月薪为 0，零工资只跳过工资流水，普通员工工资另行结算。
- V1 只跑玩家商圈里玩家自己这一间标准承租杂货店；NPC 租户 / 招商 / 模板生意 / 住宿 / 多店铺 / 多商圈均为后续版本，可写通用边界但 V1 验收不开放。单店测试不新增专门的首客冷启动、开业认知写入、公共目录替代、强制首客或额外客流保护，维持现有认知与评分规则；新店可由 NPC 实际路过按简化距离判定自然写入 `KnownShopIds`（`TSet<BusinessEntityId>`，认知指向经营实体，路过 / 导航另用空间引用），但不保证被发现或成交。
- V1 不做任何专属公共设施与公共设施类收费，也不产生这类日常扣费；扣负白名单只有经营贷款月供、店铺租金、工资三项，普通家具仍按 §6 产生保洁 / 维修工单。
- 商圈与店铺都没有独立资金账户或余额；账本 / 统计视图按唯一流水展示分类收支与净额。自营 / 承租店使用经营人的唯一经营账户，薪酬制商圈使用产权人的唯一经营账户；同一责任人名下的所有经营实体业务共享该经营账户，不按区域分账户。
- 子功能区不生成独立账套，也不成为经营实体。子区域内发生的销售、采购、工资等按 `SourceBusinessEntityId` / `TargetBusinessEntityId` 计入所属经营实体（Shop / 商圈 / 图外生意），并用可空的 `OccurredAreaRef{SceneId, AreaId}` 保留实际发生区域，不重复记账。
- 商圈经营人可以管理下属区域的其他合同，但不能修改自己作为乙方的合同；这类自指合同只能由产权人修改。
- 租金：V1 标准承租合同初始月租为 0，零租金不产生流水或负债，但收租计划仍推进；月租只能由产权人设定，玩家不能修改自己作为乙方的条款。收租时间由商圈配置；月租为正时按所属商圈计划从承租经营人的经营账户划到商圈产权人的经营账户。调租只改配置、自下一收租时点起按新配置全额收取（下期生效），不按变更日分段，也不追溯已结算租金。首期实际承租天数 = `首个收租日期 - 租约生效日期` 的日历日期差，忽略时分，例如 4 月 10 日 12:00 至 5 月 1 日 00:00 按 21 天；首期租金 = `Ceil(月租 × 实际承租天数 ÷ 30)`（签约按比例），向上取整到整数金，例如月租 1000、首期 7 天收 234 金；后续完整租赁期收完整月租；高倍速跨期按时间顺序逐期执行。租金流水两侧都记出租方 / 承租方经营实体归属，区域改挂或易主不回改历史。
- 租金属于扣负白名单：到期总是足额划转，不检查源经营账户是否足额，不生成欠租、坏账、连续失败、手动补缴或违约收铺；负余额本身不触发倒闭 / 收铺。V1 租约不保存 `ArrearsEvictionPeriods` 或 `bNoCollection`。
- 客流：由 NPC 实际进出产生，不配「客流强度」表。

## 9. 存读档

V1 必须做存读档。时间、经济、经营实体、雇佣与租约只在 Global 保存一份，Scene 只保存空间、名册、物品、现场队列与执行引用，两边不双写；每份业务状态只在唯一所有者处保存一次，其他记录只保存稳定 ID 引用，不复制物品数量／状态、钱包余额、排班、队列或统计；具体唯一归属见 [AI 决策系统架构 §7 存档](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md)。

读档按「事实 → 稳定引用 → 派生 → 检查 → 激活」执行：先恢复静态配置、游戏时刻、物品实例、空间区域、人物与背包等事实，再连接稳定 ID 引用，然后派生索引与 `bOperating` 等派生状态，完成一致性检查后才激活。时间、经济、经营实体、雇佣与租约以 Global 为准，Scene 只补空间 / 名册 / 物品 / 现场队列与执行引用，不双写、不重放事件。读档本身不发布业务事件，不补算离线时间、不重摇报价、不重排队列、不重复计客流；一致性检查通过前不启动时间、日程和 AI。

游戏绝对时间直接保存并恢复原 `GameTimeSec` 与日历配置引用。持续过程不保存旧进程 `TimeSeconds`：Flow 阶段保存 `StageElapsedRealSec`；工单认领不入档，读档后重建。候选冷却保存下一游戏日界绝对 `GameTimeSec`，随游戏时刻原值恢复，不归入现实秒计时器。

存档只在业务事件事务边界取得一致快照。消费者与员工的当前活动由 Flow 节点／进度／Stage、ExecutionId、交易引用及员工工单恢复；收银表现进度可以保存，但 `CheckoutSale` 原子提交内部不设存档点。Flow 消费 `FCheckoutResult` 并离开收银节点后才允许快照，因此只保存 Active 预留与 Pending 当前订单，不保存事务内 Processing／Completed／Failed、一次性扣货／入包计划或已提交结果；成功交易只保留唯一流水，读档后不再次成交。

至少覆盖：

- 当前游戏日期时间、日历配置版本或引用；
- NPC 名册、需求 / 状态、固定槽位背包（槽位只存 `ItemInstanceId`，其实例的 `Quantity / HitPoints / Cleanliness` 与实际存在的品质等状态由物品子系统唯一登记）、位置 / 日程、钱包、经营实体认知 `KnownShopIds: TSet<BusinessEntityId>`、候选冷却下一游戏日界绝对 `GameTimeSec` 与连续失败计数；V1 认知只记经营实体 ID，不保存强度、锚点、最后到访时间或衰减状态；
- 店铺区域、业态配置标识、建筑 / 装修（承租户资产）、商品目录 / 价格 / 补货配置、仓库子功能区、储物家具与货架实例及各自库存；
- 店铺五组统计聚合：服务组五个维度分别保存 `RollingScore / SampleCount` 及当日集中差评保护最小状态；种族 / 职业 / 阵营 / 街区四类客群桶保存来访次数、成交次数、销售额、满意度合计与样本数，打烊白跑的负满意度样本只进服务组总体声誉、不计入客群桶的来访 / 成交 / 满意度。阵营只读名册基础 `FactionTag`，不读取关系度、阵营态度或传播。星级、综合有效声誉、客单价、平均满意度与查询缓存只派生，不另存副本；读档不重放事件或按历史流水重新聚合。V1 不保存个人记忆、传播链、完整口碑矩阵或已完成上报的逐条体验历史；
- 待购清单、Active 店铺级商品预留（商品 / 数量 / 锁定单价）、Pending 收银台当前订单及其买卖方 / 锁价总额，以及对应消费流程断点和尚未上报的在途体验报告；原子收银在结果已被 Flow 消费并离开该节点后才允许快照，不保存一次性扣货 / 入包计划或已提交结果；体验上报完成后只保留统计聚合；
- `FFlowState.ExecutionId`；各 `FWorkPointQueue.Entries` 的实际顺序及每项 `ExecutionId / CustomerId / EnqueueGameSec / QueueNumber / CalledGameSec`、`NextQueueNumber`；`TrafficStats.CustomerEntriesByHour`。**`PresentPersons` 不入档**——它是生物位置的派生索引（`03A §4.1.12`），读档后随生物放置与区域归属重建。读档后按 ExecutionId 重建队列与在场到消费 Flow 的引用，不重放进店／离店事件、不重复计客流；
- 有效雇佣记录（Global 唯一登记）只保存合同与工资：`EmploymentId / CreatureID / EmployerBusinessEntityId / RoleTag / WageConfig{MonthlySalary} / HireTime / HireSource / NextWageGameSec`；**工单认领不入档**。`CreatureID → EmploymentId` 索引读档后由有效记录重建。劳动安排（排班 / 工作优先级 / 工作区）挂在 `Creature` 上单独入档，不写进雇佣记录、不在雇佣记录保存副本；不保存 `bWageUnpaid` 或任何未领薪状态；
- 人物个人钱包的 `PersonalWalletAccountId`、经营者唯一经营账户的 `BusinessWalletAccountId`、所有者 `CreatureID`、账户类型与 `int64` 余额，以及全局唯一流水；派生钱包流水索引不入档，读档后重建；区域不保存资金账户；
- 玩家资产视图不单独入档，读档后从经营资产关系聚合；
- 玩家自主开关、个人生活日程和当前自主流程；`Creature` 上的劳动安排（排班 / 工作优先级 / 工作区）单独保存，不随雇佣记录，直接操控产生的临时接管状态不覆盖已保存的自主偏好；
- 5 个贷款报价槽及实际报价，以及借据的借款人、放贷方、原始 / 剩余本金、实际利率 / 期限、固定月还本金、已结算期数、下一扣费时间与状态；放款与还款均由借款人唯一经营账户结算，V1 不保存逾期；
- 经营关系与 Global 唯一登记的当前租约：`LeaseId / LessorBusinessEntityId / TenantBusinessEntityId / LeasedAreaRef{SceneId, AreaId} / TenantCreatureId / MonthlyRent / StartGameTimeSec / NextRentGameTimeSec / SettledRentPeriodCount / Status / ExitGameTimeSec`；经营实体只保存 `LeaseId` 引用，不复制租约字段；店铺状态只手动入档 `bOpen`，`bOperating` 为纯派生值、不写入存档；不保存待生效租金、欠租或坏账；
- 读档不重新生成贷款报价，也不按当前时间重算既有贷款 / 租约的下一结算时点；V1 直接查询已保存的计划字段，后续调度索引只能作为派生数据重建；
- 建造物归属（产权方 / 租户）、硬装改动日志与家具租约引用；
- 流水中源 / 目标钱包、系统对手方、`SourceBusinessEntityId` / `TargetBusinessEntityId` 与可空 `OccurredAreaRef{SceneId, AreaId}` 的引用。

**唯一字段归属与读档顺序**：以上各项的完整“归属 / 字段 / 派生重建”对照见 [AI 决策系统架构 §7 存档](/VoxelDesign/03-架构设计/AI决策系统-架构设计.md)。顺序固定为「事实 → 稳定引用 → 派生 → 检查 → 激活」：静态配置与日历校验 → 游戏时刻 → ITEM 唯一实例 → 空间区域／建造／容器 → 人物与背包 → Global 钱包／贷款／经营实体／有效雇佣／租约 → 店铺预留／订单／统计／队列 → 目的／工单／Flow → 稳定 ID 连接 → 派生索引与 `bOperating` 等派生状态 → 一致性检查 → 激活；Scene 只恢复空间、名册、物品、现场队列与执行引用，不与 Global 双写。游戏时间戳原值恢复，候选冷却下一日界时间戳也直接恢复；移动阶段按已耗时恢复；工单认领不写入存档；读档不重放业务事件、不补算离线时间、不重摇报价、不重排队列、不重复计客流。必需配置或引用损坏时在读档激活前整体终止，不静默补洞或激活半份世界，不改写原存档，不做自动修档、自动重试或经营补偿。

## 10. UI 范围（V1 页面壳，原型后续探讨）

- 六区壳 + 区域树；
- 店铺经营页：人员 / 货 / 统计 / 营业 / 设置；活动页只保留后续入口，V1 不提供可执行投放；

- 建造 / 装修；
- 贷款 / 个人资产 / 招聘面板。
- 具体布局、控件、交互在后续原型中探讨。

## 11. V1 不做

- 主线剧情、酒店 / 餐厅，以及客房预订、入住、退房、住宿收费等酒店业务；
- 旅店客房、员工休息室、员工餐台、打盹点和员工实体居住区等子功能区玩法；V1 只保留仓库子功能区作为后备储物家具的可选空间组织，不开放其他子功能区业务；
- 供应商 / 采购单 / 在途配送 / 议价；
- 外带 / 外卖 / 送货 / 售后（退款 / 重做 / 投诉受理）；
- 关系 / 记忆 / 复杂社交，以及口碑感知与传播；
- 状态层的行为影响（Mood / Health / Hygiene / Comfort / Loyalty 均只算值与展示；不接归零自动离职、辞职梯度或偷懒权重）；
- 全部专属公共设施与公共员工，以及任何公共设施类收费 / 维护费，V1 一律不做；普通家具仍按 §6 产生保洁 / 维修工单；
- NPC 店铺 / NPC 租户招商；
- 多商圈 / 并购 / 许可 / 店铺控制授权；
- 广告、促销、集市 / 节庆 / 摊位及其他店铺活动；V1 只留活动配置与接口，不生成实例、不扣费、不执行效果；
- 背包重量 / 体积、力量载重公式与动态槽位扩缩容；
- 租期 / 续租 / 押金 / 提前退租赔付（V1 无租期、无押金；调租只改配置、自下一收租时点起按新配置收取，下期生效且不追溯）。

## 12. V1 验收流程

1. 新游戏：玩家为商圈经营人，个人钱包与唯一经营账户均为 0；商圈没有独立余额，商圈业务使用抽象产权人游商的唯一经营账户；
2. 申请经营贷款，放款进入玩家唯一经营账户；
3. 同一建造面板**先选业态与区域类型 → 拉 Shop 区域** / 填信息 / 确认 → 后台一次完成经营实体注册、空间区域、经营关系、标准租约（生成 `LeaseId`）、劳动安排与首期按比例结算，不跳详情页补建、不手动绑定；创建默认 `bOpen=false`（只是建成、不是开业），有效租约先于建造 / 家具写入 → 继续装修（免费）；
4. 放置至少一个后备储物设施（可位于仓库子功能区）→ 即时采购入后备储存 → 上架、定价；
5. 招聘板只从当前无有效雇佣记录的名册 NPC 中最多展示 5 人，不足按实际人数；图外就业也是有效合同，不吞合同、不补造人口、不擅定换工政策；定期刷新与免费手动刷新均可用且不新增人口。招聘员工后，按收银 / 补货 / 清洁 / 维修设置工种，并在 `Creature` 上设置排班与工作优先级（不写进雇佣记录）；
6. 开业**不校验任何设施**，`bOpen` 直接可置，不查入口导航、员工与库存；设施、货品、人员的缺失由运行期提醒与服务劣化体现；运行期拆除必需设施不触发系统关店；
7. NPC 由需求驱动进店 → 按店铺范围内可售货架的聚合现货选品并锁价预留 1～3 件 → 收银台排队 → 收银员唯一执行原子 `CheckoutSale` → 商品入包后按需使用 / 离店；另验证最后现货不能被两位顾客重复购买、排队调价仍按原锁价成交、未付款离队释放预留且重新选品使用新价；
8. 固定槽位背包验收：同种兼容物品可堆至 `MaxStackCount`，超过单槽上限可分到其他槽，不同品质不共堆，多个未满同类槽与任意使用空槽均为合法状态；只能部分放下的清单在选品时改为可行组合，收银时无法整单入包则不付款、不扣货、不部分入包并释放预留；
9. 首位顾客进入收银队列才生成对应收银台的 Cashier 工单，队列清空即完成；单职责收银员留位待机，其他员工按优先级执行收银 / 补货 / 清洁 / 维修；清洁度与 HP 跨维护阈值能产生对应工单，劣化只降低使用效果，清洁度 0 降低使用欲望，HP0 使用后无功能效果；玩家自主开启时按排班工作、走正常生活路径并可从个人钱包自动付款，直接操作优先，结束接管后恢复自主；另验证员工在工作 Shop 内需求不下降、离开工作区后恢复，已有 Critical 不被清空；
10. 店铺 / 商圈业务账、统计、客流随交易更新，实际经营资金只进入或离开资金责任人的唯一经营账户；租金按商圈配置时点结算且首期按比例，经营贷款按各借据扣费时点以等额本金结算，工资正常从经营账户进入员工个人钱包；另验证经营贷款、工资、租金可将源经营账户扣负且不产生逾期 / 未领薪 / 欠租，购物、采购、个人付款与本人两类资金互转余额不足仍整笔失败；
11. 工资扣负验证：经营账户不足以覆盖全部工资时仍逐笔足额发放，员工个人钱包全部到账，源经营账户为负；不存在 `bWageUnpaid`、员工优先抢薪、未领薪忠诚衰减或因此自动离职；
12. 存读档后以上状态保持一致，包括固定槽位引用、ITEM 实例数量与实际存在的 HP／清洁度／品质状态、个人钱包与经营账户余额、雇佣记录及 Global 租约；读档按「事实 → 稳定引用 → 派生 → 检查 → 激活」执行，不重放事件、不补算离线时间；
13. 玩家可以继续经营，流程不卡死。

## 13. 待落地 / 风险

- 贷款报价 / 借据、等额本金计划与高倍速逐期结算的实现核对；V1 无逾期重试；
- 招聘板定期刷新的具体周期间隔（配置数值）；
- NPC 初始个人钱包的生成分布（配置数值）；每人唯一经营账户的初始余额；
- 同一建造面板的表单字段与控件联调；组合创建、装修和开业业务入口已定义，不要求跨模式补建经营实体；
- 背包后续易腐状态共槽 / 使用 / 跨容器细规则；V1 的 `ItemInstanceRef` 已确定为稳定 `ItemInstanceId`，实例登记与读档重建见架构 §7 存档。
- 状态层的后续行为影响；V1 不再配置未领薪忠诚衰减率或 Loyalty=0 自动离职。
