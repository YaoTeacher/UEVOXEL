# 经营系统 V1 — 四链路闭环与 UE5 规范性 审阅报告

**审阅日期**：2026-11-05
**审阅对象**：`VoxelDesign/02-系统设计`（经营与 AI 分册）、`VoxelDesign/03-架构设计/AI决策系统-架构设计.md`（唯一架构规范）、`VoxelDesign/04-设计计划/经营系统-最小版本设计逻辑清单-设计计划.md`（V1 范围与验收）、`VoxelDesign/05-设计决策记录`（已确认裁决）、`VoxelDesign/06-开发规范`、根目录 `AGENTS.md`
**权威顺序**：02 系统设计＝业务规范 → 03 架构设计＝运行时/数据结构/存档唯一权威 → 04 V1 清单＝V1 范围与验收 → 05 决策记录＝已确认裁决（可指出下游文档与之矛盾，不可推翻）
**审阅方式**：四条链路各画「阶段 → 上游触发 → 状态写入方 → 事件 → 下游订阅者 → 断点」的端到端串链表，再做横向比对（事实归属矩阵 / 事件目录三方核对 / V1 边界残留 / 重复定义扫描 / 引擎机制核对）
**范围声明**：本报告只审阅**文档层面的设计闭环**，不宣称任何代码已实现或已验收；涉及 `Source/Voxel` 现状的表述一律标注「代码现状观察」。

## 0. 一页结论

**四条链路的业务规则本体是自洽且高质量的，但四条的"闭环"都不成立——断点高度集中在同一类位置上：业务规则写在 02，而运行时承载（结构字段、接口、事务边界、事件发布点、存档归属）没有在 03 落地。** 这不是「设计写错了」，而是「设计只写到了业务语义层，没有写穿到运行时层」。

| 链路 | 主链阶段 | 通 | 断 | 歧义/冲突 | 结论 |
|---|---|---|---|---|---|
| 区域与建造 | 14 | 5 | 4 | 5 | **不闭合**：事务边界、退出语义、首店空间来源、业态入口、资产归属五项均不可验收 |
| 员工工作 | 14 | 6 | 5 | 3 | **不闭合**：排班/到岗/离岗、工资结算、解雇离职三段无唯一事实源 |
| 消费者 | 10（+14 条失败分支） | 3 | 4 | 3 | **不闭合**：预留原子性、收银执行者、打烊清退、体验计分均无唯一实现点 |
| 基础运营 | 11 | 4 | 5 | 2 | **不闭合**：扣负接口、统计载体、补货阈值、日结、同刻排序五项无运行时 |

**六个横切病因（后续各章都归到这六条）**：

1. **同一结构被定义两次且互不兼容** —— `FIntent`/`FFlowState`、流程节点集、工单状态机、时间子系统宿主、Shop 模块承载形式。
2. **业务事务没有边界** —— 组合创建、锁价预留、认领/离职释放、排队破底，都是「文档只写"必须原子"，没有写在哪一行原子」。
3. **跨模块事实无主** —— 在场人员集合、客群桶、`bOperating` 派生值、补货阈值、家具租约归属，都没有唯一所有者。
4. **时间与结算时序不可实现** —— 日结/日报无载体，同刻「先足额后扣负」排序不在调度表内，高倍速补发无单帧上限。
5. **V1 存在可达性死锁** —— 负余额 + 采购必须足额 + 无兜底；家具/门未接导航使「可达」硬过滤全灭；招聘板可能为空。
6. **V1 边界与文档治理未收口** —— 记忆/客座/定金/小票等后续能力仍留在唯一架构里；Tag 未注册；08 目录五份报告被就地清空成空壳。

**一句话给决策者**：现在的文档足以让策划继续推演玩法，但**不足以让程序开第一个可编译切片**；建议先做 12 项裁决（§10），再按三批次收敛（§9）。

## 1. 判定口径

本文不使用「写得对不对」的模糊标准，统一用五个可判定的检查项。任一阶段缺下列之一即记为「断」：

| 检查项 | 含义 | 记法 |
|---|---|---|
| **触发者** | 谁在什么时刻发起这一步（玩家操作 / 事件 / `Next...Sec` / tick） | 缺 → 断 |
| **业务入口** | 这一步由哪个方法承担（文档层面的类.方法即可） | 缺 → 断 |
| **状态写入方** | 写 Global / Scene / 组件 的哪一处，且唯一 | 缺或两处 → 断/冲突 |
| **事件** | 提交后发布什么事件，谁订阅 | 缺 → 歧义（不影响闭环时）/ 断（下游靠它驱动时） |
| **下游消费者** | 谁接住这个状态（下一阶段 / UI / 统计 / 存档） | 缺 → 无消费者 |

同时横向比对四类问题：

- **双权威**：同一事实在两份文档里各自被完整定义，且措辞不同 → 埋漂移风险（违反《文档管理规范》「唯一权威」原则）。
- **双写**：同一状态有两个写入入口 → 事务二义。
- **无主**：文档要求某事实存在并被存档/展示，但没有任何结构承载它。
- **无入口 / 无消费者**：声明要做但找不到入口；或存在入口但没人消费。

### 2.2 P0（阻断 V1 验收）

**[A-1] 组合创建没有事务契约｜冲突 + 遗漏**
「一次原子提交」的集合在三处不一致：`02店:249` 只含{首期、经营关系、租约、承租人劳动安排}；`02店:371` 含六件{实体、区域关联、经营关系、租约、劳动安排、首期}；`03A:956` 只含三件。且提交横跨 Global（实体/Lease/首期）与 Scene（区域 Actor/覆盖/空间索引），`03A:212` 只说「一次提交」，无提交顺序、无失败返回、无回滚，而 `02店:520` 又明写「不建…补偿层」。
**为什么阻断**：任一 Scene 侧失败（范围非法、区域冲突、生成失败）时 Global 已写入实体、Lease 与扣款流水——留下半份世界；而 `04:247` 规定读档遇损坏整体终止，半份状态会直接导致整档不可加载。
**修法**：`03A §3.9` 增门面提交契约（固定顺序：区域预校验 → 实体 → Lease → 劳动安排 → 首期；失败逆序撤销并返回错误码）；`03A §7.1` 增 `PendingCreation` 暂存区（读档时清理）；统一 `02店:249` 与 `371` 的原子集合表述。

**[A-2] 建造退出被设施缺失阻断｜与已确认裁决正面冲突**
`02态:137`、`02店:396`、`02操:237`、`04:96` 四处规定「保存并退出建造：通过才允许退出，缺失则留在建造模式」；而 `AI决策系统-区域店铺与商圈管理-决策记录:208` 与 `V1基础规则决策记录:159` 两条已确认裁决明确「建造退出不强制开业校验、不以必需设施不足强迫留在建造模式」。UI 六区又只有一个「退出建造」按钮（`UI系统-屏幕分区:108`），没有独立「保存」动作。
**为什么阻断**：V1 主交互入口的行为二义，无法写出验收脚本；若按 02 实现则违反已确认裁决，并造成「玩家被锁在建造模式」。
**修法**：以 05 裁决为准，把四处改为「退出时给缺失清单与提醒，不阻断」；或补一条新裁决推翻决策 24 并同步全部调用点。

**[A-3] 首店空间来源未定｜冲突**
`03A:939` 规定开局「V1 预置…玩家标准承租店空间（可租标的）」，同节 `03A:943` 又写开店是「拉区域/摆模板」；`02店:371` 与 `04:277` 均写「同一建造面板圈范围…确认」；`03A:213` 又规定「既有区域租用复用原区域，不重建」。
**为什么阻断**：这决定门面走 `ConfirmExistingShopLease` 还是 `ConfirmPlayerShopCreation`，也决定「签约前已有结构归产权方」（`04:93`、`02装:141`）是否有实物对象、区域冲突检测与父区域校验是否执行。验收第 3 步无法判定通过标准。
**修法**：`03A §6.6` 删除「预置承租店空间」，改写为「预置商圈主区域，店铺区域由 Confirm 创建」，并同步 `02店 §6.14` 与 `04 §12.3`。

**[A-4] 「选业态」没有唯一入口｜冲突**
`04:85` 把「选业态（杂货）」排在创建之后的装修链路，`02店:389` 允许「建造/装修后再选」；但创建后唯一可写业态的入口说法冲突——`02操:226` 说「编辑业务可修改实体名称、业态配置引用」，`表单:19/137` 规定普通资料表单「只允许名称/LOGO」，`编辑系统-工具系统-系统设计:256` 又写「普通资料编辑不改变主经营类型」。
**为什么阻断**：若只能在创建时选，则 04 的顺序与 02店 失效；若只能事后选，则「保存退出预检」时业态尚未确定，硬校验形同跳过，而开业校验与「允许经营品类」约束都依赖业态已定。
**修法**：二选一并统一到一处——「创建面板必填（M12b 为唯一入口）」或「编辑业务→业态为正式业务入口」；同时删改 `04 §12.3` 中创建后的「选业态」步骤。

**[A-5] 租户资产归属无数据载体｜遗漏**
`PlacedByLeaseId` / 硬装改动日志被 `02装:136`、`02区:508`、`02店:474`、`04:244` 多处引用为资产归属的唯一依据，但 `03A §4.2` 的设施/储物组件（`03A:301-325`）与 `02家:123-129` 的实例字段都没有该字段，全库没有写入它的工具或门面方法，`03A §7` 存档根也没有对应表。
**为什么阻断**：`02店:474` 要求「落点与归属写入同一业务提交」，无载体即无法执行；`04:244` 把它列为存档验收项，无 schema 不可验收；退租/盘下/易主（`02装 §4`）全部缺少数据基础。
**修法**：`03A §4.2` 增 `FAssetOwnershipRef{BusinessEntityId, LeaseId}` 与硬装改动日志结构，`03A §7.1` 增存档表，并指定写入入口（家具放置工具 / 几何提交工具经建造域 Controller 调经营域门面）。

### 3.2 P0

**[S-01] 看板工单缺字段，认领主键无来源｜冲突 + 遗漏**
`FIntent` 是看板工单的唯一结构定义（`03A:486-501`），但 `03A §11.9` 的伪码去读 `TaskTypeTag`、`EstimatedDurationSec`、`Priority`、`PushGameSec`（`03A:1564/1572/1580/1591`），`02员工:131` 要求工单含「来源对象 / 基础 Priority / 预估工期 / 所需材料」，索引器去重键是「来源对象 + 类型」——这些字段在唯一结构定义里都不存在。`FWorkClaim.WorkOrderId`（`03A:456`）也没有字段来源：看板条目是 `FIntent`，其 `TargetWorkOrderId` 无从赋值。
**为什么阻断**：派生 → 认领 → 执行整条链的数据契约无法落地，去重、分带排序、临近下班过滤、认领回收键全部悬空。
**修法**：`03A §5.3` 给 `FIntent` 增 `WorkOrderId`（或明定 `IntentId` 即工单键）、`TaskTypeTag`、`SourceObjectId`、`Priority`、`EstimatedDurationSec`、`RequiredMaterials`；`§5.2` 说明 Claim 键取 `FIntent.WorkOrderId`。

**[S-02] 简易/高级两档无承载，工种固有顺序未参与排序｜冲突**
`FWorkAssignment` 只有 `TMap<GameplayTag,uint8> Priorities`（`03A:437`），没有模式标志；排序只有「优先级 → 距离 → PushGameSec」（`03A:1583-1591`），全程无「工种固有顺序」。而 `02经营:267-268` 与 `05复核:40` 明确 V1 默认走**简易模式**（启用项同优先级、按工种表 naturalPriority 扫描）。两档无法切换即两处描述互斥。
**为什么阻断**：V1 主用简易模式，「四工种优先级矩阵」无法与需求对齐。
**修法**：`03A §5.1` 加 `EBoardPriorityMode PriorityMode`；`§11.9` 排序插入 naturalPriority（来自 ConfigData 工种表）作为同级 tie-break 首位。

**[S-03] 排班与个人日程是两套时段事实，「离岗」读哪个字段未定义｜冲突**
个人日程 `WeeklyTemplate` 填 `Sleep/Duty/Free/Anything`（`03A:360-365`），劳动安排 `ShiftTemplate` 填 `Work/Rest/Sleep/Dine/Anything`（`03A:442-445`）；`RoleContext = Duty` 由前者判定（`03A:810`），「剩余班次 / 到点离岗」由后者判定（`GetRemainingShiftSec(Assignment)`，`03A:1569`）。二者谁写谁、是否同步、`EScheduleBlockType` 五值是什么，全文未定义；`02营业:59` 只承认「结构复用、语义独立」，未指定劳动时段归属。
**为什么阻断**：到岗、交接、容忍窗、离岗四个环各读不同的源，会出现「排班说下班、日程说 Free」的角色分裂——恰是 `02NPC:123` 想消除的问题。
**修法**：`03A §5.1` 明定「劳动时段唯一事实 = `FWorkAssignment.ShiftTemplate`，个人周模板的工作格由排班派生/只读镜像」，给出 `EScheduleBlockType` 五值与 Duty 判定公式。

**[S-04] 解雇/离职缺三件｜断链**
① 停用 Scene 侧劳动安排：`Fire(EmploymentId)` 属 GameInstance 劳动子系统（`03A:123-126`），而 `WorkAreaRef`/`bEnabled` 在 Creature 组件（`03A:435`），场景未加载时无写入路径；② 执行中 Flow 的终止与认领/工作位释放：各处释放清单只列「完成/失败/失效/下班/中断/死亡/回收」，`ReleaseAllFor` 注释仅「死亡/传送/流程失败」，离职不入列；③ 「立即结清」无运行时入口：`§6.5` 只描述调度器到点叫醒，`Fire()` 无结算步骤、无出参，Fire 后 `NextWageGameSec` 计划项是否移除亦未定，而 `02操:68` 要求立即结清。
**为什么阻断**：员工 LOOP 的最后一环无状态写入者与原子顺序，会留下孤儿认领 + 被占工作位（后续员工认领不到）+ 合同已止而工资仍到期。
**修法**：`03A §3.4` 增 `FireAndSettle`（结算当期 → 移出登记 → 标记 `PendingAssignmentDisable`，由场景加载/在场组件消费）；`§6.5` 列入「离职即时结算」旁路；`02行动 §4` 释放清单加「离职/解雇」。

**[S-05] 认领「不入档」却又「读档重建」，与 Flow 断点恢复组合会双执行｜冲突**
`02员工:159/186` 说认领不入档、读档重新找活；`03A:993` 与 `05复核:320` 都说「重建派生：看板、**认领**」。Claim 含 `StartGameSec`（`03A:456-459`），业务事实推不出该值，「重建」无算法。同时 Scene 保存 `ExecutionBreakpoints`（`03A:980`），恢复中的劳动者仍持有同一工单执行权，而认领已空 → 别的劳动者可再认领同一单。
**为什么阻断**：违反验收 12（存读档一致），并产生同一工单两个执行者、原子段互斥失效。
**修法**：统一为「读档后认领表清空；凡有 `ExecutionBreakpoint` 且 `Kind=Work` 的劳动者，由执行组件在读档第 8 步重新登记认领（`StartGameSec` = 读档时刻），其余重新找活」。

### 4.3 P0

**[C-01] 收银执行者双权威｜冲突**
`03A:860` 写「Pay → `CheckoutSale` 原子提交」（顾客自己付款即成交），`04:281` 写「收银员唯一执行原子 `CheckoutSale`」；`03A` 的队首＋服务槽即推进流程，不校验是否有员工在岗。
**为什么阻断**：「无收银员」分支自相矛盾——按 04 该分支应排队等待，按 03 顾客到队首就成交。验收 7 的收银链分叉。
**修法**：二者择一并改另一处——「员工占 `slot_staff_cashier` 后发起 `CheckoutSale`，顾客 Pay 只等结果」，或删去「收银员唯一执行」并同步改 04。

**[C-02] 锁价预留只有要求没有机制｜遗漏**
`CanReserveBasket` 声明为 `const`（`03A:254`），只回填 `FReservation`；全库**没有创建/插入 `ActiveReservations` 的写入口**（`03A:262` 只是字段）。「整单原子预留」只有文字要求，没有「校验 + 插入」在同一事务的定义。
**为什么阻断**：同帧两位顾客都能通过「最后一件」的校验，验收 7 的「最后现货不能被两位顾客重复购买」无机制支撑。
**修法**：改 `TryCreateReservation`（非 const，校验与插入同一调用），补 `Release`/幂等语义，明确单一写入者。

**[C-03] Flow 与预留/订单/在途体验的绑定键缺失｜断链**
`02空间:366`、`05基础:174` 要求 Flow 保存 `StockReservationId` / `ActiveCheckoutOrderId`，`03A` 的 `FFlowState`（`03A:526-539`）只有 `ExecutionId`；`03A:1663` 还引用了未声明的 `AccumulatedReport`；`§7` 存档也没有这些字段。
**为什么阻断**：离店释放、读档续跑、在途体验「一次上报」都没有绑定键；打烊与续跑会丢接收人或重复上报。
**修法**：`03A §5.4` 补字段并纳入 `§7`；`02空间 §9.8` 同步。

**[C-04] 打烊清退链无主｜断链 + 双权威**
`ExitRequested` 的发布者写「店铺经营业务」（`02事件:292`），但 `04:201` 要求「店铺聚合订阅者从 `PresentPersons ∪ 门口队列` 找全接收人、按 `(PersonId, Role)` 去重」再逐个发布；`Exited` 又写「店内自驱段发布」（`02事件:293` 注明是边界检测）。而 `PresentPersons` 没有结构、没有所有者、不在 `03A` 存档树里（`03A` 全文 0 次出现），`bPendingClearance` 无置位/清除语义，门外离队不伪造 `PresenceChanged` → 白跑上报无触发点。
**为什么阻断**：打烊三分支（店内继续 / 店内无消费离店 / 门外清退记白跑）无法落地，白跑样本会漏报或重报。
**修法**：在 `03A` 指定场景侧单一「在场聚合器」为 `PresentPersons` 所有者并入档；Global 只发 `StateChanged`；清退流程负责发 `ExitRequested` 与白跑样本（带 `Reason`/`bEntered`）。

**[C-05] 排队破底路径伪发离场事件且不释放队列项｜冲突**
`03A §11.11` 的破底处理直接 `PublishPresenceChanged(false)`、直调 `ApplyExperienceReport`、只走 `OnFlowFinished`，**没有 `Dequeue` / `QueueChanged` / 预留释放**。
**为什么阻断**：伪造 `Exited` 污染来访统计；队列项泄漏会堵住后续顾客（容量 8）；验收 7「未付款离队释放预留」不成立。
**修法**：`03A §11.11` 改为 `ExitRequested → Dequeue + QueueChanged → 释放预留 → 实际 Exited`；体验只累计不即时写统计。

**[C-06] 体验结算多入口，存在重复计分｜歧义 + 重复计分**

### 5.3 P0

**[O-01] 扣负白名单没有接口边界｜遗漏**
`03A:98-102` 的 `Transfer(...)` 没有「允许扣负」参数，`04:53` 又要求「该权限由业务结算器内部使用，不开放给普通划转 UI」。
**为什么阻断**：若 `Transfer` 验足额，工资/租金/月供无法扣负；若不验，任何调用者都能透支，白名单失效。验收 10/11 要求「三类扣负且普通支出不得透支」，当前无接口可表达。
**修法**：`03A §3.3` 增 `SettleTransfer(..., ESettlementType)` 或内部 `bAllowNegative`，按白名单枚举校验；`02经营 §3.7`、`04 §3` 同步接口边界。

**[O-02] 统计载体缺失｜遗漏**
`FShopTrafficStats` 被 `03A:265` 与 `03A:621` 两处当作字段类型使用，**全文没有定义**；`FShopClienteleRuntimeData`（`03A:1219`）定义了四类客群桶，却**没有挂进** `FShopRuntimeData`（`03A:612-622`）。而 `04:234` 要求两者都入档。
**为什么阻断**：客群四桶无所有者、客流类型未定义 → 统计与存档验收 10/12 无法落地。
**修法**：`03A §5.6` 增 `Clientele` 字段并定义 `FShopTrafficStats`（含 `CustomerEntriesByHour` 与日结字段）；`§11.3`/`§7.1`、`04 §9` 对齐。

**[O-03] 补货阈值双权威｜双权威**
`03A:589` 把它放在 `FShopProduct.RestockThreshold`（Global 商品目录）；`02经营:260` 写「补货阈值…货架配置」、`02业态:50` 写「货架实例配置」、`04:108` 又写「补货阈值属于店铺经营数据」。`补货量` 只在 `02经营:87` 提及，无字段。
**为什么阻断**：多货架同商品无法表达；补货工单的目标、存档、多货架行为都不确定。
**修法**：选定唯一所有者。若归货架，`03A §5.6` 删字段，物品模型与家具文档增「每货架阈值 + 补货量」；若归目录，改 `02经营 §3.2/§4`、`02业态 §1.3`、`04 §5` 并定义多货架语义。

**[O-04] 日结 / 日报无实现与验收｜遗漏**
`02营业:107-109` 称 V1「日结…生成日报…重置日计数」，`04:35` 要求「统计、日结按日历日切」，`03A:39` 只列了「统计服务」名称，全文无日报/日结结构、无日计数器、无存档字段、无验收项。
**为什么阻断**：02 声称属于 V1 闭环的日结段，在 03/04 不可实现。
**修法**：`03A` 增统计/日结服务接口 + 日报/日计数器并入档；`04 §2/§9/§12` 增验收。若 V1 不做，则改 `02营业 §5` 为后续并删 04 中的「日结」。

**[O-05] 负余额软锁（V1 可达性死锁）｜断链**
`02经营:188-189` 采购必须足额、负余额不触发任何后果；`02区域:212` 只说「负经营账户通过后续经营收入自然回升」；`04:67` 最多 5 笔在贷、每月只补空槽；`04:154` 玩家自主工作不领工资、`04:20` 开局钱包为 0。
**为什么阻断**：当「库存 = 0、余额 < 0、5 笔在贷」同时成立时：无法采购 → 无销售 → 无收入，月供继续扣负；个人钱包为 0、工资为 0，无法注资；无破产/资产处置/兜底 → 永久锁死。`04:287` 的验收「流程不卡死」不成立，且文档没有显式接受这个后果。
**修法**：`04 §3/§5` 增恢复阀（保留至少 1 个报价槽 / 紧急贷款 / 个人收入 / 资产处置，任一即可），或在 `02区域 §5.2` 显式接受并给出「重开档」路径；`04 §12.13` 增对应验收。

**[O-06] 同刻「先足额后扣负」不可实现｜冲突 + 遗漏**
`03A:919` 写「同刻先足额组（采购等）后扣负组」，但 `FSettlementTask`（`03A:734`）只含计划任务；采购与提前还款等**即时足额业务不在调度表内**；`05复核:216-219` 也确认调度器只排 `Next` 任务。
**为什么阻断**：`02经营:190` 给出的确定结果（采购 800 先付、工资 500 后发）无法保证，经济顺序不确定。
**修法**：`03A §5.9/§6.5` 增统一经济命令队列（同 tick 顺序：到期计划任务 → 即时足额 → 扣负组），或明确「计划任务在本 tick 玩家操作前结算」。

**结论**：J1–J3 使「开业了但没货/没顾客」，J4–J6 使「有顾客但结不了账/补不了货」，J7–J9 使「跑得起来存不下来」，J10 使「有工单没人认领」。**十条交接里有七条是同一个病根的变体：02 写了业务要求，03 没给承载。**

## 8. UE5 设计规范符合性

### 8.1 结论摘要

**分层与宿主归属的大方向是对的**：GameInstance 承担 Global 事实（时间/经济/雇佣/租约/经营实体）、World 承担场景（区域/生物/物品/体素）、Actor+组件承担现场行为、DataAsset/DataTable 承担配置、UMG+事件驱动承担 UI——这与 UE5 的子系统惯例和项目 `AGENTS.md` 一致。**问题集中在「引擎机制层没有写穿」**：类型未定却已用于容器键、非 UObject 却取弱指针、存档只有结构树没有机制、导航与体素编辑的冲突无人认领。

| 项 | 结论 | 要点 |

## 10. 需要用户裁决的 12 个问题

这些是**无法从现有文档推出唯一答案**、且决定后续所有修改方向的。合并了五组审阅的待决项，去重后按影响面排序：

1. **`FIntent`/`FFlowState` 以哪份为准？** 02 意图统一模型（自称唯一定义）还是 03 架构 §5.3？——决定决策/执行/看板三层的全部结构。
2. **时间子系统挂 GameInstance 还是 World？** 03 是 GI，02 时间系统写 World。——决定存档、跨关卡、边界事件。
3. **事件总线用哪个？** 自研 `UVoxelEventSubsystem`（03）还是 `GameplayMessageSubsystem`（05 前端决策 2）。
4. **Shop 经营模块的引擎承载形式？** 纯 struct + 子系统 TMap / UActorComponent / UObject 逻辑模块。——现在是「未定」却已被当 UObject 用。
5. **`FBusinessEntityId` 的底层类型？** 建议 V1 直接钉 `FGuid` + 自写 `GetTypeHash`，否则第一个切片就编不过。
6. **建造「退出」是否被设施缺失阻断？** 02/04 四处的「不允许退出」与两条已确认裁决正面冲突，必须二选一。
7. **V1 首店空间是预置可租标的，还是 Confirm 时新建？** ——决定门面入口、冲突检测、验收 3。
8. **「选业态」的唯一入口在创建面板还是「编辑业务」？** ——决定退出预检与开业校验是否可执行。
9. **补货阈值归货架实例还是商品目录？** 若归货架，需同时定义「多货架同商品」语义与「补货量」字段。
10. **负余额软锁如何处理？** 加恢复阀（保留 1 个报价槽 / 紧急贷款 / 个人收入 / 资产处置），还是显式接受「可能永久锁死、需重开档」。
11. **日结/日报是否属于 V1？** 属于则补 03 统计服务 + 日报结构 + 存档 + 验收；不属于则改 02 营业循环并删 04 的「日结」。
12. **读档一致性检查失败后的玩家路径？** 回主菜单 / 允许再读档 / 强制重建 GameInstance。——03 §7.2 与 04 §9 都要写。

**次优先（可稍后）**：工单/意图状态机二选一；`AvailabilityTemplate` 归属；`HomeAreaRef` vs `HomeAreaId`；维护阈值配置归属；月报归属期（按流水 GameSec 归月 vs 按结算所属期归月）；家具→NavModifier 归属。

## 附录 A：各链路「已确认通畅」的环节（可直接作为实现基线）

- **区域与建造**：区域不持业务数据；必需设施清单单一配置源；先租约后建造；空间创建与经营注册分离；组合创建命名唯一；单向数据流未被破坏；`bOpen` 单一人写入档、`bOperating` 不存第二布尔；区域树仅空间导航。
- **员工**：单一有效雇佣 + 合同绑经营实体；看板＝派生索引、索引器唯一写、玩家只读；四类工单来源闭合；`ResolveFundsOwner` 单一实现；打烊不清内部工单；玩家手动＝NPC 自主共用入口；劣化只降效果 + 可恢复。
- **消费者**：三段校验（选店不读钱包 / 到店四门禁 / 结账再校验）；锁价与调价语义；预留不扣货；原子收银全成或全败；整单预演用分离快照；打烊三态；统计唯一写者；预订与 V1 无冲突；LOD 不降决策。
- **基础运营**：`bOpen`/`bOperating`/打烊履约；三类扣负逐条 `Next`、非月界批处理；销售原子；唯一流水 + 双账户 + 资金责任人；租约 Global 唯一、首期按比例、调租下期生效；Global/Scene 不双写；FIFO 与容量硬上限。
