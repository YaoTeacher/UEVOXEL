## 2. 决策记录

### 决策1: 数据契约一致化方案

**问题**: 选区工具返回`TArray<FIntVector>`,但设计文档要求`TMap<FIntVector, FGameplayTag>`

**Council辩论发现**:
- Marcus: 当前代码返回TArray(仅位置),模板系统需要TMap(位置+类型)
- Serena: 这是数据契约违反,导致转换函数无法正常工作
- Ava: 逆向转换(模板→选区)完全缺失

**头脑风暴讨论**:
- 选项1: 修改代码实现,让选区工具直接返回TMap
- 选项2: 修改设计文档,接受TArray作为返回类型
- 选项3: 提供两个版本的函数
- 选项4: 暂缓修复

**最终决策**: **选项3 - 保留现有API兼容性,新增带类型的选区计算方法**

**理由**:
- ✅ 不破坏现有代码调用
- ✅ 保持无状态设计
- ✅ 按需查询类型(性能友好)
- ✅ 向后兼容

**实现方案**:
```cpp
// 保留现有API
static TArray<FIntVector> CalculateSelection(...);

// 新增: 带类型信息的选区计算
static TMap<FIntVector, FGameplayTag> CalculateSelectionWithTypes(
    const FVoxelEditRequest& Request,
    float BlockSize,
    UVoxelBlockWorldSubsystem* BlockWorld  // 新增参数
);
```

**影响范围**:
- 选区系统架构设计: v1.2新增接口定义
- 模板系统: 使用新增的API获取类型信息

### 决策2: 调色板构建算法规范

**问题**: 调色板构建缺少算法规范,Tag去重、排序、索引分配规则不明确

**Council辩论发现**:
- 设计文档说"构建调色板",但没有明确算法规范
- 序列化依赖索引分配规则
- 跨平台兼容性需要稳定的顺序

**头脑风暴讨论**:
- 用户认定为P0级阻塞问题,必须在实现前明确规范
- TSet vs TArray的使用差异讨论

**最终决策**: **TSet去重 + TArray排序 + 索引映射**

**算法规范**:

```cpp
// 步骤1: 收集唯一Tag(使用TSet自动去重)
TSet<FGameplayTag> UniqueTags;
for (const auto& Pair : SelectedVoxels)
{
    FGameplayTag Tag = Pair.Value;

    // 规则1: 排除空气
    if (Tag.MatchesTag(FGameplayTag::RequestGameplayTag(FName("Voxel.Block.Air"))))
        continue;

    // 规则2: 排除脚手架(整个层级)
    if (Tag.MatchesTag(FGameplayTag::RequestGameplayTag(FName("Voxel.Block.Scaffolding"))))
        continue;

    UniqueTags.Add(Tag);
}

// 步骤2: 构建调色板(按TagName排序,确保稳定性)
TArray<FGameplayTag> Palette;
Palette.Reserve(UniqueTags.Num());

// 排序规则: 按Tag的完整名称字典序
UniqueTags.Sort([](const FGameplayTag& A, const FGameplayTag& B)
{
    return A.ToString().Compare(B.ToString()) < 0;
});

for (const FGameplayTag& Tag : UniqueTags)
{
    Palette.Add(Tag);
}

// 步骤3: 构建索引映射
TMap<FGameplayTag, int32> TagToIndex;
for (int32 i = 0; i < Palette.Num(); i++)
{
    TagToIndex.Add(Palette[i], i);
}
```

**关键设计决策**:
- ✅ TSet用于快速去重(O(n)时间复杂度)
- ✅ TArray用于索引访问和序列化稳定性
- ✅ 按字典序排序确保跨平台一致性
- ✅ 过滤空气和脚手架Tag

**影响范围**:
- 选区系统架构设计: v1.2更新保存模板流程
- 模板系统架构设计: v2.3明确调色板构建算法

### 决策3: 错误处理系统设计

**问题**: 所有系统边界缺少错误处理契约,无法区分失败原因

**Council辩论发现**:
- Serena: 所有系统边界都缺少错误处理规范
- Marcus: 现有代码使用简单bool返回值,无法知道为什么失败

**头脑风暴讨论**:
- 选项1: 继续使用bool返回值
- 选项2: 使用TOptional<T>+错误码
- 选项3: 使用错误码,统一现有代码设计

**最终决策**: **选项3 - 使用错误码+统一设计现有代码**

**设计规范**:
- 错误码枚举: `EVoxelTemplateError`
- 结果结构体: `FVoxelTemplateResult`
- API模式: 返回结果结构体或输出参数+错误码

**迁移策略**:
1. 阶段1: 新代码使用新系统
2. 阶段2: 渐进式重构现有代码
3. 阶段3: 统一错误处理

**影响范围**:
- 新建文档: 编辑系统-错误处理规范.md

### 决策4: 6向旋转变换规范

**问题**: 坐标转换公式缺少旋转变换的数学规范

**Council辩论发现**:
- Serena: 坐标转换公式缺少旋转变换的数学规范
- 设计文档只说"应用旋转变换",但没有具体说明

**头脑风暴讨论**:
- 用户提出: **旋转应该以包围盒几何中心为中心,但放置时用底面中心作为定位点**
- 这个设计分离了旋转中心和定位锚点的职责

**最终决策**: **几何中心旋转 + 底面中心定位的分离设计**

**设计理念**:
```
旋转操作: 以包围盒几何中心为旋转中心
放置操作: 以底面中心为定位锚点(世界坐标固定)
```

**旋转矩阵定义**:

| 方向 | 变换规则 | 说明 |
|------|---------|------|
| Forward | `(x, y, z) → (x, y, z)` | 不变 |
| Backward | `(x, y, z) → (-x, -y, z)` | 绕Z轴180° |
| Left | `(x, y, z) → (y, -x, z)` | 绕Z轴-90° |
| Right | `(x, y, z) → (-y, x, z)` | 绕Z轴+90° |
| Up | `(x, y, z) → (x, -z, y)` | 绕X轴+90° |
| Down | `(x, y, z) → (x, z, -y)` | 绕X轴-90° |

**关键设计决策**:
- ✅ 分离关注点: 旋转中心与定位锚点职责清晰
- ✅ 符合直觉: 玩家定位点不变,旋转改变模板朝向
- ✅ 数学明确: 每个方向的变换矩阵都有明确定义
- ✅ 易于实现: 离散旋转,无需浮点运算

**影响范围**:
- 模板系统架构设计: v2.3新增旋转变换规范

### 决策5: UX交互模式澄清

**问题**: Aditi识别的UX问题 - Tag替换UI缺少位置预览,保存模板是按钮触发vs工具选择的不一致

**Council辩论发现**:
- Aditi: Tag替换UI只显示使用次数,不显示影响位置
- Aditi: 保存模板是"按钮触发"而非"工具选择",打破一致性心智模型

**头脑风暴讨论 - 用户澄清**:
1. **Tag替换UI**:
   - 显示"使用多少个方块"而非"使用次数"
   - 不需要显示位置预览,这只是简单的冲突解决器
   - 蓝图编辑场景里会提供3D预览,UI无需重复

2. **按钮vs工具**:
   - 用户澄清: **保存模板不影响场景编辑操作,只是基于选区生成文件**
   - 其他工具(移动/复制)是场景里的编辑操作,会修改世界状态
   - 这是**功能类别的本质差异**,不是交互模式的不一致

**最终决策**: **现有UX设计合理,无需修改**

**理解修正**:
- ✅ Tag替换UI是简单冲突解决器,不需要位置预览
- ✅ 保存模板是文件操作,不属于场景编辑工具
- ✅ 功能类别差异(文件操作 vs 场景编辑)是合理的设计区分

### 决策6: 选区序列化需求

**问题**: Ava提出选区需要序列化能力,行业标准支持选区持久化

**Council辩论发现**:
- Ava: 选区无法序列化,行业标准支持选区持久化
- 选区↔模板之间缺少转换桥梁,无法非破坏性编辑

**头脑风暴讨论 - 用户决策**:
- 用户: **选区本身没有保存的意义,需要保存成资产的是建筑模板**
- 用户: **如果后续玩家期望自定义笔刷,再设计笔刷选区的功能,现在不需要**

**最终决策**: **选区不需要序列化,通过模板系统实现持久化**

**持久化路径**:
```
选区(运行时) → 模板(文件) → 资产(可复用)
```

**关键设计决策**:
- ✅ 选区是编辑操作的中间状态,不应持久化
- ✅ 模板系统已提供完整的持久化能力
- ✅ 未来扩展性: 自定义笔刷功能独立设计
