## 1. 经营实体、空间与标识

**来源**：2026-10-25 业态、库存、账户议题；2026-10-30 唯一事实归属议题；本次用户确认的统一模型。

**现行决策**：

- 经营实体是资产与业务的载体，Shop、District、Abstract 使用同一基础模型；图外生意不是虚拟余额、区域特例或另一套业务。
- 全部经营实体统一登记于 `Global.BusinessEntities`。Owner、Manager、经营关系、营业日程、商品目录、预留、订单、声誉与统计归经营实体，不归区域。
- 经营实体可选空间组件，空间引用统一为 `AreaRef={SceneId,AreaId}`；无实体空间的 Abstract 不创建区域或伪造 AreaID。
- 区域只负责范围、空间树、空间查询和校验。仓库、子房间等有 AreaID，但不是独立资产或经营实体；它们不拥有 Owner、Manager、合同、账户、商品目录或声誉。
- 业务统一用 `BusinessEntityId`；03 使用逻辑 `FBusinessEntityId`，底层引擎 ID 类型尚未选定。不得用裸 AreaId、Actor 指针或区域类型充当业务身份。
- 业态静态配置描述允许品类及“功能片段类型＋可选参数条件＋MinCount”设施要求；可复用已有配置内容，但不再把区域实例的类型字段当作唯一经营事实。具体配置映射由唯一架构定义，不在此定死新表或引擎类型。
- 商品目录、营业日程、初始布局和真实库存各有自身归属，不塞入业态表；`FlowConfig` 仍按 `FlowTypeTag` 统一索引，不恢复每种店铺独占流程。

**保留原因**：静态业态约束与动态业务、物理库存分离可以避免双写；将业务从空间抽离后，同一模型才能支持商圈、店铺与无区域生意。

## 2. 账户、唯一流水与资金责任人

**来源**：2026-10-25 统一账户与自指合同；2026-10-30 全局注册表；2026-10-31 人物级双账户；本次用户确认。

**现行决策**：

- 每个人物，包括非经营 NPC、图外人物和玩家，都有一个个人钱包和一个唯一经营账户；不是成为经营者后才按需创建。人物名下的所有生意共享其经营账户。
- 个人钱包承担生活消费、工资收入与个人付款；经营账户承担经营销售收入、采购、租金、雇主工资和经营贷款。不为区域或生意另设钱包、余额、分账户或镜像账户。
- 自营／承租业务按当前经营关系使用经营人的经营账户；受薪经营业务按经营关系使用产权资金责任人的经营账户。解析依据是业务关系，不是空间父节点或“玩家主角默认账户”。
- 工资从雇主业务实时解析出的付款人经营账户转入员工个人钱包；承租经营收入与雇员工资仍归租户资金链，不因商圈产权转让变成产权方经营收入或支出。
- 本人可在个人钱包与唯一经营账户之间双向普通划转，必须源账户足额。受薪经营人可发起授权业务支出和查询相应业务账，但不能自由划转产权人的资金，也不因管理权限获得产权人全部私人账目。
- 统一账户与流水注册表各保存唯一事实。一笔交易只存一条 `TransactionId`，源／目标账户、金额、时间、操作者、类别及关联业务共同描述该次交易；两侧视图查询同一条记录，不复制两份流水。
- 业务归属一次记录 `SourceBusinessEntityId`、`TargetBusinessEntityId` 与 `OccurredAreaRef`。源、目标是两侧业务归属，不是两份账户副本；个人支付侧可以没有业务，图外交易可以没有发生区域。
- 历史业务归属保留发生时的记录，不能按当前空间父关系、当前产权或当前 Manager 回写历史流水。资金责任人实时解析用于新交易，不等于重归属既有交易。
- 金额使用整数金；报价、价格、应付、成交与余额一致。普通划转金额必须大于 0，合法零额交易与合同按各自规则处理。具体结构与引擎类型由唯一架构维护。
- 权限每次按账户所有者、当前经营关系及业务类型计算，不持久化权限缓存。资产视图按关系查询，不在人或区域存“名下生意／雇员／租户”的镜像名单。

**保留原因**：人物资金归属与业务统计分离，既支持整体经营资金压力，也避免每家生意重复账户、流水与权限逻辑；统一流水保留历史归属和双方可追查性。

## 3. 扣负白名单与普通支付

**来源**：2026-10-28 普通经营支出；2026-10-30 贷款与费用简化；2026-10-31 工资扣负；本次用户确认。

- V1 扣负仅限贷款月供、租金、工资，均从相应经营账户足额结算，不产生逾期、欠租、坏账、未领薪或补发链。余额为负本身不触发强制破产、收资产、收铺或离职。
- 消费、即时采购、个人付款、普通划转与提前还款等非白名单支出必须足额；任一步校验失败均整笔不发生，不部分扣款或隐式记债。
- 删除未领薪布尔、工资失败竞争排序、欠薪忠诚持续衰减与因此自动离职。Loyalty 等状态仍按既定 V1 展示边界处理，不借此增设辞职玩法。
- V1 无专属公共设施系统、长椅维护费、公共维护扣负或公共维护工单。店铺已有清洁／维修工单不受此裁剪影响。
- 后续普通活动若开放，应当次先付款、后执行；未付不产生当次效果或隐性欠款。V1 不生成活动实例，本条不构成活动或公共维护验收要求。

**保留原因**：合同固定成本直接结算可以省去三套欠款状态；真实商品与普通资金动作仍遵守余额约束。公共维护不是最小经营闭环的一部分。

## 4. 时间推进、宿主与固定时点结算

**来源**：2026-10-25 时间；2026-10-27 独立计划时点；2026-10-31 同刻结算排序；本次用户确认。

- 固定 30 tick／现实秒，不随倍速提高逻辑频率；1x 每 tick 推进 2 游戏秒，2x／3x／4x／8x 分别为 4／6／8／16 游戏秒。
- 暂停冻结游戏时间及依赖游戏时间的模拟，不禁止 UI、镜头和建造操作。连续需求按游戏时间增量变化，跨阈才触发业务节点。
- 日历配置与当前绝对游戏时间入档；跨日界、月界、整点和时段边界按顺序处理，不因高倍速只检查最终时刻而漏执行。
- 时间、统一事件服务在 GameInstance；时间、经济、雇佣事实只入 Global，不进入 Scene 副本。未加载场景仍按真实全局合同结算。
- 每笔租约、借据、工资记录以自己的 `Next...` 固定时点字段叫醒；派生结算索引不入档，不用每 Scene 经济服务或事件重放代替调度。
- 不同计划时点严格按时间顺序执行；完全同刻先执行必须验足额组，再执行贷款月供／租金／工资扣负组。工资已在扣负组，不再举“租金先扣导致工资失败”的旧例。
- 同组确定性排序由唯一架构落实，不在此虚构具体 ID 类型或员工竞争优先级。

**保留原因**：固定频率限制倍速开销，逐时点补执行保证日历和合同完整；同刻分组避免允许扣负的固定费用提前消耗普通支付所需余额。

## 5. Global 租约、首期收租与调租

**来源**：2026-10-25 先签约；2026-10-27 比例首租；2026-10-31 整数取整与日历天数；本次用户确认。

- 租约事实只在 `Global.LeaseRegistry` 保存，经营实体只留稳定 `LeaseId` 引用；区域不内嵌租约，资产／租务列表查询注册表，不遍历区域副本拼合同。
- 合同使用 `LeaseId`、`LessorBusinessEntityId`、`TenantBusinessEntityId`、`LeasedAreaRef`、`TenantCreatureId` 等逻辑引用；人物保留实际签约主体，不能只留业务 ID 而抹掉签约人。
- 每次新承租关系生成新 LeaseId，退租重签不复用。人物身份、业务归属与租赁空间是不同维度。
- 首期在签约生效时按 `Ceil(MonthlyRent × 生效日至当月结束的剩余日历天数 / 当月日历天数)` 计算并立即收取；天数按日历日期差，忽略时分，不硬编码除以 30，不延后至首次定期收租才收首期。
- 后续固定收租时点收完整月租。首期已付与下一定期时点不得对同一期间重复收费。
- 调租只影响下期整月，不重算已收首期、不在当期分段或追溯补差；待生效价格及生效时点按现行 02 和唯一架构落地，不再用“下一时点读取当前价”回改当期。
- V1 无押金或固定租期玩法，不保留欠租 N 期、催收开关、坏账与补缴字段作为现行规则。租金扣负并不授权自动删除资产或终止经营。
- V1 标准玩家承租 `MonthlyRent=0` 仍是有效租约；零额跳过租金流水，不等于没有签约或跳过资产归属建立。
- 自指合同不能由仅具经营人身份的乙方修改；兼具产权人时按产权业务权限处理，不能借普通表单绕过。

**保留原因**：先签约可在建筑生成与编辑时确定资产归属；日历比例与向上取整让首期明确，Global 唯一合同使场景卸载后仍可结算。

## 6. 五随机报价、等额本金与提前还款

**来源**：2026-10-29 随机报价；2026-10-30 等额本金；2026-10-31 经营贷款；本次用户要求以现行 02 为准。

- 抽象银行展示 5 个全随机报价，不保底：本金 200,000～8,000,000，10,000 步长；名义年利率 3%～15% 的整数百分点；期限 12～360 整数月。生成参数进入统一配置。
- 借走报价后不立即补位，每游戏月开始只补空缺至 5 个，不替换未借报价；最多同时持有 5 笔，不提供手动刷新。开关界面、暂停恢复与读档不重摇。
- 报价与借据保存生成时参数，后续配置不改存量合同。贷款债务主体为玩家主角，放款进入其唯一经营账户，不按区域分债。
- 等额本金：常规月本金 `B=RoundHalfUp(P/n)`，末期还全部剩余本金；当期利息 `I=RoundHalfUp(RemainingPrincipal × AnnualRate / 100 / 12)`，当期月供为应还本金＋I，`RoundHalfUp(x)=floor(x+0.5)`，均为整数金。月供随剩余本金下降，不保留固定等额本息月供蓝图。
- 每笔借据按自己的下一扣款时点结算月供，可扣负，不保存逾期或未来利息债务。
- 提前还款依现行 02 允许部分偿还剩余本金，也允许结清；不收未来利息或违约金。它不是月供扣负入口，不能借提前还款绕过普通足额校验。
- 部分提前还款后的具体计划字段与重算方式跟随现行 02、唯一架构；本记录不补造未确认算法。

**保留原因**：随机报价形成融资选择，月度补缺防止刷卡；等额本金直观表示剩余本金利息，存量参数与历史结算不受配置修改影响。

**历史参考摘要**：2026-10-29原讨论参考《运输狂热2／3》财务手册来比较借贷入口与产品卡；本项目的5报价及等额本金是自身决策，不用参考游戏的产品数量或公式替代现行规则。2026-10-31参考《双点医院》《过山车之星》的整体资金压力，仅用于解释人物经营资金与工资扣负取舍，不证明本项目已经实现。

## 7. 统一雇佣与 Creature 劳动安排

**来源**：2026-10-28 统一登记与唯一有效关系；2026-10-29 月薪；2026-10-31 工资扣负；本次用户确认劳动安排归 Creature。

- 全部有效雇佣只在 Global 统一登记，同一 Creature 同时最多一份有效合同。人物保存 EmploymentId 引用，不另存雇主合同副本或雇员镜像名单。
- `EmployerBusinessEntityId` 指向 Shop／District／Abstract 经营实体；不允许人员直接雇佣人员。工资每次经当前经营关系实时解析付款人经营账户，不快照 `EmployerCreatureId`。
- 合同保留雇员、雇主业务、月薪、入职时间与下一发薪时点等合同事实。`AvailabilityTemplate`、`ShiftTemplate`、`WorkPriorities` 等劳动安排归 Creature，不挂合同或区域；个人工作日程引用同一安排，不复制排班。
- 五块统一为 `Work / Rest / Sleep / Dine / Anything`。V1 不开放独立娱乐块、员工专用休息／餐台／实体住所，Rest／Dine／Sleep 按自身安排离店或回抽象住所，不占顾客座位或开启跨店消费。
- 固定月薪，月末结算；有效整月不按出勤、工时、关店或工单数量增减。首末月按实际在职时长／当月总时长折算，离职末月即时结清。
- 调薪按既定结算时当前月薪规则，不新增工时计薪、计件、加班或分段工资。工资进入员工个人钱包，付款人经营账户可扣负。
- 玩家受薪身份与自主开关独立：有有效薪酬合同照常领薪；非受薪自主工作不凭工单发工资。V1 预留玩家经营人月薪 0 的合法合同配置，不因此把 NPC 普通员工工资改为 0。
- 解雇移除有效合同；V1 不保存完整雇佣履历，历史工资查唯一流水。没有欠薪自动离职、挖角、换工或强制补员路径。

**保留原因**：统一登记保证招聘与工资只有一份事实；合同与劳动安排分开才能覆盖自营者安排和图外雇佣，不把劳动控制误当合同条款。

## 8. 固定 NPC 名册、初始钱包与图外真实工资

**来源**：2026-10-27 真实收入与招聘；2026-10-28 图外雇工；2026-10-30 固定名册；本次用户确认。

- 开局使用有限固定 NPC 名册，消费者和员工来自同一登记，CreatureID 稳定；离场只回收 Actor，不删除账户、雇佣、需求、日程或认知。
- 每个 NPC 初始钱包由配置生成，初始存量与定期收入分开。大部分 NPC 具有真实图外雇佣合同与工资流水，不按职业、出身或阶层凭空周期加钱。
- 图外雇主也是 Global 经营实体，通常可无区域；合同、经营账户和工资结算与图内同模型。图外工作不生成 Actor、寻路、工单或设施操作，不以“是否在图”判定失业。
- 图外雇主为**抽象账户**（`bAbstract=true`，2026-11-06 定）：不参与余额运算，支出直接发生、不补资，不写成补贴、无限注资或收入模拟。V1 不做破产机制。
- 无有效雇佣且无其他真实业务收入时，NPC 没有周期收入；个人钱包花完就真没钱，不发失业兜底。工资扣负保证合同工资结算，不等于给失业人员送钱。
- 招聘板只查询无有效合同者，最多展示 5 人，不足显示实际数量；定期与免费手动刷新只改变展示，不造人口。
- 图外合同有效者不是可随意吞并的招聘候选；V1 不因招聘需求自动终止合同、换工或强制补人。刷新周期具体数值仍待配置。
- V1 不模拟移民、流失、临时游客、行商、匿名流量池或完整图外消费／生活；只加载预置单商圈与玩家杂货店，不能把图外真实工资扩成多商圈经营玩法。

**保留原因**：固定名册保证经济与身份可追踪，图外合同减少表现成本但保留真实就业；明确资金保障边界，避免把未设计的货币源当成可用系统。

## 9. 创建、签约、装修与资产保护

**来源**：2026-10-25 先签约后建造；2026-10-30 表单权限；本次用户确认组合入口。

- 在同一建造面板圈地、填写信息、预览并确认；统一组合业务入口生成经营实体＋区域＋必要合同，调用者不用手工创建后绑定。

**来源**：2026-10-31 R11-1～R11-7；本次用户统一模型。

- Global保存经营实体、账户、唯一流水、租约、雇佣与时间事实；Scene仅保存空间与物理表现事实，不内嵌Shop业务、租约、雇佣、经济或时间副本。Creature劳动安排由人物事实保存，宿主与具体序列化按唯一架构§7。
- 工作点保存队列事实，人物Flow仅保存稳定引用与在途进度；设施／家具容器和ITEM表各自唯一，派生看板、认领、bOperating、索引与查询缓存不入档。
- 业务引用使用BusinessEntityId，区域引用AreaRef，其他稳定人物／物品／合同／执行／预留／订单／账户／借据ID保持各自语义。引擎底层ID不在本次定稿。
- 先恢复全部Global与Scene事实，再重连引用、重建派生索引、一致性校验，最后激活时间与AI；具体结构与顺序只在唯一架构§7定义，本文不再复制第二份宿主树。
- 绝对GameTimeSec原值恢复，不补算离线时间，不重放事件、不重摇报价、不重排队列、不重聚合历史或重新计来访。
- Flow阶段已执行现实秒保留，旧进程TimeSeconds不入档；工单认领派生重建，候选冷却原绝对日界恢复。
- 只在完整业务事务边界快照。收银提交及结果被Flow消费前不设存档点；只存Active预留、Pending订单与表现断点，不保存临时Processing／结果／扣货／入包计划。
- ITEM整堆转移保留ID，部分拆分新堆新ID，合堆保留目标，源耗尽删除。此身份规则仍有效，不因经营实体ID待选而重开物品规则。
- 必需配置缺失、ID重复／悬空、引用不完整或物品多槽占用时，在激活前终止整次读档，不补默认对象、不激活半份世界、不改原档、不自动修档或补偿。

**保留原因**：唯一事实加稳定引用支持续跑和校验，不需要复制余额、合同、队列或重放历史；原子快照避免二次销售与体验漏算。

**历史参考摘要（2026-10-31）**：R11-1按RimWorld公开反编译快照中整堆转移返回原对象、部分拆分创建新对象、合堆保留目标的身份生命周期作取舍；BG3SE的UUID／数量材料未被用来证明拆合规则，Minecraft无堆级持久身份的方案未采用。此处保留物品身份原因，不替经营实体选择引擎ID。
